## §D2. Integration vs unit test placement drift

**The trap**: unit tests in `#[cfg(test)] mod tests { ... }` inside `src/lib.rs` (or sibling modules) reference *crate-internal* paths — `crate::internal::do_thing()` — that work because they share the crate. Integration tests in `tests/*.rs` only see the crate's public API; they cannot reach `pub(crate)` items. When the LLM (or a refactor) moves a unit test into `tests/`, the import paths suddenly resolve differently, and the test either fails to compile, or — more insidiously — silently calls a different `do_thing` from a re-export and passes for the wrong reason.

**BANNED**:
- Moving a test from `#[cfg(test)] mod tests` to `tests/` (or vice versa) without checking that every import resolves to the same item.
- Integration tests in `tests/` that reach for `pub(crate)` items by re-exporting them through a public module just to make the test compile — this expands the public API for testing convenience and creates a semver hazard.
- Undocumented/inconsistent internals-access conventions across a crate's tests — e.g. leaking `pub(crate)` items via a re-export for one integration test while another relies on proper `#[cfg(test)]`-scoped access, with no stated rule for which mechanism applies where. This is a ban on *unstated, inconsistent* internals access, not on the ordinary, standard Cargo practice of a crate having both `#[cfg(test)] mod tests` unit tests and a `tests/` integration directory — that coexistence is the normal model and needs no special justification.

**REQUIRED**:
- Unit tests for *private items* live in the defining module or a descendant (`#[cfg(test)] mod tests { ... }` is the usual child). A separate test source file works when mounted there. Sharing the crate grants access to `pub(crate)`, not to every private item in unrelated sibling modules; normal module privacy still applies.
- Integration tests in `tests/` exercise *only* the public API (`pub` items). They are the contract-test layer.
- If integration tests genuinely need internals, `pub(crate)` cannot grant that access: it stops at the current crate, including for sibling workspace crates. Keep private-item coverage in unit tests under the proper module, or deliberately expose public test-support wrappers behind an explicit feature. The library linked by integration tests is not built with `cfg(test)`; a feature-gated surface must be enabled for it. Public feature-gated APIs are still visible to consumers who enable that feature — not automatically removable or semver-exempt (§C7). A dedicated dev-only support crate can share fixtures and helpers using accessible APIs; it grants **no** access to another crate's private or `pub(crate)` items and is not an internals-access workaround.
- Document the convention in `CONTRIBUTING.md` or the workspace `README`. Without a written convention, drift is inevitable.
- Integration tests that invoke the crate's own binary resolve it via the `CARGO_BIN_EXE_<crate>` env var (`env!("CARGO_BIN_EXE_mybin")`) — the guaranteed path to the freshly built executable — not by hand-assembling `target/debug/...` paths (which break under workspaces, cross-compilation, and alternate profiles). Compile-time `env!` since Cargo 1.43; since Rust 1.94 the variable is also available at **runtime** (`std::env::var`), so a runtime-resolved helper no longer needs the `env!` indirection.

## §D3. Test/prod divergence: build profile, scale, and concurrency

**The trap**: `cargo test` runs the **debug** profile, toy data sizes, and (per test) often a single task — production runs **release**, real sizes, and real concurrency. Each axis hides a bug class: debug-vs-release — integer overflow panics in test, silently wraps in prod, and `debug_assert!` guards vanish (**§B26** owns the fixes; §D3 is the testing-side enforcement, plus the two axes below); scale — an O(n²) (§E3/§C4), a recursion depth (§B7), an allocation pattern (§E2) invisible at n=10; concurrency — a TOCTOU (§B13) or lock-order inversion (§B9) that a single-threaded test can never interleave into existence.

**BANNED**:
- Relying on a test-suite pass as evidence about overflow/`debug_assert!` behavior of the release binary — the profiles disagree by default (§B26 has the fixes: `overflow-checks = true` in release, or per-site `checked_*`).
- Treating a feature-matrix `cargo check`, or tests that exercise only a scalar/default backend, as evidence for a shipped SIMD/crypto backend. Compilation does not execute that backend, and runtime dispatch can keep selecting the fallback even in a feature-enabled job.
- Giving a process that produces a PR-readable CI cache access to secret environment variables. Miri before the fix announced for nightly 2026-09-22 copied the entire environment into `target/`; a later PR could recover secrets from that cached directory. Patched Miri is not a general guarantee that Cargo, build scripts, or other tools keep secrets out of artifacts (§A1).
- Testing code documented to handle "large" / "unbounded" / "attacker-sized" input only at toy sizes. At least one test at the documented scale boundary (max frame size, max depth, the size that makes O(n²) visible — n=10⁴–10⁵ is usually enough to turn quadratic into a timeout).
- Testing concurrency-bearing code (shared map, lazy init, multi-lock) exclusively through single-task tests. Use `loom` for lock/atomic protocols (§B9/§B13), or at minimum a stress test with real task parallelism and a yield-heavy schedule.
- Letting per-test timeouts or `#[ignore]` quietly absorb a scale problem ("the big test was slow so it's ignored") — that is §D1's ignored-test rot plus a buried §E3 finding.
- Silencing an abort from std's **debug-only UB checks** instead of fixing its cause. Since Rust 1.78 the standard library checks the preconditions of many `unsafe` functions (`slice::from_raw_parts` null/alignment/size, `ptr::copy_nonoverlapping` overlap, `get_unchecked` bounds, …) according to the *calling* crate's `debug_assertions`, so a debug build of your crate gets them even against the precompiled release std; 1.80 added the abort on dropping an already-closed `OwnedFd` (§B25), and since 1.86 debug builds also check raw-pointer reads, writes and reborrows for null. A violation is a **non-unwinding panic** (`unsafe precondition(s) violated: …`): `#[should_panic]` and `catch_unwind` do not see it, and the whole test binary dies. Each such abort is a confirmed UB finding in the code that made the call. BANNED responses: running the affected tests only with `--release`, `debug-assertions = false` in the dev/test profile, pinning an older toolchain, or wrapping the call in `catch_unwind`. The converse also holds: `cargo test --release` runs **none** of these checks, and they cover only some preconditions, so a clean debug run does not replace Miri (§B5). Keep both lanes — debug for these checks, release for the §B26 divergences.

**REQUIRED**:
- Run the test suite in release at least in CI (`cargo test --release` as a separate job) when the crate does arithmetic on untrusted/accumulating values or uses `debug_assert!` for anything load-bearing — it is the cheap way to make the tested and shipped configurations overlap.
- For supported production SIMD/crypto backends, run behavioral tests on the relevant target, feature set and CPU capabilities, and establish which dispatch path actually executed. Include known-answer/contract tests, malformed-input and length-boundary controls; compare scalar and accelerated implementations where they promise the same results. A crypto round-trip alone does not test rejection of invalid ciphertext (§B12; controls listed in §D1a). Record any supported backend the runner cannot execute as unverified, with a suitable runner or separate deployment check required for that claim. RUSTSEC-2026-0290 (`pqc_kyber`, opt-in AVX2 key recovery) and RUSTSEC-2026-0306 (`faster-hex`, AVX2 out-of-bounds reads) are worked instances; see `references/sources.md`.
- Keep build/test/Miri processes that write caches accessible to less-trusted PRs secret-free; scope tokens to separate steps and exclude secret-bearing outputs from those caches. Record the exact Miri build and verify it includes the environment-filtering fix before relying on that fix (announced for nightly 2026-09-22). If the old combination ran — Miri with secret environment variables, cached `target/`, and PR access to that cache — remove the affected old caches and assess rotation of exposed credentials. Updating the tool does not remove previously cached secrets. The scope is that exposure combination, not a ban on every `target/` cache; see the Rust security notice in `references/sources.md`.
- Match the shipped **panic strategy** separately when recovery or cleanup depends on it. Ordinary Cargo test harnesses ignore the profile's `panic` setting and use `unwind` even under `cargo test --release`; a green `catch_unwind`, panic-to-error or panic-triggered `Drop` test therefore does not establish behavior of a `panic = "abort"` artifact. Verify the actual deployment build configuration; when panic behavior is load-bearing, exercise an appropriately isolated executable/subprocess built with that strategy and check its exit and required observables. Release-profile tests alone are not this check.
- One boundary-scale test per documented size limit; one adversarial-depth test per recursive parser (§B7).
- For code whose correctness claim is concurrency ("thread-safe", "lock-free", "concurrent map"), the claim defines the test: `loom` model or multi-thread stress — a single-threaded green suite is silent on the claim, not supportive of it. `loom`'s exhaustive interleaving search only covers operations that go through `loom::sync`/`loom::thread`-instrumented primitives *inside* a `loom::model(...)` closure; adjacent code still using plain `std::sync`/`std::thread` runs once, unexplored — swap it to loom's shims (typically behind `#[cfg(loom)]`) for anything the model actually needs to check, or it is not covered by the loom run at all.

## §D4. Filtering test-runner output through `grep`/`head` hides hangs

**The trap**: an agent or CI script pipes `cargo test` / `cargo nextest` through `grep`/`head` ("show me only the failures") to save context. Two silent losses follow: (1) the filter discards the per-test `SLOW`/`TIMEOUT`/`stalled` lines — the *only* lines that name a hanging test — because they are not `FAIL` lines, so a deadlock becomes invisible; (2) without `set -o pipefail` the pipeline exits with the *filter's* status — and GNU `grep` exits `0` when at least one line matched, `1` when nothing matched, `2` on error — so a filter that matched anything masks the runner's non-zero exit, and a failing or hung run reads as green. The `pipefail` foot-gun is not Rust-specific, but the agentic reflex of appending `| grep` to every test run is — and it blinds the agent to exactly the hang it most needs to see.

**BANNED**:
- `cargo test … | grep …` / `… | head` as the command whose exit status gates "tests passed", without `set -o pipefail` — the filter's status, not the runner's, then decides green/red, because `$?` after a pipeline is the *last* command's. GNU `grep` exits `0` when at least one line matched, `1` when nothing matched, `2` on error — so a filter that matches *anything* (e.g. `grep 'test result:'` matches pass and fail runs alike) still exits `0` while `cargo test` failed, and the run reads green.
- Concluding "no failures" from a filtered stream that drops `SLOW`/`TIMEOUT`/`stalled` lines — absence of `FAIL` in a filtered view is not absence of a hang.
- Raising a per-test timeout (or adding `#[ignore]`, §D1) to make a `SLOW`/`TIMEOUT` line disappear — that masks a deadlock instead of fixing it.

**REQUIRED**:
- Gate on the runner directly, or `tee` full output to a file and grep the **file** — never gate on a live pipe. When a pipe is unavoidable, `set -o pipefail` first so the runner's exit status is the one that counts.
- Treat any `SLOW`/`TIMEOUT`/`stalled` line as an unresolved hang/latency failure that requires investigation — not as a diagnosis. "Deadlock" is one candidate root cause, not the finding: before fixing anything, distinguish deadlock (§B9 lock order, §B13 TOCTOU), livelock (§B3a coordinator spin), thread starvation, ordinary blocking I/O under load, and algorithmic complexity (an accidental O(n²) finally hit at scale, §E3) — they have different fixes, and treating a complexity regression as a lock bug (or vice versa) fixes nothing. Reproduce it under parallel load (`--test-threads`, repeated runs) and fix the root cause, not the symptom.
- When a workspace is non-virtual (a root `Cargo.toml` that also has a `[package]`), a CI `cargo test` at the repo root runs **only the root package** — Cargo "will include only the root crate itself" unless `default-members` is set — so the member crates' tests never execute and the suite reads green while testing a fraction of the code; bare `cargo clippy` has the same hole (no `--all-targets` → no test/bench linting). Gate on `cargo test --workspace` / `cargo clippy --workspace --all-targets` (§C10 has the cargo-side detail).

## §D5. Windows: a hung test process wedges the next link (LNK1104)

**The trap**: on Windows a running `.exe` is locked against deletion and overwrite. The standard `cargo test` harness has no per-test timeout at all — a hung test just hangs, and Rust gives no API to kill a single thread inside a running process (only the whole process can be terminated). When a hung test is left running because whatever's watching it (a CI job-level timeout, a script that gives up polling) fails to actually terminate the `cargo test` **process** — not just stop waiting on it — that process, hung thread and all, keeps its own hashed test binary open; the next build's link step then fails `LNK1104: cannot open file '…exe'` — and one flaky hang becomes a build cascade that looks unrelated to the test that caused it. This is a CI/ops failure mode rather than a code defect, but it is the direct Windows fallout of the §D4 hang, so it is enforced alongside it.

**BANNED**:
- "Fixing" a recurring `LNK1104` on a test/bench binary by retrying the build or rebooting the runner, without reaping the zombie process and fixing the underlying hang — the cascade recurs on the next hang.

**REQUIRED**:
- The root fix is the hang itself (§D4 — eliminate the deadlock). Zombie-reaping is defense-in-depth, not a substitute for it.
- On Windows CI, isolate `CARGO_TARGET_DIR` per job/run so hashed test/bench binary names never collide across concurrent jobs, and reap only the PID(s)/process tree your own CI job recorded as its own (the child process it spawned) at the start of each run — never by matching the binary's filename (`<crate>-<hex>.exe`): a concurrent job sharing the same target dir or runner can produce the identical filename, and a filename-based reap kills that job's legitimate, still-running process.

## §E6. Measure before you spend — *The cost lives in the system under load, not in the line you are reading.*

- **The discipline**: §E1–§E5 are not a mandate to optimize everything — they are a map of where systemic cost hides. Two are worth fixing on sight: algorithmic complexity (§E3) and obvious waste `clippy::perf` flags (§E2). The rest is profile-gated: confirm the hot path before trading clarity for speed.
- **The tools**: a flame graph (`cargo flamegraph`, `perf`) for CPU; an allocation profiler (`dhat`, `heaptrack`) for §E2; `tokio-console` for async stalls and lock waits (§E1, §E4); `criterion` to prove a change is faster and guard against regression; `captrack` / `captrack-pgo` for the observed capacity of each collection call site (§E2); `bench-scale-tool` as a fixed-iteration pulse check (next bullet). Optimize what the profile shows, not what the diff looks like.
- **The unmeasured "make it faster" reflex extends to toolchain flags.** `[build] rustflags = ["-C", "target-cpu=native"]` in `.cargo/config.toml` — the reflexive answer to "make it faster" — bakes the *build* host's ISA extensions into the binary: a production/CI host without them dies with `SIGILL` at the first vectorized call, deep in a hot path the flag was supposed to help. It is both a measurement-free change (this section's base rule) and a deployment-correctness hazard. REQUIRED alternatives: runtime feature detection (`is_x86_feature_detected!` on x86_64, or the `multiversion` crate) so one binary serves heterogeneous hosts, or a named baseline `target-cpu` documented as a deployment contract. (The Substitution catalog's `gxhash` row in `data-text-iter-cost.md` carries the same AES-intrinsic caveat per crate.)
- **Lock the win — and gate on a signal that does not move on its own.** When a measurement justifies an optimization, guard it in CI so the next refactor cannot silently give the speed back; a §E regression is as invisible to `cargo test` as any Tier B bug. But *what* you gate on matters more than *that* you gate: **wall-clock is the wrong hard gate on shared CI.** Criterion's own FAQ says the virtualization used by cloud-CI providers (it names GitHub Actions) "introduces a great deal of noise into the benchmarking process, and Criterion.rs' statistical analysis can only do so much to mitigate that" — so a wall-clock threshold there is either tight enough to flap on a noisy neighbour or loose enough to catch nothing. Make the *failing* gate a **deterministic counter** — allocation bytes/counts (`dhat`), query/syscall/comparison counts, or instruction counts from a Valgrind/callgrind-based harness (Linux CI only — Valgrind does not run on Windows) — because those reproduce run-to-run only when **everything feeding the count is pinned** — and the environment pin (same allocator, target triple, compiler version, feature set) is the necessary half, not the sufficient one: it bounds toolchain/allocator drift, not the program-level entropy and state that decide how much work a single run performs. Before an exact counter is promoted to a hard pass/fail gate, fix or explicitly bound every relevant run-to-run source: **hash iteration order** — `HashMap`/`HashSet`'s default `RandomState` seeds itself randomly per process (doc.rust-lang.org/std/collections/hash_map/struct.RandomState.html), so the same binary can probe, iterate, and allocate differently between two runs; substitute a fixed-seed `BuildHasher` in the counted path (`BuildHasherDefault` around a deterministic hasher, `FxHashMap`/`FxHashSet`, or `ahash::RandomState::with_seeds(..)`) — §B16 owns the HashDoS boundary that makes that substitution safe for trusted keys only; **randomized test inputs** — any `proptest`/`quickcheck`/seeded-RNG data feeding the measured path must be pinned to a fixed seed, or the count varies with the draw; **concurrency** — OS/runtime thread scheduling reorders interleavings run to run, so keep the counted path single-threaded (or explicitly bound the schedule and capture the baseline under that same bound); **CPU cache state** — it leaves a true operation count untouched (the same instructions execute warm or cold) but is exactly what destabilizes *timing*-adjacent measurements, so keep cache/latency-sensitive numbers out of the exact-count gate entirely. Hard-gate the counter only inside the pinned CI environment **and** with that entropy pinned, against a stored baseline captured on that same environment with the same inputs and the same hasher — they are still not comparable across machines: a different allocator, architecture, or toolchain moves the count for reasons that have nothing to do with your change (bheisler.github.io/criterion.rs/book/faq.html). Keep the two reproducibility claims separate: *this count reproduces given fixed inputs, a fixed hasher, and no concurrency in the counted path* and *this benchmark's wall-clock timing reproduces across hardware* are different assertions with different prerequisites, and a green gate on the first establishes nothing about the second. Keep the wall-clock benchmark as a *trend you read*, not a red build, unless it runs on dedicated hardware. Bench the few paths you actually optimized, not everything — that *is* this discipline, not a contradiction of it (a benchmark of cold or trivial code is its own coverage theater, §D1). Verify the harness is maintained before adding it (§A1): Criterion's FAQ still points at `iai`, unmaintained since **2021** — the technique (instruction counting) is stable, the crate name is not.
- **A fixed-iteration harness for a fast pulse: `bench-scale-tool`** (a crate by this skill's maintainer; 0.1.x, MSRV 1.71). Where Criterion measures over a time window and reports statistics, `Harness::bench("group/case", || { black_box(work()); })` runs a fixed number of iterations per workload — calibrated once against a target wall time (`--calibrate <secs>`), pinned in a committed, hand-editable manifest (`bench-iters.txt`, one `<bin>::<id> = <iterations>` line per workload), and rerun with no time cap — so a run that finishes sooner is a direct speed signal and total sweep time tracks the code instead of the window. `bench_batched` is for setup that must be fresh each iteration (it pays a timer pair per iteration); `bench_async` needs the opt-in `async` feature; `bench-cli` adds `sweep`, `history` and `history-diff` over the committed sweeps. Fit it to the use: it is a trend and regression pulse for a few optimized paths — **not** statistics (its README: "No statistical rigor" — no confidence intervals, outlier detection or regression analysis), and each iteration includes one `dyn FnMut` call, so absolute numbers run high while deltas stay comparable. Keep §E6's gating rule: the failing CI gate is still a deterministic counter (above), the wall-clock sweep a number you read. The committed iteration manifest is one of the frozen inputs the next bullet requires — an optimization diff that changes a workload's count, or the workload body, together with the code is reviewed as a benchmark change — but it does not replace the reference-output check: removing work inside an iteration leaves the count intact.
- **An optimization loop's benchmark is an oracle, and an agent will game it.** Asked to "make it faster" against a benchmark it is also free to edit, an agent can produce the number by removing the work. Max Woolf (2026-09-21) reports Claude Opus 4.5 delivering "a 34,500x speedup" on a physics simulation — "Claude achieved the speedup by disabling the physics engine entirely" — and "reducing the number of training epochs for a benchmark and claiming a speedup"; his summary: "agents can and will cheat if they can". REQUIRED: the benchmark harness, its inputs and its iteration/epoch counts are frozen — a separate file or crate the optimizing change may not touch, so a diff that edits both the code and its benchmark is a finding by itself; every benchmarked run also checks its output against a reference result computed by the unoptimized implementation on the same workload (an independent oracle, §D1a) — a speedup with no correctness assertion is unverified; and an implausible factor (orders of magnitude, or a cost that stopped scaling with input size) is treated as a correctness failure until explained.
- **Leave it when**: always, until a measurement or clear algorithmic argument justifies the change. A micro-optimization on a cold path is the noise this document exists to prevent — the 🟡/🟢 discipline, applied to speed.

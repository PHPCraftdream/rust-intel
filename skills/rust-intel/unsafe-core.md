## §B5. Unsafe that looks safe (high UB rate in small-N studies)

**The trap**: code passes review and tests because UB doesn't manifest on typical inputs. In the small-N audit cited in [`references/sources.md`](references/sources.md), out of 40 LLM-generated `unsafe` blocks: 13 were UB on any input, 9 were UB on specific inputs (alignment, OOB, Stacked Borrows violations), 18 were correct — i.e. 22/40 (~55%) exhibited UB. The *exact rate* is directional (small sample, not stratified by model or domain), but the *pattern* — that LLM-generated `unsafe` is significantly more dangerous than LLM-generated safe code — rests on this one audit and is directional evidence, not an established result. Treat any LLM-generated `unsafe` block as high-risk until proven otherwise via miri + manual invariant audit.

**BANNED**:
- `std::ptr::read(p)` / `*p` / `&*p` without proof that the pointer is aligned for `T`; that proof may be static or a runtime alignment check before access. Use `read_unaligned`/`write_unaligned` for permitted unaligned value access, never form an unaligned reference. These operations still require the other validity, extent and ownership proofs (`align_to::<U>` is itself unsafe, not a safe-validation shortcut).
- `ptr::copy_nonoverlapping(src, dst, n)` where the `src` and `dst` ranges can overlap — e.g. shifting a buffer's tail left in place (a `memcpy` port): overlap is **UB**, even though a small non-overlapping test passes every time. For the in-buffer move use `ptr::copy` (memmove semantics — defined for overlap) or, on slices, the safe `slice::copy_within`.
- **`transmute` where the required layout relationship or the validity of *this call's actual argument and result* is not proven, stated, and true.** The standard library's own contract is size- and *value*-specific, not type-universal: `transmute` requires equal size (the compiler checks only that) **plus** a layout relationship sufficient for *this specific* conversion **plus** the concrete value being passed in and the concrete value coming out both being valid at their respective types. That last clause is about the actual value at this call site, not every bit pattern the source type can hold — a `u8` statically known to be `0` or `1` (checked, or from an exhaustive match) is sound to `transmute` to `bool` even though most `u8` values are not, because the *argument's* validity is what the contract asks for. Reserve "every possible source value must be valid at the destination type" for a *generic or unchecked* conversion API that must accept arbitrary values of the source type (e.g. `bytemuck::Pod`/`zerocopy::FromBytes` bounds) — that is a stronger, different obligation than a single concrete `transmute` call. What proves the layout half also differs by case, and a pinned repr is not always the tool: `[u8; 4]` ↔ `u32` and other same-family primitive/array/pointer-to-pointer conversions have specified layout on both sides *without* a user-written `#[repr(...)]` — do not demand one there. `*const ()` ↔ `fn() -> i32` (data pointer ↔ function pointer) is not in that same-guarantee bucket: the standard library's own `transmute` docs flag this exact conversion as *not portable to targets where function pointers and data pointers have different sizes* — a target-dependent fact to confirm, not a universally specified layout — so the `// SAFETY:` block must state the equal-size confirmation for the actual target(s), not just cite the absence of a `#[repr(...)]` requirement. A pinned repr is part of the proof once **aggregate field layout or ABI** is in play — transmuting between two `struct`s needs both on a matching pinned repr (`#[repr(C)]`, `#[repr(transparent)]`, `#[repr(u32)]`, `#[repr(packed)]`, …), because the default `#[repr(Rust)]` does not guarantee field order, padding, or stability across compiler versions (the attribute name itself is stable; the *layout it implies* is not). A **struct-to-bytes** transmute is a distinct, harder case that a repr does not settle by itself: a byte array has no representation attribute to match in the first place, `#[repr(C)]` does not guarantee the *by-value* operation preserves padding bytes, and the destination bytes must all be initialized — see the padding-byte bullet below ("Serializing a struct to bytes by a raw cast"), which is the actual proof obligation there, not "add `#[repr(C)]`". Either way, a proven layout relationship is **necessary, not sufficient**: it does not by itself prove the value-validity, provenance/lifetime, or ownership/aliasing obligations above. The `// SAFETY:` block names the layout proof appropriate to the conversion *and* the value-validity proof for the actual argument and result, or the call is banned. Prefer a checked constructor (`TryFrom`, `from_utf8`, `zerocopy::TryFromBytes`, `bytemuck::Pod`) or field-by-field conversion over `transmute` wherever one exists.
- Any `unsafe` block without `// SAFETY:` preceding it that names every invariant.
- Calling user-provided, callback, comparator, or otherwise panic-capable code while an unsafe data structure is in a temporarily invalid or partially-committed state. `catch_unwind` does not repair broken invariants; use a guard that restores validity, or separate a fallible preparation phase from an infallible commit, and inject panics in tests where the contract matters.
- Creating or using `&mut T` through a raw pointer without a valid exclusive-access/reborrow discipline. A dormant parent reference can coexist with its shorter reborrow; conflicting access through the parent or another alias while the child is active is the hazard, not mere reference-variable existence. Trace which accesses remain permitted, and check load-bearing raw-pointer reborrows with Miri.
- `mem::uninitialized::<T>()` — deprecated since Rust 1.39 (November 2019) precisely because it is unusable: the std docs state it is "immediate undefined behavior to call this function on nearly all types, including integer types and arrays of integer types, and even if the result is unused" — wider than "types with invariants". The function returns an "undef" value the optimizer is free to assume is initialized; for `bool`, `&T`, `Box<T>`, `NonZero*`, and any enum with restricted discriminants the read is UB on its face, and it stays UB even where rustc's 0x01-fill mitigation makes the bytes look defined (observed on 1.97.0: `uninitialized::<u32>()` returns `0x01010101`, `uninitialized::<bool>()` returns `true` — a mitigation, not semantics). Use `MaybeUninit::<T>::uninit()`.
- `mem::zeroed::<T>()` for any `T` whose all-zero bit pattern is not a valid value: `&T`, `&mut T`, `Box<T>`, `NonZero*`, function pointers, enums whose discriminants do not include 0, and `#[repr(transparent)]` wrappers over any of the above (`bool` is *not* invalid for `zeroed` — zero is the valid representation of `false`). The function compiles for *every* `T` regardless of whether zero is a valid bit pattern, and the misuse is not always silent: for a concrete, provably zero-invalid `T`, the `invalid_value` lint warns at compile time, and std's runtime check aborts — in debug *and* release — with a message of the form `attempted to zero-initialize type ..., which is invalid` (observed on 1.97.0 for `&u8`, `Box<u8>`, and a no-zero-discriminant enum; non-unwinding panic, exit via abort). That check is a **best-effort mitigation, not a guarantee** — the call is still UB per the reference, so this stays BANNED; "aborts loudly for some cases" is not "safe".
- **A plain load/store loop against device or shared memory** — `while unsafe { *status } & READY == 0 {}` polling an MMIO register, a DMA buffer, or `mmap`'d IPC memory: a plain load is not volatile, so the optimizer may hoist it out of the loop (the C→Rust port dropped the `volatile`) — an infinite spin reading a cached register, or a stale value the code then acts on. Use `read_volatile`/`write_volatile` for device memory outside any Rust allocation; note volatile fixes *elision*, not *atomicity* — it does **not** make cross-*thread* access defined. Anything another thread or process writes concurrently needs atomics (`AtomicU32::from_ptr` on suitably aligned memory, with §B13's ordering rules); on bare-metal, `critical_section::Mutex<RefCell<_>>` or a PAC/`volatile-register` type is the embedded-idiom answer.
- **Serializing a struct to bytes by a raw cast** — `slice::from_raw_parts(&t as *const _ as *const u8, size_of::<T>())`, or `transmute`/`transmute_copy` into a byte array — when the type has **padding** and the bytes cross a trust boundary (network, disk, IPC, a log). The padding bytes between fields are **uninitialized**: reading them is UB (miri flags it), *and* they carry whatever previously occupied that stack/heap slot — a stale pointer, key material, another request's data — straight out of the process (Heartbleed-class info disclosure; a §B12 secret-leak when those bytes are sensitive). `#[repr(C)] struct H { flag: bool, len: u32 }` has three such bytes. This is the write-direction dual of the "validate bytes → `Result` before minting" rule below, and it is *not* caught by `cargo test` (the value round-trips fine locally). Also BANNED: `unsafe impl bytemuck::NoUninit` / `bytemuck::Pod` (or the manual equivalent) on a padded type to push it through `bytes_of` — that overrides the exact compile-time check that catches this.
- **Reading a `union` field with no local proof that the storage is initialized and that the bits are valid *at that field's type*.** A Rust `union` has **no** active-field tracking and **no** implicit runtime tag: every field read simply reinterprets the union's bits at that field's type, and it is the programmer's responsibility that they are valid there — reading `3` as a `bool`, a stale discriminant as an `enum`, a reference with invalid provenance, or bytes the writer never initialized is instant UB with **zero** compiler help (the `unsafe` block is one keyword, and tests with a stub that always writes the expected variant pass). For the shape that dominates FFI — a **tagged** union, i.e. what `bindgen` emits for C, where a sibling tag field is what selects the valid interpretation — the proof *is* the tag check, and a read with no preceding tag `match` is the finding. For deliberate type-punning between representations that are valid for one another (`u32` ↔ `[u8; 4]`), the proof is a stated bit-validity argument instead; "no tag was checked" is not by itself the defect there. Also BANNED: a **non-`#[repr(C)]`** union used for FFI or for any reinterpretation that relies on C-compatible layout — the default union layout leaves field offsets unspecified, so "write field A, read field B" is not even a defined transmute. Also BANNED: checking the tag and reading the union field **in one pattern** — `Value { tag: Tag::Int1 | Tag::Int2, data: Data { int: 0 } }`, or a tuple `(tag, U { int: 0 })`. The order in which subpatterns are tested is not guaranteed to be left-to-right (match lowering moves or-patterns to the end), so the compiler can read `data.int` before it has checked `tag` — UB that Miri reports when the stored variant is another one (rust-lang/rust#158387, open). The Rust Reference recommended exactly this single-pattern form, inherited from the unions RFC (1444), until rust-lang/reference#2303 corrected it, so older text and model output contain it. Match the tag in an outer `match` and read the field inside the arm.
- Marking a public function `pub fn` when its contract actually requires invariants from the caller. If the caller must uphold something for safety, it is `pub unsafe fn`. (FFI-import twin: `safe fn` inside an `unsafe extern` block on a pointer-taking C function is the same lie with the callers on the other side — §B25's `safe fn` bullet.)
- **`unsafe` whose soundness assumes that a safe, caller-supplied implementation is correct or answers the same way twice** — a length from `len()`/`size_hint()`/`ExactSizeIterator`, a slice from `Borrow`/`AsRef`/`Deref`, an ordering from `Ord` or a comparator closure, a `Hash`/`Eq` pair, a `Pattern`/`Searcher`. Those are safe traits: a wrong or inconsistent impl is a logic bug, never UB, so memory safety may not depend on it — "safe doesn't mean correct, and it can return inconsistent or plainly wrong answers" (Microsoft FORGE, *Memory Safety Bugs in Rust Standard Library*, 2026-11-09). The standard library itself shipped the shape: `[S]::join` sized the output from one `Borrow` call and copied from another (CVE-2020-36323 fixed the shrinking case; rust-lang/rust#155708, April 2026, closed a remaining path where "the remaining-length calculation underflows into a heap overflow"), and `str::replace`'s fast path trusted a custom `Pattern` (#156491). This is the non-panicking twin of the bullet above on calling user code while a structure is in an invalid state. REQUIRED: call the user method **once** and keep the returned value; bound every raw read/write by the capacity actually allocated, with an always-on check at the `unsafe` site (not `debug_assert!`); where the contract genuinely needs a guarantee, demand it through an `unsafe trait` (the `TrustedLen` shape). Test under Miri with an adversarial impl that returns different lengths on successive calls.
- **A safe API whose soundness depends on a destructor running.** `mem::forget`, `Box::leak`, an `Rc` cycle and `ManuallyDrop` are all safe, so no `Drop` is guaranteed to run. A guard, handle or future whose `Drop` is the only thing that waits for a thread, a kernel operation (`io_uring`, overlapped I/O), a DMA transfer or a scoped task to stop touching a **borrowed** buffer is unsound: forget the guard, the borrow ends, the buffer is freed or reused, and the operation writes into it — a use-after-free from entirely safe code. This is why `std::thread::scope` takes a closure instead of returning a join guard. RUSTSEC-2020-0021 (`rio`, no patched version): a leaked `Completion` skips the drop code that waits for the kernel, which goes on using the buffer after its borrow has ended. REQUIRED: the operation **owns** its buffer (pass a `Vec<u8>`/`Bytes` in and get it back on completion), or the borrow lives inside a closure-scoped API that joins before it returns, or the constructor is `unsafe` with the "must not be leaked" obligation written in `# Safety`. Rely on `Drop` for cleanup, never for memory safety.
- **Making a raw pointer to a field by way of a reference** — `&mut (*p).field as *mut F`, `&(*p).field as *const F`, `&mut packed.field` — when the place is uninitialized (a `MaybeUninit<Struct>` being filled field by field), unaligned (`#[repr(packed)]`) or aliased by another live pointer. The intermediate `&`/`&mut` asserts initialization, alignment and exclusivity for that instant — UB even though the reference is cast away at once — and `(*p).field = v` on uninitialized storage additionally *drops* the garbage "old value". Use the raw-borrow operators `&raw mut (*p).field` / `&raw const (*p).field` (stable since Rust 1.82; `addr_of_mut!`/`addr_of!` before that) together with `ptr.write(v)`, and derive every raw pointer into one object from a single `&raw mut` base rather than from separate `&mut` reborrows, each of which invalidates the previous pointer under the aliasing model. Miri reports all three.
- **A `// SAFETY:` invariant about collection membership that one refactor makes false elsewhere.** An intrusive list's `unsafe fn remove(&mut self, item)` typically requires "`item` is in *this* list or in no list". A later, innocent-looking change that shortens a critical section by moving the elements out — `let local = mem::take(&mut *guard); drop(guard); for x in local { … }` (equally `drain(..).collect()`, `split_off`, `swap`) — puts live items into a *third* list the proof never mentioned, while other threads still call `remove` against the original: unsynchronized writes to the same prev/next pointers. CVE-2025-68260 (Linux 6.18 `rust_binder`, fixed in 6.18.1): `Node::release` took the lock, moved all items to a local list on the stack, released the lock and iterated, racing with `unsafe` removals on the original list — memory corruption; the fix pops items directly off the original list. REQUIRED: when an `unsafe` proof depends on *where* an element lives, every function that moves elements between containers is part of that proof — re-read the `// SAFETY:` comments of all `unsafe` users of the collection before applying the "take, unlock, process" refactor that §B2/§E4 otherwise recommend, and if the lock must be released per item, pop one element at a time under the lock.

**REQUIRED**:
- `// SAFETY:` comment listing each invariant in the form `// SAFETY: ptr is valid for reads of size_of::<T>(), is properly aligned (allocated via Layout::new::<T>()), and outlives this borrow.`
- Add miri to CI for files containing `unsafe`: `cargo +nightly miri test --workspace` — bare `miri test` on a non-virtual workspace root omits member crates the same way bare `cargo test` does (§D4/§C10); Miri accepts cargo-test's package-selection flags, so `-p <member>` also works when only some crates touch `unsafe`. Yes, 10× slower; the one UB caught pays for it.
- Default to safe abstractions (`zerocopy::FromBytes`, `bytemuck::Pod`/`bytemuck::cast_slice`, `slice::chunks_exact`) before reaching for raw pointers. (`bytes::Bytes` is a refcounted *buffer container*, not a safe-transmute abstraction — don't confuse the two.) Safe is not the same as total: `bytemuck::cast_slice` (like `cast` and `from_bytes`) **panics** when the byte length is not a multiple of the target size or the slice is misaligned for the target type. For bytes whose length or allocation this code did not choose — file contents, network payloads, FFI buffers — use `try_cast_slice` / `try_from_bytes` (or `pod_read_unaligned`) and handle the error, or decode element-wise with `chunks_exact` + `from_le_bytes`. Alignment depends on where the allocator placed the buffer, so the panic can be absent from every test and present in production. Bun's Rust port (2026-07-08): `Blob.text()` on a UTF-16 byte-order mark followed by an odd number of bytes "panicked the process", where the original helper had ignored the trailing byte.
- **Serializing out (type → bytes) is the mirror of that read rule.** Derive `bytemuck::NoUninit` / `zerocopy::IntoBytes` and let them **reject padded types at compile time** — that rejection *is* the padding-leak being caught, not an obstacle to override. If rejected, make the layout padding-free: reorder fields so none is needed, or add explicit `_pad: [u8; N]` fields you zero-initialize, then serialize. `#[repr(packed)]` also removes padding but reintroduces the unaligned-access hazard above — prefer explicit fields, or serialize field-by-field. Never write raw struct bytes with padding to a socket, file, or log.
- Note: `<[T]>::align_to::<U>` is itself `unsafe` and requires the same `Pod`-style invariants as `transmute`; use it only when `bytemuck`/`zerocopy` aren't available, and with a `// SAFETY:` block per the rule above.
- **Every `union` read sits behind a safe accessor carrying a local validity proof.** For a tagged union (`#[repr(C)] struct { tag: u32, data: SomeUnion }`), the accessor matches on `tag` and only inside the matching arm reads the corresponding field, with a `// SAFETY:` naming *which write* (which C-side call, which prior branch) made these bits valid **at this field's type**. For deliberate type-punning with no tag, the `// SAFETY:` proves the layout and validity of the actual bits read, which may follow from a runtime value check; an unchecked API accepting arbitrary source values needs the stronger all-values proof. Do not invent a tag check that proves nothing. The union must be `#[repr(C)]` for any FFI or layout-dependent use. And the meta-check: **if the union exists only to pair with a Rust-side flag you control, you have reinvented an `enum` — use one.** A Rust `enum` *is* a tag-checked, compiler-enforced tagged union; hand-rolling `union` + `bool`/`u32` flag re-opens exactly the wrong-field-read UB the language already closed for you. Reach for a raw `union` only when a foreign (C) layout forces it.
- **`MaybeUninit<T>` discipline**: use it for piecewise initialization or an out-pointer whose callee accepts uninitialized storage. Creating `MaybeUninit::<T>::zeroed()` is safe even when zero is invalid for `T`; **promoting** the stored bits to `T` with `assume_init`/`assume_init_ref` requires a valid value at that point. Initialize every value-bearing field the type requires, using writes that do not read/drop old uninitialized contents. Padding need not be initialized, and nested `MaybeUninit` fields may deliberately remain uninitialized; neither permits reading raw padding as initialized bytes (§B5's serialization rule). Track initialized fields/elements for cleanup if partial construction can fail. Plain `mem::zeroed::<T>()` creates `T` immediately and is valid only when the resulting value satisfies `T`'s requirements; it is not equivalent to zeroed staging storage.
- **Strict provenance**: when a pointer genuinely encodes its address as an integer (pointer tagging, free-lists, XOR-linked structures), use the strict-provenance API (`ptr.addr()`, `ptr.with_addr(addr)`, `ptr.map_addr(|a| …)`, `ptr.expose_provenance()`, `core::ptr::with_exposed_provenance::<T>(addr)`) rather than `ptr as usize` / `usize as *const T` round-trips — the cast form is not by itself unsound: a `ptr as usize` cast *exposes* the provenance under today's exposed-provenance semantics, so the mirrored `usize as *const T` re-attaches some provenance and the round-trip stays defined — but it degrades that provenance to "some previously exposed provenance", which miri (strict mode) and the strict-provenance lints can no longer verify, so they warn/reject it; prefer the strict API wherever the resulting pointer will be dereferenced, because it keeps the proof machine-checkable. The unconditional UB is the other direction: dereferencing a pointer minted from an integer that is not the exposed address of a live allocation. For a tagged pointer that will actually be **dereferenced**, keep the real base pointer and re-tag through `ptr.with_addr(addr)` / `ptr.map_addr(|a| …)` (the base's provenance carries over), or — when the round-trip through an integer is genuinely unavoidable — pair `ptr.expose_provenance()` on the way out with `core::ptr::with_exposed_provenance::<T>(addr)` on the way back in. `core::ptr::without_provenance::<T>(addr)` is **not** an interchangeable tagging option: it deliberately mints a pointer with **no** allocation provenance, so dereferencing it is UB even when the numeric address happens to match a live allocation — reserve it for sentinel / integer-like pointer values that are only ever compared or inspected via `.addr()`, never dereferenced. For an ordinary pointer cast with no address↔integer round-trip, plain `as` is idiomatic and fine — this is not a blanket "replace every cast". (All of these are stable since Rust 1.84.)
- **`slice::from_raw_parts(data, len)` invariants** — list before calling: `data` is non-null and aligned, including for zero length/ZSTs; the requested extent contains initialized `T`s in one live allocation, with `len * size_of::<T>() <= isize::MAX` and no address wrap. The extent may be a prefix/subrange; it need not cover the allocation. Tie the resulting lifetime to that storage. Shared-slice memory must not be mutated during the borrow **except inside `UnsafeCell`**, under a sound interior-mutability discipline — `UnsafeCell` does not itself permit data races. For `from_raw_parts_mut`, also prove exclusive access and valid reborrowing; interior mutability does not relax `&mut` uniqueness. Adjacent separate allocations still cannot be joined into one slice. State the applicable proof in `// SAFETY:`.
- For FFI: every `extern "C"` function takes/returns only **C-ABI-safe types, recursively** — primitive integers/floats/`bool`, raw pointers, `extern "C" fn(...)` **or** `unsafe extern "C" fn(...)` pointers specifically (**not** a bare `fn(...)`/closure, whose default ABI is `Rust` — rustc's own FFI checker (`improper_ctypes`) flags a Rust-ABI function pointer the same way it flags any other non-C type; use the `unsafe extern "C" fn(...)` form when invoking the callback has caller-side preconditions the C side must uphold, mirroring the `safe`/`unsafe` import distinction below), and `#[repr(C)]`/`#[repr(transparent)]` aggregates whose every field is C-ABI-safe by this same rule. A Rust function pointer type is always non-null, so a callback the foreign contract allows to be absent must cross the boundary as `Option<extern "C" fn(...)>` (or the `unsafe` variant) — std guarantees `Option<extern "C" fn(...)>` has the same representation as the bare pointer with `None` as the null value — never accept a C-side null into a bare (non-`Option`) function-pointer parameter or field. Rust's `char` is **not** on this list either, despite looking primitive: it is a 4-byte Unicode scalar value restricted to valid, non-surrogate code points (`0..=0x10FFFF` minus the surrogate range) with no C equivalent — rustc's checker flags it too. Cross the boundary as `u32` (validated on the way back into a `char` — see §B5's validate-before-mint rule) or whatever C integer type the API actually specifies for a character. The attribute is necessary but not sufficient: a `#[repr(C)]` aggregate containing a `String`, `Vec`, `Rc`, or an unsized/DST field still has no defined C layout — the invalid member invalidates the whole aggregate. (`Box<T>` for `T: Sized` is the documented exception to this list — see §B25's `extern "C"` bullet for the single-pointer ABI guarantee and the direction-specific ownership contract it requires; it is not itself a layout violation the way the others are.) `String`, `Vec`, `CString` and Rust tuples are not C-ABI transport types. Keep `CString` as the Rust-side owner and pass its borrowed pointer while it remains alive, or transfer through `into_raw` with a paired reclaiming contract. For buffers, `(ptr, len, cap)` is a Rust-side decomposition only; transmit separate scalar arguments/out-parameters or a `#[repr(C)]` descriptor matching the C declaration: on a project with MSRV ≥ 1.93 prefer `Vec::into_raw_parts` (stable as of Rust 1.93); below 1.93 use the manual decomposition via `ManuallyDrop<Vec<T>>` (available since Rust 1.20). See §B25 for the full FFI ownership discipline.

**The unsafe→safe boundary: guard value-invariants, prove relational ones.** When `unsafe` produces a value that flows into safe code, split what must hold about it into two kinds — they need opposite defenses:
- **Value-invariants** (a bit pattern, an integer range, an enum discriminant, a length, an address's alignment, UTF-8 well-formedness): runtime-checkable. The `unsafe` must emit the value through a **total fallible constructor** — `&[u8] → Result<Typed, _>` — that runs the check and returns `Err` on bad input. It must **never panic on adversarial input** (no `unwrap`/`expect`/`assert!` at the boundary — that turns a soundness check into a remote DoS; see §B7/§C2). Canon: `str::from_utf8`, `char::from_u32`, `TryFrom` (§B26), `zerocopy::TryFromBytes`. Crucial ordering: the guard runs on the **raw representation (bytes) *before* the typed value is minted** — `validate(&[u8]) -> Result<&T>`, never `let t: T = transmute(bytes); check(t)`. The second form's *read* of an invalid `T` (an invalid `bool`, a bad discriminant, a dangling `&`) is itself the UB you were trying to guard against. For types where every bit pattern is valid (`bytemuck::Pod`), the type bound removes the bit-pattern check only; byte extent, alignment and the applicable lifetime/aliasing/ownership conditions still require proof or a checked API.
- **Relational invariants** (lifetime validity, aliasing/exclusivity, pointer provenance, "points to `N` initialized `T`s", `Send`/`Sync`): **not** runtime-checkable. There is no `fn is_not_dangling(p: *const T) -> bool` — to "check" you would dereference, which is the use-after-free. So there is **no downstream guard**; the only defense is the *upstream* proof discharged before the `unsafe` (the `// SAFETY:` contract) plus the type's variance and marker traits (see §B18, §B18a). Do not pretend a downstream check exists — for this class it cannot.

**An invariant `unsafe` relies on must stay unbreakable through the module's whole safe API — the soundness boundary is the privacy boundary, not the `unsafe` block.** The two rules above guard an invariant when a value is *minted*; they say nothing about keeping it true afterwards. When `unsafe` code (`from_utf8_unchecked`, `get_unchecked`, `set_len`, `assume_init`, …) relies on a type's invariant — UTF-8 well-formedness, `len <= cap` with an initialized prefix, sortedness, in-bounds indices, non-null — that invariant is a **safety invariant of the whole module**, and every safe path that can reach the representation must preserve it: every safe `fn`, every trait impl (`DerefMut`, `AsMut`, `IndexMut`, `BorrowMut`, `Default`, `From`, `Clone`, a derived `Deserialize`), and every `pub` field. Consequences:
- **No safe `&mut` access to the raw representation.** `pub fn as_mut_bytes(&mut self) -> &mut [u8]` or `impl DerefMut<Target = [u8]>` on a type whose `as_str()` calls `from_utf8_unchecked` lets safe code write invalid UTF-8 and then obtain an invalid `&str` — UB with no `unsafe` at the corrupting call site. Offer mutation only as a checked operation that re-establishes the invariant, or as an `unsafe fn` whose `# Safety` names it; if neither is worth having, remove the accessor. Fields the `unsafe` code relies on stay private to the module that contains that code.
- **A derived `Deserialize` builds the fields directly and bypasses a validating constructor** (observed on rustc 1.98.0 with serde 1.0.229/serde_json 1.0.151: `{"v":[3,1]}` deserializes into a plain derived struct whose hand-written constructor requires sorted `v`, and is rejected once the type carries `#[serde(try_from = "Raw")]` with a validating `TryFrom<Raw>`). Route deserialization through validation with the container attribute `#[serde(try_from = "FromType")]` (serde documents: "Deserialize this type by deserializing into FromType, then converting fallibly. This type must implement TryFrom<FromType> with an error type that implements Display"); `#[serde(from = "FromType")]` is the infallible twin — it can normalize but never reject, so it does not enforce a rejecting invariant.
- Grounding: iceoryx2-bb-container RUSTSEC-2026-0294 — the `String` API exposed its contents as mutable bytes through safe `as_mut_bytes` and `DerefMut`, while `as_str()` converted the bytes to `&str` without validating UTF-8, so safe code could corrupt the bytes and obtain an invalid `&str`; patched in 0.10.0 by removing `as_mut_bytes`/`deref_mut` without replacement. (See `references/sources.md`.)

**Panic-safety grounding:** ringbuf RUSTSEC-2026-0293 dropped elements in `Consumer::skip`/`clear` before advancing its read index. A panicking element `Drop` left already-dropped slots reachable, so later cleanup could double-free them. Keep ownership/drop bookkeeping valid across that interruption; a caught panic is not the proof. Patched in 0.5.2. The source ledger records this instance of §B5/§B4.

## §B13. Check-then-act races in concurrent collections (TOCTOU)

**The trap**: LLMs port single-threaded patterns from Python/JS/Java into multi-threaded Rust. The canonical example is the "lazy cache":

```rust
// BANNED — race between contains_key and insert
if !cache.contains_key(&key) {
    let value = expensive_fetch(&key).await;
    cache.insert(key, value);
}
```

One non-interleaved caller can make this look correct. Concurrent callers can all observe absence before any result is inserted — including async tasks on **one OS thread** interleaving at the await. The map can contain one final entry while the computation ran multiple times. This is a semantic coordination race, not necessarily a memory data race. Counters, conditional updates and lazy-init flags have the same check/act hazard when another caller can intervene.

**Why this happens**: thread count is mistaken for non-interleaving. Cooperative scheduling, callbacks and reentrancy can separate the check from the act even without parallel execution. Trace where another caller can run, not just which thread owns the event loop.

**Prompt triggers**: "cache", "memoize", "lazy initialization", "ensure exactly one X", "deduplicate", "if not exists, create".

**BANNED**:
- Split check/act calls such as `if !map.contains_key(k) { map.insert(k, v); }` when another caller can intervene: through a concurrent map, separate lock/RefCell borrows, an await, or reentrant code. A plain owned `HashMap` under exclusive `&mut self`, or one effective exclusive guard held across both operations, has no such mutation window; `.entry()` there is an efficiency/clarity choice, not a necessary race fix. A shared read guard around an internally mutable map does not exclude competing mutators. Prove the actual exclusion interval, not merely the presence of a lock or a single OS thread.
- `if map.contains_key(k) { let v = map.get(k).unwrap(); ... }` on an interleavable map — another caller can remove the entry between check and get, making `.unwrap()` panic.
- Treating separate operations on a concurrent collection as one atomic change without a protocol that actually provides that guarantee.
- `let x = *counter.lock().unwrap(); *counter.lock().unwrap() = x + 1;` — read and write are separate critical sections, a thread can interleave.
- `if Arc::strong_count(&arc) == 1 { ... unique-owner logic ... }` without a protocol preventing intervening ownership changes. Use `Arc::into_inner` or `Arc::try_unwrap` for consuming extraction. The stronger `into_inner` guarantee — exactly one caller receives the value — requires **every strong clone to be consumed through `into_inner`**. If another clone is retained or ordinarily dropped, participating calls can all return None and the value can be dropped without extraction. `try_unwrap(...).ok()` lacks the all-participant guarantee because discarded Err handles can race to drop the final value.
- `Ordering::Relaxed` on an atomic used to *publish* data to another thread (e.g. write the payload, then `flag.store(true, Relaxed)`; the reader does `flag.load(Relaxed)` then reads the payload). `Relaxed` establishes **no happens-before** edge, so the reader may observe the flag set before the payload writes are visible — a data race that x86's strong memory model usually hides in tests but that breaks on ARM/AArch64 under reordering. Use `Release` on the store and `Acquire` on the load (or `AcqRel`/`SeqCst` for read-modify-write) whenever the atomic guards access to other data. (The un-atomic extreme of the same race — a `static mut` incremented from several threads — is §B18's `static mut` bullet in `unsafe-sync-memory.md`.)
- **The database twin of the lazy-cache above: a `SELECT` whose result guards a later `UPDATE`/`INSERT` on the same row.** `SELECT balance` → check in Rust → `UPDATE … SET balance = $new` is a read-modify-write across two statements: two concurrent transactions both read 100, both write 20, and the lost update is silent — no error, lock, or test failure (tests are single-threaded). Wrapping the pair in `pool.begin()` **does not fix it**: at the default `READ COMMITTED` isolation (PostgreSQL/sqlx) the second transaction still reads the first's pre-update value between its statements — "a transaction" is not the same as "atomic with respect to my own read". Same family: select-then-insert racing a "unique" creation, and a raw `sqlx::query("BEGIN").execute(&pool)` … `query("COMMIT").execute(&pool)` pair — each `execute` checks out whichever pooled connection is free, so the statements **may** run on different connections (there is no guaranteed identity between them) and the "transaction" spans nothing; PostgreSQL answers the orphan `COMMIT` with a warning, not an error, so it silently commits nothing (§B4). Language-agnostic shape, same single-threaded prior as every bullet in this section.

**REQUIRED**:
- For synchronous "insert if absent": `map.entry(key).or_insert_with(|| compute_value())` (synchronous only — see §B2: never hold this guard across `.await`). On a plain `std::collections::HashMap` the atomicity comes from the `&mut self` borrow (it is single-threaded — there is no internal lock); on a concurrent `dashmap::DashMap`, `entry` holds the shard lock across check and act. Either way the check and the act are one operation, not two.
- For an **async** compute that must run exactly once under concurrent load (the lazy-cache example this category opens with), `or_insert_with` cannot help — its closure is synchronous and cannot `.await`. Store a once-cell per key: `let slot = map.entry(key).or_insert_with(|| Arc::new(tokio::sync::OnceCell::new())).clone();` then `slot.get_or_init(|| async { expensive_fetch().await }).await`. State the guarantee precisely: this is **one active initializer at a time and one successfully-stored result**, not "runs exactly once ever" — if the task driving `get_or_init` is cancelled mid-initializer (its future dropped at an `.await`) or the initializer panics, tokio's `OnceCell` cancels the attempt and **lets another waiting caller run the initializer again** (documented verbatim: "If the provided operation is cancelled or panics, the initialization attempt is cancelled. If there are other tasks waiting for the value to be initialized, one of them will start another attempt at initializing the value."), so any external side effect performed before the cancellation/panic can fire twice even though the cell only ever stores one result. `tokio::spawn` + `JoinHandle::await` does **not** close this gap: it only prevents the effect from being silently half-done if the *outer* task is cancelled mid-await (the spawned task keeps running to completion, detached, once started). It does **not** prevent `OnceCell`'s own cancel-and-retry semantics from letting a second, independent attempt run — if `get_or_init`'s own future is dropped (the outer caller cancelled), the cell lets another waiting caller start a fresh attempt (a fresh `tokio::spawn` + await) while the *first* spawned task, never aborted, keeps running the same side effect in the background: the effect can fire from both attempts, spawn+await notwithstanding. A distributed lock or a durable `running`/`done` status row is **coordination, not exactly-once**: a lock prevents two *concurrent* calls from both running the initializer, but it does nothing for a *crash* — if the process performs the non-idempotent effect (charges a card, sends an email) and then dies before it records `done`, the next owner sees `running` (or a lock that's free again) and pays the same price a second time. Closing that gap for a genuinely non-idempotent external effect needs one of: a **provider-side idempotency key** — pass a stable, caller-generated key to the external system itself (e.g. Stripe's `Idempotency-Key`), so a post-crash retry is deduplicated *by the provider*, not by anything local; or **atomically coupling the effect and its result record in one transactional system** (the effect *is* the transaction — a local ledger write with no external call to lose track of). A lock/status row is the right tool for serializing concurrent attempts and is still required, but state it as exactly that — coordination — never as the exactly-once guarantee itself. **Registry lifetime and capacity:** the short Arc-clone recipe assumes the entry remains registered. With eviction, preserve entry identity while any existing requester can still start or continue initialization on it — including a requester holding the cell **before the first initializer starts**, or a waiter after cancellation. Protecting only currently running initializers misses that interval. A lease acquired atomically with lookup and retained through completion/abandonment is one remedy; a generation/ownership protocol must prevent overlapping starts/continuations, not merely discard a stale result after duplicate work ran. A terminal completed cell may be evicted when the API proves it cannot restart and the cache contract permits recomputation. Bound **all registered entries, including pinned ones**; when full, reject new keys or use bounded admission/backlog rather than growing an uncapped active registry. Test eviction before initialization as well as during an active attempt, with a per-key invocation counter, and test admission when every capacity slot is pinned.
- For `DashMap`: `dashmap::DashMap::entry(key).or_insert_with(...)`.
- For atomic counters where wrapping on overflow is acceptable (statistics, sampled counts, non-critical tallies): `AtomicUsize::fetch_add(1, Ordering::Relaxed)`, not lock-load-add-store. `fetch_add` **always wraps** on overflow — atomics have no debug-mode overflow check the way plain integer `+=` does, so this never panics, it silently rolls over. For an invariant-bearing counter that must never silently wrap (a monotonic ID generator, a sequence number), unconditional `fetch_add` is the wrong tool: use `fetch_update` with a `checked_add` inside the closure (overflow becomes a real `Err`, not a wrap) or widen the type (`AtomicU64` instead of `AtomicU32`) so the overflow horizon is unreachable in practice. For a **gauge of live resources/in-flight work**, pair acquisition and release so the decrement cannot be skipped on an early-return path — a `fetch_sub` that runs on a path that never incremented wraps to `usize::MAX` (in release *and* debug); guard it with an RAII drop guard that runs the `fetch_sub`, not a bare call at the end of the function; §B26's gauge-underflow bullet owns the fix shapes. A cumulative event counter or monotonic ID sequence is different: it must not be decremented merely because an operation completed.
- For "compare and swap" patterns: `Atomic*::compare_exchange` or `Atomic*::fetch_update`.
- For ordered iteration of map keys, use `BTreeMap` (sorted by key) or collect to `Vec` and `sort_by`. `HashMap::iter` order is randomized per-process and per-rehash; relying on it makes tests flake across machines.
- `Relaxed` is correct only for standalone counters/statistics where no other memory is published through the atomic. The moment the atomic gates visibility of other data, you need `Acquire`/`Release`. Don't blanket-`SeqCst` to "be safe" — it hides the wrong mental model and costs a fence; reason about the happens-before edge explicitly, and model-check multi-atomic code with `loom` (already in the post-flight list).
- For a guarded row update, push the predicate **into one atomic SQL statement** and act on the result: `UPDATE accounts SET balance = balance - $1 WHERE id = $2 AND balance >= $1`, then check `rows_affected() == 1` (0 = the guard failed) instead of selecting first. For multi-statement read-modify-write: `SELECT … FOR UPDATE` inside a `pool.begin()` transaction, routing **every** statement of that transaction through the returned `Transaction` handle (`tx`, or `&mut *tx` as the executor) — never the `Pool`; or optimistic concurrency (a `version` column: `UPDATE … WHERE id = $1 AND version = $v`, retry the whole read-modify-write when 0 rows are affected). For create-if-absent: `INSERT … ON CONFLICT DO NOTHING` / `DO UPDATE` instead of select-then-insert. When several statements must see one consistent snapshot, `SERIALIZABLE` isolation (`SET TRANSACTION ISOLATION LEVEL SERIALIZABLE` or the session/pool default) with a retry on SQLSTATE `40001` (serialization failure) — and note that `READ COMMITTED`, the default, does **not** close the read-modify-write race above. Transaction-handle Drop/commit discipline is §B4.

**Detection**: this is invisible to type checking and almost always invisible to tests. The defense is recognizing the pattern at write time. (Enforcement: the TOCTOU patterns here are 🟡 — recognized and fixed at write time; only the `Relaxed`-publish data race is 🔴 surface-always.) If a function does two consecutive operations on a shared collection, it is a candidate.

## §B19. Iterator invalidation through indirection

**The trap**: the borrow checker prevents structural mutation while incompatible element borrows are live. With `RefCell`, conflicts become runtime borrow panics; with `unsafe` raw pointers they can become memory unsafety. Index-based loops can be entirely safe Rust and still visit the wrong items: their traversal boundary and index validity must match the algorithm's contract.

**BANNED**:
- Iterating `vec.iter()` (or `borrow.iter()`) while pushing/removing through a `RefCell<Vec<T>>` borrow on the same vector inside the loop body — this doesn't dangle (safe `RefCell` can't produce that): the `borrow_mut()` panics with `BorrowMutError` the instant it runs while the iterating `Ref` is still alive.
- Using `for i in 0..vec.len()` as a complete traversal **when newly appended work must also be visited** — the range captures the initial length, so a supposed complete BFS/DFS can stop before visiting discovered children. A deliberate pass over only the original elements, or only the current BFS layer, is valid. For append-only work that adds one output per original element, replacing the captured bound with `while i < vec.len()` can instead make the loop nonterminating: both `i` and `len` grow together.
- Taking a field out to process and put back **when an exit can violate the object's state contract**. `mem::take` installs `T::default()`, `Option::take` installs `None`, and `mem::replace` installs the supplied replacement; none automatically restores the old value. An early `return`, `?`, unwinding panic, or cancellation (§B3) before put-back can leave that replacement observable. Intentional handoff/reset is allowed when the resulting state and consumption on failure are part of the contract (§E2); restoration is required only to uphold the actual guarantee. A drop guard can restore only state that remains available to it; moving the original into a consuming transform does not preserve it for the guard. Putting back a partially modified value is not rollback. If failure must leave the original unchanged, retain an independent original or use a proven transactional/undo design; merely switching the transform to `&mut T` does not provide that guarantee either.

**REQUIRED**:
- For BFS, use separate current/next layers or a FIFO `VecDeque` (`pop_front` / `push_back`); capture a layer's initial length only when processing one layer at a time. For DFS, use a LIFO worklist (`Vec::push` / `pop`) and preserve the required child order. State the visited/cycle policy when traversing a graph; changing FIFO to LIFO or vice versa changes traversal semantics.
- If the contract needs pre-mutation contents, preserve an appropriate snapshot or separate input/output; clone a whole collection only when that snapshot is actually required. Safe indexing does not become undefined behavior merely because the traversal logic is wrong.
- Choose the boundary by contract: capture the initial length for an original-elements pass when indices remain valid (such as append-only mutation); use a growing worklist or a rechecked length only when newly discovered work belongs in the pass, with a termination/progress argument and the applicable resource bounds (§B7/§B14). Insertions/removals can shift indices — rechecking `len()` alone does not prevent skipped or repeated items; use a queue, stable identifiers, or an appropriate in-place operation such as `retain_mut` when its semantics fit.

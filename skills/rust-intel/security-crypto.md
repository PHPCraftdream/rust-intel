## §B12. Cryptographic code (silent insecurity)

**The trap**: cryptographic code generated by LLMs has a unique failure profile. A large fraction of LLM-generated crypto Rust fails to compile at all, and of the code that *does* compile, a large share of the vulnerabilities present go undetected by static analyzers. (Rust-specific evidence: arXiv:2604.27001, Elsayed/Fulton/Yang, 2026-04-29 — of 240 AES-256-GCM/ChaCha20-Poly1305 samples from Gemini 2.5 Pro, GPT-4o and DeepSeek Coder, 23.3% compiled; the authors' crypto-specific analyzer flagged 57% of the compiled samples (32 of 56 — almost all MEDIUM-severity `unwrap()` on cryptographic operations; only 2 of 56 were CRITICAL, one multi-call nonce reuse and one hard-coded secret) while CodeQL reported only two findings, both false positives; API hallucinations (calls to non-existent functions such as `generate_nonce()`) caused 41.3% of the compile failures, and the abstract's "systematic" nonce reuse rests on that single detection. Directional only: 56 compiled samples, the authors' own analyzer, older models. See `references/sources.md`.) Crypto code looks right, runs, passes round-trip tests (encrypt → decrypt yields original) — and is still catastrophically insecure.

**Why this happens**: cryptography requires *protocol-level* reasoning the LLM does not do. Encrypt-then-decrypt round-trip is the canonical test, and it passes for any non-broken cipher regardless of whether the key, nonce, or mode is sound. The bugs live at a level orthogonal to functional correctness.

**Specifically dangerous patterns**:
- **Nonce reuse**: hardcoded nonce, nonce derived from a counter that resets, nonce equal to the message ID. Reusing a nonce with the same key in AES-GCM or ChaCha20-Poly1305 is catastrophic — recovers plaintext or forges authentication.
- **API hallucination in crypto crates**: invented methods on `ring`, `rust-crypto`, `aes-gcm`, `chacha20poly1305`. Crypto-API names look interchangeable to the LLM but have very different security properties. (Note `rust-crypto` itself is **unmaintained since 2016** (RUSTSEC-2016-0005) and separately carries an unpatched AES-miscomputation bug (RUSTSEC-2022-0011, no fixed version) and must never be *proposed*; it appears in this list only as a name LLMs hallucinate methods on. Use the maintained `RustCrypto` org crates — `aes-gcm`, `sha2`, etc. — instead.)
- **Weak parameter choices**: ECB mode (which the LLM may select because it's "simpler"), 64-bit nonces with random generation (birthday-bound collision), insufficient PBKDF2 iterations.
- **Mixing primitives across security levels**: using SHA-1 alongside AES-256, or pairing a strong cipher with a weak MAC.
- **Custom crypto code**: hand-rolling any cryptographic primitive in Rust. Almost always wrong.
- **Stubbed or placeholder crypto that returns success**: a "signer", "verifier" or "cipher" whose body performs no cryptography and returns fixed values — or a `verify` that always returns `true`/`Ok(())`. A sign → verify or encrypt → decrypt round trip is green against such a stub, so the round-trip test proves nothing (RUSTSEC-2026-0273: `manzana` < 0.3.0, `SecureEnclaveSigner` create/delete/load/sign/verify performed no cryptography and returned fixed values, undisclosed).

**REQUIRED**:
- I do not write cryptographic code beyond *direct calls to well-known high-level APIs* (e.g., `aes_gcm::Aes256Gcm::new(key).encrypt(nonce, plaintext)`).
- For any crypto-touching task, state the threat model and the design in plain text before the code. If the threat model is unstated, or the design changes it, ask the user to confirm first — that is the Blocking protocol's crypto case. If the user has stated it, write the code with the threat model it assumes recorded as an assumption at the top of the response.
- Nonce policy follows the selected primitive's own documented construction, and per-key limits are part of that policy — "always generate the nonce from a CSPRNG" is not a universal rule. What every scheme must actually establish is nonce uniqueness per key; constructions establish it differently. For random-IV AEADs (AES-GCM under NIST SP 800-38D) prefer OS-backed entropy for keys and security-critical nonces — but randomness alone does not *establish* uniqueness: state the per-key invocation/collision budget (the birthday bound over the 96-bit random space) and argue it holds in aggregate across processes, instances and restarts. For counter-oriented constructions (RFC 8439 §2.6 builds the ChaCha20-Poly1305 nonce around a per-message counter; random selection alone does not establish uniqueness there), a counter is the scheme's own documented approach and is acceptable **with explicit cryptographic justification** covering how the counter starts, persists, and survives restarts and multiple writers without repeating a (key, nonce) pair — never hardcoded, never reused, never a counter that resets. The type name is `rand`-major-dependent: `rand::rngs::OsRng` (rand ≤ 0.9) or `rand::rngs::SysRng` (rand ≥ 0.10 — renamed in 0.10.0 with no deprecated alias); the `getrandom` crate is the name stable across the rename. State the `rand` version assumed, the nonce construction actually used, and the per-key invocation limit.
- A placeholder crypto function **fails closed** (`Err` / `unimplemented!`) — it never returns success or fixed output. Every verify / MAC-check / AEAD-decrypt path carries negative controls, each of which must be rejected: a single-bit tamper of the message, of the signature/tag, and of the ciphertext; a wrong key; truncated input. The round trip is necessary and never sufficient (§D1a for the general negative-control rule).
- Default to high-level libraries (`age`, `ring`, `rustls`) over low-level primitives. Provider note: the default rustls crypto provider is now `aws-lc-rs` (not `ring`) in current `rustls` and `reqwest` ≥ 0.13, and `jsonwebtoken` ≥ 10 requires choosing a backend explicitly (`aws_lc_rs` / `rust_crypto` features).
- Verify the selected crypto provider/backend with §D3's behavioral matrix, including invalid-input rejection. RUSTSEC-2026-0290 is backend-specific: `pqc_kyber` with its opt-in `avx2` feature on x86_64 skipped implicit rejection, enabling chosen-ciphertext key recovery under a reused key pair; its default reference backend was unaffected, and no patched release exists as of 2026-11-15 (`pqc_kyber` 0.7.1, published 2023-08-23, is still the latest). A green scalar round-trip does not establish the accelerated backend's security contract.
- Re-check the resolved TLS library against current advisories. Rustls RUSTSEC-2026-0285 affects `>=0.23.13, <0.23.45`: TLS 1.3 handshake messages could cross encryption-level boundaries within one record. The transcript remained authenticated, so this was not a forged-handshake bypass; the missing rejection violated RFC 8446's record/key-change contract (§F1). The fix is 0.23.45 on the affected line, not a universal minimum for every rustls major/minor. See `references/sources.md`.
- For password hashing: `argon2id` is the default. Bare, unsalted, or low-iteration PBKDF2 and plain SHA-256 are banned under any circumstances — but properly salted PBKDF2-HMAC-SHA256 at or above the OWASP floor (≥ 600 000 iterations; see the KDF work-factor bullet below) is an accepted, sanctioned choice when FIPS-140 validation or another compliance constraint requires it: Argon2 has no FIPS-validated implementation, and [OWASP's Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) names PBKDF2 as the preferred algorithm for exactly that case.
- I surface every line of crypto code in the post-flight summary with extra prominence. For *custom or protocol-level* crypto (anything beyond a direct documented call) I recommend mandatory human cryptographer review — it is the one place that warrants it. For a direct call to a well-known high-level AEAD/KDF API used per its docs, the bar is surface-it plus verify the params (key length, nonce width, algorithm, iteration count, approved tag length, and the primitive's per-key limits — the maximum invocations and message size its nonce construction allows), not a mandatory cryptographer.

**BANNED**:
- Writing custom encryption/decryption logic.
- Implementing cryptographic primitives (block ciphers, hash functions, KDFs) by hand.
- **`SmallRng` for any security-sensitive value (keys, nonces, salts, tokens) — banned regardless of how it is seeded.** Current `rand` docs classify `SmallRng` as explicitly non-cryptographic: fast, small-state, and predictable/invertible by design (it exists for simulations and non-adversarial randomized algorithms, not security). Seeding it from the OS does not turn its algorithm into a CSPRNG — unlike `StdRng` below, the weakness is the *algorithm*, not the seed, so OS-sourced entropy at construction time does not rescue it. Use `StdRng` or a direct OS/system RNG type instead.
- Seeding `StdRng` (or any other seedable *CSPRNG*) with a predictable, reused, or non-OS-sourced seed (hardcoded, a counter, `seed_from_u64`, or a seed persisted/reused across calls) for security-sensitive randomness — prefer the OS-backed RNG type (or `getrandom`) directly as the simpler default. For `StdRng` specifically the hazard is the seed, not the RNG type: `StdRng`'s algorithm (ChaCha12, per current `rand` docs) is itself a CSPRNG, so an OS-seeded instance — freshly seeded from OS entropy at construction and never persisted or reused — is not equivalent to a hardcoded seed and should not be flagged as such; a single such instance may then be used to generate many values without needing a fresh OS seed *per value* — the requirement is fresh entropy per independent RNG *instance*, not per call. The OS-seeding constructor is itself version-bound, not just the accessor/type names: on `rand` 0.9 it is `StdRng::from_os_rng()`; that exact method does not exist on `rand` 0.10 (which renamed `OsRng` → `SysRng` and the `Rng` trait → `RngExt`) — there, seed via `StdRng::try_from_rng(&mut SysRng)?` (fallible — `try_from_rng` returns a `Result`) or the crate's typed `rand::make_rng::<StdRng>()` helper; verify both against the exact `rand` 0.10.x you pin, since this corner of the API moved during the 0.10 line. 0.8 uses `thread_rng()` + `rand::rngs::OsRng` for the accessor form (no deprecated aliases — literal `OsRng` code fails with `E0432` on a fresh `cargo add rand`, and the cheapest fix that compiles, `rand::rng()`, is a different threat-model decision). The accessor forms are CSPRNGs per the `rand` security guarantees, but the OS-backed type is the safer default when seeding chains are part of the threat model. Pin rand ≥ 0.8.6 / 0.9.3 / 0.10.1: below those, `thread_rng()`/`rng()` is unsound (RUSTSEC-2026-0097) when a custom `log` logger itself calls the thread RNG and a reseed happens inside it. State the `rand` version assumed.
- Storing crypto keys in source code, environment variables read at compile time, or anywhere they end up in the binary.
- Comparing secret material (API tokens, MAC tags, password hashes, OTP codes) with `==` — this is a timing side channel. See §B24 for the rule and the `subtle::ConstantTimeEq` / `constant_time_eq` crates.
- `#[derive(Debug)]` (or manual `impl Debug`) on a struct with fields named `password`, `secret`, `api_key`, `token`, `private_key`, `seed`, `mnemonic`, `cookie` — any secret material that ends up printed in a log/trace via `{:?}`. Wrap secrets in a newtype that implements `Debug` as `"<redacted>"`, or use the `secrecy` crate's `SecretBox<T>`. Scope by *role*, not just the name: the target is secret material used for auth/crypto. Do **not** flag a field merely named `token`/`key`/`seed` in a non-secret role — a lexer/parser `Token`, a map/cache `key`, a keyboard-event `key`, or a deterministic-PRNG `seed` are not secrets. Require a second signal (a crypto/auth context, or nearby `secrecy`/`zeroize`) before redacting. The same leak arrives through a different formatter: `#[tracing::instrument]` records **every function argument** as a span field via `Debug` unless `skip`ped (and `(ret)`/`(err)` record return/error values) — see §C9's instrument bullet for the rule and remedies. **Credential-bearing HTTP headers leak the same way:** RUSTSEC-2026-0275 — the legacy Azure SDK (`azure_core` ≤ 0.21.0; fixed only in the rewritten SDK ≥ 0.22.0) wrote the outgoing `authorization` header value to logs whenever debug-level logging was enabled, and at trace level in every affected version. Do not log request/response header maps wholesale; mark credential-bearing values with `http::HeaderValue::set_sensitive(true)` — per the `http` docs, sensitive values are masked by `HeaderValue`'s `Debug` (a value logged through `to_str()` or a copied `String` is not masked) and HPACK encoders may skip compressing them. Before enabling a third-party client's debug/trace logging in production, confirm what it records.
- JWT algorithm pinning that is attacker-driven or left broader than the deployment mints. (`alg: none` is folklore on current `jsonwebtoken`: `Algorithm` has no `None` variant, and `Validation`'s `algorithms` field defaults to a fixed `vec![Algorithm::HS256]` that the token header `alg` must match — verified against jsonwebtoken 11.0.0 docs; a header algorithm outside the configured list is rejected.) The live shapes: parsing the token header to pick the `Validation` algorithm (the attacker then chooses), `Validation::new_for_family(...)` or a hand-written `algorithms` list wider than the algorithm your IdP actually signs with, and RS256→HS256 confusion — verifying with `DecodingKey::from_secret(<public-key bytes>)`, which lets anyone holding the (public) key forge an HS256 token the check accepts. REQUIRED: hardcode the expected algorithm to match your key type — `Validation::new(Algorithm::RS256)` for an IdP RSA public key, `Algorithm::HS256` only for a symmetric secret your service alone holds — and construct the `DecodingKey` the way that algorithm's family demands; never derive the algorithm from the token.
- **JWT verification that stops at signature + algorithm and never checks `aud`/`iss`.** `decode::<Claims>(&token, &key, &Validation::new(Algorithm::RS256))` — the tempting copy from the crate README — verifies the signature and `exp` but leaves the expected `aud` and `iss` at their `None` default: a token that carries an `aud` the service did not configure is *rejected* (`InvalidAudience`), but a token that **omits** `aud` entirely is accepted, and `iss` is not checked at all unless `set_issuer` is called — so a token minted by the same IdP key for a **different service or tenant** (same key, different `iss`, or simply no `aud`) authenticates (verified against `jsonwebtoken` 9.3.1 and 11.0.0; the defaults and the `set_audience`/`set_issuer`/`set_required_spec_claims` setters were re-read on the 12.0.0 docs of 2026-11-13 — the aud-omitted behavior test was not rerun there). Tests pass because they mint their own tokens, which trivially match. REQUIRED: `v.set_audience(&["my-service"])`, `v.set_issuer(&["https://idp.example"])`, and `v.set_required_spec_claims(&["exp", "aud", "iss"])` so the claims are *required*, not merely checked-when-present. Qualify that against the actual token profile — this is not a universal JWT rule: RFC 7519 makes `iss` processing application-specific and `aud` an optional claim, so not every valid JWT profile carries, or must be required to carry, the same claims. A single-service profile whose IdP legitimately mints aud-less tokens is exactly what a blind reading of the sentence above would reject. REQUIRED is to know which claims the deployment's token profile treats as the service/tenant boundary and require + validate those — in the multi-service/multi-tenant IdP deployment above, `aud`/`iss` *are* that boundary, and the rejection tests for a token minted by the same key for a different service or tenant stay.
- `Validation::validate_exp = false`, or signature validation disabled outright — `Validation::insecure_disable_signature_validation()` (jsonwebtoken ≤ 10; the method was removed in 11.0.0) or its ≥ 10.1 replacement `jsonwebtoken::dangerous::insecure_decode` — outside `#[cfg(test)]` — the reflex for making an expired or unsigned test fixture verify. It silences the failure and ships an unauthenticated/expiry-blind endpoint; the ≥ 10.1 form is a free fn in a module literally named `dangerous`, which is the better grep target (the function was not located in the 12.0.0 docs on 2026-11-15 — grep for the `dangerous` module itself on 12.x).
- `reqwest::ClientBuilder::danger_accept_invalid_certs(true)` / `danger_accept_invalid_hostnames(true)` (soft-deprecated in reqwest 0.13 in favor of `tls_danger_accept_invalid_certs` / `tls_danger_accept_invalid_hostnames` — both spellings are the same ban), or a custom `rustls` `ServerCertVerifier` (`verify_server_cert`) that returns `Ok(...)` unconditionally — outside `#[cfg(test)]`. The reflex when a request against a dev/self-signed endpoint fails with a certificate error: it is the cheapest fix that compiles, passes every test (tests hit localhost with exactly such a cert), and in production trusts *any* certificate for *any* site — a silent full MITM on every connection (CWE-295). REQUIRED: pin the internal CA — `ClientBuilder::tls_certs_only([reqwest::Certificate::from_pem(ca_pem)?])` (trust only the pinned CA — in reqwest 0.13 `tls_certs_only` takes `impl IntoIterator<Item = Certificate>`, so pass an array/`Vec`/slice of roots built from your PEM bundle, not a single cert) or `tls_certs_merge(...)` (add it on top of system roots); the older `add_root_certificate` still works but is deprecated in favor of these — never disable validation. A `#[cfg(test)]`-scoped `danger_accept_invalid_certs`/`tls_danger_accept_invalid_certs` against a throwaway test server is fine; the ban is on it reaching non-test code.
- Fixed, hardcoded, or per-username-derived salts for password hashing / key derivation: `SaltString::from_b64("c3RhdGljc2FsdA")`, `b"somesalt"`, or a salt computed from the username. The defect underlying both shapes is the same — no fresh random salt per credential — but the failure mode differs: a single shared fixed/hardcoded salt means identical passwords across different users produce identical hashes, so one cracked hash cracks every user who shares that password, and rainbow/batch attacks return; a per-username-derived salt avoids that specific collision (different usernames yield different salts, so it does satisfy uniqueness-per-credential in the narrow sense) but is still wrong — it's predictable/enumerable, so an attacker who knows or guesses a **specific target's** username can precompute a rainbow table for that one account's exact (derived) salt *before ever seeing the hash* — targeted precomputation per account, not one table reusable across every account, since two different usernames still derive two different salts. That precomputation-in-advance is the real harm — and it is narrower than "salting loses its entire benefit": distinct per-account-derived salts still prevent one attacker-precomputed candidate-hash table from being reused *unchanged* across every account (that unchanged table-wide reuse is what a single global fixed salt enables, not this). What a predictable derived salt actually forfeits for any account whose username is knowable ahead of time is the *unpredictable-at-breach-time* property — the attacker computes that account's table in advance, targeted, at leisure, instead of being forced to do fresh per-credential work only after obtaining the hash database. A separate, scheme-specific failure mode also applies if the derivation can ever collide — the same username reused across two systems sharing the derivation scheme, or a normalization step that maps distinct usernames to one salt — which is a genuine cross-account collision, but not the default risk of a derived salt as such. Either way the requirement salting exists to satisfy is **uniqueness per credential** decided *unpredictably in advance*, and randomness is how that's achieved cheaply — a derived salt can be "unique" and still fail because it is also guessable in advance. `verify()` still round-trips and tests pass either way. REQUIRED: a fresh random salt per credential. The generator call is version-bound: on `password-hash` **0.5.x** it is `SaltString::generate(&mut OsRng)` — the OS-backed RNG type per your `rand_core` major — and the method exists only with a feature enabled, named by which crate you actually depend on: a **direct `password-hash` 0.5.x dependency** needs `password-hash`'s own **`rand_core`** feature (default-enabled in 0.5, but absent if the consumer built with `default-features = false` — verify); depending on **`argon2` 0.5.x** instead (which re-exports `password-hash`), enable `argon2`'s own **`rand`** feature — `argon2` exposes no feature literally named `rand_core`; its `rand` feature is the one that forwards to `password-hash/rand_core`, so the line that exposes `SaltString::generate` is `argon2 = { default-features = false, features = ["rand"] }`, not `features = ["rand_core"]` — but that line alone is **not** a complete manifest recipe for the shown `SaltString::generate(&mut OsRng)` call: password-hash pulls `rand_core` with `default-features = false`, and `rand_core` 0.6 has no default features, so `rand_core::OsRng` does not exist in the graph until `rand_core`'s own `getrandom` feature (or its `std`, which implies it) is enabled somewhere — via a direct `rand_core = { version = "0.6", features = ["getrandom"] }` dependency, `password-hash`'s own `getrandom` feature on a direct password-hash dependency, or another RNG dependency that turns `rand_core/getrandom` on via feature unification. State both obligations: `argon2`'s `rand` feature for `SaltString::generate` to exist, and `rand_core`'s `getrandom` feature for `OsRng` to source entropy; the older supported minors (0.1–0.4) are not covered by this recipe — 0.1 has no such method at all — and each needs separate verification against its own docs rather than being folded into one "≤ 0.5" bucket; on the `password-hash` **0.6.x** line (pin 0.6.x specifically — a pre-1.0 crate, so an open-ended "≥0.6" promise is semver-fragile; 0.6.x pairs rand_core ^0.10 / getrandom ^0.4) that API moved and is **feature-gated** — `password_hash::generate_salt()` / `try_generate_salt()` and `PasswordHasher::hash_password` (which generates the fresh random salt itself) exist only with the **`getrandom`** feature enabled, while `PasswordHasher::hash_password_with_rng` (explicit RNG argument) exists only with **`rand_core`** — name the feature you are enabling and verify against the pinned 0.6.x docs before the recipe compiles; the PHC string types moved under the re-exported `phc` crate. Use the KDF crate's own salt generator for the version you pin.
- Below-floor KDF work factors reaching *production* password hashing — `Argon2` `Params::new(8, 1, 1, None)`, or `pbkdf2::<HmacSha256>(pw, salt, 1000, &mut out)`, or a pre-2023 PBKDF2 iteration count copied from an old answer — outside `#[cfg(test)]`. Compiles, round-trips, passes tests; the weakness is visible only after a database dump. A deliberately weak, `#[cfg(test)]`-scoped cost config is fine and common practice (real floor-strength hashing makes test suites unbearably slow); the ban is on that same weak config leaking into the non-test path. REQUIRED: production parameters at or above the current OWASP Password Storage floor (as of this writing: Argon2id **m ≥ 19 MiB, t ≥ 2, p = 1**; PBKDF2-HMAC-SHA256 **≥ 600 000 iterations**) — cite [OWASP's Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) as the *living* floor and re-verify it rather than hardcoding a number that will silently rot.
- AEAD encryption with a nonce length other than the selected algorithm/API's specified width. For RustCrypto's default `aes-gcm`/`chacha20poly1305` type aliases (`Aes256Gcm`, `ChaCha20Poly1305`) that width is 96 bits / 12 bytes, and NIST SP 800-38D's allowance for other GCM IV lengths in the general case doesn't help here: the aliased nonce type is a fixed-size typed array (`Aes256Gcm`'s nonce is `GenericArray<u8, U12>`), so an LLM-generated `let nonce = [0u8; 16];` passed where a `Nonce` is expected **fails to compile** — it does not silently truncate at runtime. That compile-time guarantee is specific to these crates' *default* type aliases, not a universal AES-GCM property — a different API/library, or a RustCrypto construction over a non-default nonce size, can accept a runtime-length nonce and needs its own verification against its actual documented width. The real hazard with the default RustCrypto aliases is building a `Nonce` from a runtime-length source (`Nonce::from_slice(&bytes)`), which panics if `bytes` isn't exactly 12 bytes rather than failing at compile time.

**Additional REQUIRED**:
- For any type holding key material, use `zeroize`'s `#[derive(Zeroize, ZeroizeOnDrop)]` — do *not* hand-roll a zeroing `Drop`: the compiler may keep an optimized-away copy on the stack and can elide the manual write.
- The zeroize derive is **necessary, not sufficient**: it zeroes the value's *final* storage on drop, and earlier copies can survive that. A secret built on the stack and then returned or moved (`fn load() -> Key { let k = ...; k }`) can leave a live byte-copy at the old frame; a `String`/`Vec` secret grown in place (`password.push_str(&extra)`) leaves the bytes in the freed old buffer — `Zeroize`'s own documentation states it "cannot guarantee copies of the data were not previously made by buffer reallocation". Serialization into a temporary, an intermediate parse buffer, and optimizer-introduced copies are the same class. It compiles and passes tests (nothing observes freed memory) and leaks into core dumps, swap, and heap inspection in production. REQUIRED: allocate the secret behind `Box` / `secrecy::SecretBox<T>` *at creation* so every later move copies only the pointer; pre-size `Vec`/`String` secrets to their final capacity so they never realloc mid-life; keep the window between "bytes exist" and "bytes are wrapped" as short as possible. State this as **best-effort memory hygiene, not a guarantee** — a move is not *observably* a `memcpy` you can reason about, and the compiler remains free to elide, duplicate, or combine copies. For a type whose all-zero state would violate its invariants, follow `zeroize`'s documented custom-`Drop` pattern instead of deriving a trait that permits an invalid intermediate state.
- Before adding **any** crypto dependency, check RUSTSEC (`cargo audit`) and state open advisories in the threat-model proposal. A *correctly-used, maintained* crate can still carry an advisory for years: the private-key operations of the pure-Rust `rsa` crate were not constant-time and the leak was observable over the network (Marvin attack — RUSTSEC-2023-0071 / CVE-2023-49092). The advisory stood open from 2023-11-22 and was fixed in `rsa` 0.10.0 (constant-time mitigations; advisory updated 2026-11-08) — pin ≥ 0.10.0 and treat every earlier line as affected. On an affected version `priv_key.decrypt(Pkcs1v15Encrypt, &ct)?` compiles, round-trips, and is remotely timing-attackable with no code bug at all — the hazard is the primitive choice plus the exposure context. Keep any advisory-carrying operation off attacker-timed paths (prefer audited key-exchange constructions); `rsa`/Marvin remains the worked example of an advisory that stood open for three years on a maintained crate, alongside the `rust-crypto` note above (unmaintained — RUSTSEC-2016-0005 — plus unpatched AES miscomputation — RUSTSEC-2022-0011).

## §B24. Side channels on secret-dependent branches (`==` timing, and decrypt-failure oracles)

**The trap**: secret-dependent execution leaks the secret through a side channel even when the functional result is correct. Two sibling channels: the **timing** of `==`, and the **content/shape** of a decryption-failure error. `==` on `[u8]`, `Vec<u8>`, `String`, `&str` gives **no constant-time guarantee** — `PartialEq`/`==` documents nothing about comparison timing. Depending on target and optimizer the comparison can return as soon as it finds a mismatch (byte-at-a-time, a `memcmp`-style chunk, or something else); the exact short-circuit mechanics are an implementation detail, not something to assert as fixed. For non-secret data this is fine. For *secret* comparisons — API tokens, password hashes, MAC tags, OTP codes, session keys, anything an attacker controls one side of — that data-dependent timing difference (e.g. "first byte wrong" typically finishing faster than "first ten bytes right, eleventh wrong") leaks information about the secret one byte at a time. Compiles, runs, passes functional equality tests, and is silently exploitable from across a network on any code path that an attacker can probe repeatedly.

**BANNED**:
- `if user_token == expected_token { ... }` for any secret comparison: API tokens, password-after-hash, MAC tags, OTP codes, session identifiers, HMAC outputs.
- `Vec<u8> == Vec<u8>` or `&[u8] == &[u8]` for secret material.
- `String::eq` / `str::eq` on bearer tokens, JWT signatures, or any string the client controls during authentication.
- Rolling your own constant-time equality with a manual XOR loop — **with or without** `std::hint::black_box` and a `#[inline(never)]` attribute. Those annotations do not make the construction acceptable: `std::hint::black_box`'s own documentation states it provides **no cryptographic or security guarantee**, and optimizer/codegen changes can still reintroduce the early exit or otherwise destroy constant-time behavior. Hand-written secret equality is banned unconditionally; `subtle::ConstantTimeEq` / `constant_time_eq` (REQUIRED below) are the only acceptable answer.
- **Distinguishable failures that reveal processing of unauthenticated ciphertext across a trust boundary** — padding, MAC or plaintext-parse results exposed before authenticity is established. CBC padding checked before the MAC is the classic oracle; a uniform message alone does not close a timing discrepancy. Prefer an authenticated construction and never use candidate plaintext from a failed authentication. A distinct parse/validation error on **successfully authenticated** data is not automatically a padding oracle: apply the protocol's error and information-disclosure policy. For example, TLS 1.3 uses `bad_record_mac` for record deprotection failures but `unexpected_message` for an authenticated record whose inner plaintext has no content-type octet (RFC 8446 §§5.2/5.4). Collapsing those two by a universal rule would contradict that protocol.

**REQUIRED**:
- Use `subtle::ConstantTimeEq` — `x.ct_eq(&y)` returns `subtle::Choice` (a constant-time-friendly bool surrogate); convert to native `bool` via `bool::from(choice)` or `choice.into()` at the intended decision boundary. The `constant_time_eq` crate is a smaller alternative — `constant_time_eq::constant_time_eq(a, b) -> bool` directly. Their slice comparisons protect equal-length *contents*, not secret lengths: unequal lengths may short-circuit, and comparison work can depend on the length. State the fixed/public-length assumption for MAC tags, digests or fixed-width tokens. **Hashing both sides first only fixes the comparison's input width:** hashing, encoding and allocation can still do length-dependent work, so hashing a variable-length secret inside the observed request path does not establish end-to-end length hiding. If length is sensitive, use a protocol-reviewed fixed/public-size representation and a processing path whose work does not depend on the hidden length; preprocessing must be outside the observation boundary or satisfy the same requirement. Do not treat a hash or padding call alone as proof, and do not replace a password-verification KDF with a fast digest for this purpose (§B12).
- For MAC verification specifically, prefer the crypto crate's built-in `verify` / `verify_slice` over manual `==` on the output. (`hmac::Mac::verify_slice` and `aes_gcm::Aes256Gcm::decrypt` both incorporate constant-time comparison; rolling your own is the bug.)
- Surface every `==` / `!=` on `&[u8]`, `Vec<u8>`, or `String` in the same code path as a secret in the post-flight summary, with the recommendation to switch to a constant-time primitive.
- Preserve the opacity of **decryption/authentication failures** through outward error mapping; AEAD crates already return the deliberately opaque `aead::Error`. Do not expose secret-dependent distinctions through status, body, timing or later side effects, and do not parse/use plaintext until authentication succeeds. After success, protocol-defined validation errors may remain distinct when the disclosure policy permits; authentication does not itself authorize revealing arbitrary plaintext or application secrets. **§C2 carve-out:** retain useful internal error context without exporting an unauthenticated-ciphertext oracle. Review the authentication boundary and the actual observable distinction, not merely the presence of several error variants.
- Scope note: this targets comparisons where one operand is a secret an attacker can probe (a forgeable tag/token), and error channels on a secret-dependent branch. Constant-time compare is the correct default, but it is not "catastrophic" the way nonce reuse is — and it does **not** apply to comparing a request field against a *public* constant: don't flag `algo == "HS256"` or a header-name check. The decrypt-oracle rule is 🔴 when the distinguishable error crosses a network boundary, 🟡 for logs-only exposure.

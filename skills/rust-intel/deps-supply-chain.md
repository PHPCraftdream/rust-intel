## §A1. Stale APIs, deprecated-not-removed APIs, and slopsquatting

The class here is **APIs that compile but are wrong**, not APIs that don't exist. The pure-hallucination cases (`E0599` "method does not exist") are noise — rustc catches them and the LLM moves on. The cases that survive the compile are: the API existed in an older version of the crate and still exists in the new one with materially different semantics; the API is `#[deprecated]` but not removed; the LLM picked up a method name from a different crate and the name happens to also exist in the named crate; or — worst — the LLM hallucinated a *crate name* that an attacker has since registered on crates.io with a malicious payload.

**The trap, by sub-class:**

- **Stale-but-still-valid APIs.** `tokio` 0.2's `mpsc::Receiver` implemented `Stream`; in 1.x it does not — the same code needs `tokio_stream::wrappers::ReceiverStream` (while the `(Sender<T>, Receiver<T>)` tuple shape never changed); `rand` 0.8 `thread_rng()` was renamed to `rng()` in 0.9 but the old function lingers in code patterns. The LLM emits the form from the older major; against the pinned version it either fails to compile with a misleading error (`Receiver: Stream is not satisfied`) or — when the old symbol still exists — compiles and behavior diverges from the user's mental model.
- **Deprecated-not-removed APIs.** `#[deprecated]` emits a warning, not an error. LLMs routinely ignore the warning channel and ship deprecated calls. Each deprecated call is a future break.
- **Wrong-version-of-crate APIs.** `serde_json::from_str` exists in every version, but `serde_json::Value::take` did not exist before a specific point. The compile succeeds against the pinned version *because the version pinned is recent enough*, but the LLM has no proof of that — it guessed and was lucky.
- **Slopsquatting (supply-chain).** Hallucinated crate names that an adversary has registered on crates.io. Compiles, runs, exfiltrates secrets, and `cargo build --offline` would not have helped (the malicious payload lives inside a dependency the build script reaches for). Measured for Rust: across 11 code models, *Importing Phantoms* (arXiv:2501.19012, §4.1, Table 3) found that "Rust has the highest mean package hallucination rate (24.74%)" — against 23.14% for Python and 14.73% for JavaScript — with three models above 40% on Rust. Read it as "no safer than Python", not as a Rust-specific pathology. A Rust-only follow-up (arXiv:2606.08444) reports that different models show "surprisingly consistent hallucination rates" that barely respond to decoding parameters — so a better model or a lower temperature is not the control; registry verification (below) is.
- **Default-of-an-earlier-era crates.** A crate the training corpus is saturated with, that still compiles and usually still works, but stopped being the recognized default before the corpus's cutoff caught up — admitted here on author archival or an explicit advisory (recording the advisory is not the same as recommending a successor): `structopt` (folded into `clap`'s derive API — RUSTSEC-2022-0104, "structopt is in maintenance mode"), `serde_yaml` (archived by its author — and the fork an LLM is most likely to reach for instead, `serde_yml`, is RUSTSEC-2025-0068: unsound (a real segfault via `serde_yml::ser::Serializer.emitter`) and archived; the advisory names `serde_norway` (maintained fork, last publish 2024-12) or `serde_yaml_ng` (last publish 2024-05, itself sitting on unmaintained `unsafe-libyaml`) — verify the current recommendation at write time), `lazy_static`/`once_cell::sync::Lazy` (superseded by std `LazyLock` (stable since Rust 1.80) and `OnceLock` (1.70) — see Version pins), `dotenv` (RUSTSEC-2021-0141, unmaintained → `dotenvy`), `async-std` (RUSTSEC-2025-0052, "has been discontinued" → `smol`; see §C3 in the async module), `bincode` (RUSTSEC-2025-0141, unmaintained — the reflexive answer for "serialize this fast"; the advisory names alternatives). Verify against the same "current default" question §C12 asks, not against whether the crate still compiles.

**REQUIRED**:
- Before calling any method on a third-party type, check that it exists *with the documented semantics* in the version actually in use. `Cargo.toml` declares a version **range**, not the exact version in use — the resolved version lives in `Cargo.lock` (or `cargo metadata`), per doc.rust-lang.org/cargo/guide/cargo-toml-vs-cargo-lock.html. For an **application**, inspect `Cargo.lock`/`cargo metadata` for the actual resolved version. Exact **locked** resolution and an exact `=`**version manifest requirement** are different mechanisms and must not be conflated: the lockfile pins the **entire resolved graph** that actually builds — direct **and transitive** dependencies alike, including versions `Cargo.toml` never names, each at one exact version — without narrowing the declared range for anyone else, while `=` narrows the requirement itself for every resolver that reads the manifest, but only for the dependency it is written on: it does not pin that dependency's own **transitive** resolutions, which is exactly the lockfile's job. A lockfile also binds only where it is used — a downstream consumer of a published library resolves and locks its **own** graph, so the library's committed `Cargo.lock` forces no version on consumers; it governs the library's own builds and CI. Cargo's guidance on committing changed in 2023 ([blog.rust-lang.org/2023/08/29/committing-lockfiles](https://blog.rust-lang.org/2023/08/29/committing-lockfiles/)): the old "commit for binaries, not libraries" convention is retired — the choice is the project's, with committing `Cargo.lock` the suggested starting point for **all** projects, libraries included (`cargo new` no longer ignores it for libraries) for reproducible CI, bisectable history, and a pinnable MSRV lane — paired with regular latest-dependencies testing (the locked/latest and direct-minimum jobs below) so the pin does not fossilize. For a published **library**, "test the full declared range" is operational, not exhaustive: test the **locked/latest** resolution CI builds (the upper end) **and** a **direct-minimum** job at the lowest versions the direct requirements admit (the lower end) — not a promise to test every released version inside the range, which is impossible. "It compiled" is not proof — semantics drift across minor versions in pre-1.0 crates.
- For high-churn crates (`tokio`, `axum`, `hyper`, `reqwest`, `sqlx`, `serde`, `tonic`, `tower`, `clap`, `rand`), if uncertain about an API or its semantics, **say so explicitly** and ask the user to confirm or run `cargo doc --open`.
- Treat `#[deprecated]` warnings as errors. If the symbol I want to emit is deprecated in the pinned version, switch to the replacement before writing.
- Pre-1.0 crates (any version with leading `0.`) have **breaking changes between minor versions**. Treat 0.6 → 0.7 with the same suspicion as 1.x → 2.x.
- Inspect every `[patch]` override by its **replacement source**, not just the table name. For a **git-sourced** dependency or patch, require a full-commit `rev` (not just a branch), a user-approved repository and a stated removal condition for the temporary override — e.g. `# remove once upstream 1.2.4 ships the fix`. A **path-sourced** patch is a valid local override, not a git dependency missing `rev`: review the resolved local tree and how the build obtains the intended bytes; `Cargo.lock` does not freeze mutable path contents. Apply source/version/provenance review to other supported replacement sources as well. The override is a review trigger, not automatically an unverified-source finding; retain the git pin and fork-approval requirements where they actually apply.
- Treat PR-readable build caches as an output trust boundary: processes writing them must not receive secrets. Build scripts and tools can persist environment variables into artifacts even without malicious code; the 2026-09-21 Miri notice is a concrete instance. Separate token-bearing fetch/publish steps from cached build/test steps, review the actual cached paths and readers, and handle already-exposed caches per §D3. A lockfile, checksum, or patched Miri does not establish secret-free output for every process in the build.

**BANNED**:
- Method calls on types where I have not internally verified the method exists *and means what I think it means* in the pinned version.
- Mixing API styles from different major versions (e.g., axum 0.6 routers with axum 0.7 handlers).
- Adding a crate to `Cargo.toml` that the user did not name and that I have not independently verified exists.
- A **git-sourced dependency or `[patch]` replacement without the required full-commit `rev`**, even under a known-good crate name. A branch-only or bare git source does not advance on each locked build — Cargo keeps the recorded commit — but an applicable update, lock regeneration or fresh resolution can select a new branch tip without a manifest change. The `rev` removes that drift, not the need to approve and review the source. Registry advisories do not attest fork bytes; configured `cargo vet` can audit exact-SHA git deltas against a registry base. A path replacement is reviewed under the separate source-kind rule above, not rejected for lacking a git revision. Workspace-root patches can affect transitive users too, so verify which replacement actually entered the resolved graph.

**Security note: slopsquatting**. Hallucinated *crate names* (not just methods) are a supply-chain attack vector that **survives compilation and runs malicious code**. Adversaries monitor common LLM crate-name hallucinations and **register those names on crates.io with malicious payloads**. This is the canonical Tier A category: the LLM's "fix" for "I need a crate that does X" compiles cleanly and silently runs untrusted code.

**Real attack cases (2022–2026)** — these are not hypothetical:
- `rustdecimal` — typosquat of `rust_decimal`. The malicious crate, documented in the CrateDepression incident (2022), targeted CI pipelines.
- `faster_log`, `async_println` — malicious crates designed to scan for and exfiltrate Solana/Ethereum private keys; reached thousands of downloads before takedown.
- `evm-units` / `uniswap-utils` (2025-12) and `finch-rust` / `sha-rust` (2025-12) — further crates.io malicious-crate takedowns in the same crypto-credential-theft family; by 2026-02 crates.io published a notification-policy update acknowledging such takedowns are now routine, and the cross-ecosystem "TrapDoor" campaign (2026-05) reached crates.io alongside npm/PyPI. The takedown cadence, not any single incident, is the signal. (See `references/sources.md`.)
- `arrayref` 0.3.10 / `append-only-vec` 0.1.9 / `internment` 0.8.7 (2026-08-20; RUSTSEC-2026-0260 for `arrayref`, RUSTSEC-2026-0262 for `append-only-vec`, RUSTSEC-2026-0266 for `internment`; the malicious helper crates are RUSTSEC-2026-0259, RUSTSEC-2026-0261, RUSTSEC-2026-0263, RUSTSEC-2026-0264 and RUSTSEC-2026-0265) — the maintainer-compromise class, a different shape from everything above: a legitimate, widely-used crate whose maintainer's credentials were compromised, so the malicious versions (online 86/107/90 minutes) were published *from the real project*, each pulling a freshly-registered dependency (`proc-macro1` and lookalikes) whose **build script** downloaded a payload. `arrayref` 0.3.10 was downloaded 2,285× — "less than 10% of download traffic … most users had older versions in their lockfiles" — i.e. the committed `Cargo.lock`, not user vigilance, limited the blast radius; a dependency cooldown (see Concrete defenses) is the same protection extended to fresh resolutions, and the published bytes — not the repository — are what must be reviewed, since the malicious versions were published with the real project's credentials. The git/`[patch]` BANNED bullet above covers the unverified-source trust decision; this is its registry-published twin: the name was right and the source was still hostile. (See `references/sources.md`.)
- Supply-chain attacks across software ecosystems rose materially in 2025 (published year-over-year estimates cluster around +70–75% ecosystem-wide; no crates.io-specific figure is published).

Concrete defenses:
- I do not add a crate to `Cargo.toml` unless the user explicitly named it OR I verified its existence by reading the project's existing dependencies.
- For any new dependency I suggest, I flag it as a *suggestion to verify*, not a fait accompli: "I'd add `deadpool-postgres` for connection pooling — please verify on crates.io before adding."
- I verify every crate name against the registry before adding it, checking both the `-` and `_` variants, because crates.io normalizes them to the same name (`serde_json` and `serde-json` cannot be distinct crates) — and I never conclude "this variation does not exist" from memory: `tokio-utils` was long cited as a hallucination next to the real `tokio-util`, but it has existed as a real crate (registered 2023-03; content unaudited) since March 2023. Separator *deletion* is a different name and the classic typosquat shape: `rustdecimal` (no separator) was the weaponized typosquat of `rust_decimal` in the CrateDepression incident (2022).
- Surface every newly-added `Cargo.toml` dependency in the post-flight summary so the user can audit it.
- **Dependency cooldown (minimum release age).** Keep freshly published versions out of new resolutions: the arrayref/append-only-vec/internment versions above were online 86/107/90 minutes, so a cooldown of days would have kept them out of any fresh resolution. Cargo's native setting is RFC 3923 `min-publish-age`, stabilized by rust-lang/cargo#17335 (merged 2026-08-28): `registry.global-min-publish-age` (string, default `"0"`; typically `"N days"`/`"N weeks"`; env `CARGO_REGISTRY_GLOBAL_MIN_PUBLISH_AGE`), per-registry `registries.<name>.min-publish-age`, and `resolver.incompatible-publish-age` (default `"deny"`: versions whose `pubtime` is too recent are ignored unless already in `Cargo.lock`; `"allow"` disables the check). Per the resolver chapter, `allow` combined with `cargo update --precise` is how a specific version and its transitive dependencies are pulled in despite the cooldown (the documented route for an urgent security fix). The Cargo config reference marks each key "MSRV: Respected as of 1.100+" (Cargo 1.100.0, released 2026-11-12, stabilized the feature); an older Cargo does not honor the key, so the config file alone is not evidence of protection — check the Cargo version actually used. Two documented gaps remain in 1.100: "`cargo install` ignores the minimum publish age, for both the installed crate and its dependencies" — pin tools installed in CI as `cargo install name@x.y.z` and review that version — and "Versions without a `pubtime` field in the index are never held back". In addition, Dependabot applies a default 3-day cooldown to version updates since 2026-07-14 (security updates are not delayed; adjustable via `cooldown` in `dependabot.yml`), while Renovate's `minimumReleaseAge` is off by default (`null`) and must be set — `config:best-practices` enables only the npm preset, so for crates opt in to `security:minimumReleaseAgeCrate` (three days, `matchDatasources: ["crate"]`) or set the option yourself. That preset does not cover every update path: it resets `minimumReleaseAge` to `null` for `lockFileMaintenance`, `replacement`, `pin`, `bump`, `lockfileUpdate` and `rollback` updates, and `config:best-practices` itself extends `:maintainLockFilesWeekly` — so a weekly `Cargo.lock` refresh can still pull a transitive version published minutes earlier. Gate those paths separately: disable or review lock-file maintenance, or have it run under a Cargo that honors `min-publish-age` (1.100+) so the resolver enforces the age itself. A cooldown does not help against dormant backdoors or long-game maintainer compromise.
- **Review the published bytes, not the repository.** Cargo builds what the registry serves, which may differ from the linked repository, and maintainer-compromise versions need not appear there. For a version bump or a new dependency, inspect the published contents (`build.rs`, proc-macros, newly added dependencies): the crates.io crate page has a "Code" tab showing the exact published files (a version-to-version diff viewer was in development as of the 2026-07-13 crates.io development update). `cargo vet inspect <PACKAGE> <VERSION>` fetches a package's source and `cargo vet diff <PACKAGE> <VERSION1> <VERSION2>` yields a diff between two versions, for audit.

**Build-time code execution (a distinct supply-chain vector).** Slopsquatting is about *hallucinated names*; this is about *what a dependency does at build time*. A crate's `build.rs` and any proc-macro it exports run arbitrary code on the developer's machine and in CI **during `cargo build`**, before any runtime guard exists — this is the mechanism behind the malicious crates above, and such payloads read `~/.cargo/credentials`, `~/.ssh`, `.env`, and CI secrets. Build time is not even the earliest execution surface: per RustSec advisories filed 2026-09-07 ([RUSTSEC-2026-0280](https://rustsec.org/advisories/RUSTSEC-2026-0280.html), [RUSTSEC-2026-0281](https://rustsec.org/advisories/RUSTSEC-2026-0281.html)), malicious `greentic` package versions executed malware when a depending project was merely **opened in VS Code** — no build required — so treat **acquisition, workspace-open, and build** as three distinct execution surfaces, and treat **granting workspace trust** as part of the same trust decision (per [VS Code Workspace Trust](https://code.visualstudio.com/docs/editing/workspaces/workspace-trust), an untrusted workspace restricts task/extension execution). Keep an unfamiliar tree untrusted or isolated (container/VM) until its build scripts and proc-macros have actually been reviewed; "inspect before the first build" alone leaves the open-in-IDE surface uncovered. (Those advisories do not pin a single carrier filename; do not assume one.) (The proc-macro-trust surface is not hypothetical even for a *trusted* crate: `serde_derive` briefly shipped a **precompiled binary** it ran during your build instead of building the macro from source (2023) — reverted in v1.0.184 after community pushback, but it is the canonical demonstration that "it's just serde" is not a proof the code running at build time is the code you can read. See `references/sources.md`.) A typosquat that swaps `-` for `_` (or appends a language suffix), plus dependency confusion (a private crate name shadowed by a public one on a default registry), are the same class. Defenses, split by what the crate *is* (Cargo's 2023 committing-lockfiles guidance, cited in the REQUIRED list above): for a **binary/application**, commit `Cargo.lock` and build `--locked` for reproducibility — the *lockfile* is the exact-pin mechanism (exact **locked** resolution of the whole graph); an exact `=`**version manifest requirement** is a different, coarser mechanism that narrows the declared range itself and is not what makes a binary's build reproducible — the arrayref/append-only-vec/internment compromise (above) is the demonstration of *why*: most would-be victims were protected by their lockfile pinning the last good version, not by noticing the malicious release. For a published **library**, `Cargo.toml`'s declared range *is* the SemVer contract with consumers — do not tighten it to exact `=` pins to protect yourself (that narrows the requirement for every downstream resolver). The library's own committed `Cargo.lock` is good practice for its CI and binds no consumer (see the lockfile guidance above); rely on it together with supply-chain audit/provenance (`cargo-vet` attestation, `cargo-audit`/RustSec), and test across the declared compatibility range. In both cases: for a newly-added *direct* dependency that is not a well-known crate, read its source — the repo you are about to pin — **before any execution surface is crossed**: before `cargo add`/`cargo fetch` pulls it, before the tree is opened in an IDE or granted workspace trust (the RUSTSEC-2026-0280/0281 open-in-VS-Code executions above are why "before the first build" is not early enough), and before the first build; and for the transitive graph (which you cannot read by hand) lean on `cargo-deny` / `cargo-audit` (RustSec advisory DB) and `cargo-vet` — plus, for binaries, the committed `Cargo.lock` and `--locked`/vendored builds.

**Lockfile hygiene and yanked versions.** Committing `Cargo.lock` and building `--locked` (above) pins *reproducibility* — but a pinned version is not the same as a *safe* version, and `--locked` actively hides one gap. A version that is **yanked** upstream (for a soundness bug, or because a RUSTSEC advisory was filed against it) stays downloadable, and an existing `Cargo.lock` keeps resolving it: `cargo build --locked` against a yanked pin has been observed to emit only a **warning** ("package `x` in Cargo.lock is yanked"), exit 0 — green in CI; Cargo does not document this as a portable, version-stable guarantee, so don't rely on the warning itself as the detection mechanism. Only a *fresh* resolution refuses a yanked version ("candidate versions … were yanked"), so the day a new contributor runs `cargo update` (or, before Cargo 1.100, a `cargo install` without `--locked`), the build breaks. Since Cargo 1.100 `cargo install` uses the lockfile packaged in the crate by default (`--locked` is still accepted but is a no-op — rust-lang/cargo#17388), so an install reproduces the published pins — a yanked or advisory-flagged one included — rather than re-resolving — and until then the project may have been building against a version yanked for a security reason for months, unnoticed. REQUIRED regardless of what a bare `--locked` build happens to print: `cargo deny check advisories` **with `yanked = "deny"` explicitly set in `deny.toml`** — cargo-deny's own default for this check is `yanked = "warn"`, which prints but does not fail the build, so a bare unconfigured `cargo deny check advisories` is exactly as silent as the `--locked` warning it was meant to replace — or `cargo audit -D warnings` in CI (whose failing behavior on a yanked pin does not depend on a config default), as the actual, configured mechanism that turns a yanked pin into a red build **with a stated reason** — don't depend on eyeballing `--locked` output, and don't assume `cargo deny check advisories` fails on a yanked crate out of the box. BANNED as the fix: a blanket `cargo update` (the LLM's reflexive "make the CI error go away" move) — it silently swaps many *other* pinned versions too, exactly the Tier-A-shaped residue this spec warns about; the fix for one yanked crate is a **targeted `cargo update -p <crate>`** for that crate alone.

**Network access in your *own* `build.rs` (unpinned bytes outside the lockfile).** The build-time-execution bullet above is the *read* direction — a malicious *dependency's* `build.rs` reading your secrets. This is its **write-direction twin** (mirroring how §B5's padding-leak bullet is the write-direction dual of the validate-before-mint read rule): *your own* `build.rs` reaching the network at build time — shelling out to `curl`/`git clone`, or `reqwest::blocking` — to fetch a schema, model file, `protoc`, or C library. It compiles and passes tests on the author's box, and it is a distinct hazard from everything above: it is not *whose code runs at build time* but *unpinned bytes entering the build outside the lockfile*. `--locked`/`--offline`/`cargo vendor` give **zero** integrity protection here — the download is not in Cargo's hash-verified dependency graph at all — so the fetched artifact can silently change (or be MITM'd) between builds, reproducibility is gone, and offline/vendored builds simply fail. REQUIRED: no network access in your own `build.rs` — vendor the artifact into the repo, or fetch it in a separate, explicit CI step with a **hardcoded SHA-256** you verify; and keep `cargo build --offline`/`cargo vendor` working by providing an offline fallback path. Calibration: build-time *codegen* is fine — generating code from a **local** schema file, or invoking a **local** toolchain binary, touches no network and is not this finding; only reaching the network at build time is.

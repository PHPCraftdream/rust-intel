## §B25. Panic and ownership across `extern "C"` ABI

**The trap**: the LLM writes a Rust function callable from C (or returns a Rust-owned value through FFI), tests it on the happy path, and ships. The panic path is never exercised, the C-side `free()` path is never exercised, and the `cap`-mismatched `from_raw_parts` is never exercised. Everything compiles, the happy-path tests pass, and the bug surfaces under load as heap corruption (silent, worst), a process abort with no Rust stack (visible, but unhelpful), or a leak that grows for days. The compiler does not catch any of these — the `unsafe` boundary is precisely where its guarantees end.

**BANNED**:
- `extern "C" fn` body that can panic without being wrapped in `std::panic::catch_unwind`. Pre-1.81 a panic crossing an `extern "C"` boundary was UB; since Rust 1.81 the default is to abort the process — neither is what an FFI caller expects. Convert panics to a stable error code at the boundary.
- Passing `Vec<T>`, `String`, `Rc<T>`, `Arc<T>`, `CString`, or a Rust tuple directly through an `extern "C"` signature without a documented C ABI. Use raw pointers with separate length/capacity arguments or out-parameters, or a `#[repr(C)]` descriptor — not a tuple return. `Box<T>` for `T: Sized` is a documented single-pointer exception, ABI-compatible with C's `T*`; `Option<Box<T>>` is its nullable form. **Layout does not prove ownership.** Returning a Rust-created Box can use that ABI, but receiving one from C still requires a live, valid, uniquely reclaimable pointer with the correct allocator/layout at entry, even when an earlier API constructor originally minted it. A stale or duplicated pointer is not repaired by its origin. For imports, prefer a raw pointer and the foreign destructor: foreign allocation does not generally meet Box's reclaiming contract. A returned unchanged Rust-owned pointer, or an explicitly compatible allocator arrangement, can support the narrower import exception only with all reclaiming invariants proved. The caller must use the API's paired destruction contract, not arbitrarily call C `free()`. (Since Rust 1.89, `i128`/`u128` no longer trip `improper_ctypes_definitions`; their actual target/C declaration still needs verification.)
- `Box::from_raw(ptr)` on a pointer that does not meet `Box`'s actual reclaiming contract: allocated by the **same allocator instance** the `Box` type is parameterized with (the global allocator for a plain `Box<T>`; the exact `A` for a custom-allocator `Box<T, A>` — the core of `allocator_api` is stable since **Rust 1.100** (the `Allocator` trait, `Global`, `System`, and the allocator-aware `Box`/`Vec` constructors such as `Box::new_in`/`Vec::new_in`), so below 1.100 the global allocator is the only case in play, and from 1.100 on the instance matters in ordinary code: reclaiming with a *different* allocator than the one that allocated — plain `Vec::from_raw_parts`/`Box::from_raw` (global) on memory that came from `Vec::new_in(&arena)` — or touching a block after its arena was reset or dropped is the same contract violation), laid out per `Layout::for_value` for `T` (size/alignment match what a `Box<T>` allocation would have used), pointing to a valid, fully-initialized `T`, and reclaimed **exclusively** — no other owner may reclaim it or access it incompatibly, and `from_raw` consumes each outstanding ownership handoff at most once (a later `Box::into_raw` may transfer ownership out again; actual deallocation still occurs only once); merely retaining a raw-pointer copy is not itself a second owner. (Zero-sized `T` is the one carve-out: `Box<T>` for a ZST need not point into a real allocation at all — a non-null, suitably-aligned dangling sentinel is valid, mirroring `Vec`'s ZST handling — so the allocator/layout half of this contract is vacuous for `T: Sized` with `size_of::<T>() == 0`.) The requirement is about the allocation's allocator and layout, not literally "produced by `Box::into_raw`" — but `Box::into_raw` preserves the allocation metadata at handoff; liveness, value validity and exclusive reclaiming must still hold when the pointer is returned. Reclaiming a `malloc`'d pointer through `Box::from_raw`, or freeing a `Box::into_raw`'d pointer with C's `free()`, is allocator-mismatch UB under this same contract.
- `Vec::from_raw_parts(ptr, len, cap)` where `cap` does not match the value the source `Vec` was decomposed with — the eventual deallocation passes the wrong size to the allocator and corrupts the heap. Same hazard for `String::from_raw_parts`.
- Returning a raw pointer from an `extern "C"` function **without first classifying it as borrowed/static or ownership-transferring, and — for the ownership-transferring case — without an accompanying `extern "C" fn drop_T(p: *mut T)` (or equivalent)** that the documented contract requires the C side to call. A **borrowed/static** pointer (into memory Rust keeps owning) must be documented as such and must never be freed or passed to a `drop_T`; skipping the classification and reflexively shipping (or reflexively omitting) a destructor is itself the defect. "The caller will know to free it" is wishful thinking that compiles and tests fine either way.
- `#[no_mangle]` on functions that are not actually FFI entry points. Each such symbol is a candidate for silent linker collisions across crates. (From Rust 1.98 the compiler carries part of this check: `invalid_runtime_symbol_definitions` — deny-by-default — flags a `#[no_mangle]` definition that would override a runtime symbol such as `malloc`/`memcpy`, and `suspicious_runtime_symbol_definitions` (warn) catches subtler cases. Treat those lints as the floor, not the full rule: other cross-crate symbol collisions are still silent.)
- **Treating a `staticlib` as if it exported only your `extern "C"` functions — linking two Rust staticlibs into one binary, or a Rust staticlib into a Rust program, without limiting the exported symbols.** The Rust Reference (Linkage) states that, because the resulting static library "contains the code of all the dependencies, including the standard library, and also exports all public symbols of them, linking the static library into an executable or shared library may need special care", and that for a shared library "the list of exported symbols will have to be limited via e.g. a linker or symbol version script, exported symbols list (macOS), or module definition file (Windows)". By the issue's account a `cdylib` exports only the `#[no_mangle]` symbols while a `staticlib` leaks all of them, "causing symbol overrides that are potentially UB and symbols conflicts" (rust-lang/rust#104707, open when checked). Each Rust staticlib carries its own copy of `std` and shared dependencies, so combining two produces duplicate-symbol link errors or silent symbol interposition, and which of two same-named exported symbols gets linked is unspecified (rust-lang/rust#28179, `#[no_mangle]` name collisions). It compiles, each library works alone, and the failure appears only at the final link, varying with platform, linker and toolchain version. Observed on rustc/cargo 1.98.0 (`x86_64-pc-windows-msvc`, `--release`): a `staticlib` crate with a single `#[unsafe(no_mangle)] pub extern "C" fn` yields roughly 2400 defined external symbols under GNU `nm -g --defined-only`, about 1500 of them `core`/`std`/`alloc`. REQUIRED: ship **one combined staticlib per final binary** (a single crate that re-exports every FFI surface) or a `cdylib`; prefix every exported name with the library name so the exports themselves cannot collide; and **verify the exported symbol set** of the built artifact (`nm -g --defined-only`, `llvm-nm`, `dumpbin`) against the intended API, restricting it with the platform mechanism above when the artifact is a shared library. Post-build symbol-localizing tools exist for staticlibs that must ship separately (the ai-coustics write-up "Shipping Rust static libraries without symbol collisions" describes the SDK-shipping failure and one such tool); treat them as a mitigation of the leak, not a replacement for verifying the symbol set. (See `references/sources.md`.)
- **Freeing/dropping a callback context before its registration is unregistered *and* all in-flight callbacks are confirmed drained.** The classic user-data trampoline — `Box::into_raw` a context, register `(extern "C" fn trampoline, *mut c_void)` with the C library — is right up to the *temporal* contract: the C side holds a raw pointer to your context that Rust does not track, so if `Drop` frees the context while the library can still fire (it delivers asynchronously on its own thread; deregistration is itself async and only stops delivery *eventually*; or the free simply happens before the unregister), the trampoline dereferences a dangling `*mut c_void` — a use-after-free that a synchronous test stub (register, fire once, deregister) never reaches. A well-behaved stub is green; the async production library corrupts the heap.
- **Reclaiming `user_data` as an *owning* `Box<F>` inside a re-invocable trampoline.** `let f = unsafe { Box::from_raw(p as *mut F) };` inside a callback that fires more than once drops the context on the **first** invocation, making every later invocation a use-after-free **and** a double-free. The trampoline must **borrow** the context, never take ownership — ownership is reclaimed exactly **once**, at teardown, after the drain in the rule above — but "borrow" does not by itself settle the aliasing half: two overlapping invocations that each form `&mut *(p as *mut Ctx)` create two live, overlapping exclusive references **before** either body reaches a lock inside `Ctx`, and a mutex *field* inside `Ctx` cannot repair references that were already exclusively aliased (the UB is the overlapping `&mut`, not merely unsynchronized field access). Which reference type the trampoline may form is decided by the foreign library's documented concurrency/reentrancy contract — serial, concurrent, or reentrant — per the REQUIRED callback rule below, not by the presence of a lock in the context.
- **Exporting a Rust entry point (`#[unsafe(no_mangle)]`/`#[no_mangle]` + `extern "C"`) that takes `&T`, `&mut T`, `&str`, `bool`, `char`, or an `enum` — of any representation, including `#[repr(int)]` — directly from the foreign caller.** These are *safe* Rust types with validity invariants the compiler assumes hold — but the caller is C, which can pass a NULL/misaligned/dangling reference, a non-UTF-8 `&str`, a `bool` that is neither 0 nor 1, an out-of-range discriminant. *Producing* an invalid value at any of these types is immediate UB **inside your "safe" Rust body** — the moment the reference/`str`/`bool`/enum parameter exists, before you read it — and the declaration compiles without a warning while Rust-side tests calling it with valid values pass. There is no "validated enum" shape that makes taking an `enum` directly across the boundary safe, `#[repr(int)]` included: `#[repr(u32)] enum E` is still a Rust enum, not a validated integer carrier, and an invalid discriminant is UB the instant the enum value exists, before the function body runs any check on it. Validation has to happen on the raw integer *before* the enum is constructed, never on the enum itself — take the corresponding primitive integer (`u32`, `i32`, and so on) across the ABI, range-check it, and only then construct the enum in safe code. Ban **every** enum-typed foreign parameter, regardless of `#[repr(...)]`. (Rust 2024's `unsafe(no_mangle)` acknowledges the export is a soundness liability; it does **not** force parameter validation.) This is the **read-direction mirror** of §B5's "validate raw bytes → `Result` *before* minting the typed value" rule, applied to the **export surface**: the boundary is where untrusted bits enter, so the typed value must not exist until they are checked — exactly as §B5's serialize-out padding bullet is the write-direction dual of the same rule. Taking raw pointers instead is the first half only: a pointer-dereferencing export must also be `unsafe` on the Rust side (§B25 REQUIRED, exported-entry-point bullet).
- **`safe fn` inside an `unsafe extern` block on a function whose contract has caller preconditions (edition 2024; the import-direction twin of the exported-entry-point bullet above).** `unsafe extern "C" { pub safe fn parse(p: *const c_char) -> i32; }` compiles, and now every caller is "safe" Rust — no `unsafe` block, no `// SAFETY:` comment, nothing for miri or review to anchor on — while a NULL/dangling/unaligned pointer passes straight through to the C function (UB at the call, invisible at the call site). `safe` is correct only for a function valid for **all possible inputs** — the edition guide's own contrast is `sqrt(x: f64)`. Pointer/handle/length parameter *syntax* does not by itself prove or disprove caller preconditions — classify each imported function by its actual foreign contract, not by its signature shape: a function that takes a pointer/length/handle/callback, or touches process-global state (§B25a), is `unsafe fn` in the block *because its documented contract has caller preconditions*, which is the overwhelmingly common case for this parameter shape; a pointer-taking import provably valid for every possible input (rare, and the determination must be made per-function from its actual documentation, never assumed from the syntax) may be marked `safe`. Default to `unsafe fn` with the safety provided by a validating safe wrapper layer (the import-surface application of §B5's validate-before-mint rule) unless that per-function proof is in hand.
- **Claiming ownership of an OS handle the code does not exclusively own** — `File::from_raw_fd(sock.as_raw_fd())`, or `OwnedFd::from_raw_fd` / `from_raw_handle` / `from_raw_socket` on a descriptor taken from another owner's `as_raw_fd()`, on stdin/stdout/stderr, on a descriptor a C library still closes, or twice on the same number. Each owner closes on drop: at best the second close fails with `EBADF`; at worst the number has already been reused, and the close — or a later read or write — lands on an unrelated file or another client's socket opened in between. Under std's I/O-safety contract a raw descriptor number is as dangerous as a raw pointer, and safe code is not exempt when a library gets it wrong: tokio RUSTSEC-2026-0386 (issued 2026-10-23; patched `>=1.51.6, <1.52.0` and `>=1.53.3`) — the safe `AsyncFd::new` family accepted any `T: AsRawFd` "rather than requiring proof of ownership or validity of the file descriptor", so safe code could register a closed or reused descriptor: a use-after-free when a readiness event fires. Since Rust 1.80, dropping an `OwnedFd` whose descriptor is already closed aborts with "IO Safety violation: owned file descriptor already closed" — but only where std's debug-only UB checks are compiled in (§D3); a release build double-closes silently. REQUIRED: borrow with `AsFd` / `BorrowedFd<'_>` (`as_fd()`); duplicate with `try_clone()` / `try_clone_to_owned()` when a second owner is genuinely needed; transfer with `into_raw_fd()` paired with exactly one `from_raw_fd`; every `unsafe { …::from_raw_fd(fd) }` carries a `// SAFETY:` naming the single owner and the single closer; and a function that takes a `RawFd` and acts on it is an `unsafe fn`.
- **C strings without the NUL-termination contract, in either direction.** Outbound: `s.as_ptr()` on a `&str` / `String` / `&[u8]` where C expects `const char*` — Rust strings carry no terminator, so `strlen` reads past the allocation (a hand-declared `*const u8` / `*const c_uchar` parameter accepts `"output/".as_ptr()` with no cast and no warning); `CString::new(s).unwrap().as_ptr()` as a temporary — the `CString` is freed at the end of the statement and the pointer dangles (rustc's `dangling_pointers_from_temporaries` is warn-level only); `CString::new(untrusted).unwrap()` — panics on an interior NUL, so decide reject-versus-truncate explicitly, because the two sides disagree about where such a string ends. Inbound: `CStr::from_ptr(p)` on a buffer that is not guaranteed NUL-terminated inside its allocation — a fixed-size `[c_char; N]` field filled to capacity has no terminator — is an out-of-bounds read: RUSTSEC-2024-0377 (`dbn`: heap buffer over-read in `strlen` through `CStr::from_ptr`; patched > 0.22.0). REQUIRED: `c"literal"` (Rust 1.77) for constants; a `CString` bound to a named local that outlives the call; `CStr::from_bytes_until_nul(&buf)` (Rust 1.69) for fixed-size foreign buffers, handling its `Err`; `to_str()` versus `to_string_lossy()` chosen per §B28; `bindgen`-generated signatures (`*const c_char`) rather than hand-written pointer types. Test with a field filled to exactly N bytes and with an interior NUL.

**REQUIRED**:
- Wrap every panic-capable Rust function callable from C with `std::panic::catch_unwind`; translate `Err(payload)` into a fixed, stable `#[repr(C)]` status/error code (a `-1` sentinel, a defined error-code enum or tagged union) that the C side can match on. The `Err` payload is a `Box<dyn Any + Send>` — there is no `PanicInfo` to hand across the boundary — so never expose it as `*mut PanicInfo` or any raw pointer to the panic payload. If richer error detail must genuinely cross the boundary, wrap it first into a purpose-designed opaque error handle — a Rust-owned struct behind a raw pointer carrying only fields you chose, released by its own paired destructor function (the `rust_drop_T` rule below) — never the payload itself: its concrete type is unknown to you, and dropping an arbitrary `Box<dyn Any + Send>` can itself panic (unknown drop glue). Use the **same disposal recipe everywhere a caught panic payload is handled at any boundary in this file**: downcast it **by reference** to the two common concrete forms (`payload.downcast_ref::<&str>()`, `payload.downcast_ref::<String>()`) to read it into the data you control, and if neither matches, `std::mem::forget` the unknown payload rather than letting it drop. If that data is then logged or otherwise reported, the reporting call itself must not be able to panic — `eprintln!`/`println!` can panic if the underlying stream write fails (a closed/broken stderr), which aborts at this same non-unwinding boundary, or double-panics if it fires during unwinding; use a diagnostic sink specifically audited not to panic — checking the `Result` a `Write` call returns is necessary but **not** sufficient, because an arbitrary `Write` implementation's `write`/`write_fmt` can panic internally regardless of what it returns (a custom `Write` impl is ordinary safe code with no non-panicking contract); a pre-allocated in-memory buffer (`Vec<u8>`/`String` via `std::fmt::Write`) is a genuinely audited example, a caller-supplied `dyn Write` is not — or skip the diagnostic entirely rather than risk it. Catching also says nothing about silence: a panic hook (the default one, or any installed) runs **before** the catch — the message is already emitted and any side effects in the hook or in drop glue on the unwound frames have already happened — so "caught" is not "unobserved" or "no logging"; audit what a panic at this boundary logs and mutates even when it is caught. Document the encoding on the function's doc comment. **Precondition:** `catch_unwind` catches only an *unwinding* panic, and which panic runtime actually runs is a property of the **linkage unit**, not of this crate alone: the panic strategy is a per-crate codegen option; code **statically linked** into the final artifact (an rlib) shares the executable's panic runtime; and a genuinely **separate cdylib** carries its **own** panic runtime, which can differ from — and be isolated from — its host's. **Statically-linked rlib (do not undo this finding):** compiling the FFI crate with `panic = "unwind"` while the consuming executable stays on `panic = "abort"` does **not** make the catch work — the rlib does contain working `catch_unwind` machinery, but its code is linked *into* the executable and shares the executable's runtime, so a panic raised inside it in an abort-strategy executable aborts the process before the catch returns (probed directly: the same unwind-compiled rlib aborts under an abort-strategy executable, and the identical catch returns `Err` normally once the *executable* is switched to unwind). There, where this boundary must catch, every profile that produces the running binary — not just the FFI crate's — must use `panic = "unwind"`; and where the final linked artifact must stay on abort (size/embedded/crash policy), do not pretend `catch_unwind` protects the boundary: keep panic-capable operations out of it (validate inputs before any panicking call, total/checked APIs, no unaudited allocation-heavy paths) and treat any panic there as a process abort. **Separate cdylib (do not overgeneralize the rlib finding to it):** a separate cdylib must not be assumed to inherit its host's strategy — it can contain its own unwinding panic runtime and catch its own panic **entirely internally**, before anything returns across the C ABI: a cdylib built with `--crate-type cdylib -C panic=unwind`, exporting a plain C function that runs `catch_unwind(|| panic!(...))` and returns an integer status, was observed catching the panic inside the DLL (`caught_in_unwinding_dll=1`, the panic hook printing inside the DLL) while a `panic = "abort"` host executable importing and calling that exported function exited 0 cleanly — no unwind crossed the boundary (probed on Windows/rustc 1.97.0). None of this softens the boundary rule: an unwind crossing **between** linkage units — out of one unit across the FFI boundary into another — is the disallowed case (pre-1.81 UB; since 1.81 abort) regardless of either unit's strategy. The sound patterns are: catch and contain the panic **entirely inside one dynamically-linked unit** before it reaches the exported C ABI, or keep a consistent unwinding strategy across statically-linked units. `catch_unwind` requires an `UnwindSafe` closure — most FFI bodies are, but if you reach for `AssertUnwindSafe`, confirm no caller observes broken invariants after the catch rather than wrapping blindly.
- **Classify every raw-pointer return before deciding whether it needs a destructor.** A **borrowed/static** pointer (points into memory Rust continues to own) is documented "do not free" and gets no `drop_T`. An **ownership-transferring** return of a Rust-owned type `T` ships a paired `extern "C" fn rust_drop_T(p: Option<Box<T>>)`. The `Option<Box<T>>` signature is not stylistic: the standard library guarantees that for `T: Sized`, `Box<T>` is a single pointer ABI-compatible with C's `T*`, and represents the nullable case as `Option<Box<T>>` rather than a possibly-null `Box<T>` — so a caller that explicitly passes a NULL literal (a nullable API's absent case) gets a typed, safe no-op instead of `Box::from_raw` on null. This does **not** by itself make a double-call safe: a second call with the *same* non-null pointer from the first (now-dangling) allocation is still `Box::from_raw` on a freed allocation — UB — because the pointer's bit pattern is unchanged by the first free; `Option<Box<T>>`/the null check only catches an *actual* null literal, never a stale non-null one. Exactly-once destruction remains a caller contract to document and uphold, not something the nullable signature enforces for you. Where the exported signature must stay a bare `*mut T`, check `if p.is_null() { return; }` before `Box::from_raw` **and** declare it `pub unsafe extern "C" fn rust_drop_T(p: *mut T)` with a `# Safety` section: the null check catches only a null literal, so a safe signature would let safe Rust pass a dangling non-null pointer into `Box::from_raw` (the exported-entry-point rule below). The `Option<Box<T>>` form needs no `unsafe`: a `Box<T>` parameter is a Rust type whose validity (non-null, aligned, a live uniquely-owned allocation) safe Rust callers already guarantee — they cannot construct a dangling `Box` without their own `unsafe` at the `Box::from_raw` site — and the C side's duty to pass a pointer from this API's constructor, exactly once, stays a documented contract; clippy `not_unsafe_ptr_arg_deref` does not flag it (observed on clippy 1.98.0). The body reclaims **exactly once**, from a pointer whose origin is this API's own constructor (never a cast/offset of some other pointer), and **contains a panic from `T::drop`**: a plain `extern "C" fn` does not unwind into C — since Rust 1.81 an unwind reaching a non-`-unwind` ABI boundary such as `"C"` aborts the process instead of continuing UB — so wrap the drop in `std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| drop(b)))`. The returned `Err(payload)` is not itself an inert value to log-and-drop: it is a `Box<dyn Any + Send>` (which is not `Debug`/`Display` — `Any` provides neither), and its own destructor is unknown and can itself panic when it falls out of scope, which would then reach this same non-unwinding `extern "C"` boundary and abort the process regardless of the outer `catch_unwind`. Use the same disposal recipe as the general `catch_unwind` rule above: downcast the payload **by reference** to the two common concrete forms — `payload.downcast_ref::<&str>()` / `downcast_ref::<String>()` — and, if a diagnostic is wanted, report whichever matches through a sink proven not to panic itself (never a bare `eprintln!`/`println!` — see the general rule for why); if neither matches (an unknown payload type), `std::mem::forget`/leak the payload rather than letting it drop unexamined. Never attempt to log the `Box<dyn Any + Send>` itself, or document why `T::drop` is proven panic-free (pure deallocation, no user callbacks) and needs no guard. Document the contract on both functions: caller owns the pointer until it calls `rust_drop_T`; passing null/`None` is a defined no-op; the C side must not call `free()` on this pointer, ever. The pointer-taking contract this destructor's own `p` also carries (liveness, provenance, initialization, extent, aliasing) is the general rule stated in the `# Safety`-documentation bullet below — this bullet is the destructor-specific instance of it.
- For an ownership-transferring `Vec<T>`, decompose with `ManuallyDrop<Vec<T>>` (MSRV-safe) or `Vec::into_raw_parts` (MSRV ≥ 1.93). The resulting Rust tuple stays on the Rust side: pass its components as separate C arguments/out-parameters or a matching `#[repr(C)]` descriptor, plus a paired free function. Document that the C side must preserve the pointer and allocation metadata needed for reclamation and keep the elements valid; the simple hand-back API requires all three components unchanged. Borrowed buffers have a different lifetime/no-free contract.
- For every `#[repr(C)]` struct crossing the boundary, verify the layout against the C header. On nightly: `cargo +nightly rustc --lib -- -Zprint-type-sizes` prints field-by-field sizes and offsets for every type in the crate. On stable, write a unit test that asserts `std::mem::size_of::<MyStruct>()`, `std::mem::align_of::<MyStruct>()`, and `std::mem::offset_of!(MyStruct, field)` against the values expected by the C side. If you use `bindgen`, pin its output (commit the generated file) so changes show up in diff review. Field order, padding, and alignment must match the C side byte-for-byte.
- **Callback context lifetime: unregister → confirm in-flight callbacks are drained → free, in that order.** For a registered `(trampoline, *mut Ctx)`: teardown first calls the library's unregister/stop function, then synchronizes with any in-flight or queued invocations *per the library's documented delivery model* (a synchronous "no callback runs after stop returns" guarantee, or an explicit barrier/join if delivery is on the library's own thread), and *only then* reclaims the context (`Box::from_raw`) — exactly once. Inside the trampoline, borrow the context — never `Box::from_raw` it there — and pick the reference type from the library's documented concurrency/reentrancy contract, named in the `// SAFETY:` block: **serial** (the library documents at most one invocation in flight at a time, no reentry) — `&mut *(p as *mut Ctx)` is sound, with the proven exclusivity interval being that documented serial delivery; **concurrent** (invocations may overlap, including on different threads) — shared access only (`&*(p as *const Ctx)` or raw/`NonNull` access), with all mutation moved into synchronized interior state (`Mutex`/`Atomic*`/lock-free fields) that *every* access goes through — one `&mut` per invocation is UB **even though `Ctx` contains a lock**, because the two overlapping exclusive references exist before either body acquires the interior mutex, and no lock inside repairs them; **reentrant** (the callback may reenter the library, or itself, before returning) — shared access plus reentrancy-safe interior state (a reentrant lock, thread-local staging, or a deferred queue drained outside the callback; never a plain non-reentrant `Mutex` a nested same-thread invocation would deadlock on). State in the same `// SAFETY:` block whether the library may invoke the callback from **another thread** — if it can, shared access plus synchronized interior state is the default, the context's contents need `Send`/`Sync` discipline (feeds §B18), and the C library's own reentrancy/thread-safety contract must be audited (§B25a); `&mut` is admissible only where the serial contract is proven, not assumed from "the tests passed". Regression-test the aliasing half itself: a negative control simulating two overlapping invocations that each form `&mut Ctx` on a `Ctx` whose field is a `Mutex<_>` must be rejected (miri flags the aliasing even though the lock is never contended in the test). Calibration: a wrapper that has done this — documented unregister-is-synchronous, a named delivery contract with the matching access form, borrow-not-own trampoline, `// SAFETY:` citing the drain guarantee — is correct and not a finding; the ban is on the *free-before-drain* / *own-in-trampoline* / *overlapping-`&mut`-justified-only-by-an-interior-lock* shapes, not on callbacks per se.
- **Exported entry points take only raw pointers and primitive integers; a pointer-dereferencing export is `unsafe` on the Rust side; the body validates before any typed value exists.** An `extern "C"` fn exposed to a foreign caller takes `*const T`/`*mut T` (+ explicit lengths) and primitive scalars — the underlying integer type matching an enum's `#[repr(int)]` discriminant width (e.g. `u32`, `i32`), never the enum type itself, and never `&T`, `&str`, `bool`, or any `enum` — and its body checks null, alignment, length, UTF-8 (`str::from_utf8` → error code), and discriminant range *before* it mints any reference or typed value, returning a stable error code (not a panic — see the `catch_unwind` rule) on bad input. This is the export-surface application of §B5's validate-before-mint boundary rule: the check runs on the raw representation, and the invalid typed value is never *produced*. That validation is not the whole rule: **any exported fn that dereferences, reads/writes through, reclaims (`Box::from_raw`) or builds a slice from (`slice::from_raw_parts`) a raw-pointer argument must be declared `pub unsafe extern "C" fn` with a `# Safety` section** stating the pointer contract (next bullet). Null/length/alignment checks cannot establish liveness, provenance or initialization, so with a safe signature any safe Rust caller — in the same crate or downstream — can pass a dangling non-null pointer and cause UB: the public API is unsound. `unsafe` changes nothing for the C caller (same symbol, same calling convention), so it costs nothing there; it is required **in addition to**, never instead of, the raw-representation validation, and the validation does not discharge it. Mechanical backstop: clippy `not_unsafe_ptr_arg_deref` (correctness group, deny-by-default) — observed on clippy 1.98.0 firing ("this public function might dereference a raw pointer but is not marked `unsafe`") on each of `unsafe { (*p).n }`, `unsafe { drop(Box::from_raw(p)) }` and `unsafe { std::slice::from_raw_parts(p, len) }` inside `#[unsafe(no_mangle)] pub extern "C" fn`s, each after an `if p.is_null() { return …; }` early return; never `#[allow(clippy::not_unsafe_ptr_arg_deref)]` on an export. The lint is a floor, not the rule: observed on the same toolchain, it did not flag a private `#[unsafe(no_mangle)] extern "C" fn` that dereferences its pointer, nor a `pub extern "C" fn` that only forwards the pointer to another function. Grounding: stack-graphs RUSTSEC-2026-0302 — `sg_stack_graph_free`, `sg_stack_graph_nodes`, `sg_stack_graph_add_edges` and other pointer-taking C-API exports were safe `pub extern "C" fn`, so `sg_stack_graph_free(std::ptr::null_mut())` from safe Rust is immediate UB via `Box::from_raw`; the advisory's fix is to make every pointer-taking export `unsafe extern "C" fn` with a safety comment; no patched release (repository archived). (See `references/sources.md`.) (Validate-before-mint helpers, current std: Rust 1.95 stabilized `bool: TryFrom<{integer}>` — `bool::try_from(raw)` is `Ok` for 0/1 and `Err` otherwise — and changed matching on a `#[non_exhaustive]` enum to read the discriminant, so an out-of-range discriminant minted on the C side now surfaces at the match itself rather than hiding until a variant is touched.)
- **Document pointer contracts by role in `# Safety` and the C-facing API docs** — the `# Safety` section required on every pointer-dereferencing `pub unsafe extern "C" fn` above. Null/alignment/length checks do not establish liveness, provenance, initialization or permitted aliases. A borrowed input can refer to **caller-owned/C-allocated storage**; it need not originate from this API's constructor. Its requested read extent must be valid and initialized for the call, possibly a prefix of a larger allocation, with the relevant shared-access discipline. A pure out-pointer may refer to uninitialized writable storage if the callee promises not to read/drop the old contents; state what is initialized on success and failure before Rust promotes it to a typed value. An ownership-transferring handle or destructor call additionally needs the allocator/layout and exactly-once reclaiming contract; constructor identity applies when that API requires it, not to every pointer. Shared reads and sound interior mutability have different concurrency conditions from exclusive writes. State these obligations explicitly and prove them upstream; runtime value checks alone do not supply them.
- **Per wrapped C function, the `// SAFETY:` block states the ownership direction *with a citation to the specific C doc line/section*.** Real C libraries are **not** uniform: within one library `set_name(obj, s)` may copy its argument, `set_payload(obj, p)` may take ownership of it, `get_name()` may return a borrowed pointer into the object while `get_error()` returns a `malloc`'d string the caller must free — and conventions drift between library versions. So the audit is **per function, not per library**: for each wrapped call record, from the C documentation, who allocates, who frees, and whether a returned pointer is borrowed-from-internal or caller-owned, and encode that in the `// SAFETY:` block with the doc citation. A single uniform wrapper pattern (always `CString::into_raw`, always freeing a returned `*const c_char`) is right for some functions and a double-free or unbounded leak for the others — and a symmetric test stub passes either way. An **undocumented** ownership direction is not a guess: it is a §B5-style block-and-ask (the caller-invariant is unstated → the unsafe-invariants Blocking case).
- **A length the foreign side reports is in the foreign API's unit: convert and bound it before `slice::from_raw_parts` or a copy; record the unit next to the ownership citation.** A C out-parameter, a variable-length attribute's `ulValueLen`, or a struct length field counts *bytes* in some calls and *elements* in others, and the type gives no hint — a `usize`/`c_ulong` reads the same either way. Treating a byte count as an element count builds a slice `size_of::<T>()` times too long (an out-of-bounds read behind a safe-looking API; for `T = u8` the two coincide, so a byte-typed test never exposes it). Real case: cryptoki RUSTSEC-2026-0286 — decoding `CKA_ALLOWED_MECHANISMS` treated the byte count `ulValueLen` as a `CK_MECHANISM_TYPE` element count, so `Session::get_attributes` built an out-of-bounds slice (affected before 0.10.1 / 0.11.1 / 0.12.1). The rule: for a byte length, `n = byte_len / size_of::<T>()` and **reject a non-zero remainder** (and a zero-sized `T`); for an element length, state that in the `// SAFETY:` block and check `len * size_of::<T>()` against `isize::MAX` (§B5); in both cases bound `n` by the capacity of the buffer this side actually allocated and passed — a size-query or "needed length" result larger than the buffer is an error or a retry with a bigger buffer, never a slice length; and allocate the buffer as `T` (not a `Vec<u8>` cast to `*const T`) or copy out with `chunks_exact(size_of::<T>())` + `from_ne_bytes`, since a byte buffer carries no alignment for `T`. Then the §B5 `from_raw_parts` extent invariant applies to `n`, not to the raw reported value. This is the FFI twin of §F1's rule that a length prefix must count the spec's unit, not whichever unit the code has to hand.
- Add miri to CI for every file containing `extern "C"` blocks, exactly as §B5 requires for any `unsafe` — but note miri **interprets Rust, it does not run native code**: it cannot execute a real `extern "C"` call into a C library (it aborts with "unsupported operation: can't call foreign function" unless a shim exists). Point miri at the **Rust-side** of the boundary (pointer provenance, `#[repr(C)]` layout, the `from_raw_parts` / `Box::from_raw` ownership invariants) and isolate the actual foreign call behind `#[cfg(not(miri))]` (or a `#[cfg(miri)]` mock) so CI exercises what miri can verify instead of failing on the unsupported call.

## §B4. Drop order and RAII contracts

**The trap**: implicit `Drop` for transactions, file handles, async resources has library-specific contracts. `sqlx` implicit-rolls-back inside the async runtime — a library/backend-specific **queued rollback**, not a blocking call: `Transaction`'s `Drop` impl calls `TransactionManager::start_rollback`, which queues the `ROLLBACK` to run on the next asynchronous invocation of the underlying connection (e.g. when the connection is returned to the pool), so whether it ever runs — and whether it succeeded — is runtime-dependent and unobservable. `deadpool-postgres` sends rollback to a background task that may never run. The semantics live in library source, not signatures. Whenever rollback completion — or its potential error — must actually be observed by the caller, an **awaited** rollback is REQUIRED: call `.rollback().await` yourself; never rely on the queued drop-time behavior for that. Commit completion is the harder case — read the three-case commit-failure rule at the end of this list before wrapping `commit().await` in a timeout or a `select!` arm.

**REQUIRED** for any DB transaction / file handle / network resource:
- After the last fallible operation that might fail (e.g., `tx.commit().await`), **assume the resource's `Drop` runs in an undefined state**. Do not rely on it for correctness. For `commit()` specifically this is not even a matter of `Drop` timing: `commit()` **consumes** the transaction (`self`), so after a failed commit the caller holds no `tx` to decide anything with — the "undefined state" lives in the driver's connection state machine, not in a handle you still own (see the three-case rule below).
- For transactions: explicit `commit().await?` on the success path always. On the error path, an explicit, **awaited** `rollback().await` is REQUIRED whenever rollback's completion or potential error must actually be observed by the caller (the default case — an unswallowed rollback failure usually needs to surface, and the caller usually needs to know the rollback actually ran before proceeding) — call it yourself, don't rely on the queued drop-time behavior. The REQUIRED shape is **not** a bare `rollback().await?`: that literal form has its own trap — if the rollback *also* fails, the `?` propagates the rollback's error and silently discards the original failure that triggered the rollback in the first place, replacing the actual root cause with a secondary one. Match rollback's `Result` explicitly instead: `if let Err(rollback_err) = tx.rollback().await { return Err(MyError::RollbackFailed { source: rollback_err, original: Box::new(original_err) }); } return Err(original_err);` (or equivalent) — decide precedence explicitly, typically surfacing the original error to the caller with the rollback failure attached as context, not substituted for it. The narrow exception: when the caller has *documented*, deliberate indifference to whether/when the rollback completes or succeeds (a fire-and-forget cleanup on a path already handling a fatal error, for instance), letting the queued drop-time rollback run is an acceptable, explicitly-stated trade-off — but it is a decision to write down, not a default to fall into silently. Either way, acknowledge the failure mode of `commit().await` itself failing — and treat it as **three distinct cases**, not one (see the rule immediately after this list).
- Read the version-specific `Drop` impl docs for the library being used. State the version you assumed in a comment.
- Be aware that holding multiple drop-significant guards (file + DB tx + lock) creates an ordering problem — and "drops in reverse declaration order" is a rule only for **function-body locals**: locals (stack variables in a function body, `let` bindings) drop in **reverse declaration order**; fields of a struct/enum-variant/tuple drop in **forward declaration order**, and array/slice elements in **forward index order** (first to last); a move-closure's captured variables drop in an **unspecified order** — never rely on closure-capture order for any shutdown/cleanup contract, make the order explicit instead. Even where the order is specified, the *correct* order depends on the semantics. State which order matters.

**`commit()` failure is three distinct cases, and one of them is unknowable.** `commit()` consumes the transaction, so the retry/rollback/reconcile decision must be designed against the connection and driver state *before* the call — the compiler takes `tx` away at the call site, not at the decision point. Enumerate the cases separately:
- **Pre-commit application failure** (an error before `commit()` is ever called): unambiguous — nothing was committed; `tx` is still owned, so the explicit awaited-rollback rules above apply normally.
- **Rollback failure or cancellation** (the rollback you started errored, or its await was cancelled): the transaction may still be open on the connection. State the disposition for the connection before reusing it — check the driver's docs/pool policy: some pools retire a connection whose rollback failed, others return it with the rollback still queued; either way the caller cannot assume a clean connection.
- **Ambiguous commit completion** (COMMIT sent, response lost — a timeout firing, `select!` handing the loss to another arm, cancellation, or connection drop mid-await): the commit may or may not have taken effect, and **no client-side state proves either way**. The drivers differ inside exactly this window: tokio-postgres 0.7.18 marks the transaction done *before* awaiting the COMMIT response, so cancelling that await does not even schedule a Drop-triggered rollback; SQLx 0.9.0 clears its "open" flag only on successful completion, so its remaining paths can still queue a rollback. Neither state machine tells you whether a *delivered* COMMIT whose response was subsequently lost took effect — losing the ack is not evidence the commit didn't happen. Therefore: **blind retry of non-idempotent effects after an ambiguous commit outcome is banned** — a retry can double-apply the very effect the transaction was meant to make atomic; handling the ambiguous case requires the application's own **idempotency/reconciliation contract** (idempotency keys, dedupe, or a reconciliation query against the effect) before any retry. For payment-like at-most-once-effect operations the downstream impact of getting this wrong is high — a duplicated charge or a silently dropped one. Scope-honesty: the duplicate-effect risk here is an **inference** from acknowledgement loss plus the two driver state machines cited above — it is not a live-database experiment executed for this document. Finally, audit `timeout(...)`/`select!` usage around the **`commit().await` call itself**, not only around reads: wrapping the commit await in a timeout or a losing `select!` arm is precisely what *creates* the ambiguous case.

**BANNED**:
- **Intentional termination on any non-unwinding path** — `std::process::exit(...)`, `std::process::abort()`, a panic under `panic = "abort"`, or the double-panic abort below — from any code path where stack-local guards (database transactions, file handles, lock guards, logger flushers) still need to run their `Drop`. **All of these skip unwinding** — none of those `Drop` impls execute. `process::exit` is only the most familiar: `process::abort()` and a `panic = "abort"` panic are full destructor-skipping termination paths too, not merely a `catch_unwind` limitation — a `BufWriter` followed by an `abort()` loses its unflushed user-space output even though `BufWriter` owns a Drop-based flush. For `process::exit`: return a `Result` from `main`, or call `drop(guard)` explicitly on every guard before exiting. **A bare drop is not enough when the guard's cleanup is fallible**: `std::io::BufWriter`'s own docs warn that its `Drop` attempts a flush but silently ignores any error the flush returns — the documented fix is to call `.flush()` explicitly and check the `io::Result` *before* the drop, not to rely on the drop to do it. The same shape applies to any guard whose teardown can fail: call and check `.flush()` / `.sync_all()` / `.commit().await` / `.rollback().await` / `.close()` — whichever the type exposes — before `process::exit`, not just drop it; dropping alone discards whatever error that call would have surfaced. The same discipline then applies **uniformly across every non-unwinding path**: run the explicit, checked fallible cleanup *before* any intentional termination on these paths (exit, abort, panic-abort), or — where cleanup-before-termination cannot be promised, as with an unexpected abort — design the external state to be crash/recovery-safe (journaling, write-ahead, idempotent recovery on restart) so nothing depends on unwinding-based cleanup. Stated plainly: **RAII/Drop is not a crash-consistency guarantee across these paths.**
- A destructor that lets a panic **escape while an outer panic is unwinding** can abort the process. This is not a ban on every nested panic: under `panic = "unwind"`, an inner `catch_unwind` can contain a panic entirely inside `Drop` while the outer unwind continues. After that inner catch, `std::thread::panicking()` can still be true because of the outer panic. Prefer non-panicking cleanup; use the predicate to skip only work the cleanup contract permits skipping, such as best-effort diagnostics, not required resource release. If panic-capable cleanup is deliberately contained, prove invariants survive the catch and that payload disposal/reporting cannot let another panic escape. Downcast payloads by reference to known safe forms (`&str`/`String`); an unknown payload can have panicking drop glue, so do not drop it unexamined — retaining/forgetting it is the existing last-resort policy. Use an audited non-panicking diagnostic sink or skip reporting; arbitrary `Write` implementations and `eprintln!` can panic. `catch_unwind` does not rescue `panic = "abort"` or a panic in a panic hook. Use `AssertUnwindSafe` only with an invariant proof, and keep hook side effects distinct from whether the unwind was caught.
- `mem::forget(guard)` or wrapping a guard in `ManuallyDrop` without a later manual drop — both silently disable the RAII release (file descriptor, DB connection, lock guard never freed). This is the §C5 reflexive-`.clone()` reflex applied to `Drop`: a quick way to silence a move/borrow complaint that leaks the resource instead.
- Issuing raw `BEGIN`/`COMMIT` (or `START TRANSACTION`) statements through a connection **`Pool`** — `sqlx::query("BEGIN").execute(&pool)` … `sqlx::query("COMMIT").execute(&pool)`. Each `execute` checks out a pooled connection of the pool's choosing, so the two statements (and everything between) may run on **different connections**: the "transaction" spans nothing and the `COMMIT` is an orphan — PostgreSQL answers it with a warning and exit success, not an error. The failure is silent: a multi-statement invariant that was never atomic. Always open transactions with `pool.begin()`, route **every** statement through the returned `Transaction` handle (`tx` / `&mut *tx`), and let that handle own commit/rollback per the REQUIRED rules above. The read-modify-write isolation rules (lost updates, `READ COMMITTED` vs `FOR UPDATE`/`SERIALIZABLE`) are §B13.

**Drop at process exit — memory vs. resource (the fork that resolves the `process::exit` tension above)**: the BANNED `process::exit` / `mem::forget` rules above are about *resource-releasing* `Drop`. Not every `Drop` releases a resource, and the two cases want opposite treatment at shutdown:
- **Resource-cleanup `Drop`** (flushes a file, commits/rolls back a transaction, releases an OS lock, sends a connection-close, decrements a cross-process refcount): **must run**. Skipping it via `process::exit` / `process::abort` / a `panic = "abort"` panic / `mem::forget` / `ManuallyDrop` is the §B4 bug above — data loss or a stuck external resource.
- **Memory-only `Drop`** (a large `HashMap`, a deep tree of `Box`, an arena, a parsed AST — whose `drop` does nothing but free heap the OS is about to reclaim wholesale): running it at process exit is *wasted work*. Walking a multi-gigabyte structure node-by-node can add seconds of teardown — or look like a hang — before an exit that frees the whole address space anyway. Here `std::mem::forget`, `ManuallyDrop`, or letting `std::process::exit` skip it is the **correct** move, not a leak that matters.
- **Static-owned resources** (`static`/`static mut` items, and anything reachable only through them — a connection pool behind a `OnceLock`, a buffered logger held in a `static`): **never dropped**, even on normal exit. Returning from `main` runs destructors only for locals and for values owned in a still-live scope at that point; by design, static items get **no destructor call on normal process exit** ("Static items do not call `drop` at the end of the program" — Rust Reference, static items). So "return from `main`" is not a cleanup path for anything a global owns: every static-owned resource (pool, buffered logger, metrics reporter) needs explicit shutdown/flush logic — an explicit `shutdown()`/`flush()` before returning, or a drop-guard held as a *local* in `main` — rather than relying on program exit to release it.

So classify `Drop` by *what it does*, not by reflex. A literal-minded "always run every destructor" stalls shutdown on big structures; a literal-minded "just `process::exit` to exit fast" loses a transaction. Neither rule is right alone — skip a destructor at exit only when it is provably memory-only.

**Recursive `Drop` can overflow the stack** (ties to §B7): the auto-generated `Drop` for a self-owning recursive type — a long `Box`-linked list, a deep `Box<Node>` tree, an unbalanced syntax tree — recurses once per level as it tears down. On attacker-controlled or merely large depth that recursion overflows the stack: a `SIGSEGV`/abort, **not** a catchable panic (the §B7 DoS shape, arriving through the destructor). Tests on shallow data pass. For any recursive type whose depth is not provably bounded, hand-write an **iterative** `Drop` that unlinks nodes into a worklist `Vec` and drops them in a loop, rather than relying on the recursive default.

**Drop-order shutdown deadlock** (the concrete case of the ordering note above): a worker that exits only on channel EOF cannot finish if the joining scope retains a Sender until after the join and no independent close path can run. That is a wait cycle; merely beginning a join before eventual closure is not itself a deadlock when another actor can close the channel independently. Rust drops struct fields in **declaration order** (top to bottom) and locals in **reverse** declaration order; make worker completion reachable before waiting for the join — release the required senders/resources or initiate a receiver-close/shutdown protocol that can progress independently. Closure and draining may then complete while the join waits. Fix: drop **every** `Sender` clone — or use an independent shutdown signal — explicitly before `handle.join()` / `.await`; in a struct, hold explicit shutdown state — typically `Option<Sender>` and `Option<JoinHandle>` — and on shutdown `.take()` and drop the sender and initiate the chosen closure/revocation protocol first, then `.take()` and `.join()` the handle, in that explicit order regardless of field declaration order. Field order cannot implement this under either mechanism: dropping either a std or Tokio `JoinHandle` **detaches** the thread/task rather than joining it (a detach is not a join no matter which field comes first), so automatic field-by-field `Drop` never joins; and a custom `Drop::drop` that calls `join()` runs to completion before Rust's automatic field destruction even begins, so field order is moot there too. Tokio additionally cannot join from `Drop` at all: `Drop::drop` is synchronous and cannot `.await` a task's `JoinHandle`, so the type must expose an explicit consumed `async fn shutdown(self)` rather than shutting down from a `Drop` impl. Field order is a valid internal detail only for a type whose docs specifically promise a "joins automatically in `Drop`" wrapper contract (sender field declared before handle field) — never as a general fix. Don't leave it to incidental field order; state which drops first and why.

**Sender-count closure and receiver-directed closure are different protocols.** If the worker relies on sender disappearance alone, dropping one Sender is insufficient while another strong sending capability remains. Tokio mpsc also supports `Receiver::close()`: it stops ordinary new sends while allowing buffered data to drain, and `recv()` can reach None even while Sender values remain alive. Do not confuse this with `Sender::closed()`, which waits for closure rather than initiating it. **Pre-existing permits remain relevant after receiver close:** a reserved Permit/OwnedPermit can still send or keep the drain pending until released. Account for every outstanding permit and drain to the API's terminal None; no value can arrive after that terminal result. An independent cancellation/shutdown signal is another option when the worker's contract defines whether to drain or discard queued work. Test the selected protocol: a retained-sender control is nonterminal without explicit close, a close-and-drain control finishes with senders retained, and an outstanding-permit control delays termination until release. Observe nonterminal state with a bounded poll/try-receive or a test deadline; do not leave a blocked thread behind.

Async resources have an additional constraint that `Drop` cannot honor — see §B22 for the async-`Drop`-is-not-real problem.

### §B4a. Edition-2024 temporary-scope drop-order changes

**The trap**: migrating a crate to edition 2024 silently changes *when* temporaries drop in two places — with no runtime error and usually green tests, but a different drop order under locks and RAII guards.

- **`if let … {} else {}` scrutinee** (`if_let_rescope`): in edition 2024 a temporary created in the `if let` scrutinee drops **before** the `else` block (and at the end of the `then` block), not at the end of the whole `if`/`else`. The canonical hazard is an `RwLock`/`Mutex` deadlock: `if let Some(v) = lock.read().get(&k) { … } else { lock.write().insert(…) }` deadlocks in 2021 (the read guard is still alive in the `else`) and silently *stops* deadlocking in 2024 — or, conversely, code that relied on the temporary living into the `else` now drops it early. `cargo fix --edition` auto-rewrites to a `match` to preserve 2021 behavior; review those rewrites.
- **Tail-expression temporaries** (`tail_expr_drop_order`, RFC 3606): in edition 2024 ordinary temporaries created while evaluating a block's tail expression drop at the block boundary **before** its locals; temporary-lifetime-extension rules still apply. A value returned or moved out of the block follows its destination's scope — it is not dropped before those temporaries. A temporary guard used to compute the result can therefore release earlier. The lint is **advisory and has no autofix** — and it is not guaranteed to fire at all. A bounded two-edition probe on rustc 1.97.0 used a trailing `if let None = Some(D("temporary")) {}`-shaped tail after a local with a significant `Drop`: destruction order changed from **local-first (edition 2021) to temporary-first (edition 2024)** for that shape, and **neither** migration lint emitted under `-W rust-2024-compatibility` — a known upstream false-negative, tracked in an open rust-lang/rust issue. Do not tell yourself the migration lint will catch this: for this shape it demonstrably does not. A trailing `if let … {}` with no semicolon is *both* a tail expression and an `if let`, so it hits both rules at once — and can silently hit neither lint. Caveat held open deliberately: the probe ran on 1.97.0 only; do not assume a newer compiler fixes the false-negative without actually testing it on your pinned toolchain.
- **let-chains** (`if let A && let B`, stable 1.88, edition 2024) follow the same `if let` temporary-scope rule — reason about each chained temporary's drop point explicitly. `let`-chains also reached `match` *guards* (`match x { v if let Ok(y) = f(v) => … }`, stable **1.95**, all editions — verify against your pinned toolchain) — these do **not** share the `if let … else` drop hazard (a guard has no `else` arm), so no special drop-order review is needed there beyond normal guard-temporary scoping.
- **never-type fallback** (edition 2024) is mostly out of scope for this spec: changing `!`'s fallback from `()` to `!` is a *compile-time* break in the common case (code relying on `Default::default()` inferring `()` stops compiling), and the one genuinely silent-at-runtime interaction — fallback flowing into an `unsafe` call — is guarded by the `never_type_fallback_flowing_into_unsafe` lint, which is **warn-by-default in all editions since Rust 1.80** and **deny-by-default in edition 2024** (which stabilized in **Rust 1.85**). Because the dangerous case is deny-linted rather than silent, it sits outside this document's "survives the compiler" focus; annotate the type explicitly (`zeroed::<()>()`, `<() as Default>::default()`) when the lint fires.
- Edition 2024 also changes **`impl Trait` lifetime capture**: a return-position `-> impl Trait` now captures *all* in-scope generic lifetime parameters by default. `fn f<'a>(x: &'a [u8]) -> impl Iterator<Item = u8>` ties the returned iterator to `'a` in edition 2024 where it did not before — a borrow that used to end early now lives as long as the input. Opt out with a precise-capture bound: `+ use<>` (capture nothing) or `+ use<'b, T>` (capture only what you name). On a 2021→2024 migration this silently changes how long the return value borrows its input (this is the §B1b lifetime-leaking shape arriving via edition migration).

**REQUIRED**:
- On any 2021→2024 edition migration, run `cargo fix --edition`, then review every `tail_expr_drop_order` warning (no autofix) and every `if let … else` that holds a lock guard or other RAII type in its scrutinee — then keep going: **review significant-Drop temporaries structurally** in tail expressions and `match`/`if let` scrutinees even when the migration lints stay silent, because they demonstrably do for at least one shape (see the tail-expression bullet above). The warning list is a floor, not the census.
- For lock guards specifically, bind the guard to a `let` with an explicit scope rather than relying on a temporary's lifetime — that makes the drop point edition-independent. See §B9 (lock order) and §B2 (guard across `.await`).

## §B8. Silent task dropping (forgotten `.await`)

**The trap**: an `async fn` body's required work is abandoned when its future never reaches a polling consumer. The code can compile, and a test that checks only that the caller returned can stay green while the intended request, write or update inside that body never runs. The defect is the missing execution path for the future, not merely a missing `.await` token at its construction site.

**Why this happens**: LLMs confuse constructing an operation with driving it to completion. An `async fn` / `async` body's work starts when polled, but this is not a blanket promise about every `Future`-returning API: an ordinary `fn -> impl Future` executes its synchronous prefix at the call, and argument evaluation and destruction can have effects too. A `JoinHandle` observes already-scheduled work (§B21). Inspect the actual API and the future's eventual owner.

**Prompt triggers**: "send a notification", "log this event", "fire and forget", "make an HTTP call after the response", any background-task framing.

**BANNED**:
- `let _ = some_async_fn(...);` dropping a lazy future whose body was required to run, without handing it to a polling owner.
- Calling an async function and abandoning its required work, with no caller, combinator or executor responsible for driving the result. Deliberate cancellation/discard under the operation's contract is not a forgotten-await finding.
- `let _fut = async_fn();` whose future is never driven or forwarded and drops with required work unperformed. Boxing it (`Pin<Box<dyn Future>>`), adding an adapter (`.map(...)`, `.then(...)`), or obtaining it from an `async ||` closure does not itself schedule that lazy body.
- An `impl Future` value that reaches no polling owner despite an execution obligation. A local binding inside a non-`async` factory is not itself a defect: returning or forwarding that future to a caller that drives it is valid. Trace the ownership/consumer chain instead of inserting an eager spawn merely because the factory contains no `.await`.
- `let (tx, rx) = tokio::sync::oneshot::channel();` followed by `let _ = tx.send(value);` (discarding the `Err(value)` returned when the receiver has been dropped) **when the caller has a contractual obligation to deliver or recover that value** — the work that produced `value` is now invisible to the consumer side, and matching the `Err` to log or propagate it is the fix. Tokio's own docs describe an ignored `send` error as the expected, documented outcome when "the receiver is not interested in the value" — a receiver that was dropped *specifically because it stopped caring about the result* (a cancelled request, a timed-out caller that already moved on) makes `let _ = tx.send(value);` a legitimate, best-effort idiom, not a bug. The finding is the *unstated* case: silently discarding the error when nothing established that the receiver's disappearance was actually a "no longer wanted" signal. State which case applies in a comment; don't reflexively flag every ignored oneshot `send`.
- `rx.await.unwrap()` on a `tokio::sync::oneshot::Receiver` (the receiver *is* a `Future` — you `.await` it directly, there is no `.recv()` method) when the producer task can fail or be dropped — `RecvError` becomes a runtime panic at a distance. Handle it explicitly as a failure mode.

**REQUIRED**:
- Every required asynchronous operation reaches a polling owner: direct `.await`, a driven combinator/collection, a caller receiving the future, or the executor-appropriate spawn primitive. Storing a lazy future alone does not drive it; a `JoinHandle` instead represents work already scheduled by a spawn. Verify the intended completion/observation path.
- For fire-and-forget **lazy work**, use the executor-appropriate spawn primitive: `tokio::spawn` for a `Send` future, or `tokio::task::spawn_local`/`LocalSet::spawn_local` for a `!Send` future confined to a `LocalSet`. If the API already scheduled the operation, follow its existing handle/observation contract instead of adding another spawn. The §B21 supervision rules (hold vs. detach, graceful shutdown) apply to the resulting handle.
- Enable `#[warn(unused_must_use)]` at crate level. Verify the `#[must_use]` warning fires for ignored futures in clippy output.
- For functions returning `impl Future`, follow the result to its eventual consumer; flag required work that is actually abandoned, not the absence of `.await` at the factory site.

A spawned task that *did* run but produced a result the caller never observes is a different failure mode — see §B21 (`JoinHandle` drop ≠ abort).

## §B11. Blocking the async executor

**The trap**: LLM puts `std::thread::sleep`, `std::fs::*`, blocking HTTP clients, or synchronous DB drivers inside `async fn`. The compiler doesn't care — these are valid sync functions, and tests pass because they're single-threaded and short. Production hits the wall at ~N concurrent requests (N = tokio worker count, often the CPU core count): every worker is blocked, no other tasks make progress, latency spikes to seconds.

**Why this happens**: corpus statistics. `std::fs::read_to_string` is *vastly* more common in training data than `tokio::fs::read_to_string`.

**Prompt triggers**: "read a config file", "fetch from URL", "sleep for N seconds", "wait", "make an HTTP request", anything that does I/O.

**BANNED in any `async fn` or function called from `tokio::spawn`**:
- `std::thread::sleep`  →  `tokio::time::sleep`
- `std::fs::*` (read, write, metadata, etc.)  →  `tokio::fs::*`
- `std::io::Read` / `Write` on real files/sockets  →  `tokio::io::AsyncReadExt` / `AsyncWriteExt`
- `reqwest::blocking::*`  →  `reqwest::Client` (async)
- `rusqlite`, synchronous `postgres` crate  →  `sqlx`, `tokio-postgres`, or wrap in `tokio::task::spawn_blocking`
- CPU-bound work long enough to starve the worker *and* infrequent enough that thread-handoff + the bounded blocking pool is worth paying — wrap in `tokio::task::spawn_blocking` (the ~100µs figure is a rough floor, not a trigger to offload every burst). For short, frequent bursts prefer `consume_budget`/`yield_now` (see below); for data-parallel CPU work prefer `rayon` — handed off through `rayon::spawn` + a `oneshot`, never called inline from the async task (the rayon bullet below). Do not substitute `yield_now` for genuinely blocking work.
- Treating `tokio::time::timeout(dur, tokio::task::spawn_blocking(closure))` (or `JoinHandle::abort()`) as a way to **stop** a running blocking closure — neither can. The future returned by `spawn_blocking` resolves only when the closure returns, so `timeout` returns `Err(Elapsed)` (your 504 is sent) while the closure keeps running on a blocking-pool thread; tokio's own docs state that aborting a *running* blocking task "will not have any effect, and the task will continue running normally" (the only exception is a task that has not started yet). Every timed-out request leaves a zombie blocking thread; under attacker-shaped input (a slow regex, a large decompression — §B16, §B7) the bounded pool (512 threads, below) fills with work nobody is waiting for and every new `spawn_blocking` *and* every `tokio::fs::*` call queues behind it (§B14 queueing). Tests are green because the test's work finishes before the timeout. 🔴 when the work's duration is attacker-influenced (the §B14/§F3 escalation).
- Calling `rayon` **inline** from async code — `par_iter()` / `rayon::join` / `ThreadPool::install` / `rayon::scope` inside an `async fn` or handler. The calling tokio worker blocks until the whole parallel job finishes, so it stops polling every other task it owns; and with both runtimes defaulting to one thread per detected core the process is oversubscribed roughly 2×. PostHog's feature-flag service (post-mortem 2026-04-08): `par_iter()` ran directly inside tokio request handlers with no backpressure — p99 spikes of about 2.5 s and 504s that first looked like a database problem; after the fix mean p99 fell from about 460 ms to about 94 ms. REQUIRED: bridge with `rayon::spawn(move || { let _ = tx.send(work()); })` and `rx.await` on a `tokio::sync::oneshot` (the discarded `send` error is the receiver-gone case of §B8), cap in-flight parallel jobs with a `Semaphore` so excess requests wait asynchronously (§B14), size the two pools so that together they fit the CPU budget (`available_parallelism()` reports the container *limit*, not the request), and never hold a lock across a call into rayon — a thread waiting inside rayon can steal another job that takes the same lock (§B9).
- A child process that outlives the future awaiting it: `timeout(d, Command::new(..).output()).await`, a `select!` arm, or an early `?` drops the future and with it the `Child`, and the process keeps running — tokio's `kill_on_drop` defaults to `false` ("a spawned process will, by default, continue to execute even after the `Child` handle has been dropped"), as in std. The caller reports a timeout while the child still holds its locks, ports and files; an exited-but-unreaped child is a zombie that counts against the system's process limits, and tokio reaps dropped children only on a best-effort basis. REQUIRED: `.kill_on_drop(true)` on every `tokio::process::Command` whose future can be cancelled, and on the timeout/shutdown path an explicit `child.kill().await` (it also reaps) before returning. For `sh -c …` or any child that starts its own children, put it in its own process group (`process_group(0)` on Unix; a Job Object on Windows) and signal the group — killing the shell does not kill its descendants. This is what makes the "killable subprocess" option below real rather than assumed.

**REQUIRED**:
- For a bounded synchronous/blocking section that would otherwise monopolize a worker (a large compression/hash/parse operation or a blocking library call), use `tokio::task::spawn_blocking(|| { ... }).await?` or an appropriate CPU executor. This moves the section off the async worker; admission and work-size limits still apply (§B7/§B14). Short cooperative chunks follow the scheduling guidance below.
- The blocking pool is itself **bounded** (default `max_blocking_threads` = **512**). It is for *short* blocking operations: a task that blocks forever — a `loop { recv() }` actor, a permanent listener, a `std::sync::mpsc` drain — pins one of those threads for the process lifetime. Enough such tasks exhaust the pool, after which every new `spawn_blocking` *and* every `tokio::fs::*` call (those run on the same pool) **silently queues** in an **unbounded** queue waiting for a free thread (no backpressure — see §B14): latency rises and, if producers outpace drain, memory grows without bound. Long-lived blocking loops belong on a dedicated `std::thread`, not on `spawn_blocking`.
- For blocking work that must observe a deadline or shutdown: **cooperative cancellation inside the closure** — check an `AtomicBool` (or `tokio_util::sync::CancellationToken::is_cancelled()`) between bounded chunks of work and return early when the caller gave up — or route the work through something the OS can kill outright (a subprocess), not through `timeout`/`abort` (they only detach; see the BANNED bullet above). Pass the flag/token into the closure at spawn time; a closure that never polls a channel does not "get" cancellation either.
- `tokio::task::yield_now().await` offers cooperative scheduling, not offloading or preemption. It can allow other runnable tasks to progress between bounded chunks, including deliberately cooperative CPU work, but promises neither a particular next task nor an I/O-driver poll before resumption; enclosing combinators may prevent the yield from reaching the executor at all. It cannot make a long synchronous section or blocking syscall interruptible. Offload those sections; for short chunks, measure the scheduling/latency trade-off rather than classifying cooperation solely by an IO-bound/CPU-bound label.
- For modern tokio, `consume_budget().await` is the explicit *budget-aware* primitive: it yields *only when the task's coop budget is exhausted*, otherwise returns immediately. Prefer it to `yield_now` inside a tight async loop that wants to be cooperative without paying the unconditional re-schedule cost. Path note: the function lives at `tokio::task::consume_budget` through tokio 1.43, and moved to `tokio::task::coop::consume_budget` in **1.44.0** (the old path is `#[deprecated]` since 1.44.0). Use whichever path matches your pinned tokio.
- Verify with `tokio-console` or `tracing` spans that no task holds a worker thread longer than its budget.

## §B21. `JoinHandle` semantics: drop ≠ abort

§B8 covers required lazy work that never reaches a polling owner; this category covers already-scheduled work whose spawning code loses its handle-based observation or control.

**The trap**: `tokio::task::JoinHandle::drop()` **does not abort the task**. Still-active work remains scheduled and may retain resources beyond the spawning scope, while unobserved results are discarded. A short task can hide this in tests; a long-lived task can retain connections, locks, file descriptors or CPU for much longer than intended. `std::thread::JoinHandle` also detaches on drop. Decide the lifetime and result-observation policy rather than treating handle destruction as task termination.

**BANNED**:
- Dropping a `tokio::task::JoinHandle` without `.await`, `.abort()`, or an explicit "detached on purpose" comment. Default drop detaches still-active work and loses that handle's result/control; an independently retained `AbortHandle` or cancellation signal may still control the task but does not recover the dropped join result.
- Storing `JoinHandle`s in a `Vec` that is later dropped without the intended completion policy — this detaches any still-active tasks and discards unobserved outputs; resources can remain held until those tasks finish.
- Treating `std::thread::JoinHandle` the same way: drop also detaches, but the OS thread does not share async-runtime cleanup; resources held by the thread (locks, files) outlive the dropped handle.
- Assuming a detached task's panic is returned to its spawner. With unwinding panics, Tokio catches it and exposes a panic `JoinError` through the join handle; dropping that handle loses this result, although the default panic hook still prints to stderr. Under `panic = "abort"`, the process terminates instead (§B4). If failure must trigger alert/restart/shutdown logic, hold and await the handle (or use a `JoinSet`), or provide an explicit reporting path.

**REQUIRED**:
- If you spawn for fire-and-forget, document the intent at the spawn site: `// fire-and-forget: detached by design — task self-terminates within N seconds`. The comment is load-bearing — it tells the next reader that the missing `.await` is intentional.
- If you spawn for joinable work, hold the `JoinHandle` and call `.await` on it (or use `tokio::task::JoinSet` for fan-in across many tasks).
- For **graceful** shutdown: give the task a cancellation signal it cooperatively observes — a `tokio_util::sync::CancellationToken` polled via `select!`, or a shutdown message on a channel — so it can run its own cleanup (flush, ack, protocol close) before returning, then `.await` the `JoinHandle` to wait for that natural completion. This is tokio's own shutdown guidance (tokio.rs/tokio/topics/shutdown): signal, then wait — `.abort()` is not part of it.
- `.abort()` requests forced cancellation; it is not graceful shutdown or immediate preemption. The runtime can drop the task's future after regaining control, not between arbitrary ready `.await`s in one ongoing poll. Synchronous destructors run on that drop, but the abandoned future cannot finish its async cleanup. Where graceful cleanup is required, use abort as the fallback after cooperative shutdown exceeds its grace period: wait with `tokio::time::timeout(grace_period, &mut handle).await`; on expiry, request abort and await the still-unjoined handle to observe completion/cleanup. Explicitly disposable work may use immediate forced cancellation. Handle all outcomes: normal completion may win the race, cancellation yields a cancelled `JoinError`, and an unwinding panic yields a panic `JoinError`. Do not assume every post-abort join is cancelled, or await the handle again if the grace-period wait already consumed its result. A running `spawn_blocking` closure cannot be aborted (§B11); it needs cooperative cancellation.
- Severity: **P1** when a documented graceful-shutdown guarantee protects durable data, a protocol close handshake, or other externally-visible state — substituting `.abort()` for cooperative signaling silently drops that guarantee. **P2** when the task's in-flight work is disposable (no durability/protocol obligation), where calling abort "graceful" is imprecise terminology rather than a live correctness gap.
- Surface every spawn call whose returned `JoinHandle` is dropped (not held, not awaited, not detached-by-design) in the post-flight summary — this is a **semantic** rule, not a list of spellings to match: it applies to every Tokio API that hands back a `tokio::task::JoinHandle`, including `tokio::spawn`, `tokio::task::spawn_local`/`LocalSet::spawn_local`, `tokio::task::spawn_blocking`, and the `Handle`/`Runtime` forms of the send-spawning and blocking APIs (`Handle::spawn`, `Handle::spawn_blocking`, `Runtime::spawn`, `Runtime::spawn_blocking` — neither `Handle` nor `Runtime` has a `spawn_local` method; local/`!Send` spawning is `tokio::task::spawn_local`/`LocalSet::spawn_local` only) — all of them detach on drop; assess the unobserved result and any still-active task's lifetime against the intended policy.
- A spawned **periodic** task (timer-driven flush/reaper/sweeper) whose lifetime should track its owner's must hold a `Weak<T>`, not a strong `Arc<T>`, and exit when `upgrade()` returns `None`. A strong clone keeps the owner alive forever (its `Drop` never runs), inverting RAII. Pair it with a `..._exits_on_drop` test: drop the last strong ref, then assert the task terminated (no hang). This is the "stop when nobody needs me" shape; when shutdown is *explicit/supervised*, use the `AbortHandle`/`CancellationToken` path above instead — `Weak` and a cancellation signal answer different questions and are not interchangeable.
- Using a `clone()` of a shared `CancellationToken` as the handle by which a sub-scope cancels *itself*: a clone is the *same* token node, so `child.cancel()` inside one connection's local error path cancels the whole service — the parent and every sibling holding that token included. For a scope that may cancel itself, spawn with `token.child_token()` (a real child node: its `cancel()` does not touch the parent, but the parent's cancellation still reaches it); reserve `clone()`s for pure observers that only listen for cancellation.

## §B22. `async Drop` is not real (yet)

§B4 covers synchronous RAII contracts (transactions, file handles, locks). This category covers what is **not** possible with `Drop` in async code — async cleanup must happen *before* the drop, not inside it.

**The trap**: the LLM writes `impl Drop` for a database connection, file handle, network socket, or cache flusher and puts `tokio::spawn(async move { self.close().await })` or `block_on(async { ... })` inside the `drop` method. In tests the runtime stays alive long enough for the spawned task to run, or the test thread is not the runtime, and the resource closes by luck. In production the spawned task is fire-and-forget and may not complete before runtime shutdown; the `block_on` variant deadlocks or panics because it re-enters the runtime from a sync context held by the runtime. The result is silent: resource never closes, connection pool exhausts, log buffer never flushes.

**BANNED**:
- `impl Drop` that calls `tokio::spawn(async move { ... self.close().await ... })` from the `drop` method — the spawned task may outlive the drop (fine but irrelevant) and may not run before runtime shutdown (lethal). The async cleanup is **fire-and-forget**, not RAII.
- `tokio::runtime::Handle::block_on(...)` inside `Drop::drop` for resources owned by a tokio runtime — re-entering the runtime from a sync context held by the runtime panics with "Cannot start a runtime from within a runtime" **on every flavor** (current_thread and multi_thread alike; measured in a `Drop` running on a multi-thread worker). There is no "deadlock instead" branch to bet on.
- `futures::executor::block_on(...)` in `Drop::drop` — different runtime, but the same logical issue: any `.await` inside that wants to talk to the tokio runtime cannot, and any I/O bound on the tokio runtime hangs. Unlike the two `block_on`s above it does not panic *on tokio nesting* specifically (it has its own, narrower same-thread re-entrancy check instead — see §B15c): on a multi-thread runtime it can even appear to work by luck (another worker drives the awaited I/O), and on `current_thread` it deadlocks the drop silently — precisely because tests can pass, this is the more insidious variant.
- Treating `Drop` as a place to "flush the buffer" or "send the close frame" — `Drop` cannot do async work, period.

**REQUIRED**:
- Provide an explicit `async fn close(self) -> Result<...>` and require callers to call it. Mark the type `#[must_use = "call .close().await to release resources cleanly"]` so the unused-handle is at least a warning.
- For RAII-like ergonomics, return a `CloseGuard` (or analog) that, when dropped without explicit `.close().await`, **logs an error and emits a metric — and never panics**. A `panic!` from `Drop::drop` is a defect in its own right (§B4's panic-in-`Drop` rule): the guard's `Drop` runs most often while an error or panic is already in flight, and a panic during unwinding is a double panic that aborts the process. Enforce the explicit-close discipline with type-level and process tools instead — `#[must_use = "call .close().await to release resources cleanly"]` (bullet above), a consuming `async fn close(self)` that turns post-close use into a compile error, code review, or tests that fail the *test* on an unclosed guard — never a panic from `Drop`. This is a discipline pattern, not a guarantee; document it.
- Document the type's actual fallback: what synchronous `Drop` releases and which guarantees require `.close().await` (flush, acknowledgement, protocol close, pool readiness). Missing async close is not automatically an OS-handle leak when the owned handle still closes on drop. Specify the disposition after an error or cancellation of the consuming close future as well (§B4/§F3).
- Where synchronous best-effort release is available, use it as the `Drop` fallback and distinguish it from the explicit async close guarantee. Report a resource leak only when the type's actual ownership/cleanup behavior leaves that resource unreleased.

## §C9. `tracing` span leakage across `tokio::spawn`

**The trap**: `tracing::Span::current()` reads the *thread-local* current span. `tokio::spawn` moves the future to another worker thread, where the current span on entry is the runtime's default span — **not** the parent's. Logs and traces emitted from inside the spawned future are therefore detached from the parent's request context; correlation breaks; tracing dashboards show orphan spans with no parent.

**BANNED**:
- `tokio::spawn(async move { ... tracing::info!(...) ... })` (or the equivalent `Handle::spawn`/`Runtime::spawn` method forms — the rule covers any future-spawning API, free function or runtime-handle method, plus any local-runtime/builder path of the same shape) inside a request handler with an active span, *without* attaching the parent span — via `.in_current_span()` **or** an explicit `.instrument(parent_span)` (both from `tracing::Instrument`; either satisfies the rule, the defect is spawning with no span attached) — the spawned future runs outside the parent span.
- Reading `Span::current()` *inside* the spawned future body and expecting it to be the parent — by the time the future runs, the thread-local has been reset.
- Using `tokio::task::spawn_blocking` (or the `Handle::spawn_blocking`/`Runtime::spawn_blocking` method forms) and assuming the parent span is preserved — `spawn_blocking` moves work to a separate blocking-pool thread; the span is lost there too.
- Storing per-request context in a std `thread_local!`, writing it before an `.await` and reading it after. Thread migration is only ONE of the two corruption mechanisms — this is the *general* form of the span hazard above (which is one instance of it): on a multi-thread runtime a task can migrate to a **different worker thread** at any `.await`, so the value read after the await belongs to *whatever other task last ran on the new worker* — or the thread-local default — not to this task. A current-thread runtime / `LocalSet` prevents the migration but NOT the hazard, because it does not prevent **interleaving on the one thread**: task A writes `tenant = 1` and yields at an `.await`; task B, scheduled on the **same thread**, writes `tenant = 2`; task A resumes on that same thread and reads `tenant = 2` — reproducible deterministically with two plain futures polled on one thread, no runtime required. Either mechanism is silent (wrong request-id / tenant / locale / **auth context** propagated; compiles; passes single-threaded tests) — and when the state carries tenant/auth data this is cross-request security contamination, not just broken correlation. Use `tokio::task_local!` (the value travels *with the task* across awaits, interleavings and thread hops — and out-of-scope access fails loudly instead of returning stale data; see the `spawn_blocking` note below) or context **explicitly passed** into the future (a parameter / a field of the async block). A true OS `thread_local!` is acceptable only when the whole usage interval has **exclusive ownership of the thread** — no other task is polled on it between this task's write and its read — or the context is explicitly restored on **every single poll**; "it's all on one OS thread" (current-thread runtime, `LocalSet`) is not that proof — it rules out migration only.
- Logging PII through `{:?}` / `#[derive(Debug)]` / `tracing` fields — email, full name, phone, address, government ID, card number, IP. §B12 covers cryptographic *secrets* by field name, but PII is a separate compliance class (GDPR / PCI / CCPA): it compiles, tests pass, and the leak surfaces only in production logs at audit time. Classify PII fields and redact them (a redacting newtype, `tracing` field filtering, or skip via `#[derive(Debug)]` customization).
- Recording secret material through `#[tracing::instrument]`: automatic argument fields, explicit `fields(...)`, and `ret`/`err` events are **independent paths**. `skip` / `skip_all` suppress automatic arguments only — `#[instrument(skip_all, ret)]` still records the returned token, and `#[instrument(skip_all, err)]` still records a secret-bearing error. For arguments, use `skip(password)` only when the remaining arguments are approved to log, or `skip_all` with approved metadata such as `fields(operation = "login")`; an email is not automatically non-sensitive metadata. For outputs, omit `ret`/`err` or redact the formatter actually selected: `ret` defaults to `Debug` (supports `ret(Display)`) and records only the `Ok` value for a `Result`; `err` records `Err` via `Display` by default (supports `err(Debug)`). Redacting only `Debug` does not protect a `Display` event. Explicit `fields(...)` must not reintroduce skipped secrets or disallowed PII. Assert on captured spans **and** events for the relevant argument, success and error paths. 🔴 for secret leakage on any of these paths (§B12); 🟡 for PII/payload-volume policy (§E5).
- Untrusted input logged via `tracing::info!("... {} ...", user_input)` or `format!`/`println!` passes raw control characters (ANSI escapes, newlines) through unescaped — only `{:?}` escapes them. Into a **plain-text or terminal** log sink this lets an attacker forge log lines, clear the terminal, or inject ANSI (a structured/JSON sink is largely immune). For values reaching such a sink as free text, log via `{:?}` or sanitize control characters, and keep the logging/subscriber stack patched against known log-injection advisories — the worked instance is tracing-subscriber RUSTSEC-2025-0055 (ANSI escape injection via logged input; patched ≥ 0.3.20).

**REQUIRED**:
- Wrap spawned futures with the parent span: `tokio::spawn(my_fut.in_current_span())` (requires `use tracing::Instrument;` in scope). The `in_current_span()` adapter binds the *current* span to the future at spawn time, so it is restored when the future is polled. The explicit form `tokio::spawn(my_fut.instrument(parent_span))` is the equally valid sibling method on the same `Instrument` trait — use it whenever the parent span is *not* `Span::current()` at the spawn site (captured before an earlier `.await`, stored in a struct, passed in from a caller); do not contort code to make `in_current_span()` apply, and do not flag `.instrument(parent)` as a violation — the ban is on spawning with *no* span attached.
- For `tokio::task::spawn_blocking`, capture the span explicitly and re-enter it inside the closure:
  ```rust
  let span = tracing::Span::current();
  tokio::task::spawn_blocking(move || {
      let _guard = span.enter();
      // ... sync work ...
  }).await?;
  ```
  Note this restores only the *span*. `tokio::task_local!` values do **not** travel into a `spawn_blocking` closure (it runs on a fresh blocking-pool thread with no task scope), so capture every `task_local`/request-context value (tenant, auth, request-id, locale) *before* the call and move it into the closure explicitly. The failure there is *loud*, not a silent stale read: accessing a tokio task-local outside its scope panics (`with`/`get`) or returns `Err(AccessError)` (`try_with`/`try_get` — tokio's `LocalKey` docs) — it never returns the previous request's value. The silent cross-request corruption is the *std* `thread_local!` hazard above (values persist on the pooled thread); the task-local hazard is a guaranteed panic/error mid-request — still a defect (the request dies at the access site), just a different one.
- For nested spawns (a spawned task spawns another), repeat `.in_current_span()` at each spawn — the property is not transitive automatically without it.

## §E1. Serialism that need not exist — *Independent work done in sequence is latency you chose to pay.*

- **Where it shows up**: `let a = fetch_a().await; let b = fetch_b().await;` when a and b are independent — the second waits on the first for nothing. CPU-bound work (hashing, compression, parsing a large blob) inside an `async fn`, stalling the runtime worker. A data-parallel loop pinned to one core. A task spawned per tiny item, paying scheduler cost that dwarfs the work.
- **The cheaper move**: independent futures → `tokio::join!`/`try_join!` (concurrent on one task) — prove independence first; a shared `&mut` or lock makes them serial anyway. A dynamic set → `futures::stream::iter(..).buffer_unordered(N)` or a `JoinSet`, bounded (unbounded fan-out is §B14, not a speed-up). CPU-bound → `tokio::task::spawn_blocking` (mind the pool, §B11) or hand to `rayon`; data-parallel → `rayon`'s `par_iter`, run off the async worker (`rayon::spawn` + `oneshot`, bounded — §B11; inline `par_iter` in a handler is the PostHog p99 incident there). Coalesce tiny tasks into batches.
- **Leave it when**: the awaits are genuinely dependent, the path is cold, or concurrency adds contention costing more than the serial latency saved. Concurrency changes cancellation — each branch must be cancel-safe (§B3).

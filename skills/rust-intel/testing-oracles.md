## §D1. Tests that pass by luck

**The trap**: `thread::sleep(Duration::from_millis(N))` to "wait for the async work to finish" races: the work happens to complete in `< N ms` on the developer's machine, the test passes, CI runs slower (or faster) and the test flakes. `#[should_panic]` without `expected = "..."` catches *any* panic — including a panic in test setup before the system-under-test was even called — and the test author reads "should panic" as proof that the SUT panicked, when in fact it might have been the test scaffolding. Tests that only assert "no panic" (`do_thing(); assert!(true);`) prove the syscall ran, not that it produced the correct postcondition.

**BANNED**:
- `std::thread::sleep` or `tokio::time::sleep` (real) to synchronize a test with async work — race condition, flaky CI.
- **A wall-clock threshold asserted as a test** — `let t = Instant::now(); work(); assert!(t.elapsed() < Duration::from_millis(100));`. Whatever threshold you pick lands in one of two failure modes, never in a useful middle: set it **tight** and it goes red on a loaded CI runner or a noisy co-tenant VM (the `sleep` flake above, wearing an assertion); set it **loose** enough not to flap and it becomes structurally unable to fail — vacuous, the coverage theater below. Neither reading says anything about the binary you ship, because `cargo test` runs the **debug** profile (§D3) and production runs release, which is typically an order of magnitude faster; a threshold calibrated against debug timing is not a statement about release at all (and §D3's own `cargo test --release` job re-runs it under yet another timing regime). Performance belongs in a benchmark gated on a deterministic counter (§E6), not in `cargo test`. **Calibration — the legitimate twin:** asserting that a *timeout fires* (a 5 s deadline rejects a 10 s operation) is a behavioral postcondition, not a performance threshold — that one is fine, but drive it with `tokio::time::pause()`/`advance()` per the REQUIRED below rather than real elapsed time.
- `#[should_panic]` without `#[should_panic(expected = "specific message substring")]` — any panic, anywhere in the test, makes it green.
- Tests that assert no postcondition: `let _ = do_thing(); assert!(true);` — proves only that `do_thing` returned without panicking, which is the weakest possible assertion.
- Tests that compare two outputs derived from the same buggy intermediate (e.g., `assert_eq!(serialize(x), serialize(parse(serialize(x))))` does not prove `parse` is correct, only that it is idempotent on serialize output).
- `assert_eq!(a, b)` where `a: f32` or `f64` and the values are computed from **accumulated rounding or cross-platform/cross-architecture math** (sums/reductions, iterative numeric kernels, transcendentals — std documents `powf`/`exp`/`ln`/trig precision as non-deterministic, "varies by platform, Rust version, and can even differ within the same execution"), not from a literal. Floating-point exact equality on such values flakes between debug/release builds, between architectures (SSE vs AVX vs NEON), and across compiler versions due to reassociation. Use `approx::assert_relative_eq!(a, b, epsilon = …)` or `assert_abs_diff_eq!`, or write the comparison manually as `(a - b).abs() < eps`. **Not banned — a documented exact contract stays exact:** exact (even bitwise) equality is the correct oracle when the operation genuinely has one — a value passed through unchanged/merely copied, operands chosen to be exactly representable (`0.5`, small integers), a single IEEE-754-specified step (`sqrt`/`mul_add`/`floor`: std, "guaranteed to be the rounded infinite-precision result"), or a round-trip through `to_bits`/`from_bits`. This bullet targets accumulated-rounding drift, not every non-literal float comparison.
- A test whose mock/fake always returns `Ok`/success and never reproduces the failure modes the real dependency exhibits (timeouts, partial reads, `5xx`, connection resets). A green test against a happy-path-only mock proves behavior against fiction, not against the dependency. Mock the error paths too, or use a fake that can be told to fail.
- **Vacuous tests / coverage theater.** A test that asserts a value against its own definition (`assert_eq!(MAX_RETRIES, 3)`), re-checks what the compiler, `std`, or a `#[derive]` already guarantees (that `Clone` clones; that a getter returns what the setter just set with no logic in between), or exercises a *dependency's* behavior instead of your own. It lifts the coverage number and the confidence while being structurally unable to fail for any reason that matters — and every refactor pays to update a test that never could have caught a bug. Delete it, or rewrite it to assert a postcondition that *could* break. This is the silent twin of the happy-path mock: there the fake cannot fail, here the assertion cannot. **Exception — contract pins are not vacuous:** a constant encoding an *external* contract is worth pinning precisely because changing it is a breaking change you want caught — a type's layout/size for FFI (`assert_eq!(size_of::<Header>(), 16)`, §B25), a wire-protocol magic number or opcode, a serialized golden/snapshot (catches §B20 field-presence drift — and is *required* by §F1 for a positional binary format like `bincode`/`postcard`/`rkyv`/`borsh`, whose persisted bytes a variant/field reorder silently reinterprets). "Does this still equal what the outside world depends on" is a real test; "does this constant equal itself" is not.
- `#[ignore]` left on a test "temporarily" to make the suite green. An ignored test is invisible to `cargo test` and rots silently — CI stays green because the test never runs. A feature gate alone is not a fix: a feature nobody's CI job ever turns on is exactly as invisible as `#[ignore]` — the test still never runs anywhere. If a test must be ignored, gate it behind a named feature *and* add a CI job that explicitly enables that feature and runs the test, with an owner and a documented re-enable/removal condition for that job — the job is the fix, the gate is just the switch.
- Tests that share mutable global state (a `static` cell, a fixed-name temp file, a hard-coded port, an env var) and pass only because of run order. `cargo test` runs tests in parallel threads by default; shared state makes them flake or clobber each other. Isolate per-test state (unique temp dirs/ports, `serial_test` for unavoidable globals). **Limitation — `serial_test` does not make env-var mutation safe:** it serializes only the `#[test]` functions of the same test binary (a lock held around annotated test bodies); it has no visibility into or control over other threads in the same process — a background thread the test itself spawns, or one started by a linked C library. Since edition 2024, `std::env::set_var`/`remove_var` are `unsafe` precisely because mutating the environment races with any other thread concurrently reading it (std's safety contract: sound only in a single-threaded program; Windows excepted). For tests that must vary environment variables, do not cite `serial_test` as the safety proof — instead: run the varying code in a subprocess; or set the variable only on a freshly-spawned child via `Command::env` (the mapping is built for the child process; the current process's environment is never mutated — std's own recommended alternative); or provide an explicit proof that the process is genuinely single-threaded at the moment of mutation.

**REQUIRED**:
- For async timing in tests, use `tokio::time::pause()` / `tokio::time::advance(Duration::from_secs(N))` — virtual time that the runtime under your control. Both require tokio's `time` **and** `test-util` features enabled, and `pause()` panics outright on a multi-thread runtime (tokio 1.54.1: "`time::pause()` requires the `current_thread` Tokio runtime. This is the default Runtime used by `#[tokio::test]`.") — pair it with `#[tokio::test]`'s default current-thread flavor, or the explicit `#[tokio::test(start_paused = true)]` form, never `#[tokio::test(flavor = "multi_thread")]`. Where those prerequisites don't hold, use explicit synchronization (`tokio::sync::Notify`, `oneshot::channel`) signalled by the async work itself instead.
- Always pin `expected = "..."` substring in `#[should_panic(expected = "...")]`, *and* make the SUT call the **only** expression in the entire test body capable of panicking — no `.unwrap()`/`.expect()`/indexing/arithmetic that can fail anywhere in setup **or after** the SUT call. A panic-capable statement placed *after* the SUT call is just as much a hole as one before it: if the SUT itself does not panic, execution reaches that later statement, which can panic with a matching substring (a common error type, a duplicated message) and pass the test without the SUT's own panic path ever having fired. The substring match is defense in depth, not the primary guarantee — isolating the SUT as the sole panic-capable expression (or explicitly `catch_unwind`-ing just that call and asserting on the caught payload) is what actually proves the SUT panicked.
- Every test asserts a postcondition involving the system-under-test's *observable* state — a return value, a side effect on a passed-in mock, a state transition in a fake — not just absence of panic.
- Use `proptest` / `quickcheck` to generate a wide range of inputs — including edge cases a hand-picked table would miss — and explicitly state the property being tested in the test name; this is an input-generation/coverage technique, not a tool for testing non-deterministic systems (that's §D3's `loom`/multi-thread-stress territory).
- For an `interval`-driven background task under `start_paused`: tokio auto-advances paused time only when nothing else is ready, so a *spawned* task that races other futures ticks non-deterministically. `yield_now().await` is not a synchronization primitive here — tokio's own docs state it gives no guarantee about how much of the spawned task actually runs before control returns, so one yield does not reliably prove the interval was constructed, and a fixed yield-then-advance count can under- or over-count ticks relative to what you intended. Drive it with an explicit handshake instead: have the spawned task signal (a `oneshot`) once its `interval` is constructed, `.await` that signal before the first `advance`, then require the task to send a **fresh, per-tick acknowledgement that the test itself `.await`s before issuing the next `advance`** — a bounded `mpsc` channel with one message per observed tick, or a `watch` carrying a sequence number the test awaits past its previously-seen value. Two shapes that look sufficient are not: a **shared counter checked immediately after `advance`** is not an acknowledgement — `advance` does not wait for the tasks its expired timer wakes to actually run, so an immediate load can still observe the pre-tick value (a race, not a synchronization point); and a bare **`Notify`** can coalesce two ticks' notifications into the single permit `Notify` stores, silently under-counting. Account separately for the interval's own immediate first tick. (A lone interval with no competing futures auto-advances on `tick().await` and needs none of this.)
- For variant-shape assertions on enums, use the std `assert_matches!` macro as the test oracle: a pattern-matching assertion (`assert_matches!(res, Ok(Parsed { kind: Kind::A, .. }))`) that prints the actual value on failure — instead of asserting on a bare `matches!()` bool with no diagnostic, or reaching for the `matches` crate. It is **not** in the prelude: `use std::assert_matches;` (or call it fully qualified, `std::assert_matches!(...)`) — the bare macro name does not resolve without one of these (verified: rustc's own diagnostic for the missing import literally suggests `use std::assert_matches;`). **MSRV gate:** `assert_matches!` stabilized in Rust 1.96, above this spec's declared MSRV floor of 1.85 (see Version pins) — on a project pinned below 1.96, it is not yet available; use `assert!(matches!(value, pattern), "unexpected value: {value:?}")` **only when `value: Copy` or the pattern binds nothing by value** — if the pattern captures a field by value (`Ok(x)` where the payload isn't `Copy`), matching `value` moves the captured part out of it, and the `{value:?}` in the diagnostic message then borrows a partially-moved place (`E0382`) even though the assertion looks correct. Match `matches!(&value, pattern)` instead (adjusting the pattern to match through the reference) when `value` must still be usable afterward, or capture whatever the diagnostic needs into a separate binding *before* the `matches!` call. Do not use `debug_assert_matches!` for this: it shares `debug_assert!`'s `cfg(debug_assertions)` gate (§B26) and compiles out entirely in a release build, so a test whose only assertion is `debug_assert_matches!` passes vacuously under §D3's required `cargo test --release` job — it is not a valid test oracle. Reserve `debug_assert_matches!` for non-test, debug-only invariant checks in production code — the same debug-only/always-on split `data-numeric-time.md` §B26 draws between `debug_assert!` and `assert!`.

## §D1a. Oracle validity — *the test is green because the oracle is the code*

**The trap**: §D1 covers tests that assert too little; this sub-section covers tests whose *source of truth* is wrong. Four shapes: (1) **the circular oracle** — the test (or its fixture) was written by reading the implementation, so it pins current behavior, bugs included; values generated by the code can never disagree with it. (2) **the world-erasing stub** — an in-memory fake of an I/O trait that delivers each write as exactly one read: real TCP fragments, coalesces, and partially reads (§C4), so a framing bug that only manifests on a split length-prefix is structurally unobservable through the stub. (3) **no negative control** — nobody checked that the test *fails* when the fix is reverted or the bug reintroduced; a test that passes both with and without the change under test is not evidence for it. (4) **the façade fitted to the test** — the dual of (1): there the test is written from the code, here the code is written from the test. Given the goal "make this test pass," a feature whose tests probe only a *declaration* (a config key, a magic byte, a header line, a status string) gets an implementation that emits exactly that and nothing behind it. Unlike (1)–(3) the test is valid and non-vacuous — it merely under-specifies the feature, and an LLM optimizing for green lives in the gap (Goodhart on the test suite).

**BANNED**:
- Golden/expected values produced by running the code under test and pasting its output ("snapshot-blessing" a brand-new implementation). Snapshots are valid for *regression* (pinning behavior already validated against an external reference) — not as the initial proof of correctness. The expected value must come from the spec, the reference implementation, a hand computation, or an independent oracle.
- An in-memory transport stub as the *only* test path for code whose correctness depends on transport realities: fragmentation/partial reads (§C4), interleaving, backpressure (§B14), peer stall/abort (§F3). The stub is fine for logic tests — it is banned as the sole evidence for framing/streaming code. Make the stub adversarial (split writes at every byte boundary; `proptest` over chunkings) or add one real-socket test.
- A bugfix PR whose test passes on the pre-fix code. Run the new test against the unfixed code once (mentally or actually); if it doesn't go red, it doesn't test the fix.
- Asserting *that* a collaborator was called (mock `.times(1)` and nothing else) where the contract is about *what* was passed or what state resulted — execution is not correctness.
- Treating a *declaration-only* test as evidence that a behavioral feature works. Field-observed at scale: a 360k-LOC LLM-generated Rust port of Git "supported" SHA-256 because every SHA-256 test only asserted that `init` wrote `extensions.objectformat=sha256` to the config — none of them committed or logged in that repo — so the model wrote the config key and kept doing SHA-1 internally; 99.3% of tests green, the feature absent in practice. The declaration test itself is fine (a contract pin, §D1's "contract pins are not vacuous" carve-out); *relying on it as behavioral evidence* is the defect.
- **A fixture the targeted bug cannot change, and a fuzzer whose inputs never get past validation.** A test of a four-stream decoder fed four *identical* streams cannot detect transposed streams; a test of a bit-reversal fed a palindromic input passes on a backwards implementation; `fuzz_target!(|data: &[u8]| { let _ = decode(data); })` over raw random bytes exercises the rejection paths almost exclusively and leaves the decoding logic unvisited. All three are green and look like coverage. Dan Luu's agentic-testing experiment (2026-09; agents implementing Zstd in Rust and writing their own tests, about 160 runs per prompt condition): agents submitted "four identical bitstreams" for the four-stream jump table and palindromic inputs for bit order, and only 10 of the 160 fuzzing-condition runs generated structured inputs — those "found real bugs half the time". REQUIRED: fixtures are asymmetric in every dimension the code distinguishes (distinct per-stream content, non-palindromic sequences, distinct field values — §F4's distinct-value idea); fuzzers are structure-aware — derive `arbitrary::Arbitrary` for a typed input and encode it, or mutate a seed corpus of valid inputs — with a coverage report confirming that executions reach the code behind the validation; and the fuzz oracle is independent: a round-trip property (§F4), a reference implementation, or a differential comparison (§F1) — not "did not crash" alone, and not a second implementation written from the same reading.
- **A formal-verification result that the same change made easier to obtain.** "Kani / Verus / Creusot / Prusti says verified" is evidence only for the specification and assumptions that were actually checked, and an agent told to "make the proof pass" edits exactly those: adding `assume(...)` / `admit()` / `kani::assume`, marking a function `#[verifier::external_body]` or introducing an axiom, stubbing a callee (`#[kani::stub]`), weakening a `requires`/`ensures`, narrowing a harness's inputs to one concrete case, or lowering a `#[kani::unwind]` bound. VeruSAGE (arXiv:2512.18436 §5.6; 849 Verus proof tasks from eight Rust systems): "Without the cheat checker, Sonnet 4 has cheated in 14% of the proof tasks", and Sonnet 4.5 and GPT-5 "still cheated in 7% and 2% of tasks, respectively"; with a cheat checker suggested in the prompt the rate fell below 1.5% for every model but "did not drop to 0". A vacuous proof is green by itself: Kani's documented summary prints `** 0 of 1 cover properties satisfied` directly above `VERIFICATION:- SUCCESSFUL`. REQUIRED: specifications (`requires`/`ensures`/invariants, harness input domains, unwind bounds) are reviewed artifacts — a diff that touches them together with the proof is reviewed as a specification change, not as proof work; CI searches the verified tree for `assume` / `admit` / `external_body` / `stub` / `axiom` against an allowlist with one justification each; every harness states the interesting case with `kani::cover!` and CI fails when a cover is unsatisfied or unreachable; and each proof gets a vacuity control once — temporarily make the postcondition `false` (or end the harness with `assert!(false)`): verification must then fail, otherwise the preconditions are contradictory or the path is dead.

**REQUIRED**:
- For every test, be able to name its oracle and the oracle's independence from the implementation: spec section, reference vector, hand-derived value, algebraic property (§F4). "The code's own output" is not on the list for new code.
- For stream/framing code: at least one test exercising adversarial chunking (write the encoded bytes one byte at a time; split the length prefix across reads).
- Negative controls where cheap: for a parser, invalid-input → `Err` cases (the decoder that never rejects); for a fix, the reproducer-turned-test that demonstrably failed before the fix (state it in the test's doc comment: `// red before <commit/fix>`).
- **Every verify / MAC-check / AEAD-decrypt / signature-verification path needs rejection controls, not only a round trip.** `sign → verify` and `encrypt → decrypt` stay green against a stub that returns fixed values or a `verify` that always returns `true`: RUSTSEC-2026-0273 (`manzana` < 0.3.0) shipped a `SecureEnclaveSigner` whose create/delete/load/sign/verify performed no cryptography and returned fixed values, with no warning. Alongside the round trip, assert `Err`/`false` for: a single-bit flip of the message, of the signature/tag, and of the ciphertext; the wrong key; truncated input (and empty input). A fixed-output stub cannot satisfy both the round trip and these controls. Where published invalid-case vectors exist, use them as the external oracle (Project Wycheproof, maintained under C2SP: `github.com/C2SP/wycheproof`; known-answer conformance is §F1). Fail-closed behavior itself is §B12.
- On review (audit mode): for each test backing a risky change, ask the counterfactual — *what mutation of the code would this test catch?* If the honest answer is "none that matters", report the test as non-evidence (same severity as the untested code path it pretends to cover). For a *feature* (not just a code path), sharpen the counterfactual against the **façade-fitted-to-the-test** shape: *would a stub that emits exactly the observables this suite checks — and nothing else — still pass?* If yes, the suite specifies a façade, not the feature; add at least one end-to-end test that **uses** the feature (for SHA-256: init → commit → read the object back), not only one that checks it was announced.

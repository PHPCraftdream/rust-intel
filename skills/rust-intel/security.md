## §B12. Cryptographic code (silent insecurity)

**The trap**: cryptographic code generated by LLMs has a unique failure profile. A large fraction of LLM-generated crypto Rust fails to compile at all, and of the code that *does* compile, a large share of the vulnerabilities present go undetected by static analyzers. Crypto code looks right, runs, passes round-trip tests (encrypt → decrypt yields original) — and is still catastrophically insecure.

**Why this happens**: cryptography requires *protocol-level* reasoning the LLM does not do. Encrypt-then-decrypt round-trip is the canonical test, and it passes for any non-broken cipher regardless of whether the key, nonce, or mode is sound. The bugs live at a level orthogonal to functional correctness.

**Specifically dangerous patterns**:
- **Nonce reuse**: hardcoded nonce, nonce derived from a counter that resets, nonce equal to the message ID. Reusing a nonce with the same key in AES-GCM or ChaCha20-Poly1305 is catastrophic — recovers plaintext or forges authentication.
- **API hallucination in crypto crates**: invented methods on `ring`, `rust-crypto`, `aes-gcm`, `chacha20poly1305`. Crypto-API names look interchangeable to the LLM but have very different security properties. (Note `rust-crypto` itself is **unmaintained since 2016** (RUSTSEC-2016-0005) and separately carries an unpatched AES-miscomputation bug (RUSTSEC-2022-0011, no fixed version) and must never be *proposed*; it appears in this list only as a name LLMs hallucinate methods on. Use the maintained `RustCrypto` org crates — `aes-gcm`, `sha2`, etc. — instead.)
- **Weak parameter choices**: ECB mode (which the LLM may select because it's "simpler"), 64-bit nonces with random generation (birthday-bound collision), insufficient PBKDF2 iterations.
- **Mixing primitives across security levels**: using SHA-1 alongside AES-256, or pairing a strong cipher with a weak MAC.
- **Custom crypto code**: hand-rolling any cryptographic primitive in Rust. Almost always wrong.

**REQUIRED**:
- I do not write cryptographic code beyond *direct calls to well-known high-level APIs* (e.g., `aes_gcm::Aes256Gcm::new(key).encrypt(nonce, plaintext)`).
- For any crypto-touching task, I propose the design in plain text first and ask the user to confirm the threat model before writing code.
- Nonces are generated via a CSPRNG — prefer OS-backed entropy for keys and security-critical nonces, **never** hardcoded, never reused, never derived from a counter without explicit cryptographic justification. The type name is `rand`-major-dependent: `rand::rngs::OsRng` (rand ≤ 0.9) or `rand::rngs::SysRng` (rand ≥ 0.10 — renamed in 0.10.0 with no deprecated alias); the `getrandom` crate is the name stable across the rename. State the `rand` version assumed.
- Default to high-level libraries (`age`, `ring`, `rustls`) over low-level primitives. Provider note: the default rustls crypto provider is now `aws-lc-rs` (not `ring`) in current `rustls` and `reqwest` ≥ 0.13, and `jsonwebtoken` ≥ 10 requires choosing a backend explicitly (`aws_lc_rs` / `rust_crypto` features).
- For password hashing: `argon2id` is the default. Bare, unsalted, or low-iteration PBKDF2 and plain SHA-256 are banned under any circumstances — but properly salted PBKDF2-HMAC-SHA256 at or above the OWASP floor (≥ 600 000 iterations; see the KDF work-factor bullet below) is an accepted, sanctioned choice when FIPS-140 validation or another compliance constraint requires it: Argon2 has no FIPS-validated implementation, and [OWASP's Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) names PBKDF2 as the preferred algorithm for exactly that case.
- I surface every line of crypto code in the post-flight summary with extra prominence. For *custom or protocol-level* crypto (anything beyond a direct documented call) I recommend mandatory human cryptographer review — it is the one place that warrants it. For a direct call to a well-known high-level AEAD/KDF API used per its docs, the bar is surface-it plus verify the params (key length, nonce width, algorithm, iteration count), not a mandatory cryptographer.

**BANNED**:
- Writing custom encryption/decryption logic.
- Implementing cryptographic primitives (block ciphers, hash functions, KDFs) by hand.
- **`SmallRng` for any security-sensitive value (keys, nonces, salts, tokens) — banned regardless of how it is seeded.** Current `rand` docs classify `SmallRng` as explicitly non-cryptographic: fast, small-state, and predictable/invertible by design (it exists for simulations and non-adversarial randomized algorithms, not security). Seeding it from the OS does not turn its algorithm into a CSPRNG — unlike `StdRng` below, the weakness is the *algorithm*, not the seed, so OS-sourced entropy at construction time does not rescue it. Use `StdRng` or a direct OS/system RNG type instead.
- Seeding `StdRng` (or any other seedable *CSPRNG*) with a predictable, reused, or non-OS-sourced seed (hardcoded, a counter, `seed_from_u64`, or a seed persisted/reused across calls) for security-sensitive randomness — prefer the OS-backed RNG type (or `getrandom`) directly as the simpler default. For `StdRng` specifically the hazard is the seed, not the RNG type: `StdRng`'s algorithm (ChaCha12, per current `rand` docs) is itself a CSPRNG, so an OS-seeded instance — freshly seeded from OS entropy at construction and never persisted or reused — is not equivalent to a hardcoded seed and should not be flagged as such; a single such instance may then be used to generate many values without needing a fresh OS seed *per value* — the requirement is fresh entropy per independent RNG *instance*, not per call. The OS-seeding constructor is itself version-bound, not just the accessor/type names: on `rand` 0.9 it is `StdRng::from_os_rng()`; that exact method does not exist on `rand` 0.10 (which renamed `OsRng` → `SysRng` and the `Rng` trait → `RngExt`) — there, seed via `StdRng::try_from_rng(&mut SysRng)?` (fallible — `try_from_rng` returns a `Result`) or the crate's typed `rand::make_rng::<StdRng>()` helper; verify both against the exact `rand` 0.10.x you pin, since this corner of the API moved during the 0.10 line. 0.8 uses `thread_rng()` + `rand::rngs::OsRng` for the accessor form (no deprecated aliases — literal `OsRng` code fails with `E0432` on a fresh `cargo add rand`, and the cheapest fix that compiles, `rand::rng()`, is a different threat-model decision). The accessor forms are CSPRNGs per the `rand` security guarantees, but the OS-backed type is the safer default when seeding chains are part of the threat model. Pin rand ≥ 0.8.6 / 0.9.3 / 0.10.1: below those, `thread_rng()`/`rng()` is unsound (RUSTSEC-2026-0097) when a custom `log` logger itself calls the thread RNG and a reseed happens inside it. State the `rand` version assumed.
- Storing crypto keys in source code, environment variables read at compile time, or anywhere they end up in the binary.
- Comparing secret material (API tokens, MAC tags, password hashes, OTP codes) with `==` — this is a timing side channel. See §B24 for the rule and the `subtle::ConstantTimeEq` / `constant_time_eq` crates.
- `#[derive(Debug)]` (or manual `impl Debug`) on a struct with fields named `password`, `secret`, `api_key`, `token`, `private_key`, `seed`, `mnemonic`, `cookie` — any secret material that ends up printed in a log/trace via `{:?}`. Wrap secrets in a newtype that implements `Debug` as `"<redacted>"`, or use the `secrecy` crate's `SecretBox<T>`. Scope by *role*, not just the name: the target is secret material used for auth/crypto. Do **not** flag a field merely named `token`/`key`/`seed` in a non-secret role — a lexer/parser `Token`, a map/cache `key`, a keyboard-event `key`, or a deterministic-PRNG `seed` are not secrets. Require a second signal (a crypto/auth context, or nearby `secrecy`/`zeroize`) before redacting. The same leak arrives through a different formatter: `#[tracing::instrument]` records **every function argument** as a span field via `Debug` unless `skip`ped (and `(ret)`/`(err)` record return/error values) — see §C9's instrument bullet for the rule and remedies.
- JWT algorithm pinning that is attacker-driven or left broader than the deployment mints. (`alg: none` is folklore on current `jsonwebtoken`: `Algorithm` has no `None` variant, and `Validation`'s `algorithms` field defaults to a fixed `vec![Algorithm::HS256]` that the token header `alg` must match — verified against jsonwebtoken 11.0.0 docs; a header algorithm outside the configured list is rejected.) The live shapes: parsing the token header to pick the `Validation` algorithm (the attacker then chooses), `Validation::new_for_family(...)` or a hand-written `algorithms` list wider than the algorithm your IdP actually signs with, and RS256→HS256 confusion — verifying with `DecodingKey::from_secret(<public-key bytes>)`, which lets anyone holding the (public) key forge an HS256 token the check accepts. REQUIRED: hardcode the expected algorithm to match your key type — `Validation::new(Algorithm::RS256)` for an IdP RSA public key, `Algorithm::HS256` only for a symmetric secret your service alone holds — and construct the `DecodingKey` the way that algorithm's family demands; never derive the algorithm from the token.
- **JWT verification that stops at signature + algorithm and never checks `aud`/`iss`.** `decode::<Claims>(&token, &key, &Validation::new(Algorithm::RS256))` — the tempting copy from the crate README — verifies the signature and `exp` but leaves the expected `aud` and `iss` at their `None` default: a token that carries an `aud` the service did not configure is *rejected* (`InvalidAudience`), but a token that **omits** `aud` entirely is accepted, and `iss` is not checked at all unless `set_issuer` is called — so a token minted by the same IdP key for a **different service or tenant** (same key, different `iss`, or simply no `aud`) authenticates (verified against `jsonwebtoken` 9.3.1 and 11.0.0). Tests pass because they mint their own tokens, which trivially match. REQUIRED: `v.set_audience(&["my-service"])`, `v.set_issuer(&["https://idp.example"])`, and `v.set_required_spec_claims(&["exp", "aud", "iss"])` so the claims are *required*, not merely checked-when-present.
- `Validation::validate_exp = false`, or signature validation disabled outright — `Validation::insecure_disable_signature_validation()` (jsonwebtoken ≤ 10; the method was removed in 11.0.0) or its ≥ 10.1 replacement `jsonwebtoken::dangerous::insecure_decode` — outside `#[cfg(test)]` — the reflex for making an expired or unsigned test fixture verify. It silences the failure and ships an unauthenticated/expiry-blind endpoint; the ≥ 10.1 form is a free fn in a module literally named `dangerous`, which is the better grep target.
- `reqwest::ClientBuilder::danger_accept_invalid_certs(true)` / `danger_accept_invalid_hostnames(true)` (soft-deprecated in reqwest 0.13 in favor of `tls_danger_accept_invalid_certs` / `tls_danger_accept_invalid_hostnames` — both spellings are the same ban), or a custom `rustls` `ServerCertVerifier` (`verify_server_cert`) that returns `Ok(...)` unconditionally — outside `#[cfg(test)]`. The reflex when a request against a dev/self-signed endpoint fails with a certificate error: it is the cheapest fix that compiles, passes every test (tests hit localhost with exactly such a cert), and in production trusts *any* certificate for *any* site — a silent full MITM on every connection (CWE-295). REQUIRED: pin the internal CA — `ClientBuilder::tls_certs_only([reqwest::Certificate::from_pem(ca_pem)?])` (trust only the pinned CA — in reqwest 0.13 `tls_certs_only` takes `impl IntoIterator<Item = Certificate>`, so pass an array/`Vec`/slice of roots built from your PEM bundle, not a single cert) or `tls_certs_merge(...)` (add it on top of system roots); the older `add_root_certificate` still works but is deprecated in favor of these — never disable validation. A `#[cfg(test)]`-scoped `danger_accept_invalid_certs`/`tls_danger_accept_invalid_certs` against a throwaway test server is fine; the ban is on it reaching non-test code.
- Fixed, hardcoded, or per-username-derived salts for password hashing / key derivation: `SaltString::from_b64("c3RhdGljc2FsdA")`, `b"somesalt"`, or a salt computed from the username. The defect underlying both shapes is the same — no fresh random salt per credential — but the failure mode differs: a single shared fixed/hardcoded salt means identical passwords across different users produce identical hashes, so one cracked hash cracks every user who shares that password, and rainbow/batch attacks return; a per-username-derived salt avoids that specific collision (different usernames yield different salts, so it does satisfy uniqueness-per-credential in the narrow sense) but is still wrong — it's predictable/enumerable, so an attacker who knows or guesses a **specific target's** username can precompute a rainbow table for that one account's exact (derived) salt *before ever seeing the hash* — targeted precomputation per account, not one table reusable across every account, since two different usernames still derive two different salts. That precomputation-in-advance is the practical harm: it collapses the entire benefit salting is supposed to buy (forcing an attacker to compute a fresh table only *after* a breach, per credential) for any account whose username the attacker knows ahead of time. A separate, scheme-specific failure mode also applies if the derivation can ever collide — the same username reused across two systems sharing the derivation scheme, or a normalization step that maps distinct usernames to one salt — which is a genuine cross-account collision, but not the default risk of a derived salt as such. Either way the requirement salting exists to satisfy is **uniqueness per credential** decided *unpredictably in advance*, and randomness is how that's achieved cheaply — a derived salt can be "unique" and still fail because it is also guessable in advance. `verify()` still round-trips and tests pass either way. REQUIRED: a fresh random salt per credential. The generator call is version-bound: on `argon2`/`password-hash` ≤ 0.5 it is `SaltString::generate(&mut OsRng)` — the OS-backed RNG type per your `rand_core` major; on ≥ 0.6 (rand_core ^0.10 / getrandom ^0.4) that API moved — password-hash 0.6 exposes `password_hash::generate_salt()` / `try_generate_salt()` (getrandom-backed, no RNG argument), the PHC string types moved under the re-exported `phc` crate, and `hash_password` generates a fresh random salt itself — so use the KDF crate's own salt generator for the version you pin.
- Below-floor KDF work factors reaching *production* password hashing — `Argon2` `Params::new(8, 1, 1, None)`, or `pbkdf2::<HmacSha256>(pw, salt, 1000, &mut out)`, or a pre-2023 PBKDF2 iteration count copied from an old answer — outside `#[cfg(test)]`. Compiles, round-trips, passes tests; the weakness is visible only after a database dump. A deliberately weak, `#[cfg(test)]`-scoped cost config is fine and common practice (real floor-strength hashing makes test suites unbearably slow); the ban is on that same weak config leaking into the non-test path. REQUIRED: production parameters at or above the current OWASP Password Storage floor (as of this writing: Argon2id **m ≥ 19 MiB, t ≥ 2, p = 1**; PBKDF2-HMAC-SHA256 **≥ 600 000 iterations**) — cite [OWASP's Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) as the *living* floor and re-verify it rather than hardcoding a number that will silently rot.
- AEAD encryption with a nonce length other than the selected algorithm/API's specified width. For RustCrypto's default `aes-gcm`/`chacha20poly1305` type aliases (`Aes256Gcm`, `ChaCha20Poly1305`) that width is 96 bits / 12 bytes, and NIST SP 800-38D's allowance for other GCM IV lengths in the general case doesn't help here: the aliased nonce type is a fixed-size typed array (`Aes256Gcm`'s nonce is `GenericArray<u8, U12>`), so an LLM-generated `let nonce = [0u8; 16];` passed where a `Nonce` is expected **fails to compile** — it does not silently truncate at runtime. That compile-time guarantee is specific to these crates' *default* type aliases, not a universal AES-GCM property — a different API/library, or a RustCrypto construction over a non-default nonce size, can accept a runtime-length nonce and needs its own verification against its actual documented width. The real hazard with the default RustCrypto aliases is building a `Nonce` from a runtime-length source (`Nonce::from_slice(&bytes)`), which panics if `bytes` isn't exactly 12 bytes rather than failing at compile time.

**Additional REQUIRED**:
- For any type holding key material, use `zeroize`'s `#[derive(Zeroize, ZeroizeOnDrop)]` — do *not* hand-roll a zeroing `Drop`: the compiler may keep an optimized-away copy on the stack and can elide the manual write.
- The zeroize derive is **necessary, not sufficient**: it zeroes the value's *final* storage on drop, and earlier copies can survive that. A secret built on the stack and then returned or moved (`fn load() -> Key { let k = ...; k }`) can leave a live byte-copy at the old frame; a `String`/`Vec` secret grown in place (`password.push_str(&extra)`) leaves the bytes in the freed old buffer — `Zeroize`'s own documentation states it "cannot guarantee copies of the data were not previously made by buffer reallocation". Serialization into a temporary, an intermediate parse buffer, and optimizer-introduced copies are the same class. It compiles and passes tests (nothing observes freed memory) and leaks into core dumps, swap, and heap inspection in production. REQUIRED: allocate the secret behind `Box` / `secrecy::SecretBox<T>` *at creation* so every later move copies only the pointer; pre-size `Vec`/`String` secrets to their final capacity so they never realloc mid-life; keep the window between "bytes exist" and "bytes are wrapped" as short as possible. State this as **best-effort memory hygiene, not a guarantee** — a move is not *observably* a `memcpy` you can reason about, and the compiler remains free to elide, duplicate, or combine copies. For a type whose all-zero state would violate its invariants, follow `zeroize`'s documented custom-`Drop` pattern instead of deriving a trait that permits an invalid intermediate state.
- Before adding **any** crypto dependency, check RUSTSEC (`cargo audit`) and state open advisories in the threat-model proposal. A *correctly-used, maintained* crate can still carry an advisory that is open by design: the pure-Rust `rsa` crate's private-key operations are not constant-time and the leak is observable over the network (Marvin attack — RUSTSEC-2023-0071 / CVE-2023-49092, no fixed version available). `priv_key.decrypt(Pkcs1v15Encrypt, &ct)?` compiles, round-trips, and is remotely timing-attackable with no code bug at all — the hazard is the primitive choice plus the exposure context. Keep any advisory-carrying operation off attacker-timed paths (prefer audited key-exchange constructions); name `rsa`/Marvin as the worked example alongside the `rust-crypto` note above (unmaintained — RUSTSEC-2016-0005 — plus unpatched AES miscomputation — RUSTSEC-2022-0011).

## §B24. Side channels on secret-dependent branches (`==` timing, and decrypt-failure oracles)

**The trap**: secret-dependent execution leaks the secret through a side channel even when the functional result is correct. Two sibling channels: the **timing** of `==`, and the **content/shape** of a decryption-failure error. `==` on `[u8]`, `Vec<u8>`, `String`, `&str` gives **no constant-time guarantee** — `PartialEq`/`==` documents nothing about comparison timing. Depending on target and optimizer the comparison can return as soon as it finds a mismatch (byte-at-a-time, a `memcmp`-style chunk, or something else); the exact short-circuit mechanics are an implementation detail, not something to assert as fixed. For non-secret data this is fine. For *secret* comparisons — API tokens, password hashes, MAC tags, OTP codes, session keys, anything an attacker controls one side of — that data-dependent timing difference (e.g. "first byte wrong" typically finishing faster than "first ten bytes right, eleventh wrong") leaks information about the secret one byte at a time. Compiles, runs, passes functional equality tests, and is silently exploitable from across a network on any code path that an attacker can probe repeatedly.

**BANNED**:
- `if user_token == expected_token { ... }` for any secret comparison: API tokens, password-after-hash, MAC tags, OTP codes, session identifiers, HMAC outputs.
- `Vec<u8> == Vec<u8>` or `&[u8] == &[u8]` for secret material.
- `String::eq` / `str::eq` on bearer tokens, JWT signatures, or any string the client controls during authentication.
- Rolling your own constant-time equality with a manual XOR loop — **with or without** `std::hint::black_box` and a `#[inline(never)]` attribute. Those annotations do not make the construction acceptable: `std::hint::black_box`'s own documentation states it provides **no cryptographic or security guarantee**, and optimizer/codegen changes can still reintroduce the early exit or otherwise destroy constant-time behavior. Hand-written secret equality is banned unconditionally; `subtle::ConstantTimeEq` / `constant_time_eq` (REQUIRED below) are the only acceptable answer.
- **Distinguishable decryption-failure errors across a trust boundary** — distinct `thiserror` variants / messages / HTTP statuses for "bad padding" vs "MAC mismatch" vs "invalid UTF-8 after decrypt", returned or mapped to the client. This is the classic padding-oracle shape (CWE-208 behavioral discrepancy / CWE-209 error-message exposure; Vaudenay): it hands the attacker a decryption oracle exploitable byte-at-a-time. It is tempting precisely because *distinct, context-carrying errors are good style everywhere else* — see the §C2 carve-out below. Compiles and passes tests (the tests even assert the distinct variants). Also arises when CBC+HMAC is hand-assembled instead of using an AEAD and padding is checked before, or distinguishably from, the MAC.

**REQUIRED**:
- Use `subtle::ConstantTimeEq` — `x.ct_eq(&y)` returns `subtle::Choice` (a constant-time-friendly bool surrogate); convert to native `bool` via `bool::from(choice)` or `choice.into()`. **Never** branch on `Choice` directly; the entire point of `Choice` is to keep the comparison branch-free until the explicit conversion. The `constant_time_eq` crate is a smaller alternative — `constant_time_eq::constant_time_eq(a, b) -> bool` directly. Either is acceptable for any secret comparison.
- For MAC verification specifically, prefer the crypto crate's built-in `verify` / `verify_slice` over manual `==` on the output. (`hmac::Mac::verify_slice` and `aes_gcm::Aes256Gcm::decrypt` both incorporate constant-time comparison; rolling your own is the bug.)
- Surface every `==` / `!=` on `&[u8]`, `Vec<u8>`, or `String` in the same code path as a secret in the post-flight summary, with the recommendation to switch to a constant-time primitive.
- Collapse every decryption / verification / post-decrypt-parse failure into **one opaque error value on one code path** before it crosses a trust boundary. AEAD crates (`aes-gcm`, `chacha20poly1305`) already return the deliberately opaque `aead::Error` ("intentionally opaque to avoid sidechannel leakage") — *preserve* that opacity through every error-mapping layer; do not "improve" it with context, distinct variants, or per-cause statuses. **§C2 carve-out (crypto boundary):** §C2's general rule — carry error context, don't collapse `?`-propagated errors into one useless message — is correct everywhere *except* here. Error context stops at the crypto boundary: on a decrypt/verify path a distinguishable error *is* the vulnerability. §C2 is cross-referenced back to this bullet.
- Scope note: this targets comparisons where one operand is a secret an attacker can probe (a forgeable tag/token), and error channels on a secret-dependent branch. Constant-time compare is the correct default, but it is not "catastrophic" the way nonce reuse is — and it does **not** apply to comparing a request field against a *public* constant: don't flag `algo == "HS256"` or a header-name check. The decrypt-oracle rule is 🔴 when the distinguishable error crosses a network boundary, 🟡 for logs-only exposure.

## §C2. Error handling discipline

**The trap**: `anyhow::Error` in library crates poisons downstream error handling. `unwrap()` and `expect()` in non-test code is a runtime panic waiting to happen. The `?` operator silently loses context if `From` impls are too eager.

**REQUIRED**:
- In **published library crates** (anything shipped to crates.io with a `pub` API that other authors consume): use `thiserror` for typed errors, never `anyhow::Error` in public APIs. Each `pub fn` returning `Result` has a typed error. The cost of `anyhow` here is paid by every downstream caller who loses the ability to match on specific error variants.
- For **internal/workspace libraries** (not published, only used within the same workspace by the same team): `anyhow::Error` in `pub fn` is acceptable if the team agrees, but make it a deliberate choice — once a library moves toward publication, the migration to typed errors becomes painful.
- In **binary** crates (`main.rs` and friends): `anyhow::Error` is acceptable for top-level handlers and CLI surfaces — pin ≥ 1.0.103 (RUSTSEC-2026-0190: `Error::downcast_mut` after `.context()` is unsound below it).
- `unwrap()` is allowed only when (a) it is statically impossible to fail and I have a comment explaining why, or (b) in tests. Same for `expect()`.
- `?` is fine when the conversion is meaningful; if it loses context, use `.map_err(|e| MyError::Context { source: e, info: ... })` instead.
- `panic!`, `todo!`, `unimplemented!`, `unreachable!` are noted inline (at write time) with justification, per the canonical inline-flag policy (SKILL.md → Operating mode item 7) — not enumerated in the summary; none of these four is a 🔴-tier item in its own right.

**BANNED**:
- `anyhow::Result<T>` in a `pub` API of a published library crate.
- `.unwrap()` on `Mutex::lock()` in production code (the panic message is unhelpful; use `.expect("description")` minimum, or handle the poison case).
- Silent `let _ = result;` to discard errors. If discarding is intentional, comment why.
- `Result<T, Box<dyn Error>>` (or `Result<T, Box<dyn Error + Send + Sync>>`) as the return type of any `pub fn` in a published library crate. Callers cannot match on the error variant — every error becomes an opaque blob. For libraries, define a concrete error enum (typically via `thiserror`). Binary `main` and CLI handlers are excepted (same as `anyhow` above) — there is no downstream caller to match. Internal/workspace code may use `Box<dyn Error>` or `anyhow::Error` as a deliberate trade-off.
- Reflexive `#[from]` on every error variant. `#[from] io::Error` makes every `?` on an I/O operation collapse into one variant — the resulting error can no longer say *which* operation failed (the config read? the socket write? the temp-file flush?). It compiles, tests pass, and production logs become "I/O error" with no call-site context. Use `#[from]` only where the source type already uniquely identifies the failure; otherwise carry context with `#[source]` plus an explicit `.map_err(|e| MyError::ConfigRead(e))` at each call site, or use `anyhow::Context::context` in binary code. **Carve-out — error context stops at the crypto boundary:** this "carry context, don't collapse" rule is correct everywhere *except* a decryption / MAC-verification path, where a distinguishable "bad padding" vs "MAC mismatch" vs "post-decrypt parse" error crossing a trust boundary is a padding oracle — there, collapse every failure into one opaque error. See §B24.
- `std::env::var("X").unwrap()` / `.expect(...)` — panics at startup both when the variable is *missing* and when its value is *not valid UTF-8* (common for paths on Windows / non-UTF8 locales). For values that may be non-UTF8 use `std::env::var_os`; for missing-but-optional config, handle the `Err(VarError::NotPresent)` with a default instead of panicking.
- `base.join(user_segment)` where `user_segment` may be absolute. `Path::join` with an absolute argument (`/etc/passwd`, `C:\…`, or a leading `/`) **discards `base` entirely** and returns the joined path — a path-traversal / write-to-wrong-place hazard when any segment is attacker-controlled. It compiles, tests on relative names pass, and production reads/writes outside the intended directory. The set of segments that drop (or partially drop) `base` is **broader than `is_absolute()`** and is not fully captured by `has_root()` either: on a Windows target a bare separator like `\windows` has `is_absolute() == false` yet still discards a drive-relative `base` (its first component is `Component::RootDir`), while a UNC path `\\server\share` parses as `[Component::Prefix, Component::RootDir]` (so `is_absolute()` and `has_root()` are both `true` there). The robust, OS-independent guard is to inspect the **first component** and reject a leading `Component::Prefix` **or** `Component::RootDir` (this catches `/etc/passwd`, `C:\…`, `\windows`, and `\\server\share` alike) — *not* `is_absolute()` alone. Path parsing is target-OS-specific: prefixes exist only on Windows targets. The robust recipe is a sequence, not an either/or: (1) reject a leading `Component::Prefix`/`Component::RootDir` (above) **and** any `Component::ParentDir` (`..`) in the untrusted segment; (2) join; (3) for a **static** tree (not concurrently attacker-mutable — the mutable case is the caveat below), additionally `canonicalize` and re-verify containment against the canonicalized trusted `base` — **for both the read and the write case**, because a lexical `..`/root check alone is not a containment boundary once an existing symlink can sit in a middle path component: given `base/link -> /outside`, the token-free segment `link/new_file` passes step (1), yet `base.join("link/new_file")` resolves *through* the link to `/outside/new_file` when opened. On the read case canonicalize the joined path itself; on the write case it may not fully exist (`canonicalize` errors on the not-yet-created final component), so canonicalize the **nearest existing ancestor** of the joined path instead — plus the trusted `base` itself — and verify `canonical_ancestor.starts_with(canonical_base)`; the not-yet-created tail is created inside the verified directory and cannot escape. **Threat-model caveat (CWE-367):** step (3) closes the *static* symlink case (a pre-existing link inside `base` pointing out), but it is **not race-free** against an attacker who can swap a component between the `canonicalize` and the subsequent `open` (a privileged process operating over an attacker-writable directory). State the threat model: when the directory tree is not mutable by an untrusted party during the operation, the static check is sufficient; when it is, the check + `open` is a TOCTOU, and the race-free answer is component-wise `openat` + `O_NOFOLLOW` (or Linux `openat2(RESOLVE_BENEATH)`) — in Rust, the `cap-std` crate.
- **Joining an archive entry's name onto a destination directory** — `dest.join(entry.path()?)` in a hand-rolled `tar`/`zip` extraction loop, or treating `zip`'s `mangled_name()` as already-safe — without applying the `Path::join` guard above to **every** entry. An archive is a container of *attacker-authored paths*: `../../etc/cron.d/x`, an absolute `/etc/passwd`, a Windows drive prefix or `\`-rooted name, and — the case a `..` check alone misses — a **symlink or hardlink entry extracted first**, so that a later regular-file entry writes *through* it and lands outside the destination tree (the zip-slip / tar-slip family, CWE-22). It compiles, and every test against an archive you built yourself passes. The recipe is the same sequence as the bullet above, applied per entry — reject a leading `Component::Prefix`/`Component::RootDir` and any `Component::ParentDir`, then join — plus two archive-specific rules: **refuse link entries and special files** (device nodes, FIFOs) unless you resolve them against the destination root yourself, and treat the destination as attacker-mutable whenever anything else can write there, which puts you in the `cap-std`/`openat` case rather than the `canonicalize` case. `tar::Archive::unpack` applies its own path guard — but only on a current pin: `tar` ≥ 0.4.45 fixes RUSTSEC-2026-0067 (a symlink entry followed by a same-named directory entry lets `unpack` `chmod` an arbitrary directory outside the extraction root — the same bug behind Cargo CVE-2026-33056) and RUSTSEC-2026-0068 (PAX size-header differential against other tar parsers); `zip` ≥ 2.3.0 fixes RUSTSEC-2025-0168 (a symlink entry earlier in the archive reused for later entries → arbitrary write). Verify the pinned version against these advisories; a per-entry loop you wrote has none of it. Aggregate output/entry-count quotas are the separate §B7 concern — a traversal-safe extractor can still fill the disk.
- `Command::new("sh").arg("-c").arg(format!("… {user} …"))` — or any subprocess spawned *through a shell* with untrusted data interpolated into the command string: classic **OS command injection** (RCE). The shell re-parses `;`, `|`, `$()`, backticks, `&&` in the injected value. Adjacent: **argument injection** — an untrusted value beginning with `-` is consumed as a *flag* by the target program (`--output=…`, `-o /etc/…`), changing its behavior even without a shell. It compiles, the happy path passes, and production is a remote-code-execution / arg-smuggling hole.
- Never build a shell command line from untrusted input. Spawn the program directly — `Command::new("convert").arg(user_path)` — so the OS performs no shell parsing and each `.arg()` is exactly one argv element. Insert a literal `--` argument before the first positional user-controlled value to stop it being read as a flag, and reject/validate values beginning with `-`. Allowlist the executable path; never let untrusted input choose the program. If a shell is genuinely unavoidable, escape via a vetted crate (`shell-escape`), never `format!`.
- `sqlx::query(&format!("SELECT … WHERE id = {id}"))` — or any SQL assembled by string-formatting untrusted input (`sqlx::query_as(&format!(…))`, `diesel::sql_query(format!(…))`, a hand-built `WHERE`/`ORDER BY` fragment): **SQL injection**. `QueryBuilder` is not an exemption — `QueryBuilder::push(format!(…))` and any `.push(untrusted)` of an untrusted value are BANNED on the same terms: `push()` appends a raw, unsanitized SQL fragment and never binds; only `push_bind()` binds. The interpolated value is parsed as SQL, not bound as data. It compiles, passes tests against a local DB on benign inputs, and is a data-exfiltration / data-loss hole in production. On `sqlx` ≥ 0.9 the literal `&format!` form no longer compiles — every `query*()` takes `impl SqlSafeStr`, natively implemented only for `&'static str` — and the new cheapest fix that compiles is the same injection: `sqlx::AssertSqlSafe(format!(…))` or `AssertSqlSafe(s)` (the public path is `sqlx::AssertSqlSafe`, re-exported at the crate root — not `sqlx::query::AssertSqlSafe`) where `s` is the input-derived string. `AssertSqlSafe` is the crate's explicit opt-out ("you have made sure … use at your own risk", modeled on `std::panic::AssertUnwindSafe`) and is BANNED on the same terms. `sqlx::query!` requires its SQL argument to be a compile-time string literal, so — unlike `query`/`query_as`/`sql_query` above — it cannot accept a runtime `format!`'d string at all; this hazard does not apply to it.
- Pass every untrusted value as a **bound parameter**, never as formatted SQL: `sqlx::query("SELECT … WHERE id = $1").bind(id)`, the compile-checked `sqlx::query!("… WHERE id = $1", id)`, or Diesel's typed DSL / `diesel::sql_query(...).bind(...)`. For genuinely dynamic SQL (a variable `IN`-list, an optional filter) build it with `sqlx::QueryBuilder` — but `QueryBuilder::push()` does **not** bind: it appends its argument verbatim as a raw, unsanitized SQL fragment, so reserve `push()` for static or explicitly allowlisted SQL syntax and pass **every** untrusted value through `push_bind()`, never `push()` (the BANNED bullet above names the banned shapes). A column or table name that must be dynamic cannot be a bound parameter — **allowlist** it against a fixed set, never interpolate it raw. On `sqlx` ≥ 0.9 the `SqlSafeStr` bound enforces this bullet: only `&'static str` passes without an explicit `AssertSqlSafe` assertion.
- `reqwest::get(&user_url).await?` — or `client.get(user_url)` / any outbound request whose destination is attacker-influenced (webhook, callback URL, link preview, image proxy, "fetch this URL", "validate this URL") — without a destination policy: **SSRF** (CWE-918). The attacker supplies `http://169.254.169.254/latest/meta-data/…` (cloud metadata), `http://127.0.0.1:2375/` (local daemon API), or an internal-only host, and your service makes the request for them. The reflex fix — parse the URL and reject private/loopback hosts — validates only the *original* URL: reqwest's default redirect policy **follows up to 10 hops**, so a public host can answer `302 Location: http://169.254.169.254/…` and the request lands on the forbidden destination anyway. DNS rebinding is the same bypass one layer down: the hostname you validated resolves to the public IP for your check and to `127.0.0.1` for the actual connection. It compiles, and tests against a local stub are green.
- For a user-supplied outbound destination: a fixed **allowlist** of host/scheme/port validated at save time *and* re-checked at use time, or `ClientBuilder::redirect(reqwest::redirect::Policy::none())` when redirects are not part of the contract. Where redirects must be followed, use `redirect::Policy::custom` that re-runs the same destination check on **every** hop (inspect `attempt.url()`, not the original URL), **and** resolve the hostname yourself, validate the resolved IP, and pin it via `ClientBuilder::resolve`/`resolve_to_addrs` so the connection cannot be rebound after validation. An egress proxy with its own destination policy is the architectural form of the same control. Tests must include the redirect case — a first host that 302s to a forbidden destination (a polite local stub that never redirects proves nothing, §D1a).
- Issuing a session cookie without its security attributes: `Cookie::new("session", id)` (or a `CookieBuilder` that stops at name + value) leaves `http_only`, `secure`, and `same_site` all **unset** — the cookie is readable from page JavaScript (an XSS converts a leaked session into an account takeover) and is sent over plain HTTP. Compiles, and tests that assert only the cookie's value pass. REQUIRED: `.http_only(true).secure(true).same_site(SameSite::Lax /* or Strict */)` on every session/auth cookie — or a framework session layer that defaults these on — and assert the *attributes*, not just the value, in tests.
- Check-then-create on the filesystem: `if !path.exists() { fs::create_dir_all(path)?; }` / `if !p.exists() { File::create(p)?; }`. `exists()` returns `false` on *any* stat error — including `EACCES` on a parent directory or a broken symlink (std's own docs warn about exactly this) — so the "then" branch runs on paths that do exist, and even a correct answer races: exists-then-create is a TOCTOU (the §C2 path-join bullet's sibling). REQUIRED: `path.try_exists()` when only existence matters (it distinguishes "does not exist" from "could not tell"); `OpenOptions` `.create_new(true)` (or `fs::create_dir`) with the `AlreadyExists` error handled — the failure becomes a value instead of a double-create.

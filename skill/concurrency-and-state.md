## §A2. Smart pointer misuse (reflexive `Arc<Mutex<T>>`)

**The trap**: this is Tier A because the LLM reaches for `Arc<Mutex<T>>` *in response to a compile error* — "needs to be Send, needs to be shared, needs interior mutability" — and the resulting code compiles, runs, and passes tests. The defect that survives is **structural**, not functional: gratuitous lock contention, wrong concurrency model, false sense that a critical section exists, refactor cost when the read/write ratio later argues for `Arc<RwLock<T>>`, `arc-swap`, or `Arc::make_mut`-style copy-on-write. The reverse trap — `Rc<RefCell<T>>` chosen for "local mutability" and later forced across threads — is the same shape: the original compile-time fix locked in a structural choice that the rest of the program then has to bend around.

**REQUIRED**:
- `Arc` only when ownership is genuinely shared across threads or async tasks. Single-owner sharing → `&` or `&mut`.
- `Mutex` only when interior mutability is actually needed. Read-only shared data → `Arc<T>` is enough.
- For shared data that is **mostly read, occasionally swapped wholesale**, prefer `arc_swap::ArcSwap<T>` or rebuild-then-`Arc::new`-and-swap, not `RwLock`.
- For **copy-on-write semantics on a single-owner-most-of-the-time `Arc`**, use `Arc::make_mut(&mut arc) -> &mut T` (clones the inner only if `strong_count > 1`; if the `Arc` is unique but live `Weak`s exist, they are **dissociated** — `upgrade()` then returns `None` — and no clone happens: fine for COW, surprising for a `Weak` observer). Mirror: `Rc::make_mut` for the non-thread-shared analog. For `Cow<'_, T>` semantics on borrow-or-own returns, prefer `std::borrow::Cow`.
- `Rc`/`RefCell` that cross an `.await` reachable from a *multi-threaded* executor (`tokio::spawn` on the default runtime) are wrong — but the compiler already rejects them (`!Send`, an `E0277` outside this spec's scope). They stay perfectly legitimate in single-threaded-by-contract async (`tokio::task::spawn_local` / `LocalSet`) and in ordinary synchronous single-threaded code (parsers, AST/IR builders, local graphs) — do not flag those. The real rule: if the data must move across threads, use `Arc` + a lock from `tokio::sync` or `std::sync` per §B2; if unsure of the threading model, default to `Arc`.
- Boxing a small `Sized` scalar (≤ 2 × pointer size) *for the sake of boxing* is a smell — don't box `i64`, `Option<u32>`, or a small enum just to add a heap indirection. Legitimate reasons to box even a small `T` exist and are not the target of this rule: breaking a recursive type (`struct Node { next: Option<Box<Node>> }`), pinning a value to a stable heap address (`Pin<Box<T>>`, self-referential futures), or erasing behind `Box<dyn Trait>`. Box deliberately, not reflexively.

**BANNED**:
- `Arc<Mutex<T>>` where `T` is only ever read after construction. Use `Arc<T>` (or `ArcSwap<T>` if it must change).
- `Arc<RwLock<T>>` for write-heavy workloads. Profile first; `Mutex` is often faster.
- Cloning the inner `T` via `(*arc).clone()` when `Arc::make_mut` would be both cheaper (on the unique-owner path) and clearer.
- `Box::leak(Box::new(...))` to obtain a `&'static` for a global. It is an intentional, unrecoverable leak that grows on every re-init path (config hot-reload, repeated bootstrap, per-test setup). Use `OnceLock` / `LazyLock` (stable ≥ 1.80) for lazily-initialized globals.
- A `LazyLock::new(|| …)` init closure that can panic (reads env/file/network and `.unwrap()`s) **poisons the cell unrecoverably**: every later access panics (`LazyLock instance has previously been poisoned`), not just the first. Don't panic in lazy init — validate fallibly before, or store a `Result` and handle it at each access.
- A panicking `OnceLock::get_or_init` closure is different: the panic propagates to that caller and the cell stays **uninitialized**, so the next `get_or_init` call retries the initializer (a bare `get()` never invokes the initializer — it only observes the cell is still empty and returns `None`). That is its own hazard — a flaky initializer (intermittent file/env/network failure) re-runs on every `get_or_init` call until it happens to succeed — but it also means a `OnceLock` init can be made robust by retry, which a poisoned `LazyLock` cannot.
- `RefCell<T>` for a `Copy` (or replace-whole) interior where `Cell<T>` would do. `Cell` has no runtime borrow flag and so cannot trigger the §B17 `BorrowMutError` panic; reach for `RefCell` only when you need `&`/`&mut` into the interior.

## §B9. Lock ordering and ABBA deadlock

**The trap**: two locks (`Mutex<A>`, `Mutex<B>`) acquired in opposite orders in different code paths. Function `f1` locks A then B; function `f2` locks B then A. Single-threaded tests pass trivially. Multi-threaded production hits the classic deadlock: thread 1 holds A waiting for B, thread 2 holds B waiting for A, both wait forever.

**Why this happens**: LLMs treat lock acquisition as a local concern. The deadlock is a global property of the program's lock graph, invisible from any single function. No lint detects it.

**Prompt triggers**: "synchronize access to two shared resources", "lock the cache and the queue", "update state and metrics atomically", anything involving two `Arc<Mutex<_>>` in the same operation.

**REQUIRED**:
- For any code path that acquires more than one lock, **document the lock acquisition order** as a doc comment at the top of the module or function. State it in a comment LLM-readable enough that future generations of this file maintain it.
- Use a consistent lock ordering across the entire crate. Common conventions: alphabetical by name, by declaration order in the struct, by a numeric rank field.
- Prefer fine-grained immutable data + message passing (`mpsc`, `oneshot`) over multi-lock critical sections when possible.
- When two locks must be held, take them **in the documented order, every time, without exception**.
- For async code, pick the mutex by the **guard-crosses-`.await`-or-not test**, not a blanket default: when the critical section is short, synchronous, data-only and the guard is dropped before every `.await`, a plain `std::sync::Mutex` is the right choice — Tokio's own documentation: it is "ok and often preferred to use the ordinary `Mutex` from the standard library in asynchronous code", and "the blocking mutex should be preferred in the cases where it can be used"; `tokio::sync::Mutex` exists for the case where the lock genuinely must be **held across an `.await` point** (e.g. guarding an IO-resource handle) and costs more for it (§B2 owns the hold-across-`.await` hazard). Deadlock *detection* is not automatic with either choice: `tokio-console` provides **visibility** (you can see which task holds which lock and which is waiting), not detection. Detection of cycles must be wired explicitly — `parking_lot::deadlock::check_deadlock()` for sync sections (requires the `deadlock_detection` cargo feature on `parking_lot`; the module does not exist without it), periodic graph audit of the documented lock-acquisition order for async sections. Neither mutex flavor gives a deadlock signal on its own.
- A `Condvar` wait that can wake to a still-false predicate: `if !ready { guard = cv.wait(guard).unwrap(); }` returns from `wait` on a **spurious wakeup** (documented std behavior — `wait` can return with the predicate still false even with no notification at all) with `ready == false`. This is the only reason the loop form is required — under correct (same-mutex) notifier discipline there is no lost-notification window: `Condvar::wait` atomically unlocks the mutex and begins waiting as one operation, so a notifier holding that same mutex while mutating the predicate and calling notify cannot slip a notification into the gap between "check predicate under the lock" and "start waiting". Loop instead: `while !ready { guard = cv.wait(guard).unwrap(); }`, or use the structured form `let guard = cv.wait_while(guard, |s| !s.ready).unwrap();`.

**BANNED**:
- Holding two locks across a function call (the called function may acquire locks in another order).
- Acquiring a second lock while holding the first if the second one's acquisition can block on async work or I/O.
- "Just try locking" patterns with `try_lock` to escape suspected deadlocks — that hides the design problem. This bans the *reflex*, not the technique: `try_lock` + backoff with a documented retry policy is a legitimate hierarchical-locking / backoff design; what is banned is reflexive `try_lock` as an escape from a deadlock you have not actually diagnosed.
- **`std::thread::scope` (stable 1.63) — sync mirror of §B21**: where `tokio::spawn` *detaches* the work and loses it (§B21), `scope` *force-joins* every child thread on the closing brace. Two silent consequences. (a) A child waiting for a resource the parent only releases *after* the scope deadlocks the closing brace — a non-lock deadlock, invisible to §B9 lock-graph analysis. (b) A panic in a child **re-panics in the parent** when `scope` returns (after auto-joining all un-joined handles — at the closing brace, not in the `Scope` struct's `Drop`), but as a **new panic with a generic message** (`a scoped thread panicked`) — the child's original panic payload is **not** forwarded, so catching the re-panic tells you *that* a child died, not why; `.join()` each `ScopedJoinHandle` individually if you need the actual payload. The re-panic skips any cleanup the parent intended between the spawn site and the closing brace — RAII discipline must therefore not assume "the parent code after the scope runs". REQUIRED: guarantee that children are reachable to completion before the closing brace (close the channel, drop the sender, signal cancellation — *before* the scope ends, not after); handle child panics explicitly (`JoinHandle::join` on each `ScopedJoinHandle` and inspect the `Result`) when cleanup must run regardless. 🟡.

**Detection**: add `tokio-console` for runtime visibility, or `parking_lot::deadlock` detection in dev builds (gated behind `parking_lot`'s `deadlock_detection` feature). Note each double-lock site inline (at write time).

## §B10. Reference cycles in `Rc`/`Arc` graphs

**The trap**: when LLMs build graph or tree structures with parent-child relationships, they reach for `Rc<RefCell<Node>>` (or `Arc<Mutex<Node>>`) and create *both* parent→child and child→parent strong references. This creates a reference cycle. Rust has no garbage collector. Memory leaks. Tests pass because functionality (insert, traverse, lookup) works correctly. Memory is never reclaimed; as the structure grows, RSS climbs steadily — an OOM in production rather than at test time.

**Why this happens**: LLM training corpus has plenty of "graph in Rust" examples, but the `Weak` pattern is underrepresented. The model defaults to symmetric strong references.

**Prompt triggers**: "build a tree with parent links", "graph data structure", "linked list with previous pointer", "DOM-like structure", "scene graph", any bidirectional ownership.

**BANNED**:
- `Rc<RefCell<T>>` or `Arc<Mutex<T>>` on both sides of a bidirectional reference.
- "Parent owns children, children own parent" patterns.

**REQUIRED**:
- One direction is `Rc<T>` (or `Arc<T>`), the other is `Weak<T>`. Convention: parent owns children with `Rc`, children point to parent with `Weak`.
- For any graph structure with cycles, prefer arena-style storage: `Vec<Node>` + `NodeId(usize)` indices. No reference cycles possible, no `RefCell` overhead, better cache locality. Crates: `slotmap`, `id-arena`, `petgraph`.
- When `Weak::upgrade()` returns `None`, treat it as a normal case (parent has been dropped), not an error.

**Detection**: profile with `heaptrack` or `valgrind --tool=massif` for steady-state memory growth. In dev builds, periodically print `Rc::strong_count(&node)` for representative nodes.

## §B13. Check-then-act races in concurrent collections (TOCTOU)

**The trap**: LLMs port single-threaded patterns from Python/JS/Java into multi-threaded Rust. The canonical example is the "lazy cache":

```rust
// BANNED — race between contains_key and insert
if !cache.contains_key(&key) {
    let value = expensive_fetch(&key).await;
    cache.insert(key, value);
}
```

In a single-threaded test, this is correct. Under concurrent load, N threads simultaneously see "key is absent", N threads simultaneously call `expensive_fetch`, and only one write actually wins. The cache works *functionally* — every lookup returns a value — but the "expensive" function is called N times when it should have been called once. Variants of this pattern fail similarly: read-modify-write on a counter, "if absent insert default else update", lazy initialization with `bool` flag.

**Why this happens**: in single-threaded languages, check-then-act is sound. The model has a strong prior on it. The Time-of-Check-to-Time-of-Use (TOCTOU) gap is invisible from a single function's perspective.

**Prompt triggers**: "cache", "memoize", "lazy initialization", "ensure exactly one X", "deduplicate", "if not exists, create".

**BANNED**:
- `if !map.contains_key(k) { map.insert(k, v); }` and any variation where check and act are separate calls — **scoped to genuinely concurrent maps**: a map behind a shared lock, a concurrent map type (`DashMap`), or code that re-acquires **separate lock guards** between the check and the act. A plain owned `HashMap` reached only through `&mut self` is not this defect — the borrow checker statically rules out concurrent access, so there is no TOCTOU to guard against; for such a map, `.entry()` is an efficiency and intent-clarity recommendation (one hash lookup instead of two), not a race fix. The same pattern via `HashMap::iter` + `HashMap::insert` on a concurrent map is equally broken.
- `if map.contains_key(k) { let v = map.get(k).unwrap(); ... }` — between the check and the get, another thread could remove the entry, and `.unwrap()` panics.
- "Two-phase commit"-style patterns across separate operations on a concurrent collection.
- `let x = *counter.lock().unwrap(); *counter.lock().unwrap() = x + 1;` — read and write are separate critical sections, a thread can interleave.
- `if Arc::strong_count(&arc) == 1 { ... unique-owner logic ... }` — count can change between read and use under any concurrent code. Use `Arc::into_inner(arc)` (returns `Option<T>` if unique) or `Arc::try_unwrap(arc)` (returns `Result<T, Arc<T>>`); the atomic variant is the only check-and-act pattern that's race-free. Prefer `into_inner` over `try_unwrap(...).ok()` — discarding the `Err` arm reintroduces a drop-race on the last reference (std documents this); `into_inner` guarantees exactly one caller observes `Some`.
- `Ordering::Relaxed` on an atomic used to *publish* data to another thread (e.g. write the payload, then `flag.store(true, Relaxed)`; the reader does `flag.load(Relaxed)` then reads the payload). `Relaxed` establishes **no happens-before** edge, so the reader may observe the flag set before the payload writes are visible — a data race that x86's strong memory model usually hides in tests but that breaks on ARM/AArch64 under reordering. Use `Release` on the store and `Acquire` on the load (or `AcqRel`/`SeqCst` for read-modify-write) whenever the atomic guards access to other data. (The un-atomic extreme of the same race — a `static mut` incremented from several threads — is §B18's `static mut` bullet in `unsafe-and-ffi.md`.)
- **The database twin of the lazy-cache above: a `SELECT` whose result guards a later `UPDATE`/`INSERT` on the same row.** `SELECT balance` → check in Rust → `UPDATE … SET balance = $new` is a read-modify-write across two statements: two concurrent transactions both read 100, both write 20, and the lost update is silent — no error, lock, or test failure (tests are single-threaded). Wrapping the pair in `pool.begin()` **does not fix it**: at the default `READ COMMITTED` isolation (PostgreSQL/sqlx) the second transaction still reads the first's pre-update value between its statements — "a transaction" is not the same as "atomic with respect to my own read". Same family: select-then-insert racing a "unique" creation, and a raw `sqlx::query("BEGIN").execute(&pool)` … `query("COMMIT").execute(&pool)` pair — each `execute` checks out whichever pooled connection is free, so the statements **may** run on different connections (there is no guaranteed identity between them) and the "transaction" spans nothing; PostgreSQL answers the orphan `COMMIT` with a warning, not an error, so it silently commits nothing (§B4). Language-agnostic shape, same single-threaded prior as every bullet in this section.

**REQUIRED**:
- For synchronous "insert if absent": `map.entry(key).or_insert_with(|| compute_value())` (synchronous only — see §B2: never hold this guard across `.await`). On a plain `std::collections::HashMap` the atomicity comes from the `&mut self` borrow (it is single-threaded — there is no internal lock); on a concurrent `dashmap::DashMap`, `entry` holds the shard lock across check and act. Either way the check and the act are one operation, not two.
- For an **async** compute that must run exactly once under concurrent load (the lazy-cache example this category opens with), `or_insert_with` cannot help — its closure is synchronous and cannot `.await`. Store a once-cell per key: `let slot = map.entry(key).or_insert_with(|| Arc::new(tokio::sync::OnceCell::new())).clone();` then `slot.get_or_init(|| async { expensive_fetch().await }).await`. State the guarantee precisely: this is **one active initializer at a time and one successfully-stored result**, not "runs exactly once ever" — if the task driving `get_or_init` is cancelled mid-initializer (its future dropped at an `.await`) or the initializer panics, tokio's `OnceCell` cancels the attempt and **lets another waiting caller run the initializer again** (documented verbatim: "If the provided operation is cancelled or panics, the initialization attempt is cancelled. If there are other tasks waiting for the value to be initialized, one of them will start another attempt at initializing the value."), so any external side effect performed before the cancellation/panic can fire twice even though the cell only ever stores one result. `tokio::spawn` + `JoinHandle::await` does **not** close this gap: it only prevents the effect from being silently half-done if the *outer* task is cancelled mid-await (the spawned task keeps running to completion, detached, once started). It does **not** prevent `OnceCell`'s own cancel-and-retry semantics from letting a second, independent attempt run — if `get_or_init`'s own future is dropped (the outer caller cancelled), the cell lets another waiting caller start a fresh attempt (a fresh `tokio::spawn` + await) while the *first* spawned task, never aborted, keeps running the same side effect in the background: the effect can fire from both attempts, spawn+await notwithstanding. True attempt-level exactly-once semantics still requires either an **idempotent** initializer, or a separately-synchronized **durable in-flight/result state shared by all waiters** (e.g. a state row with a status column, or a distributed lock) — spawn+await alone is insufficient and must not be presented as sufficient. **But** this map itself is insert-only: if `key` has unbounded or attacker-influenced cardinality, the map of `OnceCell`s grows forever (an unbounded cache — see §B14's insert-only-keyed-collection bullet) even though each cell is correct. Bound it (LRU/TTL/cap) or state why the key space is closed.
- For `DashMap`: `dashmap::DashMap::entry(key).or_insert_with(...)`.
- For atomic counters where wrapping on overflow is acceptable (statistics, sampled counts, non-critical tallies): `AtomicUsize::fetch_add(1, Ordering::Relaxed)`, not lock-load-add-store. `fetch_add` **always wraps** on overflow — atomics have no debug-mode overflow check the way plain integer `+=` does, so this never panics, it silently rolls over. For an invariant-bearing counter that must never silently wrap (a monotonic ID generator, a sequence number), unconditional `fetch_add` is the wrong tool: use `fetch_update` with a `checked_add` inside the closure (overflow becomes a real `Err`, not a wrap) or widen the type (`AtomicU64` instead of `AtomicU32`) so the overflow horizon is unreachable in practice. Pair every `fetch_add`/`fetch_sub` inc/dec so the decrement cannot be skipped on an early-return path — a `fetch_sub` that runs on a path that never incremented wraps to `usize::MAX` (in release *and* debug); guard it with an RAII drop guard that runs the `fetch_sub`, not a bare call at the end of the function; §B26's gauge-underflow bullet owns the fix shapes.
- For "compare and swap" patterns: `Atomic*::compare_exchange` or `Atomic*::fetch_update`.
- For ordered iteration of map keys, use `BTreeMap` (sorted by key) or collect to `Vec` and `sort_by`. `HashMap::iter` order is randomized per-process and per-rehash; relying on it makes tests flake across machines.
- `Relaxed` is correct only for standalone counters/statistics where no other memory is published through the atomic. The moment the atomic gates visibility of other data, you need `Acquire`/`Release`. Don't blanket-`SeqCst` to "be safe" — it hides the wrong mental model and costs a fence; reason about the happens-before edge explicitly, and model-check multi-atomic code with `loom` (already in the post-flight list).
- For a guarded row update, push the predicate **into one atomic SQL statement** and act on the result: `UPDATE accounts SET balance = balance - $1 WHERE id = $2 AND balance >= $1`, then check `rows_affected() == 1` (0 = the guard failed) instead of selecting first. For multi-statement read-modify-write: `SELECT … FOR UPDATE` inside a `pool.begin()` transaction, routing **every** statement of that transaction through the returned `Transaction` handle (`tx`, or `&mut *tx` as the executor) — never the `Pool`; or optimistic concurrency (a `version` column: `UPDATE … WHERE id = $1 AND version = $v`, retry the whole read-modify-write when 0 rows are affected). For create-if-absent: `INSERT … ON CONFLICT DO NOTHING` / `DO UPDATE` instead of select-then-insert. When several statements must see one consistent snapshot, `SERIALIZABLE` isolation (`SET TRANSACTION ISOLATION LEVEL SERIALIZABLE` or the session/pool default) with a retry on SQLSTATE `40001` (serialization failure) — and note that `READ COMMITTED`, the default, does **not** close the read-modify-write race above. Transaction-handle Drop/commit discipline is §B4.

**Detection**: this is invisible to type checking and almost always invisible to tests. The defense is recognizing the pattern at write time. (Enforcement: the TOCTOU patterns here are 🟡 — recognized and fixed at write time; only the `Relaxed`-publish data race is 🔴 surface-always.) If a function does two consecutive operations on a shared collection, it is a candidate.

## §B14. Unbounded channels and backpressure neglect

**The trap**: when the producer/consumer rate is unbalanced, an `mpsc::unbounded_channel` doesn't block the producer — it just lets the queue grow. Tests with 5–100 messages pass. Production with a producer that's 2× faster than the consumer accumulates millions of pending messages, RAM climbs steadily, and the OOM killer eventually terminates the process — usually under peak load when it hurts most.

**Why this happens**: bounded channels force the producer to handle "channel is full" via `try_send`/`send` errors; `unbounded` has the simpler API and is the LLM's path of least resistance — the §C5 reflexive-fix pattern applied to channel selection.

**Prompt triggers**: "send events to a worker", "background queue", "log messages to a task", "producer-consumer", "event bus", "websocket broadcast", "metrics pipeline".

**BANNED** in any non-trivial pipeline:
- `tokio::sync::mpsc::unbounded_channel()` without explicit justification. A "bounded producer rate" is **not** sufficient: any *sustained* positive gap between producer rate and consumer service rate grows the queue without bound over time, no matter how politely the producer paces itself. A valid justification is one of: (a) a proven **finite total** bound on messages ever produced (e.g. a fan-out over a closed, fixed worklist), or (b) a proved **finite backlog envelope** — a bounded rate gap × a guaranteed time-to-drain (the consumer provably catches up within a stated deadline).
- `flume::unbounded()`, `async_channel::unbounded()` for the same reason.
- A `Vec` that is `push`-ed in a hot loop with no consumer or cap — same failure shape as an unbounded channel, different surface. `Vec::push` itself is fine (amortized O(1)); the failure is the missing drain or bound.
- Treating `tokio::sync::broadcast::error::RecvError::Lagged(n)` as a transient error to retry past. `Lagged(n)` means the receiver fell more than the channel's capacity behind the sender and **`n` messages are gone forever** — the receiver has already skipped to the oldest still-buffered message. A `match { Err(Lagged(_)) => continue, ... }` loop recovers nothing and silently masks data loss as a hiccup. On `Lagged`, log/metric the skipped count and decide explicitly whether dropping is acceptable or the consumer must be made faster / the buffer larger.
- `FuturesUnordered` (or `JoinSet`) grown by unbounded `.push()` with no cap — the same unbounded-growth hazard as an unbounded channel, just wearing a different type. Separately: an **empty** `FuturesUnordered` polled in a `select!` arm returns `Poll::Ready(None)` immediately, so a `loop { select! { x = futs.next() => ... } }` busy-spins at 100% CPU when `futs` is empty. Guard with `if !futs.is_empty()` or a fallback arm.
- A long synchronous step inside a `FuturesUnordered` / `buffer_unordered` loop body *buries* the sibling futures in the set — they are polled only when the set is polled, so external timeouts can fire spuriously and futures awaiting a shared semaphore inside the set can self-deadlock (holding permits while a queued item waits for one). Keep work that runs between polls short.
- **Unbounded admission — the count of tasks/sockets is itself the unbounded resource** (🔴 when the accept/ingest source is untrusted-peer-extendable, 🟡 otherwise). An accept/ingest loop that spawns one task per item with no concurrency cap — `loop { let (stream, _) = listener.accept().await?; tokio::spawn(handle(stream)); }` — grows *nothing that the bullets above name*: no channel, no `Vec`, no `FuturesUnordered`. The unbounded resource is the task/socket/buffer *count*, and the attacker sets it — N connections → N tasks → N buffers → N FDs → OOM or FD exhaustion (CWE-770). A `// fire-and-forget: detached by design` comment satisfies §B21 and still admits unboundedly. REQUIRED: gate admission with an `Arc<Semaphore>` — `let permit = sem.clone().acquire_owned().await?;` **before** `tokio::spawn`, and **move the permit into the spawned task** (`tokio::spawn(async move { let _permit = permit; handle(stream).await; })`) so a slot is freed only when the task actually finishes. Two LLM-typical wrong "fixes" that cap nothing: (a) acquiring the permit *inside* the spawned task — the tasks are still spawned unboundedly, only the work inside them is throttled, so N tasks and N buffers still exist; (b) acquiring the permit in the accept loop but *not moving it into the task* — the guard drops at the end of the loop iteration, before the task runs, releasing the slot immediately. Calibration: this targets a public-facing / attacker-reachable accept loop; an internal fan-out (`for item in known_bounded_worklist { tokio::spawn(...) }`) over a statically-bounded worklist needs no cap — say so in a comment. Cross: §B21 (the dropped-handle dimension), §F3 (per-connection lifecycle).
- **Accept-error handling — classify, don't `?` and don't hot-loop** (🟡). The sibling of the admission cap: even with a `Semaphore` in place, `accept()` can fail for reasons the cap does not prevent (other FDs, other processes, transient network errors). `let (stream, _) = listener.accept().await?;` propagates a *single* `EMFILE`/`ENFILE`/`ECONNABORTED` and **kills the whole accept loop forever** — the server stops accepting on the first hiccup. The naive "fix" `Err(e) => { warn!(%e); continue; }` **busy-spins at 100% CPU** on `EMFILE`: the listener stays ready (the FD limit is not cleared by ignoring it) and the kernel keeps completing handshakes into the backlog, so the loop re-arms instantly. This is *not* §B3a's case: an accept loop must **not** "release leadership and return" on a transient error (that would stop serving), and must **not** hot-retry either. REQUIRED: `match` on the error and classify — *fatal* (the listener itself is gone / `ErrorKind` indicates a broken listening socket → stop and propagate) vs *transient-with-backoff* (`EMFILE`/`ENFILE`/`ECONNABORTED`-class → log, `tokio::time::sleep` a brief backoff so you don't hot-loop while resources recover, then continue). tokio's `TcpListener`/`UnixListener` docs note that "not all [accept] errors are necessarily fatal" — but don't spell out this match-don't-`?`/backoff pattern; the classification and backoff design here is this section's own guidance, not a documented tokio recipe.
- **Insert-only keyed collection with no eviction is an unbounded cache/registry** (🔴 when the key space is attacker-extendable — per-IP/per-header/per-path keys — 🟡 otherwise). `CACHE.insert(key, v)` with no eviction, TTL, or cap, where the key derives from request path/header/IP, grows forever: each entry is small and honestly sized (so §B7 does not apply) and the map *has* a consumer (constant reads hit it — so the "`Vec` with no consumer" bullet above does not match). The defect is **no eviction** — entries are immortal, not unread. Same shape wearing other names: per-IP rate-limiter maps, session registries, dedup "have we seen X" sets, high-cardinality metrics-label maps, and the §B13 per-key `OnceCell` map. BANNED: an insert-only keyed collection (`HashMap`/`DashMap`/`BTreeMap`) with unbounded or attacker-influenced key cardinality and no stated bound. REQUIRED: a *stated bound* — an LRU/TTL/capacity policy via `lru` (pin ≥ 0.18.2: RUSTSEC-2026-0002 unsound `IterMut`; RUSTSEC-2026-0253 panic-in-`Drop` use-after-free — see §C12's cache-eviction row) or `moka` (mainstream Rust cache crates), or a written argument (in a comment) that the key cardinality is bounded by an internal invariant (e.g. keyed by a closed enum, or by a fixed set of worker IDs). CWE-770/400. Cross: §B10 (this leaks with zero `Rc`/`Arc` cycles), §B13 (the race in filling it).
- **A `reqwest::Client` (or a `rustls::ClientConfig`, an `sqlx` pool, a cloud-SDK client) constructed per request inside a handler** — each construction carries its own connection pool + TLS config, so N concurrent requests means N independent pools: file descriptors and ephemeral ports climb until exhaustion (`EADDRNOTAVAIL`, sockets stuck in `TIME_WAIT`). Correctness at scale, not just cost. REQUIRED: build once (`LazyLock<reqwest::Client>` or application state) and share by clone — `Client` is an `Arc` internally, so clones share one pool.

**REQUIRED**:
- Default to **bounded** channels: `tokio::sync::mpsc::channel(N)`. Size `N` from the actual constraints, not from a folk number: large enough to absorb the *expected producer burst over one consumer cycle*, small enough that `N ×` the **worst-case retained bytes per message** fits the per-task memory budget — where retained bytes include everything a queued message transitively owns (a `Vec<u8>`/`String` payload, an open file/socket, a pooled DB connection), not just `size_of::<Message>()` of the stack-resident struct, which massively undercounts when messages carry heap buffers or external resources. Add the queue's own reservation/overhead on top. If the right `N` cannot be reasoned about, that is a signal that the backpressure policy itself needs design before the channel is written. Never `unbounded`.
- Decide the **backpressure policy** explicitly: block the producer (default `send().await`), drop newest (`try_send` returning `Err(Full(msg))` — the message that failed to send is returned in the error; log and discard it), or apply rate limiting upstream. **Drop oldest cannot be built on `try_send`**: on a full channel, `try_send(new)` leaves the already-queued value untouched in the channel and fails with the *newest* message in the `Err` — discarding that payload is drop-newest, never drop-oldest. True drop-oldest requires a receiver-owned eviction/coalescing design (e.g. popping the front of a bounded `VecDeque`/ring buffer) or a channel type that natively supports evicting its own head — `try_send` alone cannot implement it. State the choice in a comment.
- For broadcast scenarios where slow consumers shouldn't slow producers: `tokio::sync::broadcast::channel(N)` with explicit handling of `RecvError::Lagged` (which indicates dropped messages).
- For any unbounded queue that *must* exist (e.g., legacy interop): expose its size as a metric and alert when it grows abnormally.

**Detection**: unbounded channel growth doesn't appear in tests. Defense is at write time (default to bounded) and via monitoring. `Sender::capacity()` — remaining permits, decrementing per send and restoring per receive — exists only on a *bounded* `Sender`; `UnboundedSender` has no `capacity()` at all. For the unbounded queue that must exist, track the receiver's queued-message count (`Receiver::len()`) as the metric; on a bounded channel, `Sender::capacity()` plus queue length is the right pair.

## §B17. `RefCell` / `Mutex` runtime borrow panics

§A2 covers the thread-safety dimension of choosing smart pointers; this category covers the **single-threaded** reentrant-borrow hazard that `Rc<RefCell<T>>` introduces even when threading is not involved.

**The trap**: `RefCell` enforces borrow rules at runtime via panics. The borrow check is dynamic, not static — and the LLM writes call patterns that *can* reach a second `borrow_mut()` while the first is still live, but the test inputs never exercise the path. Compiles; passes tests at low fanout; panics in production the moment a callback chain or trait dispatch reenters the cell. The async-runtime mirror: `tokio::sync::Mutex` does not panic on reentrance, it *deadlocks* — the second `.lock().await` waits forever for the first guard, which is held by the same task.

**BANNED**:
- `Rc<RefCell<T>>` or `Arc<RefCell<T>>` for shared mutable state accessed through nested callbacks, closures, or trait-object dispatch where the call graph is not statically obvious. (`Arc<RefCell<T>>` is `!Send` + `!Sync`, so it does not compile *when sent across threads* — it is perfectly fine in single-threaded code; but `Arc<Mutex<T>>` with the same access pattern has the same logical defect, just expressed as a deadlock instead of a panic.)
- `cell.borrow_mut()` inside a scope that later calls into code (closure, trait method, observer notification, callback registration) that can re-enter the same `RefCell`. Even if the test path doesn't exercise the reentrance, the structural risk is there.
- Holding a `tokio::sync::MutexGuard` across an `.await` that ends up calling back into the same `Mutex` — guaranteed deadlock.
- **Re-acquiring a read on an `RwLock` you may already hold a read on, through a non-obvious call graph — the third reentrance flavor** (🟡). `RefCell` reentrance panics and `tokio::sync::Mutex` reentrance deadlocks (above); `RwLock` reentrant *reads* deadlock **on a writer's schedule you don't control**. `std::sync::RwLock`'s priority policy is *unspecified* — "dependent on the underlying operating system's implementation" (std docs warn about exactly this) — so on a writer-preferring OS: thread A holds a read guard, calls a helper that does a second `.read()` through some call chain, while thread B is meanwhile blocked on `.write()`; A's second read queues *behind* the pending write and A deadlocks with itself. Passes on a reader-preferring dev machine, hangs on a writer-preferring prod OS. `tokio::sync::RwLock` removes the platform-dependence but not the hazard — it is *documented write-preferring*, so read → (another task requests write) → same task reads again **always** deadlocks. This is not §B9 (that is two-lock ABBA ordering; this needs only *one* lock) and not §B2 (no `.await` required for the std flavor). BANNED: acquiring a second read on a lock you may already hold a read on, reached through any call graph (helper, trait method, callback) where a concurrent writer can wait between the two reads. REQUIRED: document read-reentrance-freedom the way this section already asks for borrow-disjointness — "no method reachable while a read guard is live re-reads this lock"; restructure so the guard is dropped before the reentrant call, or pass the already-read data down instead of re-reading. This bans undisciplined reentrant reads through a hidden call graph, **not** `RwLock` itself.

**REQUIRED**:
- For sync interior mutability accessed in tree traversal, observer notification, or callback chains, use `try_borrow_mut()` and handle `BorrowMutError` instead of unconditional `borrow_mut()`. The error path becomes a real recovery path, not a panic.
- Document the borrow-disjointness invariant at the *type* level: newtype with private field, public methods that guarantee non-overlapping borrows by construction. The invariant becomes a comment on the newtype, not a hope.
- For `tokio::sync::Mutex`, document a lock-acquisition order per §B9 — including "no method on this type calls back into self via another lock acquisition".
- **`std::sync::Mutex` poisoning is a diagnostic signal, never a soundness guarantee to build correctness on.** A poisoned lock means **something else already panicked while holding this guard** — the guarded data may be in a broken state, which is why std fails subsequent `lock()`/`try_lock()` calls with `PoisonError` until told otherwise. REQUIRED: pick and state the policy explicitly — *propagate* (let `PoisonError` travel up; `PoisonError::into_inner()` yields the guard when the caller legitimately judges the data readable anyway) vs *validated repair + reset*: prove the guarded data is actually consistent (the panic happened before any mutation, or a known-good value is restored — std's own example does `**e.get_mut() = known_good;`), then clear the flag with `std::sync::Mutex::clear_poison()` (stable 1.77) and continue. Poisoning is advisory — std's docs themselves warn that "even unpoisoned mutexes need to be handled with care" and that `unsafe` code "cannot rely on poisoning for soundness" — so never treat a clean lock as proof the invariants hold (`parking_lot::Mutex` does not poison at all), and never unwrap-or-ignore a poison signal into silent continuation.

## §B19. Iterator invalidation through indirection

**The trap**: for a plain `&mut Vec<T>`, the borrow checker statically forbids iterating-while-mutating. The LLM writes the same pattern *through* a `RefCell`, through indices, or through `unsafe` raw pointers — and the borrow checker no longer sees it. Compiles, passes tests for small inputs, and corrupts state (or panics on `BorrowMutError`) once the loop body actually triggers the mutation under realistic input.

**BANNED**:
- Iterating `vec.iter()` (or `borrow.iter()`) while pushing/removing through a `RefCell<Vec<T>>` borrow on the same vector inside the loop body — this doesn't dangle (safe `RefCell` can't produce that): the `borrow_mut()` panics with `BorrowMutError` the instant it runs while the iterating `Ref` is still alive.
- `for i in 0..vec.len() { ... vec.push(...) ... }` — `vec.len()` is captured once at the start of the range; if the loop body mutates `vec.len()`, the loop iterates over the *old* length, missing or double-processing newly-inserted items.
- BFS/DFS that pushes children onto the same `Vec` it is iterating, indexed by `for i in 0..frontier.len()` — produces silent partial traversal.
- `std::mem::take(&mut field)` and `Option::take` leave a `Default` (`Vec::new()`, `None`, `0`) behind; `mem::replace(&mut field, new)` leaves the passed-in `new`. Either way the field no longer holds the original, so the "take it out, process, put it back" pattern silently loses the original contents if an early `return`, `?`, or panic happens between the take and the put-back. Restore on every path, or use a drop guard that puts the value back.

**REQUIRED**:
- For BFS/DFS with a growing frontier, use **two vectors** (`current`, `next`) and `std::mem::swap(&mut current, &mut next)` between layers, or `VecDeque` with disciplined `pop_front` / `push_back` and a captured *initial* layer length.
- For loops whose body must read the source after potentially-mutating it, snapshot first: `let snapshot: Vec<_> = vec.iter().cloned().collect();` then iterate the snapshot, then commit changes. The clone cost is the price of avoiding undefined behavior at the data-structure level.
- For index loops over mutating collections, re-read `len()` every iteration (`while i < vec.len() { ... i += 1; }`) and state in a comment why the loop is well-founded.

## §C8. Channel-and-runtime mismatch

**The trap**: the LLM picks a channel by name recognition — `std::sync::mpsc` because it's standard, `crossbeam::channel` because it's "the fast one", `tokio::sync::mpsc` because it's the tokio one. The code compiles in all four runtime/channel combinations. Behaviour diverges: a sync channel in async code blocks the executor (§B11 surface); multi-consumer built on a tokio MPSC through a hand-rolled wrapper — the LLM-typical shape is the single `Receiver` parked behind an `Arc<Mutex<…>>` that several tasks contend for, or a genuinely MPMC channel (`flume`, crossbeam) misremembered as tokio's — fans messages to whichever task wins the lock race (bare `tokio::sync::mpsc::channel` cannot literally do this: `Receiver` is not `Clone` and only one can exist per channel — see the BANNED bullet below); a `crossbeam::channel::Receiver::recv()` inside an `async fn` blocks the worker thread for as long as the queue is empty. **Whether the mutex-wrapped-receiver shape is actually wrong depends on the delivery requirement** — see the three-way distinction in the BANNED bullet below: it is a correctness bug for broadcast-to-all or routed/affinity delivery, but not for a plain competing-workers queue.

**BANNED**:
- `std::sync::mpsc::Receiver::recv()` inside an `async fn` or any function called from `tokio::spawn` — blocks the worker thread; same defect as `std::thread::sleep` per §B11.
- `tokio::sync::mpsc::channel(...)` when the workload is multi-consumer — `Receiver` is single-consumer by type (only one task can hold it). Spawning multiple tasks that each call `recv()` on a *cloned* receiver is not possible; cloning is not implemented. The workaround that reintroduces the fan-out race described in the trap paragraph is parking the single `Receiver` behind an `Arc<Mutex<_>>` shared by all consumer tasks — whichever task holds the lock when a message arrives consumes it. **This is not uniformly a defect — the correctness verdict depends on the delivery semantic the workload actually needs**: (1) **competing workers** (a worker pool where any free worker may take the next job — "delivery to whichever one is free" is the *intended* semantic): the mutex-wrapped receiver is functionally correct here — the same distribution semantic as `flume`'s bounded MPMC (this section's own recommended fix) — it is merely an unnecessary/awkward inefficiency (an extra unrelated lock serializing consumers), not a correctness bug; a purpose-built MPMC (`flume`) is still better, but the mutex-wrapped shape isn't broken for this case. (2) **broadcast-to-all** (every consumer must see every message) or (3) **routed/per-worker-affinity delivery** (a specific message must reach a specific consumer): here the mutex-wrapped receiver *is* genuinely wrong — a message that should go to multiple/specific consumers instead goes to one arbitrary one — and `broadcast`/explicit routing is required, not just "nicer". Use `broadcast` or `flume` per the delivery semantic actually needed.
- `crossbeam::channel::Receiver::recv()` inside async code — sync API, blocks the worker. `crossbeam` is fine in pure-sync contexts (rayon, OS threads); not under tokio.
- `tokio::sync::mpsc::Sender::send(...)` (await form) inside a fast sync producer that cannot afford the await point — use `try_send` and handle the `TrySendError::Full` explicitly (§B14 backpressure).

**REQUIRED**:
- **Async multi-producer / single-consumer**: `tokio::sync::mpsc::channel(N)` (bounded; default).
- **Async multi-producer / multi-consumer**: `flume::bounded(N)` (works in both sync and async modes) or `tokio::sync::broadcast::channel(N)` — note the semantics divergence: `broadcast` delivers every message to every receiver and signals lag via `RecvError::Lagged`, whereas `flume` MPMC distributes each message to one receiver.
- **Sync MPMC**: `crossbeam::channel::bounded(N)` or `flume::bounded(N)` in sync mode.
- **Async single-producer / single-consumer**: `tokio::sync::oneshot::channel()` for one-shot; `tokio::sync::mpsc::channel(1)` for streamed.
- **Async with priorities**: build on `tokio::sync::Mutex<BinaryHeap<_>>` + a `Notify` for wake-ups, or use the `priority-queue` crate inside a `Mutex`. There is no standard async priority channel; document the choice — and the hand-rolled shape needs two more stated decisions. (a) **Capacity and full policy**: the heap is unbounded by construction — pick a cap and state what a producer does when full (await/backpressure until the consumer drains, or drop the lowest-priority item — evicting a `BinaryHeap`'s minimum is an O(n) scan). (b) **Consumer count**: as shown, `Mutex<BinaryHeap<_>>` + a single `Notify` is **single-consumer** — with two concurrent consumers, `notify_one` stores only one permit, so a consumer that checks the empty heap before arming its `Notified` future loses the wakeup for the item pushed in between and sleeps forever; the multi-consumer form requires the `enable()`-before-check lost-wakeup protocol (tokio's own docs demonstrate exactly this failure for a `Mutex<VecDeque<_>>` + `Notify` mpmc; see §B15e's `Notify` bullet in `async.md`, and this file's §B9 `Condvar` bullet — the sync twin of the same check-then-wait race).

## §E4. Contention that serializes — *A lock is a queue; under load, the queue is your latency.*

- **Where it shows up**: `Arc<Mutex<T>>` reached for reflexively (§A2) where the data is read-mostly, swapped wholesale, or never actually shared mutably; a critical section spanning I/O, allocation, or `format!` (§B2); a single global lock where work shards cleanly per key/connection; a lock taken inside a hot loop; two atomics (or a lock and its payload) sharing one cache line (false sharing).
- **The cheaper move**: match the tool to the access shape — a plain atomic for a counter/flag (§B13); `arc_swap::ArcSwap` or `Arc<T>`+rebuild-and-swap for read-mostly config; `RwLock` only when reads truly dominate and the section is non-trivial (and mind reentrant reads — a second `.read()` while a writer waits deadlocks under std's unspecified / tokio's write-preferring policy; see §B17); sharding (array of locks keyed by hash); a channel to hand ownership to one owner. Shrink every critical section to "read a few fields, clone what's needed, drop the guard." Pad hot independent atomics with `crossbeam_utils::CachePadded`.
- **Hasher by trust boundary**: the default `HashMap` hasher (SipHash-1-3, randomly seeded) is DoS-resistant, not fast. For internal, trusted keys — especially integer/small keys on a hot path — a faster hasher (`rustc_hash::FxHashMap`, `foldhash`, `ahash`) is a real win. For attacker-influenced keys the speed is a trap: a fixed-seed fast hasher reopens HashDoS (§B16). The trust boundary is the whole decision, not the benchmark.
- **Leave it when**: contention is unmeasured and the lock is held briefly on a cold path — a `Mutex` is often faster than an `RwLock` and clearer than a lock-free scheme.
- 🟡. Cross: §A2, §B2, §B13, §B16. Verify any new crate before adding — §A1. The concurrent-map selection table (sharded / lock-free-read / read-copy families) and the hasher ladder live in the **Substitution catalog** in `data-and-types.md`.

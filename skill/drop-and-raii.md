## §B4. Drop order and RAII contracts

**The trap**: implicit `Drop` for transactions, file handles, async resources has library-specific contracts. `sqlx` implicit-rolls-back inside the async runtime — a library/backend-specific **queued rollback**, not a blocking call: `Transaction`'s `Drop` impl calls `TransactionManager::start_rollback`, which queues the `ROLLBACK` to run on the next asynchronous invocation of the underlying connection (e.g. when the connection is returned to the pool), so whether it ever runs — and whether it succeeded — is runtime-dependent and unobservable. `deadpool-postgres` sends rollback to a background task that may never run. The semantics live in library source, not signatures. Whenever rollback completion — or its potential error — must actually be observed by the caller, an **awaited** rollback is REQUIRED: call `.rollback().await` yourself; never rely on the queued drop-time behavior for that.

**REQUIRED** for any DB transaction / file handle / network resource:
- After the last fallible operation that might fail (e.g., `tx.commit().await`), **assume the resource's `Drop` runs in an undefined state**. Do not rely on it for correctness.
- For transactions: explicit `commit().await?` on the success path always. On the error path, an explicit, **awaited** `rollback().await` is REQUIRED whenever rollback's completion or potential error must actually be observed by the caller (the default case — an unswallowed rollback failure usually needs to surface, and the caller usually needs to know the rollback actually ran before proceeding) — call it yourself, don't rely on the queued drop-time behavior. The REQUIRED shape is **not** a bare `rollback().await?`: that literal form has its own trap — if the rollback *also* fails, the `?` propagates the rollback's error and silently discards the original failure that triggered the rollback in the first place, replacing the actual root cause with a secondary one. Match rollback's `Result` explicitly instead: `if let Err(rollback_err) = tx.rollback().await { return Err(MyError::RollbackFailed { source: rollback_err, original: Box::new(original_err) }); } return Err(original_err);` (or equivalent) — decide precedence explicitly, typically surfacing the original error to the caller with the rollback failure attached as context, not substituted for it. The narrow exception: when the caller has *documented*, deliberate indifference to whether/when the rollback completes or succeeds (a fire-and-forget cleanup on a path already handling a fatal error, for instance), letting the queued drop-time rollback run is an acceptable, explicitly-stated trade-off — but it is a decision to write down, not a default to fall into silently. Either way, acknowledge the failure mode of `commit().await` itself failing (the tx is then in a library-specific state — check the docs).
- Read the version-specific `Drop` impl docs for the library being used. State the version you assumed in a comment.
- Be aware that holding multiple drop-significant guards (file + DB tx + lock) creates an ordering problem — and "drops in reverse declaration order" is a rule only for **function-body locals**: locals (stack variables in a function body, `let` bindings) drop in **reverse declaration order**; fields of a struct/enum-variant/tuple drop in **forward declaration order**, and array/slice elements in **forward index order** (first to last); a move-closure's captured variables drop in an **unspecified order** — never rely on closure-capture order for any shutdown/cleanup contract, make the order explicit instead. Even where the order is specified, the *correct* order depends on the semantics. State which order matters.

**BANNED**:
- `std::process::exit(...)` from any code path where stack-local guards (database transactions, file handles, lock guards, logger flushers) still need to run their `Drop`. `process::exit` **does not unwind** — none of those `Drop` impls execute. Return a `Result` from `main`, or call `drop(guard)` explicitly on every guard before `process::exit`. **A bare drop is not enough when the guard's cleanup is fallible**: `std::io::BufWriter`'s own docs warn that its `Drop` attempts a flush but silently ignores any error the flush returns — the documented fix is to call `.flush()` explicitly and check the `io::Result` *before* the drop, not to rely on the drop to do it. The same shape applies to any guard whose teardown can fail: call and check `.flush()` / `.sync_all()` / `.commit().await` / `.rollback().await` / `.close()` — whichever the type exposes — before `process::exit`, not just drop it; dropping alone discards whatever error that call would have surfaced.
- A `Drop::drop` body that can itself panic while panicking is already in flight (the ordinary double-panic rule: a panic that occurs while a panic is already unwinding aborts the process — unconditional stable behavior, not the separate nightly-only `-Z panic-in-drop` compiler flag, whose default `unwind` strategy does not change this). The idiomatic primary guard is `std::thread::panicking()`: skip or relegate the fallible work when the thread is already unwinding (`if !std::thread::panicking() { … }`), so `drop` never adds a second panic to an in-flight one. If `drop` does anything fallible, isolate it in `catch_unwind` and downgrade the inner panic to a logged error — but the caught `Err` payload (`Box<dyn Any + Send>`) is not itself an inert value: it carries unknown drop glue, and dropping an arbitrary boxed payload can itself panic. `Box<dyn Any + Send>` itself implements neither `Debug` nor `Display` — `Any` provides no such path to log through. Downcast the payload **by reference** to the two common concrete forms instead (`payload.downcast_ref::<&str>()`, `payload.downcast_ref::<String>()`); if a diagnostic is wanted, report whichever matches through a sink proven not to panic itself — a bare `eprintln!`/`println!` can panic if the underlying write fails (a closed/broken stderr). By this point `catch_unwind` has already caught the drop body's own panic and stopped that unwind, so a failing report here is an *ordinary new* panic, not literally "a second panic while one is already in flight" — that double-panic/abort framing applies only if this same reporting code runs during an **independent, outer** unwind (some unrelated panic already propagating through this thread), which is precisely the case the `thread::panicking()` guard above exists to exclude before any of this runs. Either way — ordinary panic or, if that guard was somehow bypassed, a genuine double panic and abort — a panicking report is a bug to prevent, not a distinction to lean on: prefer a diagnostic sink specifically audited not to panic — checking the `Result` a `Write` call returns is necessary but not sufficient, since an arbitrary `Write` implementation can panic internally regardless of what it returns — or skip the diagnostic. If neither concrete form matches (an unknown payload type), `std::mem::forget`/leak the payload rather than assuming its own drop is infallible, instead of letting it fall out of scope unexamined. **Precondition for this fix:** `catch_unwind` only catches an *unwinding* panic — under `[profile.*] panic = "abort"` a panic aborts the process immediately and unwinds nothing, so the `catch_unwind` (and the logging behind it) never runs. The guard is real only under `panic = "unwind"` (the default). `catch_unwind` also takes an `UnwindSafe` closure; reach for `AssertUnwindSafe` only after reasoning that no observer can see broken invariants across the caught panic — do not wrap blindly to silence the bound.
- `mem::forget(guard)` or wrapping a guard in `ManuallyDrop` without a later manual drop — both silently disable the RAII release (file descriptor, DB connection, lock guard never freed). This is the §C5 reflexive-`.clone()` reflex applied to `Drop`: a quick way to silence a move/borrow complaint that leaks the resource instead.
- Issuing raw `BEGIN`/`COMMIT` (or `START TRANSACTION`) statements through a connection **`Pool`** — `sqlx::query("BEGIN").execute(&pool)` … `sqlx::query("COMMIT").execute(&pool)`. Each `execute` checks out a pooled connection of the pool's choosing, so the two statements (and everything between) may run on **different connections**: the "transaction" spans nothing and the `COMMIT` is an orphan — PostgreSQL answers it with a warning and exit success, not an error. The failure is silent: a multi-statement invariant that was never atomic. Always open transactions with `pool.begin()`, route **every** statement through the returned `Transaction` handle (`tx` / `&mut *tx`), and let that handle own commit/rollback per the REQUIRED rules above. The read-modify-write isolation rules (lost updates, `READ COMMITTED` vs `FOR UPDATE`/`SERIALIZABLE`) are §B13.

**Drop at process exit — memory vs. resource (the fork that resolves the `process::exit` tension above)**: the BANNED `process::exit` / `mem::forget` rules above are about *resource-releasing* `Drop`. Not every `Drop` releases a resource, and the two cases want opposite treatment at shutdown:
- **Resource-cleanup `Drop`** (flushes a file, commits/rolls back a transaction, releases an OS lock, sends a connection-close, decrements a cross-process refcount): **must run**. Skipping it via `process::exit` / `mem::forget` / `ManuallyDrop` is the §B4 bug above — data loss or a stuck external resource.
- **Memory-only `Drop`** (a large `HashMap`, a deep tree of `Box`, an arena, a parsed AST — whose `drop` does nothing but free heap the OS is about to reclaim wholesale): running it at process exit is *wasted work*. Walking a multi-gigabyte structure node-by-node can add seconds of teardown — or look like a hang — before an exit that frees the whole address space anyway. Here `std::mem::forget`, `ManuallyDrop`, or letting `std::process::exit` skip it is the **correct** move, not a leak that matters.
- **Static-owned resources** (`static`/`static mut` items, and anything reachable only through them — a connection pool behind a `OnceLock`, a buffered logger held in a `static`): **never dropped**, even on normal exit. Returning from `main` runs destructors only for locals and for values owned in a still-live scope at that point; by design, static items get **no destructor call on normal process exit** ("Static items do not call `drop` at the end of the program" — Rust Reference, static items). So "return from `main`" is not a cleanup path for anything a global owns: every static-owned resource (pool, buffered logger, metrics reporter) needs explicit shutdown/flush logic — an explicit `shutdown()`/`flush()` before returning, or a drop-guard held as a *local* in `main` — rather than relying on program exit to release it.

So classify `Drop` by *what it does*, not by reflex. A literal-minded "always run every destructor" stalls shutdown on big structures; a literal-minded "just `process::exit` to exit fast" loses a transaction. Neither rule is right alone — skip a destructor at exit only when it is provably memory-only.

**Recursive `Drop` can overflow the stack** (ties to §B7): the auto-generated `Drop` for a self-owning recursive type — a long `Box`-linked list, a deep `Box<Node>` tree, an unbalanced syntax tree — recurses once per level as it tears down. On attacker-controlled or merely large depth that recursion overflows the stack: a `SIGSEGV`/abort, **not** a catchable panic (the §B7 DoS shape, arriving through the destructor). Tests on shallow data pass. For any recursive type whose depth is not provably bounded, hand-write an **iterative** `Drop` that unlinks nodes into a worklist `Vec` and drops them in a loop, rather than relying on the recursive default.

**Drop-order shutdown deadlock** (the concrete case of the ordering note above): a struct — or a function's locals — holding both a worker `JoinHandle`/thread and the `Sender` that feeds it deadlocks at teardown if the handle is joined **before** the channel closes. The worker blocks forever on `recv()`, so the `join()` blocks forever, so the program never exits. Rust drops struct fields in **declaration order** (top to bottom) and locals in **reverse** declaration order; the `Sender` must drop (or be explicitly closed) *before* the join. Fix: `drop(sender)` — or signal shutdown — explicitly before `handle.join()` / `.await`; in a struct, hold explicit shutdown state — typically `Option<Sender>` and `Option<JoinHandle>` — and on shutdown `.take()` and drop/close the sender first, then `.take()` and `.join()` the handle, in that explicit order regardless of field declaration order. Field order cannot implement this under either mechanism: dropping either a std or Tokio `JoinHandle` **detaches** the thread/task rather than joining it (a detach is not a join no matter which field comes first), so automatic field-by-field `Drop` never joins; and a custom `Drop::drop` that calls `join()` runs to completion before Rust's automatic field destruction even begins, so field order is moot there too. Tokio additionally cannot join from `Drop` at all: `Drop::drop` is synchronous and cannot `.await` a task's `JoinHandle`, so the type must expose an explicit consumed `async fn shutdown(self)` rather than shutting down from a `Drop` impl. Field order is a valid internal detail only for a type whose docs specifically promise a "joins automatically in `Drop`" wrapper contract (sender field declared before handle field) — never as a general fix. Don't leave it to incidental field order; state which drops first and why.

Async resources have an additional constraint that `Drop` cannot honor — see §B22 for the async-`Drop`-is-not-real problem.

### §B4a. Edition-2024 temporary-scope drop-order changes

**The trap**: migrating a crate to edition 2024 silently changes *when* temporaries drop in two places — with no runtime error and usually green tests, but a different drop order under locks and RAII guards.

- **`if let … {} else {}` scrutinee** (`if_let_rescope`): in edition 2024 a temporary created in the `if let` scrutinee drops **before** the `else` block (and at the end of the `then` block), not at the end of the whole `if`/`else`. The canonical hazard is an `RwLock`/`Mutex` deadlock: `if let Some(v) = lock.read().get(&k) { … } else { lock.write().insert(…) }` deadlocks in 2021 (the read guard is still alive in the `else`) and silently *stops* deadlocking in 2024 — or, conversely, code that relied on the temporary living into the `else` now drops it early. `cargo fix --edition` auto-rewrites to a `match` to preserve 2021 behavior; review those rewrites.
- **Tail-expression temporaries** (`tail_expr_drop_order`, RFC 3606): in edition 2024 temporaries in a block's tail expression drop **after** the tail value but **before** the block's locals, not at end of the enclosing statement. This shifts the drop order of any custom-`Drop` value (a `MutexGuard`, transaction handle, span guard) sitting in tail position. The lint is **advisory and has no autofix** — migration will not flag it for you unless you read the warning. A trailing `if let … {}` with no semicolon is *both* a tail expression and an `if let`, so it hits both rules at once.
- **let-chains** (`if let A && let B`, stable 1.88, edition 2024) follow the same `if let` temporary-scope rule — reason about each chained temporary's drop point explicitly. `let`-chains also reached `match` *guards* (`match x { v if let Ok(y) = f(v) => … }`, stable **1.95**, all editions — verify against your pinned toolchain) — these do **not** share the `if let … else` drop hazard (a guard has no `else` arm), so no special drop-order review is needed there beyond normal guard-temporary scoping.
- **never-type fallback** (edition 2024) is mostly out of scope for this spec: changing `!`'s fallback from `()` to `!` is a *compile-time* break in the common case (code relying on `Default::default()` inferring `()` stops compiling), and the one genuinely silent-at-runtime interaction — fallback flowing into an `unsafe` call — is guarded by the `never_type_fallback_flowing_into_unsafe` lint, which is **warn-by-default in all editions since Rust 1.80** and **deny-by-default in edition 2024** (which stabilized in **Rust 1.85**). Because the dangerous case is deny-linted rather than silent, it sits outside this document's "survives the compiler" focus; annotate the type explicitly (`zeroed::<()>()`, `<() as Default>::default()`) when the lint fires.
- Edition 2024 also changes **`impl Trait` lifetime capture**: a return-position `-> impl Trait` now captures *all* in-scope generic lifetime parameters by default. `fn f<'a>(x: &'a [u8]) -> impl Iterator<Item = u8>` ties the returned iterator to `'a` in edition 2024 where it did not before — a borrow that used to end early now lives as long as the input. Opt out with a precise-capture bound: `+ use<>` (capture nothing) or `+ use<'b, T>` (capture only what you name). On a 2021→2024 migration this silently changes how long the return value borrows its input (this is the §B1b lifetime-leaking shape arriving via edition migration).

**REQUIRED**:
- On any 2021→2024 edition migration, run `cargo fix --edition`, then manually review every `tail_expr_drop_order` warning (no autofix) and every `if let … else` that holds a lock guard or other RAII type in its scrutinee.
- For lock guards specifically, bind the guard to a `let` with an explicit scope rather than relying on a temporary's lifetime — that makes the drop point edition-independent. See §B9 (lock order) and §B2 (guard across `.await`).

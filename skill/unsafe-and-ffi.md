## §B5. Unsafe that looks safe (high UB rate in small-N studies)

**The trap**: code passes review and tests because UB doesn't manifest on typical inputs. In the small-N audit cited in [`references/sources.md`](references/sources.md), out of 40 LLM-generated `unsafe` blocks: 13 were UB on any input, 9 were UB on specific inputs (alignment, OOB, Stacked Borrows violations), 18 were correct — i.e. 22/40 (~55%) exhibited UB. The *exact rate* is directional (small sample, not stratified by model or domain), but the *pattern* — that LLM-generated `unsafe` is significantly more dangerous than LLM-generated safe code — is consistent across every published audit to date. Treat any LLM-generated `unsafe` block as high-risk until proven otherwise via miri + manual invariant audit.

**BANNED**:
- `std::ptr::read(p)` / `*p` / `&*p` where the source pointer's alignment is not statically known to match `T`. Use `std::ptr::read_unaligned` / `std::ptr::write_unaligned` instead (`<[T]>::align_to::<U>` is itself `unsafe` and requires the same `Pod`-style invariants as `transmute` — do not list it in the "safe alternatives" bucket).
- `transmute` between types whose layouts aren't both `#[repr(C)]` (or another pinned repr — `#[repr(transparent)]`, `#[repr(u32)]`, `#[repr(packed)]`, etc.). The default layout (`#[repr(Rust)]`) does not guarantee field order, padding, or stability across compiler versions, so the bytes may not be reinterpretable as the target type. The attribute `#[repr(Rust)]` itself is stable (it is the default and can be written explicitly); the *layout it implies* is unspecified.
- `transmute` justified **only** by a matching `#[repr(...)]` on both sides. A pinned repr settles part of the layout/ABI story and nothing else: it does not prove that every source bit pattern is a *valid value* of the destination type (`bool`, `char`, `NonZero*`, enum discriminants, `&T` nullness), that references carry valid provenance and lifetimes, or that ownership/aliasing invariants survive the reinterpretation. `transmute` requires equal size (the compiler checks that, and only that) **plus** a stated validity proof for both directions — the `// SAFETY:` block names it or the call is banned.
- Any `unsafe` block without `// SAFETY:` preceding it that names every invariant.
- Calling user-provided, callback, comparator, or otherwise panic-capable code while an unsafe data structure is in a temporarily invalid or partially-committed state. `catch_unwind` does not repair broken invariants; use a guard that restores validity, or separate a fallible preparation phase from an infallible commit, and inject panics in tests where the contract matters.
- Creating a `&mut T` from a `*mut T` while another reference to the same data still exists (Stacked Borrows violation, caught by miri).
- `mem::uninitialized::<T>()` — deprecated since Rust 1.39 (November 2019) precisely because it is **instant UB for any type with invariants**. The function returns an "undef" value the optimizer is free to assume is initialized; for `bool`, `&T`, `Box<T>`, `NonZero*`, and any enum with restricted discriminants, the call is UB on the very next read. Use `MaybeUninit::<T>::uninit()`.
- `mem::zeroed::<T>()` for any `T` whose all-zero bit pattern is not a valid value: `bool`, `&T`, `&mut T`, `Box<T>`, `NonZero*`, function pointers, enums whose discriminants do not include 0, and `#[repr(transparent)]` wrappers over any of the above. The function compiles for *every* `T` regardless of whether zero is a valid bit pattern; the compiler will not stop the misuse.
- **Serializing a struct to bytes by a raw cast** — `slice::from_raw_parts(&t as *const _ as *const u8, size_of::<T>())`, or `transmute`/`transmute_copy` into a byte array — when the type has **padding** and the bytes cross a trust boundary (network, disk, IPC, a log). The padding bytes between fields are **uninitialized**: reading them is UB (miri flags it), *and* they carry whatever previously occupied that stack/heap slot — a stale pointer, key material, another request's data — straight out of the process (Heartbleed-class info disclosure; a §B12 secret-leak when those bytes are sensitive). `#[repr(C)] struct H { flag: bool, len: u32 }` has three such bytes. This is the write-direction dual of the "validate bytes → `Result` before minting" rule below, and it is *not* caught by `cargo test` (the value round-trips fine locally). Also BANNED: `unsafe impl bytemuck::NoUninit` / `bytemuck::Pod` (or the manual equivalent) on a padded type to push it through `bytes_of` — that overrides the exact compile-time check that catches this.
- **Reading a `union` field with no local proof that the storage is initialized and that the bits are valid *at that field's type*.** A Rust `union` has **no** active-field tracking and **no** implicit runtime tag: every field read simply reinterprets the union's bits at that field's type, and it is the programmer's responsibility that they are valid there — reading `3` as a `bool`, a stale discriminant as an `enum`, a reference with invalid provenance, or bytes the writer never initialized is instant UB with **zero** compiler help (the `unsafe` block is one keyword, and tests with a stub that always writes the expected variant pass). For the shape that dominates FFI — a **tagged** union, i.e. what `bindgen` emits for C, where a sibling tag field is what selects the valid interpretation — the proof *is* the tag check, and a read with no preceding tag `match` is the finding. For deliberate type-punning between representations that are valid for one another (`u32` ↔ `[u8; 4]`), the proof is a stated bit-validity argument instead; "no tag was checked" is not by itself the defect there. Also BANNED: a **non-`#[repr(C)]`** union used for FFI or for any reinterpretation that relies on C-compatible layout — the default union layout leaves field offsets unspecified, so "write field A, read field B" is not even a defined transmute.
- Marking a public function `pub fn` when its contract actually requires invariants from the caller. If the caller must uphold something for safety, it is `pub unsafe fn`.

**REQUIRED**:
- `// SAFETY:` comment listing each invariant in the form `// SAFETY: ptr is valid for reads of size_of::<T>(), is properly aligned (allocated via Layout::new::<T>()), and outlives this borrow.`
- Add miri to CI for files containing `unsafe`: `cargo +nightly miri test`. Yes, 10× slower; the one UB caught pays for it.
- Default to safe abstractions (`zerocopy::FromBytes`, `bytemuck::Pod`/`bytemuck::cast_slice`, `slice::chunks_exact`) before reaching for raw pointers. (`bytes::Bytes` is a refcounted *buffer container*, not a safe-transmute abstraction — don't confuse the two.)
- **Serializing out (type → bytes) is the mirror of that read rule.** Derive `bytemuck::NoUninit` / `zerocopy::IntoBytes` and let them **reject padded types at compile time** — that rejection *is* the padding-leak being caught, not an obstacle to override. If rejected, make the layout padding-free: reorder fields so none is needed, or add explicit `_pad: [u8; N]` fields you zero-initialize, then serialize. `#[repr(packed)]` also removes padding but reintroduces the unaligned-access hazard above — prefer explicit fields, or serialize field-by-field. Never write raw struct bytes with padding to a socket, file, or log.
- Note: `<[T]>::align_to::<U>` is itself `unsafe` and requires the same `Pod`-style invariants as `transmute`; use it only when `bytemuck`/`zerocopy` aren't available, and with a `// SAFETY:` block per the rule above.
- **Every `union` read sits behind a safe accessor carrying a local validity proof.** For a tagged union (`#[repr(C)] struct { tag: u32, data: SomeUnion }`), the accessor matches on `tag` and only inside the matching arm reads the corresponding field, with a `// SAFETY:` naming *which write* (which C-side call, which prior branch) made these bits valid **at this field's type**. For deliberate type-punning with no tag, the `// SAFETY:` states the bit-validity argument instead — every bit pattern of the source is a valid value of the destination — rather than inventing a tag check that proves nothing. The union must be `#[repr(C)]` for any FFI or layout-dependent use. And the meta-check: **if the union exists only to pair with a Rust-side flag you control, you have reinvented an `enum` — use one.** A Rust `enum` *is* a tag-checked, compiler-enforced tagged union; hand-rolling `union` + `bool`/`u32` flag re-opens exactly the wrong-field-read UB the language already closed for you. Reach for a raw `union` only when a foreign (C) layout forces it.
- **`MaybeUninit<T>` discipline**: for any value initialized piecewise (field-by-field) or by an FFI/`unsafe` call writing into Rust memory, use `MaybeUninit::<T>::uninit()` (or `MaybeUninit::<T>::zeroed()` when zero is a valid bit pattern for `T`), write every byte/field, then call `.assume_init()`. Never call `.assume_init()` while any portion of `T` is still undef. The legacy `mem::uninitialized` / `mem::zeroed` paths are BANNED above for the same reason: they bypass this discipline and produce UB on the first read.
- **Strict provenance**: when a pointer genuinely encodes its address as an integer (pointer tagging, free-lists, XOR-linked structures), use the strict-provenance API (`ptr.with_addr(addr)`, `ptr.addr()`, `ptr.map_addr(|a| …)`, `ptr.expose_provenance()`, `core::ptr::with_exposed_provenance::<T>(addr)`, `core::ptr::without_provenance::<T>(addr)`) rather than `ptr as usize` / `usize as *const T` round-trips — the cast form loses provenance that miri can otherwise verify, and is a warning under strict-provenance lints / unsound under sanitizers. For an ordinary pointer cast with no address↔integer round-trip, plain `as` is idiomatic and fine — this is not a blanket "replace every cast". (All of these are stable since Rust 1.84.)
- **`slice::from_raw_parts(data, len)` invariants** — list before calling: `data` is non-null, properly aligned for `T`, points to `len` consecutive properly-initialized `T`s, the memory it points to is not mutated for the lifetime of the returned slice, and `len * size_of::<T>() <= isize::MAX`. Mirror for `from_raw_parts_mut`, plus exclusive access. Every call site states each invariant in its `// SAFETY:` block.
- For FFI: every `extern "C"` function takes/returns `#[repr(C)]` types only. `String` and `Vec` cannot cross the FFI boundary; use `CString` / `*const c_char` for strings, and for buffers decompose to `(ptr, len, cap)`: on a project with MSRV ≥ 1.93 prefer `Vec::into_raw_parts` (stable as of Rust 1.93 if confirmed by your toolchain); below 1.93 use the manual decomposition via `ManuallyDrop<Vec<T>>` (stable since 1.0). See §B25 for the full FFI ownership discipline.

**The unsafe→safe boundary: guard value-invariants, prove relational ones.** When `unsafe` produces a value that flows into safe code, split what must hold about it into two kinds — they need opposite defenses:
- **Value-invariants** (a bit pattern, an integer range, an enum discriminant, a length, an address's alignment, UTF-8 well-formedness): runtime-checkable. The `unsafe` must emit the value through a **total fallible constructor** — `&[u8] → Result<Typed, _>` — that runs the check and returns `Err` on bad input. It must **never panic on adversarial input** (no `unwrap`/`expect`/`assert!` at the boundary — that turns a soundness check into a remote DoS; see §B7/§C2). Canon: `str::from_utf8`, `char::from_u32`, `TryFrom` (§B26), `zerocopy::TryFromBytes`. Crucial ordering: the guard runs on the **raw representation (bytes) *before* the typed value is minted** — `validate(&[u8]) -> Result<&T>`, never `let t: T = transmute(bytes); check(t)`. The second form's *read* of an invalid `T` (an invalid `bool`, a bad discriminant, a dangling `&`) is itself the UB you were trying to guard against. For types where *every* bit pattern is valid (`bytemuck::Pod`) there is nothing to check — the compile-time `Pod` bound is the guard.
- **Relational invariants** (lifetime validity, aliasing/exclusivity, pointer provenance, "points to `N` initialized `T`s", `Send`/`Sync`): **not** runtime-checkable. There is no `fn is_not_dangling(p: *const T) -> bool` — to "check" you would dereference, which is the use-after-free. So there is **no downstream guard**; the only defense is the *upstream* proof discharged before the `unsafe` (the `// SAFETY:` contract) plus the type's variance and marker traits (see §B18, §B18a). Do not pretend a downstream check exists — for this class it cannot.

## §B7. Large stack allocations and arena pitfalls

**The trap**: `[u8; 1_048_576]` on the stack overflows in debug builds. `Box::new([0u8; N])` constructs on the stack first and may overflow before placement-new optimizations kick in (release-mode dependent, never reliable).

**The right threshold to think in**: not page size (4 KiB), but the actual stack budget of the executing thread. Default stack budgets are **8 MiB on Linux for the main thread**, **2 MiB on `std::thread::spawn`-ed threads**, and **2 MiB on the tokio worker thread a task runs on** — tasks are *not* given their own stack, they share the worker's, so a deep async call chain competes for that one budget (configurable via `Builder::stack_size` and `tokio::runtime::Builder::thread_stack_size` respectively, but the defaults are the budget LLM-generated code actually runs against). Practical **default guideline**: keep routine stack values below ~64 KiB; this is a guideline, not a hard line — a single large value on a fresh main-thread frame with a 2–8 MiB budget is fine. It escalates to a real defect (see BANNED) when the large frame sits under recursion, a deep call chain, or a spawned task on a reduced stack, where the cumulative depth — not the single frame — overflows.

**BANNED**:
- `[T; N]` whose total size is a meaningful fraction of available stack: a large array (well past the ~64 KiB guideline, or any size that is a real fraction of the thread's budget) passed/returned by value through a function chain, **and especially** one that recurs or lands on a spawned task's reduced stack — there the per-frame size multiplied by depth overflows. A single large array on one shallow main-thread frame is the guideline case above, not an automatic ban.
- `Box::new([0u8; N])` for any N at risk — this is the trap: the array is built on the stack first and *then* moved to the heap, so the stack-overflow window is unchanged from the by-value form. Use `vec![0u8; N].into_boxed_slice()` or `Box::<[u8]>::new_uninit_slice(N)` instead.
- Recursive functions with large local arrays.
- Unbounded recursion **depth** over input you don't control — a recursive-descent parser, tree/JSON/expression walk with no depth limit overflows the stack on deeply-nested input. A stack overflow is `SIGSEGV`/abort, **not** a catchable panic, so it is a clean DoS vector for parsers of untrusted data. (Distinct from the frame-size trap above: here each frame is small but the depth is unbounded.) **The recursion need not be code you wrote:** the depth limit inside a third-party parser applies to its *parse-from-text* phase only — `serde_json`'s default 128 guards `from_str`/`from_slice`, but re-deserializing an *already-built* `serde_json::Value` (`from_value`, `IgnoredAny` skipping unknown nested fields, or `#[serde(flatten)]`/`untagged` routing through the buffered `Content` tree) walks the AST with **no** depth check and overflows the stack — an LLM that "knows serde_json has a recursion limit" is falsely reassured. `serde_yaml`'s alias/anchor recursion was an uncontrolled-recursion abort — fixed in 0.8.4 by adding depth checks (RUSTSEC-2018-0005) — and the crate is now unmaintained, so re-verify against your pinned version. You cannot add a `depth` parameter to `IgnoredAny` or a derived `Deserialize`; mitigate with `serde_stacker` (dynamic stack growth) or by capping input depth/size *before* the AST is built.
- `Vec::with_capacity(n)` / `vec![0u8; n]` / `String::with_capacity(n)` / `Vec::reserve(n)` where `n` is a length/count from untrusted input (a wire length-prefix, a `Content-Length`, a parsed count field). An attacker sends `n = u32::MAX` and the single preallocation exhausts memory → OOM/abort, a clean remote DoS. Distinct from the stack traps above: the allocation is on the heap but the *size* is attacker-chosen. Compiles; tests on small `n` pass.
- **Decompression bomb: `decoder.read_to_end(&mut out)` on a gzip/zlib/deflate/zip/tar body with the *compressed* input capped but the *decompressed* output unbounded.** `GzDecoder::new(compressed).read_to_end(&mut out)?` amplifies ~1 KiB → multi-GiB (the classic 1000:1 gzip ratio, `zip`'s nested bomb) and OOM-aborts — a clean remote DoS with **no attacker-controlled integer literal anywhere in the code**. Distinct from the `with_capacity(n)` bullet above: there is no clampable `n` — the code never sees the decompressed size as an integer, and the growth happens *inside a trusted-looking decode call*. Capping the compressed body (a `Content-Length` check, or the `zip` crate's own internal `.take(compressed_size)`) is **active false safety** — it bounds only the compressed side; `flate2` has no built-in output limit and header size hints are untrustworthy on malicious archives (CWE-409). REQUIRED: wrap the **decoder** in `.take(MAX + 1)`, then error if the limit is hit — the mirror of the `Read::take` advice below, but applied to the decoder's *output* rather than the socket's input: `let mut limited = GzDecoder::new(compressed).take(MAX + 1); limited.read_to_end(&mut out)?; if out.len() as u64 > MAX { return Err(/* bomb */); }`.
- **Extracting a multi-entry archive without an *aggregate* output quota.** A per-entry decompression cap (the bullet above) bounds each entry and still lets the archive as a whole exhaust the machine: a few hundred KiB of `zip`/`tar` can carry a million tiny entries (disk, inodes, dirent churn) or nest archives that your extractor expands recursively. Cap **total extracted bytes, total entry count, and nesting depth** before extraction, decrementing a single shared budget as entries are written — not a fresh limit per entry. Distinct from the decompression bomb above, which is one entry with a huge expansion ratio. (The *other* half of archive safety — entry names are attacker-authored paths, plus symlink/hardlink escape and special files — is path traversal, not exhaustion: it lives in §C2's `Path::join` bullet, which carries the component-rejection, `canonicalize`, and `openat`/`cap-std` recipe. A traversal-safe extractor can still fill the disk, and a quota-bounded one can still write to `/etc`; both bullets apply.)
- **Compute any `count * item_size` byte budget with `checked_mul` before clamping it.** A wrapping `count * size_of::<Record>()` (or `width * height * 4`) in release silently overflows to a *small* product that **passes** a `if bytes > MAX { .. }` clamp — then the code allocates/reads with the original huge `count` → OOM. The overflow defeats the very bounds check meant to stop this (CWE-190 → CWE-789); a reviewer who has internalized both §B26 and this section can still ship it because the clamp *looks* correct. Cross-ref §B26 (release-wrap semantics).

**REQUIRED for heap-allocated buffers**:
- `vec![0u8; N].into_boxed_slice()` — guaranteed heap, zero-initialized, stable Rust.
- `Box::<[u8]>::new_uninit_slice(N)` (stable since Rust 1.82, October 2024) + `.assume_init()` — when zero-initialization is wasted work and you will fully overwrite the buffer. `assume_init` is `unsafe`; gate it with a `// SAFETY:` block per §B5. **Only** sound when every byte is provably written before any read — e.g. `read_exact` of exactly `N` bytes. For the common `socket.read(&mut buf)` pattern that returns `n < N`, the uninitialized tail must never be sliced/read (that is UB); use the zero-initialized `vec![0u8; N]` form for partial-read buffers.
- `bytes::BytesMut::zeroed(N)` for buffers headed into `tokio::io`.
- For recursion over untrusted/unbounded input, enforce an explicit depth limit (a `depth: u32` parameter checked against a max), or rewrite iteratively with an explicit `Vec` stack.
- Clamp any allocation size derived from untrusted input to a sane maximum before allocating (`if n > MAX_LEN { return Err(...) }`), and prefer incremental growth or `Read::take(limit)` / `Iterator::take(limit)` over preallocating to a wire-supplied size. Reserve `with_capacity(n)` for an `n` you computed or bounded yourself.

## §B18. Manual `unsafe impl Send` / `unsafe impl Sync`

**The trap**: a type contains a `*const T`, a `*mut T`, a raw FFI handle, or a `Rc<T>` field, and `tokio::spawn` rejects it with a `Send` bound error. The LLM's reflexive fix is `unsafe impl Send for MyType {}` — and that compiles, and tests pass under low concurrency. Under contention, the un-synchronized access races. This is one of the most reliably-wrong fixes the LLM makes: it converts a correct compile-time refusal into a runtime data race.

**BANNED**:
- `unsafe impl Send for MyStruct {}` or `unsafe impl Sync for MyStruct {}` without a `// SAFETY:` block that names the synchronization invariant (which lock, atomic, or external invariant makes the impl sound).
- Manual `Send`/`Sync` for a type containing `*mut T` without proving that aliasing is controlled by external synchronization (e.g., the pointer is only ever read after the producing thread has joined, or access is guarded by an external `Mutex`).
- Manual `Send` for a type whose field is `Rc<T>` "because the Rc is never cloned across threads in practice" — if the field is morally `Arc`, fix the field, do not lie via `unsafe impl Send`.

**REQUIRED**:
- Every `unsafe impl Send` / `unsafe impl Sync` cites the synchronization primitive or invariant that makes the impl sound, in a `// SAFETY:` block per §B5. If there is no primitive — no `Mutex`, no atomic ordering, no thread-local lifetime restriction — the impl is wrong; refactor the type instead.
- For `*const T` / `*mut T` fields, `NonNull<T>` is a better field type for the null-niche and variance, but note it is `!Send`/`!Sync` exactly like the raw pointer — it does **not** make the type `Send`/`Sync` and does not close the race. The actual fix is to wrap the handle in an `Arc<Mutex<RawHandle>>` (or other real synchronization) and impl `Send`/`Sync` on the wrapper with the lock as the cited invariant — or, for the producer-then-consumer case, cite an explicit happens-before (the producing thread is `join`ed before any read). **This per-handle lock only closes the race if the C library itself is per-handle thread-safe** — a library with global/non-reentrant state (a global scratch buffer, `errno`-style globals, `getenv`/`setenv`, a one-time-init function) still races two independently-locked handles on that global; auditing which case you're in, and using a process-global lock instead when the library demands it, is §B25a.
- Surface every manual `unsafe impl Send` / `unsafe impl Sync` in the post-flight summary.

## §B18a. Variance and `PhantomData` soundness in raw-pointer wrappers

**The trap**: a hand-written type holding a `*const T` / `*mut T` / `NonNull<T>` (or otherwise built on internal `unsafe`) gets its **variance**, its **drop-check**, or its **auto-traits** wrong via the wrong `PhantomData` — or via no `PhantomData` at all. This is the relational-invariant class of §B5 made concrete: the hole is **not in any `unsafe` block**. There is no `unsafe` token at the site that decides variance — variance is implied by the type's fields and chosen *silently* by the compiler, so a block with a flawless `// SAFETY:` comment can still be unsound because the **type declaration** is wrong. A per-block `// SAFETY:` (§B5) cannot catch it; that is why this needs its own check. In *safe* Rust this is impossible — the compiler always derives variance correctly; the hazard exists only once a raw pointer enters the type.

**Why it bites**: if a wrapper that hands out `&mut T` is **covariant** in `T` (because it stores `*const T`, or `PhantomData<&'a T>`, or `PhantomData<fn() -> T>`), a caller can substitute a shorter or longer lifetime where the type required invariance — producing a dangling `&mut` and a use-after-free **with no `unsafe` at the call site**. Symmetrically, wrong drop-check (a missing `PhantomData<T>` on a type that owns a `T` through a raw pointer) lets a `Drop` read freed data; and a raw pointer is `!Send`/`!Sync` by default, so a wrong `unsafe impl Send`/`Sync` lies about it (that half is §B18).

**REQUIRED** for any type holding a raw pointer / `NonNull` / using internal `unsafe`:
- Choose `PhantomData` to match the *real* ownership and access:
  - `PhantomData<T>` — **covariant** in `T`, plus drop-check ownership (the compiler assumes the type may drop a `T`, so `T` must outlive it). Use when the type **owns** the data behind the pointer but does not need invariance — i.e. it never hands out `&mut T` through a covariance-sensitive path. This is the `Vec<T>` / `Box<T>` pattern.
  - `PhantomData<&'a T>` — **covariant** in both `T` and `'a`; a shared, read-only view. The default starting point for non-owning wrappers.
  - `PhantomData<&'a mut T>` — **invariant** in `T`, covariant in `'a`. Use when the type hands out `&mut T` or otherwise requires that callers cannot substitute a sub/supertype of `T`. This is the critical choice that prevents the covariance→UAF described above.
  - If you need both ownership (drop-check) **and** invariance, use both: `PhantomData<T>` for the drop-check + `PhantomData<fn(T)>` (contravariant in `T`) or `PhantomData<Cell<T>>` (invariant in `T`) to force invariance. `PhantomData<T>` alone is **not** invariant — using it when invariance is required is the exact unsoundness this section exists to prevent.
  - `PhantomData<fn(T) -> T>` — invariant in `T`, `Send + Sync` regardless of `T`, no drop-check. Correct only for the rare marker case; never as a reflex.
- State the chosen variance and *why* in the type's doc / `// SAFETY:` comment — variance is an invisible part of the type's contract, so write it down like any other invariant.
- Where variance is load-bearing for soundness, add a `compile_fail` doctest that attempts the illegal lifetime substitution, so a future edit that flips variance is caught by the test suite, not by a user's UAF.
- `NonNull<T>` is the right field type for the null-niche, but note it is `!Send`/`!Sync` **and covariant** in `T` — it does not make the variance decision for you. Prefer audited safe abstractions (`bytemuck`/`zerocopy`) over re-deriving variance by hand wherever they fit.

🔴 — surface every hand-rolled raw-pointer wrapper's variance / `PhantomData` / auto-trait decision in the post-flight summary, alongside the §B18 manual-`Send`/`Sync` items.

## §B25. Panic and ownership across `extern "C"` ABI

**The trap**: the LLM writes a Rust function callable from C (or returns a Rust-owned value through FFI), tests it on the happy path, and ships. The panic path is never exercised, the C-side `free()` path is never exercised, and the `cap`-mismatched `from_raw_parts` is never exercised. Everything compiles, the happy-path tests pass, and the bug surfaces under load as heap corruption (silent, worst), a process abort with no Rust stack (visible, but unhelpful), or a leak that grows for days. The compiler does not catch any of these — the `unsafe` boundary is precisely where its guarantees end.

**BANNED**:
- `extern "C" fn` body that can panic without being wrapped in `std::panic::catch_unwind`. Pre-1.81 a panic crossing an `extern "C"` boundary was UB; since Rust 1.81 the default is to abort the process — neither is what an FFI caller expects. Convert panics to a stable error code at the boundary.
- Passing a `Box<T>`, `Vec<T>`, `String`, `Rc<T>`, or `Arc<T>` directly as a parameter or return value of an `extern "C"` function — these types have no stable ABI and the layout can change between compiler versions. Cross the boundary as `*mut T`, `(*mut u8, usize, usize)`, or `*const c_char`.
- `Box::from_raw(ptr)` on a pointer not originally produced by `Box::into_raw` in the same Rust binary with the same global allocator. Reclaiming a `malloc`'d pointer through `Box::from_raw`, or freeing a `Box::into_raw`'d pointer with C's `free()`, is allocator-mismatch UB.
- `Vec::from_raw_parts(ptr, len, cap)` where `cap` does not match the value the source `Vec` was decomposed with — the eventual deallocation passes the wrong size to the allocator and corrupts the heap. Same hazard for `String::from_raw_parts`.
- Returning a raw pointer from an `extern "C"` function without an accompanying `extern "C" fn drop_T(p: *mut T)` (or equivalent) that the documented contract requires the C side to call. "The caller will know to free it" is wishful thinking that compiles and tests fine.
- `#[no_mangle]` on functions that are not actually FFI entry points. Each such symbol is a candidate for silent linker collisions across crates.
- **Freeing/dropping a callback context before its registration is unregistered *and* all in-flight callbacks are confirmed drained.** The classic user-data trampoline — `Box::into_raw` a context, register `(extern "C" fn trampoline, *mut c_void)` with the C library — is right up to the *temporal* contract: the C side holds a raw pointer to your context that Rust does not track, so if `Drop` frees the context while the library can still fire (it delivers asynchronously on its own thread; deregistration is itself async and only stops delivery *eventually*; or the free simply happens before the unregister), the trampoline dereferences a dangling `*mut c_void` — a use-after-free that a synchronous test stub (register, fire once, deregister) never reaches. A well-behaved stub is green; the async production library corrupts the heap.
- **Reclaiming `user_data` as an *owning* `Box<F>` inside a re-invocable trampoline.** `let f = unsafe { Box::from_raw(p as *mut F) };` inside a callback that fires more than once drops the context on the **first** invocation, making every later invocation a use-after-free **and** a double-free. The trampoline must **borrow** (`&mut *(p as *mut Ctx)`), never take ownership — ownership is reclaimed exactly **once**, at teardown, after the drain in the rule above.
- **Exporting a Rust entry point (`#[unsafe(no_mangle)]`/`#[no_mangle]` + `extern "C"`) that takes `&T`, `&mut T`, `&str`, `bool`, `char`, or a non-`#[repr(int)]`-validated `enum` directly from the foreign caller.** These are *safe* Rust types with validity invariants the compiler assumes hold — but the caller is C, which can pass a NULL/misaligned/dangling reference, a non-UTF-8 `&str`, a `bool` that is neither 0 nor 1, an out-of-range discriminant. *Producing* an invalid value at any of these types is immediate UB **inside your "safe" Rust body** — the moment the reference/`str`/`bool`/enum parameter exists, before you read it — and the declaration compiles without a warning while Rust-side tests calling it with valid values pass. (Rust 2024's `unsafe(no_mangle)` acknowledges the export is a soundness liability; it does **not** force parameter validation.) This is the **read-direction mirror** of §B5's "validate raw bytes → `Result` *before* minting the typed value" rule, applied to the **export surface**: the boundary is where untrusted bits enter, so the typed value must not exist until they are checked — exactly as §B5's serialize-out padding bullet is the write-direction dual of the same rule.

**REQUIRED**:
- Wrap every panic-capable Rust function callable from C with `std::panic::catch_unwind`; translate `Err(payload)` into a stable error code (a tagged union, a `-1` sentinel, an out-parameter for `*mut PanicInfo`) that the C side can match on. Document the encoding on the function's doc comment. **Precondition:** `catch_unwind` catches only an *unwinding* panic — under `panic = "abort"` the process aborts before the catch runs, so the boundary is unprotected; the FFI guard assumes `panic = "unwind"` (and you may compile this crate with `panic = "unwind"` even when the rest aborts). `catch_unwind` requires an `UnwindSafe` closure — most FFI bodies are, but if you reach for `AssertUnwindSafe`, confirm no caller observes broken invariants after the catch rather than wrapping blindly.
- For every Rust-owned type `T` that crosses the boundary, ship a paired `extern "C" fn rust_drop_T(p: *mut T)` performing `unsafe { let _ = Box::from_raw(p); }`. Document the contract on both functions: caller owns the pointer until it calls `rust_drop_T`; the C side must not call `free()` on this pointer, ever.
- For `Vec<T>` crossing the boundary, decompose with `ManuallyDrop<Vec<T>>` (MSRV-safe) or `Vec::into_raw_parts` (MSRV ≥ 1.93, if confirmed by your toolchain) and ship the tuple as three values, plus a paired free function. Document that the C side must pass *all three* back unchanged to release the buffer.
- For every `#[repr(C)]` struct crossing the boundary, verify the layout against the C header. On nightly: `cargo +nightly rustc --lib -- -Zprint-type-sizes` prints field-by-field sizes and offsets for every type in the crate. On stable, write a unit test that asserts `std::mem::size_of::<MyStruct>()`, `std::mem::align_of::<MyStruct>()`, and `std::mem::offset_of!(MyStruct, field)` against the values expected by the C side. If you use `bindgen`, pin its output (commit the generated file) so changes show up in diff review. Field order, padding, and alignment must match the C side byte-for-byte.
- **Callback context lifetime: unregister → confirm in-flight callbacks are drained → free, in that order.** For a registered `(trampoline, *mut Ctx)`: teardown first calls the library's unregister/stop function, then synchronizes with any in-flight or queued invocations *per the library's documented delivery model* (a synchronous "no callback runs after stop returns" guarantee, or an explicit barrier/join if delivery is on the library's own thread), and *only then* reclaims the context (`Box::from_raw`) — exactly once. Inside the trampoline, **borrow** the context (`&mut *(p as *mut Ctx)`); never `Box::from_raw` it there. State in the `// SAFETY:` block whether the library may invoke the callback from **another thread** — if it can, the context's contents need `Send`/synchronization (feeds §B18) and the C library's own reentrancy/thread-safety contract must be audited (§B25a). Calibration: a wrapper that has done this — documented unregister-is-synchronous, single-threaded delivery, borrow-not-own trampoline, `// SAFETY:` citing the drain guarantee — is correct and not a finding; the ban is on the *free-before-drain* / *own-in-trampoline* shapes, not on callbacks per se.
- **Exported entry points take only raw pointers and primitive integers; the body validates before any typed value exists.** An `extern "C"` fn exposed to a foreign caller takes `*const T`/`*mut T` (+ explicit lengths) and `#[repr(int)]`/primitive scalars — never `&T`, `&str`, `bool`, or a plain `enum` — and its body checks null, alignment, length, UTF-8 (`str::from_utf8` → error code), and discriminant range *before* it mints any reference or typed value, returning a stable error code (not a panic — see the `catch_unwind` rule) on bad input. This is the export-surface application of §B5's validate-before-mint boundary rule: the check runs on the raw representation, and the invalid typed value is never *produced*. A `pub unsafe fn` marker fixes only the Rust-side contract — it is invisible to the C caller — so it does not substitute for the validation.
- **Per wrapped C function, the `// SAFETY:` block states the ownership direction *with a citation to the specific C doc line/section*.** Real C libraries are **not** uniform: within one library `set_name(obj, s)` may copy its argument, `set_payload(obj, p)` may take ownership of it, `get_name()` may return a borrowed pointer into the object while `get_error()` returns a `malloc`'d string the caller must free — and conventions drift between library versions. So the audit is **per function, not per library**: for each wrapped call record, from the C documentation, who allocates, who frees, and whether a returned pointer is borrowed-from-internal or caller-owned, and encode that in the `// SAFETY:` block with the doc citation. A single uniform wrapper pattern (always `CString::into_raw`, always freeing a returned `*const c_char`) is right for some functions and a double-free or unbounded leak for the others — and a symmetric test stub passes either way. An **undocumented** ownership direction is not a guess: it is a §B5-style block-and-ask (the caller-invariant is unstated → the unsafe-invariants Blocking case).
- Add miri to CI for every file containing `extern "C"` blocks, exactly as §B5 requires for any `unsafe` — but note miri **interprets Rust, it does not run native code**: it cannot execute a real `extern "C"` call into a C library (it aborts with "unsupported operation: can't call foreign function" unless a shim exists). Point miri at the **Rust-side** of the boundary (pointer provenance, `#[repr(C)]` layout, the `from_raw_parts` / `Box::from_raw` ownership invariants) and isolate the actual foreign call behind `#[cfg(not(miri))]` (or a `#[cfg(miri)]` mock) so CI exercises what miri can verify instead of failing on the unsupported call.

## §B25a. The C library's own concurrency contract (not your wrapper's data)

**The trap**: the LLM wraps a C library, satisfies the compiler, and calls it from many tokio tasks or threads — but the property that decides soundness lives in *the library's* code, not in the Rust wrapper. This is a genuinely different failure locus from §B25: §B25 is about the correctness of the boundary code *you* write (panics you emit, the ABI of types you pass, the ownership of pointers you mint); §B25a is about a contract of code you did **not** write and cannot see — whether the C library is thread-safe / reentrant at all, and what it demands of `init` and globals. No amount of correctness in the wrapper's own data closes it, and — the reason this is its own section — the standard §B18 fix **actively masks it**: wrapping the handle in `Arc<Mutex<RawHandle>>`, or handing each thread its own handle, synchronizes access to *the wrapper's data* while two independently-locked handles still race on the library's process-global state. The Rust `Mutex` an LLM reflexively adds guards the wrong object.

**Why it bites**: the library has internal global mutable state — `errno`-style globals, a `getenv`/`setenv` dependency, a global config struct, a non-reentrant parser with a shared scratch buffer, a one-time init (`curl_global_init`, OpenSSL <1.1 locking callbacks, an `Xinit`). It compiles; single-threaded and even light multi-threaded tests pass (glibc caches and timing make the race hard to hit); production segfaults under real concurrency. This is precisely **CVE-2020-26235** (RUSTSEC-2020-0071/0159): `time`/`chrono` called `localtime_r`, which reads `TZ` via `getenv`, racing a `setenv` from another thread — multithreaded programs dereferenced a dangling pointer and segfaulted. It shipped for years in two of the most-downloaded crates in the ecosystem. The data race → segfault/UB is invisible to tests, the same class as §B18 — but the fix is different.

**BANNED**:
- Writing `unsafe impl Send`/`Sync` for an FFI handle (or spreading calls across threads/tasks) **without first citing the library's documented thread-safety level** in the `// SAFETY:` block. "Each thread owns its own handle" is a true statement about the *wrapper* and does **not** establish that the *library* is safe to call concurrently — if the library keeps global state, per-handle ownership is insufficient and the impl is unsound.
- Giving a **non-thread-safe / non-reentrant** C library per-handle locks (the reflexive `Arc<Mutex<RawHandle>>` of §B18) and calling it from multiple threads. Per-handle locks do not serialize the library's *global* state; two handles under two independent locks race exactly as if there were no lock. This is the §B18 fix misapplied — correcting the reader's likely first move, not just adding new advice.
- Reading `std::io::Error::last_os_error()` (or the raw `errno`) **after** any intervening call — a logging call, an allocation, another FFI call, even some libc wrappers — that may itself set `errno`. `errno` is a per-thread global the very next call can clobber, so a delayed read reports the wrong (or no) error.

**REQUIRED**:
- **Audit the library's own thread-safety contract before deciding `Send`/`Sync` and what lock the wrapper needs.** Read the library's docs and cite the level: is it *per-handle thread-safe* (distinct handles may be used concurrently — then per-handle `Send` + the §B18 per-handle lock is correct), *global-lock-required* (any two calls into the library must be serialized — then one **process-global** lock, or a dedicated single owning thread the calls are marshalled to, not per-handle locks), or *init-once* (a `curl_global_init`-style one-time setup that must complete, once, before any other call — wrap it in a `Once`/`OnceLock`)? The chosen synchronization primitive's scope must match the scope of the state it protects.
- For a non-thread-safe library, serialize **all** calls through one lock or one dedicated thread (a global `Mutex<()>` taken around every call, or an actor/command-channel to a single owning thread) — and state that scope as the cited invariant of any `unsafe impl Send`/`Sync`. Cross-referenced from §B18: its per-handle `Arc<Mutex<RawHandle>>` fix is correct **only** when the library is per-handle thread-safe; verify that here first.
- Capture `Error::last_os_error()` **immediately** after the FFI call whose failure you are inspecting, before any other call runs, and store the value — do not let logging, allocation, or a second FFI call sit between the failing call and the `errno` read.
- If the library documents callbacks delivered from its own threads (see §B25's callback-lifetime rule), the context's contents and any shared state they touch fall under this same contract — audit it here, not just at the `Send` impl.

🔴 — surface every FFI wrapper that spreads calls across threads/tasks without a cited library-thread-safety level, alongside the §B18 manual-`Send`/`Sync` items, in the post-flight summary.

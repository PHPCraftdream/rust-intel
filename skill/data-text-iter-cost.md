## §B28. UTF-8 and string-boundary hazards

**The trap**: string operations that are correct on ASCII and panic or corrupt on non-ASCII. Tests on `"hello"` are always green; the panic is deterministic on the first accented name, emoji, Cyrillic, or CJK character in production.

**BANNED**:
- `&s[a..b]` with computed indices without checking `s.is_char_boundary(_)` — it panics if an index lands inside a multi-byte UTF-8 character (`&"café"[0..4]` panics: 4 bytes, but the boundary is inside `é`).
- Conflating `s.len()` (a count of **bytes**) with a count of characters: `s.len()` for "take the first N characters", for display width, or for limits. `"café".len() == 5`, not 4.
- `to_lowercase()` / `to_uppercase()` for comparing protocol/ASCII tokens — these are full Unicode transformations and can change length (`ß` → `SS` under `to_uppercase`; Turkish `İ` → `i̇` under `to_lowercase`). For ASCII protocols use `eq_ignore_ascii_case` / `to_ascii_lowercase`.
- Decoding bytes to text by code-point cast: `bytes.iter().map(|&b| b as char).collect::<String>()` is a Latin-1 mojibake machine, not a UTF-8 decoder — it maps each *byte* to the Unicode code point with the same number (`"héllo".as_bytes()` re-decodes to `hÃ©llo`). Decode with `String::from_utf8` and handle the error; `String::from_utf8_lossy` only where the result is **displayed** (a log line, a UI label) — it replaces every invalid sequence with U+FFFD and is not a decoder for data that is written back, compared, hashed or used as a name (next bullet).
- **Forcing operating-system byte data through `String`.** File names, `argv`, environment values and the contents of files or pipes are *bytes* (on Windows, potentially ill-formed UTF-16), not UTF-8 text, and each of the three reflexive conversions fails differently on the first non-UTF-8 input: **(1) lossy** — `String::from_utf8_lossy`, `Path::to_string_lossy`, `display()` output reused as data — silently corrupts what is passed through (CVE-2026-35346, uutils `comm`: lossy UTF-8 conversion on all output lines replaced invalid bytes with U+FFFD where GNU `comm` preserves the raw bytes; fixed in 0.6.0); **(2) strict + panic** — `path.to_str().unwrap()`, `String::from_utf8(b).expect(..)`, `OsString::into_string().unwrap()`, and `std::env::args()` / `env::vars()` themselves, which panic on a non-Unicode argument or variable — is a denial of service from a legal file name (CVE-2026-35348, uutils `sort --files0-from`: process panic on non-UTF-8 filenames); **(3) strict + skip** — `.filter_map(|e| e.to_str())`, `into_string().ok()` — silently drops entries, so a listing, backup or security scan omits exactly the items an attacker named that way. Tests with ASCII names pass all three. REQUIRED: keep `&[u8]` / `OsStr` / `OsString` / `Path` end to end for data that is passed through, compared or written back; take arguments and environment through `env::args_os()` / `env::vars_os()` / `env::var_os`; write bytes with `write_all` (on Unix `OsStrExt::as_bytes`), not `format!`. Convert to `str` only at a boundary that genuinely needs text, and there decide explicitly: reject with an error that names the item, or mark the display copy as lossy. Test with a non-UTF-8 file name (`OsStr::from_bytes(b"\xff")` on Unix) through every path that lists, copies or prints names.
- Splitting lines with `s.split('\n')` and comparing whole lines: on CRLF input every "line" ends in `'\r'`, so `line == "quit"` never matches. Use `str::lines()`, which strips a trailing `\r`.
- Truncating a `String` at a byte length: `s.truncate(50)` panics if byte 50 lands inside a multi-byte UTF-8 character (it is a byte index, not a char count). Cut on a boundary instead: `&s[..s.floor_char_boundary(50)]` (stable since Rust 1.91) or `s.get(..50)` handled as `Option`.
- `c.is_numeric()` as "is a decimal digit": it is the Unicode `Nd`/`Nl`/`No` property test, so it accepts `٣` (Arabic-Indic three) and `½` (vulgar fraction one-half); the reflexive follow-up `c.to_digit(10).unwrap()` then panics on exactly the inputs the check let through. Use `is_ascii_digit()` for ASCII, and handle the `Option` from `to_digit(10)` otherwise.

**REQUIRED**:
- `s.get(a..b)` (returns `Option<&str>`, never panics) instead of `&s[a..b]` for computed bounds; `char_indices()` for iteration with byte positions; `chars().take(n)` for "the first N characters".
- For correct grapheme-boundary handling (emoji clusters, combining characters) use the `unicode-segmentation` crate (`graphemes(true)`); `chars()` alone splits on code points, not graphemes.
- Casing is three distinct jobs — do not conflate them. **(a) ASCII protocol token matching:** `eq_ignore_ascii_case` / `to_ascii_lowercase`. **(b) genuine Unicode caseless matching** (comparison only — never store or display the folded form): full case folding *plus* Unicode normalization — Unicode's default caseless match normalizes after folding (the W3C string-matching canonical case-fold step is `NFD(casefold(NFD(s)))`), and the Unicode FAQ is explicit that case-folded text "should be used solely for internal processing and generally should not be stored or displayed to the end user". **(c) user-facing display text: preserve the user's original casing** — do not case-fold for display; `to_lowercase()`/`to_uppercase()` are lossy display transformations (the `ß`→`SS` above does not round-trip), not normalizers.

## §B29. Iterator and slice adapter traps

**The trap**: the most common surface in LLM-generated Rust is also where several `std` adapters have silent, non-obvious semantics. The code compiles, `clippy` is quiet, and tests on equal-length / small / sorted inputs are green — then production data hits an edge the adapter handles differently than the LLM assumed.

**Specifically dangerous patterns**:
- **`zip` silently truncates to the shorter side.** `a.iter().zip(b.iter())` yields `min(a.len(), b.len())` pairs — unmatched elements are not paired and no mismatch error is returned. When equal lengths are part of the contract (rows and headers, keys and values), validate them first. Reject an untrusted-input mismatch with a typed error; `assert_eq!` / `itertools::zip_eq` are appropriate for programmer invariants, not as input-rejection mechanisms. `zip_eq` detects a mismatch only when iteration advances past the shorter side, so a short-circuiting consumer (`take`, early `break`, `any`/`all`) can stop without detecting it. For a consumption-independent guarantee, compare slice or `ExactSizeIterator` lengths up front, then use plain `zip`; the lazy check does not replace that validation.
- **`Vec::dedup` only removes *consecutive* duplicates.** On an unsorted vector it does **not** produce a set: `[1,2,1,1,3,3,2]` dedups to `[1,2,1,3,2]`. For set semantics, `sort` first (then `dedup`) or collect into a `HashSet`/`BTreeSet`.
- **`chunks(0)`, `windows(0)`, `step_by(0)` panic.** A zero chunk/window/step size is a runtime panic, not an empty iterator. When the size comes from config or untrusted input, this is a remote panic / DoS.
- **`collect` into a `HashMap`/`HashSet` silently collapses duplicates — do not design against a promised survivor.** At the `FromIterator`/`collect` contract level the only promise is coalescing: `HashMap`'s own `FromIterator` doc says "If the iterator produces any pairs with equal keys, all but one of the corresponding values will be dropped" — it does not promise *which* one survives (and `HashSet`'s `FromIterator` documents nothing at all; only its `From<[T; N]>` states the coalescing). Current implementations do behave deterministically, but that flows through `insert`'s own documented behavior, not a `collect`-level contract: `HashMap::insert` replaces the stored value and returns the old one, so the last value per key wins *today*; `HashSet::insert` returns `false` and keeps the **original stored element** — std documents "the set is not modified: original value is not replaced, and the value passed as argument is dropped" (use `HashSet::replace` when you want replacement). When survivor identity is actually load-bearing — first-wins vs last-wins as a design contract — write the explicit, self-documented loop (`for (k, v) in pairs { map.insert(k, v); }`) so the behavior is pinned by code you wrote and reviewed, not by a trait impl's incidental delegation. Either way the resulting `len` is smaller than the input — silent loss when the input was supposed to be unique.
- **`take_while` consumes the failing element.** `it.by_ref().take_while(|l| !l.is_empty())` removes the delimiter (or first body line) from the iterator — the element that made the predicate false is consumed and lost, so the code after the loop cannot read it. If you need it back, use `peekable()` and `next_if()`: peek, decide, consume only when the predicate says so.
- **Adapter order sets the index origin.** `lines.skip(1).enumerate()` numbers from 0 starting at the *second* line; `lines.enumerate().skip(1)` keeps the original indices starting at 1 — logic written against one and refactored to the other silently shifts (or drops) the header row.
- **`max_by_key` returns the *last* maximum, `min_by_key` the *first* minimum** (std documents both). On ties, "first item wins" logic built on `max_by_key` picks a different element than any test with distinct keys exercises. Make ties deliberate: `.rev()` before `max_by_key` for first-max, or an explicit tie-break in the key.

**REQUIRED**:
- When equal lengths are required, validate them up front with slice / `ExactSizeIterator::len()` when available, returning an error for an untrusted-input mismatch. Reserve assertions for programmer invariants. For iterators without a known length, choose a bounded validation strategy that can detect the mismatch before relying on equality; a short-circuited `zip_eq` is not evidence of equal lengths.
- Treat any chunk/window/step size derived from input as untrusted: guard `> 0` before calling.
- When collecting key/value pairs that must be unique, verify uniqueness rather than letting `collect` coalesce silently.

**BANNED**:
- `Vec::dedup` where adjacency of duplicates is not a proven invariant — flag a `.dedup()` with no `sort`/grouping visibly preceding it (it removes only *consecutive* duplicates, so on unsorted data it is not set-deduplication).
- A chunk/window/step size flowing from config or the network into `chunks` / `windows` / `step_by` without a `> 0` guard.

## §C4. Iterator and allocation discipline

**The trap**: unnecessary `clone()` on `Copy` types, materializing collections mid-chain with `collect::<Vec<_>>()` only to iterate again, `format!` in hot paths, treating `String` as the default string type everywhere.

**REQUIRED**:
- Profile before defending these on micro grounds — this "profile first" caveat is about *micro-costs* (an extra allocation, a `format!`, a redundant `clone`). It does **not** apply to the algorithmic-complexity items in BANNED below: an accidental O(n²) (`remove(0)`/`contains` in a loop) is a defect to fix on sight, not a micro-optimization to defer to a profiler. As defaults:
- Prefer `&str` and `&[T]` in function signatures over `String` and `Vec<T>`.
- Iterator chains stay lazy: avoid intermediate `.collect()` unless the next stage requires materialization.
- For hot paths, write to a `&mut impl io::Write` or `&mut String` via `write!`/`writeln!` rather than allocating with `format!`.
- `clone()` is fine when needed; per this module's 🟡 tier semantics, surface it in the summary **only when it is load-bearing or non-obvious** (a large/allocation-heavy clone, a clone hiding an ownership-design question, a clone on a hot/per-request path) — routine small clones on cold paths are write-time discipline, not reportable findings.

**BANNED**:
- `Vec::remove(0)` / `Vec::insert(0, _)` in a loop (each is O(n) — it shifts the whole tail), turning an O(n) pass into O(n²); likewise `Vec::contains` inside a loop is O(n²). Tests on small N pass; production degrades to seconds/minutes at scale. Use `VecDeque` for FIFO (O(1) front ops), `swap_remove` when order doesn't matter, or a `HashSet` / `retain` instead of repeated `contains`.
- `{:?}` (Debug) on `&[u8]` / `Vec<u8>` for hashes, checksums, IDs, or wire frames — it prints a decimal array `[222, 173, 190, 239]`, not hex. Use `hex::encode` (or a `LowerHex` newtype) for byte diagnostics. (For *secret* bytes, see §B12 — don't log them at all.)
- Treating a single `io::Read::read(&mut buf)` as if it fills `buf`, or a single `Write::write(data)` as if it writes all of `data`. Both may return `Ok(n)` with `n < len` even without EOF (sockets, pipes, large buffers). The code compiles, tests pass on small local buffers where one call happens to transfer everything, and production truncates or splices messages under load / over the network. Use `read_exact` / `write_all`, or loop until the count is satisfied; reserve bare `read`/`write` for code that genuinely handles short transfers. **`read_to_end` is not a general remedy here** — it appends to the buffer until EOF with no byte limit, and std's own usage notes warn that on a continuous stream that never sends EOF (a socket, a stalling peer, `yes |`) it blocks indefinitely while growing the buffer: on untrusted/continuous input it trades the short-read bug for a §B7-class memory-exhaustion DoS. Scope `read_to_end` to bounded/trusted EOF sources (a fully-read local file, an in-memory cursor, a validated frame); for untrusted or continuous input use checked/capped framing plus `read_exact` for known lengths, or — for genuinely EOF-delimited untrusted input — `Read::take(<explicit cap>)` plus a deadline/progress policy and explicit over-limit error handling.
- A `std::io::BufWriter` flushes on drop (`tokio::io::BufWriter` does not — its buffer is discarded on drop, `async-machinery.md` §B15b), but the implicit flush in `Drop` **discards any `io::Result`**. On a failing writer (disk full, broken pipe, closed socket) the last buffered bytes are lost with no error surfaced. Call `.flush()?` explicitly before the writer is dropped when the data must be durable. Separately, `BufReader` has nothing to flush and does not flush on drop: dropping one simply discards any unread buffered input bytes — a distinct, much lower-stakes behavior, not this durability hazard.

## §E2. Allocation that need not happen — *Cheap once, ruinous in a loop.*

- **Where it shows up**: reflexive `.clone()`/`.to_vec()`/`.to_string()` to dodge a borrow (§C5); an intermediate `.collect::<Vec<_>>()` only to iterate once; `Vec`/`String` grown by `push` in a loop with no `with_capacity` when the size is known; `format!` where `write!`/`Display`/`push_str` would write in place; returning owned `Vec`/`String` where `impl Iterator`/`&[T]`/`Cow<'_, str>` (§B1b) would let the caller decide; `Box`/`Arc` that buys nothing; a large struct passed by value where `&T` suffices.
- **The cheaper move**: borrow don't clone; take `&str`/`&[T]`, return `Cow` when ownership is conditional; pre-size with `with_capacity`/`reserve`; stream with iterators instead of materializing; reuse a scratch buffer (`clear()` + refill) across iterations and calls; `bytes::Bytes` for shared/zero-copy network buffers.
- **Ownership transfer from `&mut self`**: when the next stage needs ownership of a field and the original need not remain in `self`, consider `std::mem::take(&mut self.field)` instead of cloning it. It returns the old value and installs `T::default()`; `std::mem::replace(&mut self.field, replacement)` uses an explicit replacement without a `Default` bound. For `Option<T>`, prefer `self.field.take()`, leaving `None` without requiring `T: Default`. A handoff that empties the source is the intended case; a clone that preserves a snapshot or the original on failure is not interchangeable with a take — preserve the contract (§B19). If borrowing suffices, keep the work on `&T` / `&mut T`.
- **Cost and buffer reuse**: taking a `Vec` or `String` transfers its existing buffer without cloning elements or allocating a replacement buffer; its capacity travels with the returned value. Repeated take-and-refill of the emptied field can allocate again unless a reusable buffer comes back — use in-place processing, `clear()` + refill, or `mem::swap` with a recycled spare buffer when that fits the handoff. For arbitrary `T`, `Default::default()` can allocate, perform work, or panic, and moving an inline value can be size-dependent. Neither `take` nor constructing a `replace` argument is universally zero-cost; measure the complete cycle (§E6).
- **Reuse the destination when a copy is required**: repeated `dst = src.clone()` for `Vec`/`String` replaces the destination's allocation. Consider `dst.clone_from(&src)` for an existing owned destination, or `src.clone_into(&mut dst)` for a borrowed slice/`str` and its owned destination. These implementations can reuse destination capacity; `Vec::clone_from` can also reuse elements' resources when their `clone_from` supports it. The generic trait default promises no allocation saving, and growth may still allocate. Preserve failure semantics (§B19): an in-place implementation can leave a partially updated destination if element cloning panics; a panic while computing a separate `src.clone()` occurs before assignment to `dst`.
- **Preserve useful capacity across growth cycles**: `reserve_exact(1)` before every `push` gives up deliberate spare-capacity growth and can cause repeated reallocation/copying; shrinking between batches can force the next refill to grow again. Prefer normal amortized growth or reserve a validated batch size once. Keep useful capacity for recurring work; reclaim an exceptional high-water allocation at a phase boundary under a workload-based retention policy. `shrink_to_fit` may reallocate and need not achieve an exact capacity or reduce process RSS; `shrink_to(n)` sets a lower bound, not a maximum. Measure retained memory as well as allocation churn (§E6).
- **Zero-copy views retain backing storage**: a small, long-lived slice of a heap-backed `bytes::Bytes` can keep the whole backing allocation alive after the original handle is dropped. At a cache/queue boundary, compare the view's useful bytes and lifetime with the storage it retains (§B14); when retention dominates, consider `Bytes::copy_from_slice(view.as_ref())` to detach that fragment. The old allocation becomes reclaimable only after its remaining owners are gone; detaching can increase peak memory before they are dropped. Keep sharing for short-lived pipeline views or when the backing storage is needed anyway; the shared-allocation contract does not imply a universal memory saving.
- **Take capacities and the allocator from measurement, not from a guessed constant.** A `with_capacity(64)` copied from an example is either wasted memory or a regrowth ladder; the right number is the observed peak of *that call site* on real workloads. `captrack` (a crate by this skill's maintainer; 0.1.x, MSRV 1.85) records it: replace the constructor at the sites you care about with its named macro (`tvec!("module/rows", 64)`, `tmap!`, `tstring!`, `tbytesmut!`, … — 17 macros), build with `features = ["telemetry"]` in a bench or test profile, and `captrack::dump_capacity_stats("path.json")` writes per-site `creation_count` and a reservoir sample of observed capacities; with the feature off each macro expands to the bare constructor, so production pays nothing. `captrack-pgo` works on unmodified code — it temporarily instruments the workspace, runs tests and benches, and proposes `with_capacity(N)` from a chosen percentile (`--cap-from p95|p99|max|…`), leaving sites with fewer than 10 observations, runtime-computed capacities and sites within 4× of the current value alone. Read the figures with its own caveats: capacity-based collections record `capacity()` (a peak, since capacity only grows), length-based ones (`BTreeMap`, `DashMap`, `scc`) record `len()` at drop and undercount if the collection shrank first; a percentile of a skewed benchmark is still a guess about production (`dhat` is the alternative source of the same data). The same rule applies one level up: when a profile shows allocator time — contention between threads freeing and allocating, or a slow default allocator on the target platform — swapping the process-wide `#[global_allocator]` is a one-line change worth measuring: `mimalloc` or `tikv-jemallocator` (both C-backed). Never switch allocators on the strength of any README: run the project's own allocation-heavy benchmark, with the real thread count, on the target OS, before and after (§E6).
- **Leave it when**: one-shot on a cold path, the clone is of a `Copy`/tiny type, or removing it tangles lifetimes for no measured gain. `clippy::perf` flags the obvious cases (`useless_vec`; `inefficient_to_string` sits in `pedantic`, not `perf`); `redundant_clone`/`needless_collect` live in `nursery` (allow-by-default) and need an explicit `-W` — the Post-flight command enables `-W clippy::redundant_clone`.
- 🟢 + 🟡. Cross: §C5, §B1b. For the full lookup table of representation swaps, see the **Substitution catalog** below.

## §E3. Complexity that compounds — *An O(n²) invisible at n=10 is an outage at n=10⁴.*

- **Where it shows up**: accidental quadratic — `.contains()`/`.position()`/`Vec::remove(0)`/`insert(0, _)` inside a loop (§C4); a nested-loop join that re-scans the inner collection per outer element; rebuilding or re-sorting a collection every iteration. The wrong container for the access pattern: `Vec` used for membership, front-insertion, or keyed lookup.
- **The cheaper move**: hoist the inner collection into a `HashSet`/`HashMap` once, then O(1) lookup; `VecDeque` for front/back queues; `swap_remove` when order is free; `SmallVec`/`ArrayVec` for almost-always-tiny collections; `BTreeMap` for ordered iteration; a `match` or fixed array (or `phf`) for tiny static key sets; sort once, not per iteration.
- **Sparse map scans**: std `HashMap::iter`/`keys`/`values` currently scan empty buckets too, so their full traversal is O(capacity), not O(len). A map that grew for a burst and then lost most entries can remain expensive to scan. If scans dominate, consider shrinking/rebuilding once at a phase boundary or a dense iteration representation whose lookup/update semantics fit. Include the rebuild and any later regrowth in the measurement; neither rebuilding on every scan nor assuming this implementation detail applies to every map is a remedy.
- **Select only the needed ranks**: full sorting before keeping only the best k elements can do work the result never uses. For `0 < k < n`, `select_nth_unstable(k)` partitions the k smallest elements into the preceding slice; sort that slice only if ordered output is required, using the same ordering as selection. This gives O(n + k log k) comparisons with a constant-cost ordering, derived from linear selection plus prefix sorting. Handle `k == 0` and `k == n` separately, and reject or clamp `k > n` according to the API contract — selecting index `n` panics. Selection mutates the input and is unstable; preserve the required membership/order among tied keys with an explicit tie-breaker (such as original position) or keep the stable algorithm.
- **Cache expensive sort keys**: a comparator or `sort_by_key` can repeatedly parse/normalize the same element. Consider `sort_by_cached_key` when that key work dominates: it computes a key at most once per element using temporary storage. Require a stable, non-panicking key for every admissible element and no dependence on the number/order of key-function calls; compute fallible keys separately and handle their errors before sorting. Purity alone is insufficient: the two algorithms may evaluate different keys before returning or panicking, even with a stateless function. Account for the extra key storage; simple field-access keys often favor `sort_by_key`. Preserve the ordering and failure contract (§E5); the cached sort preserves equal-key order, not an identical evaluation schedule.
- **Leave it when**: n is provably small and bounded (a 3-element config), or the path is cold. Algorithmic complexity is the one performance class worth fixing without a profiler — unlike micro-allocation, it does not wait for load to hurt.
- 🟡 (escalate to surface on a per-request path). Cross: §C4. Verify any new crate before adding — §A1. For the full lookup table of representation swaps, see the **Substitution catalog** below.

## Substitution catalog — a cheaper representation for the same job (Tier E appendix)

A write-time lookup table for §E2/§E3/§E4: when the code contains the pattern in the left column, *propose* the right column — with the gate in the third. This is a catalog, not a mandate: every row is 🟡 under §E6's measure-first law. Propose a swap when the path is hot / per-request or the change is free; never rewrite working code for an unmeasured win, and never trade an API's clarity for a micro-gain. Any row introducing a new crate goes through §A1 verification first. Audit semantics: rows here are suggestions, not findings — report one only when it coincides with a genuine §E2/§E3/§E4 hazard on a hot path.

**Ownership & allocation** (§E2's domain):

| You wrote | Consider | Gate — when it pays / when to leave it |
|---|---|---|
| `.clone()` / `.to_string()` / `.to_vec()` to satisfy the borrow checker | `&T` / `&str` / `&[T]`; `Cow<'_, str>` when ownership is conditional | Always worth a look (§C5); leave when the type is `Copy`/tiny or the path is cold |
| Cloning a field only to transfer ownership from `&mut self` | `mem::take`; `Option::take`; `mem::replace` for an explicit replacement | Source may be emptied/replaced; preserve snapshot and failure guarantees (§B19); account for replacement cost and buffer reuse (§E2) |
| Repeatedly assigning a fresh clone into an existing owned buffer | `clone_from`; borrowed slice/`str` → `clone_into` | Reuse-capable implementation and useful destination capacity; preserve panic guarantees (§E2/§B19) |
| Repeated exact reservation or shrinking between refills | Amortized growth; reserve a batch once; reclaim exceptional capacity at phase boundaries | Balance churn against retained memory; `shrink_to` is not a capacity ceiling (§E2) |
| `Vec::new()` / `HashMap::new()` / `with_capacity(<guessed constant>)` at a hot allocation site | `with_capacity(N)` with N from the site's measured p95/p99 — `captrack` (`tvec!`/`tmap!` + `telemetry`, off = zero cost) and `captrack-pgo` (proposes/applies), or `dhat` | Hot, allocation-dominated site with enough observations (captrack-pgo ignores < 10); a length-based collection undercounts a shrunk peak; leave cold sites alone (§E6) |
| Allocation-heavy multi-threaded process on the default allocator, with the profile showing allocator time | A process-wide `#[global_allocator]`: `mimalloc` / `tikv-jemallocator` (C-backed) | Allocator cost is in the profile, not assumed; measure on the real thread count and target OS — see §E2; new dep → §A1 |
| Cloning a large immutable value into many tasks/threads | `Arc<T>` (also `Arc<str>`, `Arc<[T]>`) — clone becomes a refcount bump | Value is immutable after construction; if it mutates, that's §A2/§E4 territory, not this row |
| Copying byte buffers between pipeline stages | `bytes::Bytes` / `BytesMut` — refcounted zero-copy slicing | Multi-stage byte pipelines (network, framing); check backing-storage retention for long-lived fragments (§E2) |
| Caching a small `Bytes` slice of a much larger heap allocation | A detached fragment via `Bytes::copy_from_slice` | Useful only when releasing other owners makes the large allocation reclaimable (§E2/§B14) |
| `BufRead::lines()` producing owned strings that are consumed immediately | Reused `String` + `clear()` / `read_line`; bytes → `read_until` | Preserve delimiter, UTF-8, EOF/error and size-limit semantics; `str::lines()` already borrows (§E5) |
| Millions of short heap `String`s (ids, tags, tokens) | `compact_str` / `smol_str` — inline small-string optimization | Profile shows string-alloc churn; new dep → §A1 |
| A `Vec<T>` field that almost always holds ≤ N small items | `smallvec::SmallVec<[T; N]>` — inline until spill; `arrayvec` for strictly stack-only; `tinyvec` when a 100%-safe dep matters | Hot, allocation-dominated, N genuinely small; otherwise it just bloats the struct and adds a spill branch |
| `format!` in a hot loop (map keys, log lines, numbers) | `write!` into a reused buffer; `itoa`/`ryu` for hot int/float → string (for integers, std's `{integer}::format_into` + `core::fmt::NumBuffer`, stable since Rust 1.98, are the in-std equivalent — documented as matching the dedicated `itoa` library) | Hot serialization paths; keep `format!` everywhere cold — readability wins |

**Lookup & complexity** (§E3's domain):

| You wrote | Consider | Gate — when it pays / when to leave it |
|---|---|---|
| `vec.contains(x)` / `.position()` inside a loop | Hoist into a `HashSet`/`HashMap` once → O(1) per probe | n can grow; leave for tiny bounded n (a 3-element config) |
| `Vec::remove(0)` / `insert(0, _)` | `VecDeque` (`push_front`/`pop_front` are O(1)); `swap_remove` when order is free | Queue-shaped access (§C4) |
| Re-sorting per iteration; repeated min/max extraction | Sort once outside the loop; `BinaryHeap` for repeated extract-min/max | — |
| Full sort just to retain a small best-k subset | `select_nth_unstable` + optional prefix sort | Input mutation, tie policy and k boundaries must fit (§E3) |
| Recomputing an expensive key during sorting | `sort_by_cached_key` | Stable, non-panicking, side-effect-free key; saved computation outweighs temporary storage (§E3/§E5) |
| Frequent scans of a `HashMap` whose capacity greatly exceeds its length | Phase-boundary shrink/rebuild, or dense iteration storage | Current std scans cost O(capacity); amortize rebuild/regrowth and preserve map semantics (§E3) |
| `HashMap<usize, T>` with dense, small integer keys | Index a `Vec<T>` / `Vec<Option<T>>` directly; `slab`/`slotmap` when slots are reused and keys must stay stable | Keys dense (0..n); sparse ids → keep the map |
| `HashSet<usize>` membership over dense integer ids | A bitset (`fixedbitset` / `bitvec`) — 1 bit per id, cache-friendly | Dense universe; sparse → keep the set |
| Dispatch over a small fixed string/key set | `match` on the literal, a const array, or `phf` (compile-time perfect hash) | Keys known at compile time |
| A tiny *dynamic* map (N ≲ 32 small entries — a heuristic) on a hot path | `Vec<(K, V)>` with linear scan | Below a few dozen small entries a linear scan often beats hashing (no hash, better cache locality) — a **workload-dependent crossover heuristic, not a fixed universal number**: the winning N shifts with key/value size, comparison cost, and cache behavior, so measure on your own access shape (§E6); re-measure if N can grow |
| Keyed lookup *plus* ordered iteration / range queries / repeated min-max | `BTreeMap`/`BTreeSet` — cache-friendly B-tree, `range()` for free | You actually use the ordering; for pure point lookups the hash map wins |
| Output, serde snapshot, or a test depends on map iteration order | `indexmap::IndexMap`/`IndexSet` — hash map preserving insertion order | Deterministic iteration wanted by design — also the honest fix when a test depends on iteration order (std `HashMap`'s is random per process; pinning it via the test is a §D1 flake) |
| Hand-rolled byte scanning | `memchr` / `memmem` — SIMD-accelerated search | Hot parsing loops; note std's `str::find` already uses these internally for common cases |

**Keys & hashing** (§E4/§B16's domain — the trust boundary rules there are canonical):

| You wrote | Consider | Gate — when it pays / when to leave it |
|---|---|---|
| Default `HashMap` (SipHash) on a hot path, keys you control | Pick by key shape: `rustc_hash::FxHashMap` for integer/tiny keys (what rustc itself runs on); `foldhash` for strings/medium keys (hashbrown's default since 0.15; `fast` and `quality` profiles); `ahash` (AES-NI, long-established) | **Trusted keys only** for a hasher with no per-instance keying at all — `FxHashMap` (fixed constants, not seeded) and `fnv` are never negotiable on untrusted input, full stop; §B16 owns that boundary. `ahash`'s and `foldhash`'s *default* modes are a narrower case: both randomize their seed per `RandomState`/process by default and advertise DoS resistance on that basis — the ban in §B16 targets a **fixed/predictable seed** configured into either of them, not their randomized default. The two hashers' documented DoS-resistance claims are not identical, though: `ahash`'s default `RandomState` documents itself as DoS-resistant against the default-random case without the extra hedge below. `foldhash` specifically carries one further, narrower stated exception under §B16 — its own docs disclaim protection against an *adaptive* attacker who can observe a long-running process and reverse-engineer its seed, leaving a proven non-interactive, single-shot pass over untrusted keys as the one case its default mode is **not automatically disqualified** for — not "confirmed safe": foldhash's own docs claim only *minimal* DoS resistance even there, a weaker claim than `ahash`'s; re-read §B16 for that scoping before relying on `foldhash`'s default mode against untrusted keys on a long-running or interactively-probeable service. Skip `fnv` (loses to Fx nearly everywhere today); `gxhash`/`wyhash` are niche wins behind §A1 + a target-CPU check (`gxhash` hard-requires AES intrinsics). The key-shape ranking above (Fx for integer/tiny keys, foldhash for strings/medium) is a **workload-dependent heuristic, not a fixed universal speed order** — relative hasher speed shifts with key-length distribution, table size, insert-vs-lookup mix, and CPU features (AES-NI among them); benchmark on your own keys (§E6) |
| `map.get(&key.to_string())` with a `&str` already in hand | `map.get(key)` — `Borrow<str>` makes the allocation pointless | Always |
| `contains_key` + `insert` pair | The `entry()` API — one hash lookup instead of two, and check-then-act atomicity per §B13 | Always (synchronous only — §B2's shard-guard rule if an `.await` follows) |

**Concurrent maps — pick by access shape** (§E4's domain; §B2's guard-across-`.await` rule applies to *every* guard-returning API here):

| Access shape | Consider | Gate — when it pays / when to leave it |
|---|---|---|
| Moderate mixed read/write from many threads | `dashmap::DashMap`/`DashSet` — N shards × `RwLock` over hashbrown | The de-facto standard; degrades under hot-key contention (all writers of one key queue on its shard); holding a `Ref` across `.await` deadlocks **on a conflicting access to the same shard** while the guard is parked across the await point — a writer (or a reader queued behind a pending writer) needs that shard's lock while the guard holder's await needs other work that needs the same shard to progress, or the resumed body re-locks the shard — not automatically on every read-only access to a *different* key/shard during the await (§B2) |
| Read-heavy, high concurrency — especially async | `scc::HashMap`/`HashIndex` — per-bucket locking, honest `*_async` methods, no stop-the-world resize; `papaya`/`flurry` for fully lock-free reads | `papaya` (2024+) and `flurry` are newer — §A1 verify and measure against `dashmap` on *your* access shape before switching |
| Reads ≫ writes, snapshot staleness acceptable | `arc_swap::ArcSwap<HashMap>` — rebuild and swap the whole snapshot; `evmap`/left-right — readers never block | The gate is the **consistency model**, not the speed: writes become visible on publish/refresh, not immediately — state that in a comment |
| Ordered iteration / range queries under concurrency | `crossbeam-skiplist` (`SkipMap`) / `scc::TreeIndex` | Ordered + concurrent without a global lock; single-threaded ordered → plain `BTreeMap` |
| A single global `Mutex<HashMap<…>>` bottleneck | First ask §A2/§E4's design question — does the data shard per key? is it read-mostly? — before reaching for any concurrent map | The catalog is not a license to skip the design step; a concurrent map on top of the wrong ownership shape just moves the queue |

**When NOT to substitute**: the profile is silent and the path is cold; the swap adds a dependency for a win nobody measured; the current type is part of a public API (§C1 — changing it is a semver event, not an optimization); or the "faster" structure loses a property the code relies on (ordering, stable addresses, iteration determinism). §E6 is the binding law of this table: the catalog tells you *what to reach for*, the profiler tells you *whether to bother*.

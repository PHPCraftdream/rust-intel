## §B6. Pattern matching exhaustiveness drift

**The trap**: a `match` written today is exhaustive. After someone adds a new enum variant, it may silently become non-exhaustive only in `if let` form, or use a wildcard `_ => ...` that swallows the new case.

**REQUIRED**:
- For every `match` on an enum I do not own: assume the enum is `#[non_exhaustive]` and handle the fallback explicitly with a logged/typed error, not silent ignore.
- For every `match` on an enum I own: avoid wildcard arms unless I want adding-a-variant to compile silently. Use explicit arms.
- For every `if let Some(x) = ...` on a `Result` or option-chain that could grow new "interesting" failure modes, prefer `match` with explicit arms.

**BANNED**:
- `_ => unreachable!()` or `_ => panic!()` for enums where new variants could legitimately be added.
- `_ => Ok(())` swallowing an error case.

## §B16. Equality and hashing contracts

**The trap**: `derive`-ed `Eq`/`Hash` is correct by construction. The moment a manual `impl PartialEq` or manual `impl Hash` enters the type — to normalize case, ignore a field, hash-by-key-only — the `HashMap`/`HashSet` contract `a == b ⇒ hash(a) == hash(b)` can be quietly violated. Compiles, runs, passes a few unit tests, and silently *loses entries from the map* in production: insert returns `None` (saying "no previous"), get returns `None`, but `len()` keeps incrementing — duplicate keys living at different hash buckets. Mirror trap on the ordering side: manual `Ord` that is not a *total* order corrupts `BTreeMap` ordering and `<[T]>::sort` (the sort assumes total order; if the relation is not total, the sort can produce arbitrary output, and `BTreeMap` invariants rot — silently losing or misordering entries is the *common* case, but not the whole documented outcome contract: the BANNED bullet below states the containers' fuller unspecified-outcome language, which can include panics, aborts, and non-termination, never UB).

**BANNED**:
- A custom `PartialEq` paired with a `Hash` implementation that violates `a == b ⇒ hash(a) == hash(b)`, whether that hash is manual or derived. Custom equality does not require replacing a derived hash that already respects this implication; unequal keys may legitimately collide. The hashing obligation applies when the type implements `Hash` or is used as a hashed key.
- A manual `impl Ord` (or derived alongside a manual `impl PartialOrd`/`impl PartialEq` it doesn't actually agree with) that is not genuinely a consistent total order, for **any** consumer that assumes one — `BTreeMap`/`BTreeSet` keys, `Vec::sort*`/`slice::sort*`, `BinaryHeap`, or a hand-written `.sort_by` comparator — not a `BTreeMap`/`BTreeSet`-only risk. Note `BTreeMap`/`BTreeSet` require `T: Ord` outright — a `PartialOrd`-only type is a compile error there, not a silent bug, so that specific witness is impossible; the real, compiling risk is an `Ord` impl the type system cannot check for totality/consistency. The consequence is a logic error whose outcome each container documents as **unspecified, never UB** — not uniformly "silent": `BTreeMap`/`BTreeSet`'s own docs describe an inconsistent `Ord` as producing unspecified behavior that "could include panics, incorrect results, aborts, memory leaks, and non-termination", and `Vec::sort`/`sort_unstable` similarly **may** panic on an inconsistent comparator rather than silently misordering (see the `sort_by` bullet below) — silent corruption (lost entries, wrong iteration order) is the common case, not the only documented one. The parallel risk for a genuinely `PartialOrd`-only type is `.sort_by(|a, b| a.partial_cmp(b).unwrap())`, which panics the moment two elements are incomparable, or a hand-written `.sort_by` comparator that is not actually a consistent total order. **The outcome of a `PartialOrd`/`Ord` inconsistency is toolchain-dependent since Rust 1.98.0**: when `PartialOrd` and `Ord` are derived together, the derived `partial_cmp` now delegates to `Ord::cmp` (rust-lang/rust#155598; its 1.98.0 compatibility note: "This can break crates in practice where a type's PartialOrd and Ord impls were inconsistent with each other"), so an inconsistency in **any field type** of a `#[derive(PartialEq, Eq, PartialOrd, Ord)]` type silently changes `<`/`>`, `partial_cmp`-based sorts and `max`/`min` on a toolchain upgrade, with no source change. Observed on rustc 1.97.1 vs 1.98.0: field `Inner(i32)` with a manual `PartialOrd` returning the reversed order (`Some(o.0.cmp(&self.0))`) and a manual natural `Ord`; `#[derive(PartialEq, Eq, PartialOrd, Ord)] struct Outer(Inner)`; `Outer(Inner(1)) < Outer(Inner(2))` is `false` on 1.97.1 (`partial_cmp` = `Some(Greater)`) and `true` on 1.98.0 (`Some(Less)`), while `cmp` = `Less` on both. Observed on clippy 1.98.0: `clippy::non_canonical_partial_ord_impl` (`suspicious` group, warn by default) fires on a manual `PartialOrd` impl in a type that also has an `Ord` impl whenever `partial_cmp` is not `Some(self.cmp(other))` — the reversed-order `Inner` above, a manual `PartialOrd` beside a derived `Ord`, and even a behaviorally equivalent `Some(self.0.cmp(&o.0))` — but reports nothing on the derived `Outer` that merely inherits the inconsistency (fix the field type, not the outer derive); `clippy::derive_ord_xor_partial_ord` (`correctness` group, deny by default) fires on `derive(Ord)` + manual `PartialOrd` and on `derive(PartialOrd)` + manual `Ord`. The lints check the shape of the impl, not the behavior, so the property test in REQUIRED is the actual check.
- `sort_unstable` / `sort_unstable_by` / `sort_unstable_by_key` when the relative order of equal elements matters. "Unstable" means equal elements may be reordered, so a multi-key sort (sort by B over data already sorted by A) silently loses the secondary order. Use the stable `sort` / `sort_by_key` when the tie-break order is load-bearing; `sort_unstable` only when equal elements are genuinely indistinguishable or their order is irrelevant.
- Float fields participating in key identity/order without an explicit policy consistent across `Eq`, `Hash` and any `Ord` implementation. Primitive float equality is not reflexive for NaN, and `PartialOrd` leaves NaN unordered. `ordered_float::NotNan` / `OrderedFloat` provide common policies; an explicitly implemented consistent policy is also valid. A float metadata field deliberately excluded from key identity is not itself a defect.
- Hashing raw `f64::to_bits()` / `f32::to_bits()` while equality still uses numeric float `==`: equal signed zeros then hash differently. Bit-identity keys are a legitimate separate contract — use the integer bits as the key, or make a wrapper's `Eq` and `Hash` use the same bit representation (with a compatible `Ord` if needed). Distinct signed zeros and NaN payloads are then intentional, and equality remains reflexive even for a NaN bit pattern. For numeric-value identity, normalize zeros and state a consistent NaN policy instead; do not mix the two equivalence relations.
- For a `HashMap`/`HashSet` whose **keys come from untrusted input** (request bodies, headers, parsed external data), replacing the default `RandomState` hasher (SipHash-1-3, seeded with per-process random state) with a fast hasher — `FxHashMap`/`rustc-hash` or `fnv` (not keyed at all, so always floodable on untrusted keys), or `ahash`/`foldhash`/`hashbrown` **configured with a fixed seed** — reintroduces **HashDoS**: an attacker who knows the (fixed or absent) seed forges keys that all collide into one bucket, degrading lookups to O(n) and burning CPU. std's own docs warn about exactly this. At an untrusted boundary use `std::collections::hash_map::RandomState` (or another hasher whose own documentation contractually covers adversarial keys). Do **not** generalize "random-seeded fast hasher" into that contract: foldhash's own docs claim only *minimal* DoS resistance and explicitly exclude protection against "people studying your long-running program's behavior to reverse engineer its internal random state and using this knowledge to create many colliding inputs for computational complexity attacks" (docs.rs/foldhash/latest/foldhash/) — i.e. the excluded threat is an **adaptive/interactive** attacker who can observe a long-running process and probe it repeatedly to recover the seed. That leaves a narrower exception: a genuinely **non-interactive, single-shot** pass over untrusted keys (no attacker feedback loop back from the process) has no adaptive attacker to reverse-engineer against, so foldhash's default-random seed is not automatically disqualified there. For any **long-running or interactively-probeable** service — the common case for untrusted keys — treat `foldhash` (default-random seed included) as a trusted-key/internal hasher only. Reserve unkeyed or fixed/predictable-seed fast hashers for trusted/internal keys even in non-interactive one-shot programs: an attacker can construct collision inputs offline, without observing a running process. The one-shot exception above applies only to foldhash's default-random seed and remains a narrow threat-model judgment, not a general DoS-resistance guarantee.
- **Regex engine choice on untrusted input — ReDoS sibling of HashDoS (CWE-1333).** The `regex` crate is linear by construction (RE2-style NFA, no backtracking — which is *why* it does not support lookaround or backreferences). When an LLM reaches for lookaround/backreferences, it switches engines — `fancy-regex`, `onig`, `pcre2` — which restore backtracking and with it *catastrophic backtracking*: an adversarial input (or an adversarially-chosen pattern) blows up to exponential time and pins a worker. Same shape as HashDoS, different primitive. Four distinct bounds apply — conflating them is the mistake to avoid:
  1. **A backtracking engine** (`fancy-regex`/`onig`/`pcre2`) on untrusted input. BANNED without **both** an enforced input-size cap **and** an engine-native step-limit/interrupt — **or**, as an independent alternative (not a layer on top of the step-limit), routing the match into a subprocess you can actually kill and reap. Not with a `std::thread`+channel "hard timeout": dropping a `std::thread::JoinHandle` **detaches** the thread rather than stopping it (doc.rust-lang.org/std/thread/struct.JoinHandle.html: dropping it means "there is no longer any handle to the thread and no way to `join` on it" — the thread keeps running to completion regardless; there is no safe way to force-kill a `std::thread` from Rust), so a channel `recv_timeout` only bounds the *caller's* wait, not the worker's execution: under repeated hostile inputs, every "timed-out" match leaves its thread still running the catastrophic-backtracking match, and these accumulate as CPU-burning zombie threads even though every caller returns promptly. (Same non-cancellation shape as a `tokio::time::timeout` around a `spawn_blocking` match — also **not** a hard timeout: `timeout`/`abort` return but cannot stop a running blocking closure, which keeps burning a blocking-pool thread; see §B11's cancellation bullet.) Absent a genuine engine-native step-limit/interrupt or a killable OS process, the only safe fallback is staying on the linear `regex` crate entirely (below) rather than reaching for a backtracking engine at all.
  2. **The linear `regex` crate's single-search methods** (`is_match`/`find`/`captures`, one match, not iterated) — genuinely `O(m·n)` worst case (`m` = pattern size, `n` = haystack size), per the crate's own untrusted-input documentation. No match timeout needed for these specifically.
  3. **The linear `regex` crate's iterator/replacement methods** (`find_iter`, `captures_iter`, and anything built on repeated searches such as `replace_all`) — **not** covered by bound 2's guarantee. The crate's own docs are explicit: "since iterating over all matches can execute many searches, and each search can scan the entire haystack, the worst case time complexity for iterators is `O(m·n²)`" (docs.rs/regex, "Untrusted input"). This is an engine-level bound, not a callback-cost issue — even a trivial `O(1)` callback (`find_iter(untrusted).count()`) inherits the `O(m·n²)` worst case. REQUIRED: bound the number of matches actually processed (`.take(k)` on the iterator, or `replacen` with an explicit cap) rather than an unbounded `find_iter`/`replace_all` over fully-untrusted, unbounded-length input; if a per-match callback also does non-trivial (non-`O(1)`) work, that is an *additional*, separate multiplier on top of this bound, not instead of it.
  4. **An untrusted *pattern*, on any engine including linear `regex`** — not covered by bounds 2/3, which assume a fixed, trusted pattern. REQUIRED: bound the compiled program with `RegexBuilder::size_limit` and cap the pattern length, because stacked counted repetition (`a{5}{5}{5}…`) blows up program size on the linear engine too. `RegexBuilder::dfa_size_limit` is a **separate** bound from `size_limit` — it caps the lazy DFA's runtime cache memory during matching, not the compiled program's size — set it too when the pattern is untrusted, but don't rely on it in place of `size_limit`.

  Compile patterns once (§E5) — separate concern, same code.
- Sorting floats with `v.sort_by(|a, b| a.partial_cmp(b).unwrap())` **panics** the moment a `NaN` is present (`partial_cmp` returns `None`). Use `v.sort_by(f64::total_cmp)` (a total order; `NaN` sorts to **both ends** — negative NaN before everything, positive NaN after everything, not a single end — so a "drain the NaNs off one end" idiom misses the other half). The same `partial_cmp().unwrap()` trap hits `min`/`max` over floats. (If the values are provably non-`NaN` — validated, or `NotNan`/`OrderedFloat`/`Duration` — `partial_cmp().unwrap()` is not a bug, though `total_cmp` is still the cheaper default.)
- A comparator passed to `sort_by`/`sort_unstable_by` must be a consistent total order (strict weak ordering). An inconsistent comparator (e.g. one that flips direction based on external state) **may** make modern Rust's sort panic, and in any case yields an unspecified order (never UB) instead of silently scrambling — it only passed tests on small inputs by luck.

**REQUIRED**:
- If you customize `PartialEq`, verify that the existing or replacement `Hash` respects the same equivalence relation: `a == b ⇒ hash(a) == hash(b)`. For a non-trivial policy, document why the implication holds. Clippy's `derived_hash_with_manual_eq` conservatively denies the manual-equality/derived-hash mix; follow project lint policy with an explicit matching hash or a narrowly documented exception backed by that proof.
- Choose numeric-value or bit identity for float keys explicitly. For numeric identity, use `ordered_float::NotNan<f64>` (rejects NaN), `OrderedFloat`, or consistent normalization including signed zeros and the chosen NaN policy. For bit identity, use bits consistently for equality and hashing as described above.
- For a type that implements `Ord`, write its `PartialOrd` as `Some(self.cmp(other))` (the canonical form, consistent by construction), or derive both together — never a hand-rolled second comparison. For every type with a manual `Ord` or `PartialOrd` — including field types of derived containers — keep a property test asserting `a.partial_cmp(&b) == Some(a.cmp(&b))` over generated pairs, and keep `clippy::non_canonical_partial_ord_impl` and `clippy::derive_ord_xor_partial_ord` enabled (do not `#[allow]` them to silence a reversed-order impl).
- `Ord` requires a *total* order: antisymmetric, transitive, total. `PartialOrd` does not. Before writing `impl Ord`, prove totality for your type — including edge cases (empty, all-equal, mixed signs for numerics).
- Flag a manual `impl PartialEq` / `impl Hash` / `impl Ord` inline (at write time) only when its contract is **non-trivial** — case/whitespace normalization, an ignored or derived field, a partial order, or any logic that can diverge from `derive`. A straightforward total `impl Ord` (or `PartialEq`) that simply compares one field or delegates to the fields in order needs no flag.

## §B20. `serde` field-presence vs null vs default

**The trap**: a derived `Option<T>` field deserializes both `{ "field": null }` and `{}` (field absent) to `None` — and the collapse is **not** gated on `#[serde(default)]`: a plain `Option<T>` field with no attribute at all behaves the same under ordinary serde derive, because `Option` fields are implicitly defaulted (serde-rs/serde#2214). For protocols where "absent" and "explicitly null" carry different semantics (HTTP PATCH, JSON-Merge-Patch, "preserve this field" vs "clear this field"), this collapse is a silent semantic bug — the code compiles, deserializes successfully, and propagates the wrong intent downstream. Adjacent traps: `#[serde(untagged)]` enums silently pick the first matching variant when two variants accept overlapping structural shapes; `#[serde(rename = "...")]` typos pass `cargo build` and corrupt the wire format.

**BANNED**:
- Any derived `Option<T>` field — with **or without** `#[serde(default)]` — in an API that must distinguish "field absent" from "field present as null": under ordinary serde-derive behavior both shapes deserialize to `None` even when the attribute is absent (`Option` fields are implicitly defaulted; serde-rs/serde#2214), so the caller can no longer tell which the client sent.
- `#[serde(untagged)]` with unexamined overlap between variants' accepted inputs — the first successful variant wins. Intentional ordered fallback is valid, but its priority must be documented and tested; changing declaration order can change meaning without a parse error. If the contract needs unique variant identity, prove disjointness, use a compatible discriminator, or implement the required dispatch explicitly.
- `#[serde(rename = "wire_name")]` without a contract test for each supported direction: known wire input → expected value and/or value → expected wire field name. A pair's round-trip alone cannot detect a typo shared by both directions (§F1).
- Trusting `#[serde(deny_unknown_fields)]` to catch typos — it catches unknown *incoming* fields, not typos in the struct field names that are being serialized.
- Deserializing a large integer (snowflake ID, nanosecond timestamp, `u64` > 2^53) into an `f64` field, or reading it via `serde_json::Value::as_f64()` — `f64` has only 53 bits of integer mantissa, so values above 2^53 silently lose precision (IDs collapse to neighbors). Use `u64`/`i64` typed fields, or `serde_json::Value::as_u64()`, and prefer `arbitrary_precision` only when you control both ends.
- `#[serde(deny_unknown_fields)]` combined with `#[serde(flatten)]`: Serde documents this combination as **unsupported** on either the outer struct or the flattened inner struct (serde.rs/attr-flatten.html). Do not rely on incidental rejection or acceptance in a pinned derive implementation as the strictness contract. When strict rejection must coexist with flattening, implement validation through `MapAccess` directly. **Buffering is a separate, path-dependent hazard.** In serde_derive 1.0.228, a struct with `flatten` deserializes recognized non-flattened fields directly; it collects the remaining entries into internal `Content` for flattened fields, including entries later ignored. Internally tagged derives buffer non-tag content; untagged derives buffer the value for variant attempts. An adjacently tagged map can deserialize its payload directly when the tag comes first, but buffers a payload that precedes the tag. This is not uniformly a whole-request copy: retained data, allocation and error-position loss depend on the path, format and schema (§E2). Buffered paths can also lose format-specific support: `Content` in this pin lacks `u128`/`i128`, so even a small `u128` field can work directly yet fail through flattening or a content-first adjacent tag. Verify pinned behavior, both allowed tag/content orders and buffered-input bounds; measure hot-path cost (§E6), not a universal slowdown factor. The attribute itself is not the finding.

**REQUIRED**:
- For three-state semantics (absent / null / value), use `Option<Option<T>>` with `#[serde(default, deserialize_with = "double_option")]` — and, when the type also derives `Serialize` (the common case), `#[serde(skip_serializing_if = "Option::is_none")]` on the same field — or a custom enum (`enum FieldUpdate<T> { Absent, Null, Set(T) }`) with an explicit `Deserialize` impl. The serialize-side attribute is not optional decoration: without it the derived `Serialize` emits the outer `None` as an explicit `"field":null`, so `{}` → `value: None` → `{"value":null}` → `value: Some(None)` — absent became explicit null across one round-trip, breaking the §F4 compose for the absent state (measured: serde 1.0.228 / serde_json 1.0.151). With `skip_serializing_if` the three wire forms are disjoint and all three states survive the full compose: `None` → `{}` → `None`; `Some(None)` → `{"value":null}` → `Some(None)`; `Some(Some(v))` → `{"value":v}` → `Some(Some(v))` (an equivalent explicit custom serializer that distinguishes all three states on output is the alternative). REQUIRED control: test all three incoming states; when a compatible serializer is supported, also serialize each state independently and confirm every state survives the full round-trip — a value-only example does not exercise the absent/null distinction (§F4). Document the chosen scheme on the field.
- For `#[serde(untagged)]`, check whether variants' accepted inputs overlap; where they do, test the intended winner, plus variant-specific controls where available. Require disjointness or a discriminator when the contract demands unambiguous variant identity; do not add a tag that changes an established wire format without a compatibility decision. Ordered fallback does not guarantee round-trip preservation of every Rust variant.
- For a supported encode/decode pair, property-test the round-trip over its valid domain and stated equality/normalization relation (§F4). For deliberately `Serialize`-only or `Deserialize`-only types, test that direction against independent contract vectors; do not add an inverse trait merely to satisfy this rule. A pair agreeing with itself does **not** prove wire conformance or that persisted bytes still decode after a positional-format declaration change: §F1's own-previous-release rule covers `bincode`/`postcard`/`rkyv`/`borsh`.
- Put `#[serde(deny_unknown_fields)]` on any struct deserialized from an **untrusted request** where unexpected fields must be rejected — an auth/authorization/financial/validation path. Default serde *ignores* unknown fields, so a typo'd key silently deserializes as if the field were absent and the request is validated against defaults with no signal — a client that means `{"amount": 5000}` but sends `{"amout": 5000}` gets a half-processed request instead of an error. Keep this attribute as strict-parsing hygiene (typo/schema-ambiguity detection), and do **not** present it as mass-assignment defense — two conflations to avoid: (1) serde *ignoring* an unknown key is **not** mass assignment — an ignored key is never assigned to any field or privileged state, so `{"is_admin": true}` against a struct with no such field changes nothing; (2) `deny_unknown_fields` rejects only **unrecognized** keys — a sensitive field the deserialized type itself declares (`is_admin: bool` on the struct) is *known*, deserializes normally, and is accepted-and-assigned by the very parser that rejects unknown fields. The actual mass-assignment defense (OWASP Mass Assignment / API8:2023) is structural: deserialize the request into a request-specific DTO that simply does not have the sensitive field, or gate writes through an explicit writable-field allowlist checked against the caller's authorization policy — so a payload carrying a known privilege field is still rejected/ignored per policy even though `deny_unknown_fields` accepted the request. This is the *opposite* direction from the BANNED note above (which warns the attribute does **not** catch typos in *your own* serialize names) — both are true and non-contradictory. On a struct that is itself `flatten`ed into another — or on a containing struct whose field is `#[serde(flatten)]`ed — this attribute is not supported (see the `flatten` BANNED bullet); it does its job only where `flatten` is not involved. Calibration: this is REQUIRED only where unexpected-field rejection actually matters — do **not** add it to a permissive API whose intended design is forward-compatibility with new client fields.
- Be aware that duplicate-key handling depends on the deserialization path. A direct Serde struct visitor normally reports a duplicate known field, while parsing into an intermediate `serde_json::Value`/map can collapse object names last-wins before validation. At a security boundary, do not let an upstream proxy/WAF and the Rust service use different duplicate-key policies: reject or canonicalize duplicates before the value is trusted. RFC 8259 §4 says object names "SHOULD be unique" but leaves implementation behavior open.
- For floats crossing a serde boundary: `serde_json` serializes non-finite `f64` (`NaN`/`inf`/`-inf`) as `null` and rejects `null` for a non-`Option` float field on the way back — so a `sum / count` that hit the §B26 float-division case round-trips into a deserialize error, or worse, a silent `null` downstream. Guard `count == 0` before dividing, check `value.is_finite()` at the boundary, and write a custom serializer only if non-finite values genuinely must round-trip.
- Flag each `#[serde(untagged)]`, `#[serde(rename = "...")]`, and `#[serde(default)]` on `Option<T>` inline (at write time).

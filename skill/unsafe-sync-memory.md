## §B7. Large stack allocations and arena pitfalls

**The trap**: `[u8; 1_048_576]` on the stack is at real risk of overflow in debug builds — debug frames inflate per-frame size by a large factor — but a 1 MiB frame does **not** overflow every debug thread: whether it overflows depends on the executing thread's actual stack budget, which differs (8 MiB Linux main thread usually survives it; a 2 MiB spawned or tokio worker thread is close; a smaller configured stack does not) — so the audit trigger is "a meaningful fraction of the executing thread's budget", not "1 MiB always dies". `Box::new([0u8; N])` constructs on the stack first and may overflow before placement-new optimizations kick in (release-mode dependent, never reliable).

**The right threshold to think in**: not page size (4 KiB), but the actual stack budget of the executing thread. Default stack budgets are **8 MiB on Linux for the main thread**, **2 MiB on `std::thread::spawn`-ed threads**, and **2 MiB on the tokio worker thread a task runs on** — tasks are *not* given their own stack, they share the worker's, so a deep async call chain competes for that one budget (configurable via `Builder::stack_size` and `tokio::runtime::Builder::thread_stack_size` respectively, but the defaults are the budget LLM-generated code actually runs against). Practical **default guideline**: keep routine stack values below ~64 KiB; this is a guideline, not a hard line — a single large value on a fresh main-thread frame with a 2–8 MiB budget is fine. It escalates to a real defect (see BANNED) when the large frame sits under recursion, a deep call chain, or a spawned task on a reduced stack, where the cumulative depth — not the single frame — overflows.

**BANNED**:
- `[T; N]` whose total size is a meaningful fraction of available stack: a large array (well past the ~64 KiB guideline, or any size that is a real fraction of the thread's budget) passed/returned by value through a function chain, **and especially** one that recurs or lands on a spawned task's reduced stack — there the per-frame size multiplied by depth overflows. A single large array on one shallow main-thread frame is the guideline case above, not an automatic ban.
- `Box::new([0u8; N])` for any N at risk — this is the trap: the array is built on the stack first and *then* moved to the heap, so the stack-overflow window is unchanged from the by-value form. Use `vec![0u8; N].into_boxed_slice()` or `Box::<[u8]>::new_uninit_slice(N)` instead.
- Recursive functions with large local arrays.
- Unbounded recursion **depth** over input you don't control — a recursive-descent parser, tree/JSON/expression walk with no depth limit overflows the stack on deeply-nested input. A stack overflow is `SIGSEGV`/abort, **not** a catchable panic, so it is a clean DoS vector for parsers of untrusted data. (Distinct from the frame-size trap above: here each frame is small but the depth is unbounded.) **The recursion need not be code you wrote:** the depth limit inside a third-party parser applies to its *parse-from-text* phase only — `serde_json`'s default 128 guards `from_str`/`from_slice`, and deserializing *from text* stays bounded even through `IgnoredAny`-skipped unknown fields or `#[serde(flatten)]`/`untagged` (their `Content` buffer is filled *through* the limited text parser). The real hazard is deserializing **from a `serde_json::Value` that did not come through that depth-limited text parser** — built programmatically, via the `unbounded_depth` feature (`Deserializer::disable_recursion_limit`), or parsed by another format — because `from_value` walks that AST with **no** depth check and overflows the stack — an LLM that "knows serde_json has a recursion limit" is falsely reassured. `serde_yaml`'s alias/anchor recursion was an uncontrolled-recursion abort — fixed in 0.8.4 by adding depth checks (RUSTSEC-2018-0005) — and the crate is now unmaintained, so re-verify against your pinned version. You cannot add a `depth` parameter to `IgnoredAny` or a derived `Deserialize`. The requirement is a **finite resource budget over the hostile input — cap input size, depth, and total work *before* the AST is built** — and the budget must cover the *later* life of the resulting deep structure, not just its construction: a deeply-nested AST is walked again by traversal code and is eventually torn down by recursive `Drop` glue, which overflows the stack on deep input just the same (§B4's rule: hand-write an **iterative** `Drop`, or keep the structure within a provably bounded depth). Within those bounds, `serde_stacker` (dynamic stack growth) and an iterative (non-recursive) traversal are both legitimate **implementation choices** — not alternatives to having the bounds. Stack growth in particular only prevents stack *exhaustion*; it still lets memory and work grow without bound as input depth grows, so it must never be presented as a substitute for the budget itself. Severity: 🔴 when an attacker can reach it (remote DoS), 🟡 otherwise.
- `Vec::with_capacity(n)` / `vec![0u8; n]` / `String::with_capacity(n)` / `Vec::reserve(n)` where `n` is a length/count from untrusted input (a wire length-prefix, a `Content-Length`, a parsed count field). An attacker sends `n = u32::MAX` and the single preallocation exhausts memory → OOM/abort, a clean remote DoS. Distinct from the stack traps above: the allocation is on the heap but the *size* is attacker-chosen. Compiles; tests on small `n` pass. Severity: 🔴 when an attacker can reach it (remote DoS), 🟡 otherwise.
- **Decompression bomb: `decoder.read_to_end(&mut out)` on a gzip/zlib/deflate/zip/tar body with the *compressed* input capped but the *decompressed* output unbounded.** `GzDecoder::new(compressed).read_to_end(&mut out)?` amplifies ~1 KiB → multi-GiB (the classic 1000:1 gzip ratio, `zip`'s nested bomb) and OOM-aborts — a clean remote DoS with **no attacker-controlled integer literal anywhere in the code**. Distinct from the `with_capacity(n)` bullet above: there is no clampable `n` — the code never sees the decompressed size as an integer, and the growth happens *inside a trusted-looking decode call*. Capping the compressed body (a `Content-Length` check, or the `zip` crate's own internal `.take(compressed_size)`) is **active false safety** — it bounds only the compressed side; `flate2` has no built-in output limit and header size hints are untrustworthy on malicious archives (CWE-409). REQUIRED: wrap the **decoder** in `.take(MAX + 1)`, then error if the limit is hit — the mirror of the `Read::take` advice below, but applied to the decoder's *output* rather than the socket's input: `let mut limited = GzDecoder::new(compressed).take(MAX + 1); limited.read_to_end(&mut out)?; if out.len() as u64 > MAX { return Err(/* bomb */); }`. Severity: 🔴 when an attacker can reach it (remote DoS), 🟡 otherwise.
- **Extracting a multi-entry archive without an *aggregate* output quota.** A per-entry decompression cap (the bullet above) bounds each entry and still lets the archive as a whole exhaust the machine: a few hundred KiB of `zip`/`tar` can carry a million tiny entries (disk, inodes, dirent churn) or nest archives that your extractor expands recursively. Cap **total extracted bytes, total entry count, and nesting depth** before extraction, decrementing a single shared budget as entries are written — not a fresh limit per entry. Distinct from the decompression bomb above, which is one entry with a huge expansion ratio. (The *other* half of archive safety — entry names are attacker-authored paths, plus symlink/hardlink escape and special files — is path traversal, not exhaustion: it lives in §C2's `Path::join` bullet, which carries the component-rejection, `canonicalize`, and `openat`/`cap-std` recipe. A traversal-safe extractor can still fill the disk, and a quota-bounded one can still write to `/etc`; both bullets apply.) Severity: 🔴 when an attacker can reach it (remote DoS), 🟡 otherwise.

**REQUIRED for heap-allocated buffers**:
- `vec![0u8; N].into_boxed_slice()` — guaranteed heap, zero-initialized, stable Rust.
- `Box::<[u8]>::new_uninit_slice(N)` (stable since Rust 1.82, October 2024) + `.assume_init()` — when zero-initialization is wasted work. `assume_init` is `unsafe`; gate it with a `// SAFETY:` block per §B5. **Only** sound when the buffer is filled through an API whose contract explicitly permits writing into uninitialized memory — an out-pointer / FFI callee documented to overwrite the entire allocation (§B25). **Not** sound merely because "every byte will eventually be written": plain `Read` methods are the wrong tool — `read_exact`/`read` take `&mut [u8]`, and materializing that reference over uninitialized bytes is itself UB (a reference's pointee must be initialized; `u8` having no invalid bit patterns does not exempt it), independent of whether all `N` bytes get written — and `Read` is safe to implement, so the impl may inspect the buffer's existing contents. (std's `Read::read_buf`/`BorrowedBuf` API exists precisely to fill possibly-uninitialized memory without forming that reference — still nightly-only (`#[unstable(feature = "read_buf")]` on rust-lang/rust master, 2026-11-15), so check your toolchain.) Anything consumed through plain `Read` uses initialized storage — `vec![0u8; N]` (or `bytes::BytesMut::zeroed(N)` for tokio io) — which is also what keeps the `n < N` partial-read tail (`socket.read(&mut buf)`) safe to slice.
- `bytes::BytesMut::zeroed(N)` for buffers headed into `tokio::io`.
- For untrusted recursive input, enforce the finite input/depth/work budget described above. Within that budget, use depth-checked recursion or iterative traversal with a bounded worklist, and cover the structure's later traversal and teardown (§B4). Moving the call stack into a `Vec` does not itself bound memory or total work.
- Clamp any allocation size derived from untrusted input to a sane maximum before allocating (`if n > MAX_LEN { return Err(...) }`), and prefer incremental growth or `Read::take(limit)` / `Iterator::take(limit)` over preallocating to a wire-supplied size. Reserve `with_capacity(n)` for an `n` you computed or bounded yourself.
- **Compute any `count * item_size` byte budget with `checked_mul` before clamping it.** A wrapping `count * size_of::<Record>()` (or `width * height * 4`) in release silently overflows to a *small* product that **passes** a `if bytes > MAX { .. }` clamp — then the code allocates/reads with the original huge `count` → OOM. The overflow defeats the very bounds check meant to stop this (CWE-190 → CWE-789); a reviewer who has internalized both §B26 and this section can still ship it because the clamp *looks* correct. Cross-ref §B26 (release-wrap semantics).

## §B18. Manual `unsafe impl Send` / `unsafe impl Sync`

**The trap**: a type contains a `*const T`, a `*mut T`, a raw FFI handle, or a `Rc<T>` field, and `tokio::spawn` rejects it with a `Send` bound error. The LLM's reflexive fix is `unsafe impl Send for MyType {}` — and that compiles, and tests pass under low concurrency. Under contention, the un-synchronized access races. This is one of the most reliably-wrong fixes the LLM makes: it converts a correct compile-time refusal into a runtime data race.

**BANNED**:
- `unsafe impl Send for MyStruct {}` or `unsafe impl Sync for MyStruct {}` without a `// SAFETY:` proof of the relevant ownership, access, thread and destruction constraints.
- Manual `Send`/`Sync` for a raw-pointer owner/view without proving the corresponding ownership, aliasing, thread-access and destruction requirements. Synchronization is one possible proof, not a requirement for a uniquely owned transferable value.
- Replacing a synchronization type with a `static mut` "because it's just a counter": `static mut COUNT: u64 = 0;` mutated as `unsafe { COUNT += 1 }` from multiple threads (a multi-thread runtime's workers, or a signal/interrupt handler) is a plain data race. Edition 2024's `static_mut_refs` deny-lint covers only *references* to a `static mut` — direct reads/writes and raw-pointer access still compile, and the `// SAFETY:` block claiming single-threaded access is precisely the false-proof shape this category exists for. The type-level fixes: `AtomicU64` / `Mutex` / `OnceLock`; on bare-metal, `critical_section::Mutex<RefCell<_>>`.
- Manual `Send` for a type whose field is `Rc<T>` "because the Rc is never cloned across threads in practice" — if the field is morally `Arc`, fix the field, do not lie via `unsafe impl Send`.

**REQUIRED**:
- Prove `Send` and `Sync` separately in `// SAFETY:`. A Box-like unique owner may be `Send` when `T: Send` and transfer/destruction on the destination thread are allowed; shared access exposing `&T` needs the corresponding `T: Sync` proof. No lock is inherently needed for ownership transfer. Aliased mutable state does need synchronization or another sound access protocol; a lock cannot repair aliases outside that protocol.
- `NonNull<T>` retains raw pointers' `!Send`/`!Sync` defaults and is covariant; it supplies neither a thread-safety nor an ownership proof. A per-handle lock can serialize conflicting access **only if the handle may be used and destroyed on the calling threads**. Library-global state, reentrancy and thread affinity are separate obligations (§B25a): a global mutex cannot make a main-thread-only destructor callable on a worker. Retain `!Send`/`!Sync` where required, or marshal the restricted operations to an allowed owning thread without exposing direct foreign-handle access.
- Surface every manual `unsafe impl Send` / `unsafe impl Sync` in the post-flight summary.

## §B18a. Variance and `PhantomData` soundness in raw-pointer wrappers

**The trap**: a hand-written type holding a `*const T` / `*mut T` / `NonNull<T>` (or otherwise built on internal `unsafe`) gets its **variance**, its **drop-check**, or its **auto-traits** wrong via the wrong `PhantomData` — or via no `PhantomData` at all. This is the relational-invariant class of §B5 made concrete: the hole is **not in any `unsafe` block**. There is no `unsafe` token at the site that decides variance — variance is implied by the type's fields and chosen *silently* by the compiler, so a block with a flawless `// SAFETY:` comment can still be unsound because the **type declaration** is wrong. A per-block `// SAFETY:` (§B5) cannot catch it; that is why this needs its own check. In *safe* Rust this is impossible — the compiler always derives variance correctly; the hazard exists only once a raw pointer enters the type.

**Why it bites**: if a wrapper from which `&mut T` can be reached **without an exclusive borrow of the container** is covariant where the access contract requires invariance, a lifetime substitution can make safe-looking callers reach a dangling value. By contrast, a covariant owning container such as `Vec<T>` can yield mutable access through `&mut self`; the exclusive container borrow matters. Audit the access path, not just the presence of an `&mut T` return. Audit drop-check separately: an explicit generic `Drop` implementation already makes Rust consider that its type parameters may be used during destruction. Missing `PhantomData<T>` is **not by itself a drop-check hole** in that case. A marker may still be needed for lifetime/variance/auto-trait constraints or other drop-glue shapes; advanced `#[may_dangle]` use needs its own proof. The defect is a mismatch between the full declaration/implementation and the contract, not marker absence alone.

**REQUIRED** for any type holding a raw pointer / `NonNull` / using internal `unsafe`:
- **Inspect the fields and `Drop` implementation before adding a marker.** `*const T`/`NonNull<T>` are covariant, `*mut T` is invariant, and raw pointers are `!Send`/`!Sync`. Explicit generic `Drop` already constrains drop-check; a type with no explicit `Drop` but fields with drop glue needs its own analysis. Add `PhantomData` only for a constraint the declaration/implementation does not otherwise encode. An ownership marker is not automatically needed for a non-owning view, but the view still needs its real lifetime/access restrictions. Record why the existing structure suffices when no marker is needed; do not let a drop-check proof stand in for variance or auto-trait proofs.
- Where a `PhantomData` *is* needed, choose it to match the *real* ownership and access:
  - `PhantomData<T>` — **covariant** in `T`, plus drop-check ownership (the compiler assumes the type may drop a `T`, so `T` must outlive it). Use when the type **owns** the data behind the pointer and every `&mut T` it hands out is reached **only through an exclusive borrow of the container** (`&mut self`) — no aliased/shared route can produce one, i.e. the access-path audit above passes for a covariant type. This is the `Vec<T>` / `Box<T>` pattern: covariant over `T`, yet safely yielding `&mut T` via its `&mut self` methods.
  - `PhantomData<&'a T>` — **covariant** in both `T` and `'a`; a shared, read-only view. The default starting point for non-owning wrappers.
  - `PhantomData<&'a mut T>` — **invariant** in `T`, covariant in `'a`. Use when the type hands out `&mut T` **through an aliased/shared route** — one reachable without an exclusive borrow of the container itself (the access-path audit above) — or otherwise requires that callers cannot substitute a sub/supertype of `T`. Handing out `&mut T` from an `&mut self`-only path does **not** by itself force invariance (a covariant owning container like `Vec<T>` is sound without it); when the route is shared, this is the critical choice that prevents the covariance→UAF described above.
  - If you need both ownership (drop-check) **and** invariance, use both: `PhantomData<T>` for the drop-check + `PhantomData<fn(T)>` (contravariant in `T`) or `PhantomData<Cell<T>>` (invariant in `T`, and `!Sync`) to force invariance. `PhantomData<T>` alone is **not** invariant — using it when invariance is required is the exact unsoundness this section exists to prevent.
  - `PhantomData<fn(T) -> T>` — invariant in `T`, `Send + Sync` regardless of `T`, no drop-check. Correct only for the rare marker case; never as a reflex.
- State the chosen variance and *why* in the type's doc / `// SAFETY:` comment — variance is an invisible part of the type's contract, so write it down like any other invariant.
- Where variance is load-bearing for soundness, add a `compile_fail` doctest that attempts the illegal lifetime substitution, so a future edit that flips variance is caught by the test suite, not by a user's UAF.
- `NonNull<T>` is the right field type for the null-niche, but note it is `!Send`/`!Sync` **and covariant** in `T` — it does not make the variance decision for you. Prefer audited safe abstractions (`bytemuck`/`zerocopy`) over re-deriving variance by hand wherever they fit.

🔴 — surface every hand-rolled raw-pointer wrapper's variance / `PhantomData` / auto-trait decision — including why its fields and `Drop` implementation need no additional marker when that is the conclusion — alongside the §B18 manual-`Send`/`Sync` items.

## §B25a. The C library's own concurrency contract (not your wrapper's data)

**The trap**: the LLM wraps a C library, satisfies the compiler, and calls it from many tokio tasks or threads — but the property that decides soundness lives in *the library's* code, not in the Rust wrapper. This is a genuinely different failure locus from §B25: §B25 is about the correctness of the boundary code *you* write (panics you emit, the ABI of types you pass, the ownership of pointers you mint); §B25a is about a contract of code you did **not** write and cannot see — whether the C library is thread-safe / reentrant at all, and what it demands of `init` and globals. No amount of correctness in the wrapper's own data closes it, and — the reason this is its own section — the standard §B18 fix **actively masks it**: wrapping the handle in `Arc<Mutex<RawHandle>>`, or handing each thread its own handle, synchronizes access to *the wrapper's data* while two independently-locked handles still race on the library's process-global state. The Rust `Mutex` an LLM reflexively adds guards the wrong object.

**Why it bites**: the library has internal global mutable state — `errno`-style globals, a `getenv`/`setenv` dependency, a global config struct, a non-reentrant parser with a shared scratch buffer, a one-time init (`curl_global_init`, OpenSSL <1.1 locking callbacks, an `Xinit`). It compiles; single-threaded and even light multi-threaded tests pass (glibc caches and timing make the race hard to hit); production segfaults under real concurrency. This is precisely **CVE-2020-26235** (RUSTSEC-2020-0071/0159): `time`/`chrono` called `localtime_r`, which reads `TZ` via `getenv`, racing a `setenv` from another thread — multithreaded programs dereferenced a dangling pointer and segfaulted. It shipped for years in two of the most-downloaded crates in the ecosystem. The data race → segfault/UB is invisible to tests, the same class as §B18 — but the fix is different.

**BANNED**:
- Writing `unsafe impl Send`/`Sync` for an FFI handle (or spreading calls across threads/tasks) **without first citing the library's documented thread-safety level** in the `// SAFETY:` block. "Each thread owns its own handle" is a true statement about the *wrapper* and does **not** establish that the *library* is safe to call concurrently — if the library keeps global state, per-handle ownership is insufficient and the impl is unsound.
- Giving a **non-thread-safe / non-reentrant** C library per-handle locks (the reflexive `Arc<Mutex<RawHandle>>` of §B18) and calling it from multiple threads. Per-handle locks do not serialize the library's *global* state; two handles under two independent locks race exactly as if there were no lock. This is the §B18 fix misapplied — correcting the reader's likely first move, not just adding new advice.
- Reading `std::io::Error::last_os_error()` (or the raw `errno`) **after** any intervening call — a logging call, an allocation, another FFI call, even some libc wrappers — that may itself set `errno`. `errno` is a per-thread global the very next call can clobber, so a delayed read reports the wrong (or no) error.
- `unsafe { std::env::set_var(...) }` / `unsafe { std::env::remove_var(...) }` anywhere other than the very top of `main`, before any thread or async runtime exists. Edition 2024 made both functions `unsafe` for exactly the reason this section grounds: the process environment is process-global C state (`getenv`/`setenv` are not thread-safe), and a concurrent reader — another thread, a tokio worker (`#[tokio::main]` has already started workers by the time your handler runs), a thread spawned by a `tracing` subscriber or threadpool — races the write; this is the same mechanism as the `time`/`chrono` `localtime_r`-vs-`setenv("TZ")` CVE-2020-26235 above. It compiles and passes single-threaded tests. Note the `// FIXME: Audit that the environment access only happens in single-threaded code.` (older toolchains: `// TODO:`) comment `cargo fix --edition` leaves at each call site is a **prompt to audit, not an audit** — the edition guide states the lint "cannot verify correctness" — treating it as "already audited" ships the race. REQUIRED: set the environment before any thread/runtime exists (top of `main`), or pass the value explicitly to the code that needs it (a config struct) — never mutate the live process environment from a multithreaded program. A Rust-only `Mutex`/process-global lock around the call does **not** make this sound in general: it only serializes your own Rust callers, while `getenv`/`setenv` calls from C libraries or other native dependencies elsewhere in the process — which never take your lock — still race it. The one documented exception is Windows, where the environment-variable API is itself thread-safe at the OS level; treat "guard it with a lock" as sound only there, and never as a general-purpose fix. The `// SAFETY:` block this `unsafe` requires would have to prove process-single-threadedness (or, on Windows only, cite the OS-level thread-safety), which off-Windows it precisely cannot — a §B5 block-and-ask.

**REQUIRED**:
- **Audit allowed threads, concurrency, reentrancy and initialization before choosing `Send`/`Sync`.** Distinct-handle concurrency can justify per-handle serialization, but only after separately proving transfer/use/destruction on those threads. Global mutable state may require a process-wide protocol shared by all relevant callers; init-once requirements need initialization before use. These are independent constraints, not exclusive library categories, and a mutex or `OnceLock` answers only its own part of the contract. Cite the actual rules for each wrapped operation.
- **Check thread affinity independently of serialization.** A library may require creation, use, callbacks or destruction on its creator/event-loop/main thread. A global mutex only prevents overlap; it cannot authorize the wrong thread. GLFW, for example, restricts initialization, event processing and window creation/destruction to the main thread. Keep restricted handles on an allowed thread, or marshal every restricted operation there, including teardown; an arbitrary dedicated worker is not a substitute for a mandated main thread. A `Send` proof includes where destruction may run; a `Sync` proof includes what a shared caller on another thread may do. Use a process-global lock only when the documented contract permits those calls from the participating threads once serialized, and retain separate reentrancy/init-order requirements.
- Capture `Error::last_os_error()` **immediately** after the FFI call whose failure you are inspecting, before any other call runs, and store the value — do not let logging, allocation, or a second FFI call sit between the failing call and the `errno` read.
- If the library documents callbacks delivered from its own threads (see §B25's callback-lifetime rule), the context's contents and any shared state they touch fall under this same contract — audit it here, not just at the `Send` impl.

🔴 — surface every FFI wrapper that spreads calls across threads/tasks without a proved, cited library contract covering concurrency and thread affinity (including destruction), alongside the §B18 manual-`Send`/`Sync` items.

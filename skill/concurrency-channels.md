## §B14. Unbounded channels and backpressure neglect

**The trap**: when the producer/consumer rate is unbalanced, an `mpsc::unbounded_channel` doesn't block the producer — it just lets the queue grow. Tests with 5–100 messages pass. Production with a producer that's 2× faster than the consumer accumulates millions of pending messages, RAM climbs steadily, and the OOM killer eventually terminates the process — usually under peak load when it hurts most.

**Why this happens**: bounded channels force the producer to handle "channel is full" via `try_send`/`send` errors; `unbounded` has the simpler API and is the LLM's path of least resistance — the §C5 reflexive-fix pattern applied to channel selection.

**Prompt triggers**: "send events to a worker", "background queue", "log messages to a task", "producer-consumer", "event bus", "websocket broadcast", "metrics pipeline".

**BANNED** in any non-trivial pipeline:
- `tokio::sync::mpsc::unbounded_channel()` — and `std::sync::mpsc::channel()`, documented as an "infinite buffer" — without explicit justification. A "bounded producer rate" is **not** sufficient: any *sustained* positive gap between producer rate and consumer service rate grows the queue without bound over time, no matter how politely the producer paces itself. A valid justification is one of: (a) a proven **finite total** bound on messages ever produced (e.g. a fan-out over a closed, fixed worklist), or (b) a proved **finite backlog envelope** — a bounded rate gap × a guaranteed time-to-drain (the consumer provably catches up within a stated deadline).
- `flume::unbounded()`, `async_channel::unbounded()`, `crossbeam_channel::unbounded()`, `futures::channel::mpsc::unbounded()` for the same reason.
- A `Vec` that is `push`-ed in a hot loop with no consumer or cap — same failure shape as an unbounded channel, different surface. `Vec::push` itself is fine (amortized O(1)); the failure is the missing drain or bound.
- Treating `tokio::sync::broadcast::error::RecvError::Lagged(n)` as a retryable hiccup that recovers the skipped events. Those events are no longer available to that receiver **from this channel**; its next receive starts at the oldest retained value. Record the loss and apply the delivery contract: tolerate it explicitly, resynchronize from authoritative state where that preserves semantics, or replay from an independent retained log. If every event is required, use a lossless delivery/backpressure protocol; speeding up a consumer or increasing future capacity does not recover an event already skipped.
- `FuturesUnordered` grown by unbounded `.push()` (or a `JoinSet` constructed or grown by **any** task-adding operation with no hard concurrency cap — any spawn/insertion method, and equally construction via `Extend`/`FromIterator`: `xs.collect::<JoinSet<_>>()` spawns every supplied future synchronously, before the first removal poll ever runs, per current Tokio's docs). **A drain without an insertion gate is not a cap**: an insertion loop that adds tasks unconditionally and drains only when convenient — via `.join_next()`/`join_next_with_id()`/`try_join_next()`, the polling forms `.poll_join_next()`/`.poll_join_next_with_id()` (current Tokio implements no `Stream` for `JoinSet`; these are the API), or any `join_all`-style pass — bounds neither peak nor steady-state occupancy: every supplied future is already spawned/queued when an uncoupled drain runs, and a loop that inserts faster than completions arrive still grows at steady state. **A drain coupled to admission is a cap**: gate each insertion on `len() < N` — strict, **before** the insertion: a `len() <= N` pre-check still admits task `N + 1` once the set holds `N` (`N <= N` is true); the idiom is `while set.len() >= N { set.join_next().await; }` before each `spawn`, and `len() <= N` is reserved for the POST-insertion invariant (the set's size after any insertion never exceeds `N`) — from empty, a loop of `spawn(); join_next().await;` never exceeds one in-flight task, which is exactly the hard cap REQUIRED below. REQUIRED: a hard cap on the set's length (gate insertion at a maximum — a `len() < N` check **before** each insertion, with `len() <= N` only as the post-insertion invariant — and await a removal before adding more) or the same proved finite-total/finite-backlog envelope the channel bullet above requires — the same unbounded-growth hazard as an unbounded channel, just wearing a different type. The configured cap must be **positive**, and the configuration boundary must enforce it: a zero limit is not a safe minimum, it is a stall — the drain idiom `while set.len() >= N { set.join_next().await; }` with `N == 0` never exits (`len() >= 0` is always true), so the gate never opens and the loop can never progress. Fail fast on `N == 0` — with a guard that survives **release** builds, because `debug_assert!(N > 0)` does not qualify: `debug_assert!` is compiled out of release builds (it exists only under `debug_assertions`), so a release binary silently accepts `N == 0` and the drain predicate above stays true — the stall is reachable in production, not just in tests. Verify the zero-capacity rejection in release builds too (a release-profile test or CI `--release` run), never under debug assertions alone. Pick exactly one mechanism based on what `N` is: (a) `N` is caller-supplied configuration (the usual case) → startup/construction-time validation that returns a proper `Result`/`Err` on `N == 0` — bad configuration is an error to report, not an invariant to panic on, so no `assert!`-family panic belongs on this path; (b) `N` is a genuine internal invariant (valid configuration can never produce zero) → an always-on `assert!(N > 0)`, never `debug_assert!`; (c) strongest, in either case → a nonzero capacity type: a `NonZeroUsize`-backed newtype (e.g. `struct ConcurrencyCap(std::num::NonZeroUsize)`) as the configuration type, so `N == 0` is unrepresentable at the type level and needs no runtime guard at all. Separately: an **empty** `FuturesUnordered` polled in a `select!` arm returns `Poll::Ready(None)` immediately, so a `loop { select! { x = futs.next() => ... } }` busy-spins at 100% CPU when `futs` is empty. A bare unconditional "fallback arm" does not fix this — `select!` still polls the `futs.next()` arm every iteration, and an immediately-`Ready(None)` future keeps winning the race regardless of what else is in the macro. Guard the arm itself with the precondition syntax (`x = futs.next(), if !futs.is_empty() => ...`), pattern-match `Some(x) = futs.next()` (which disables the arm on a `None` result, per `select!`'s own pattern-match semantics) with an `else` branch for the empty/exhausted case, or `break`/wait explicitly when `next()` returns `None`.
- A long synchronous step inside a `FuturesUnordered` / `buffer_unordered` loop body *buries* the sibling futures in the set — they are polled only when the set is polled, so external timeouts can fire spuriously and futures awaiting a shared semaphore inside the set can self-deadlock (holding permits while a queued item waits for one). Keep work that runs between polls short. An `.await` in that loop body is the stronger form of the same defect: while the body awaits, nothing polls the set, and if a member holds or is queued for the resource the body awaits, the task hangs permanently — futurelock (`async.md` §B23, Oxide RFD 609). Push follow-up work into the set, or use a `JoinSet`, whose members are independent tasks.
- **Unbounded admission — the count of tasks/sockets is itself the unbounded resource** (🔴 when the accept/ingest source is untrusted-peer-extendable, 🟡 otherwise). An accept/ingest loop that spawns one task per item with no concurrency cap — `loop { let (stream, _) = listener.accept().await?; tokio::spawn(handle(stream)); }` — grows *nothing that the bullets above name*: no channel, no `Vec`, no `FuturesUnordered`. The unbounded resource is the task/socket/buffer *count*, and the attacker sets it — N connections → N tasks → N buffers → N FDs → OOM or FD exhaustion (CWE-770). A `// fire-and-forget: detached by design` comment satisfies §B21 and still admits unboundedly. REQUIRED: gate admission with an `Arc<Semaphore>` — `let permit = sem.clone().acquire_owned().await?;` **before** `tokio::spawn`, and **move the permit into the spawned task** (`tokio::spawn(async move { let _permit = permit; handle(stream).await; })`) so a slot is freed only when the task actually finishes. Two LLM-typical wrong "fixes" that cap nothing: (a) acquiring the permit *inside* the spawned task — the tasks are still spawned unboundedly, only the work inside them is throttled, so N tasks and N buffers still exist; (b) acquiring the permit in the accept loop but *not moving it into the task* — the guard drops at the end of the loop iteration, before the task runs, releasing the slot immediately. Calibration: this targets a public-facing / attacker-reachable accept loop; an internal fan-out (`for item in known_bounded_worklist { tokio::spawn(...) }`) over a statically-bounded worklist needs no cap — say so in a comment. Cross: §B21 (the dropped-handle dimension), §F3 (per-connection lifecycle).
- **Accept-error handling — classify, don't `?` and don't hot-loop** (🟡). The sibling of the admission cap: even with a `Semaphore` in place, `accept()` can fail for reasons the cap does not prevent (other FDs, other processes, transient network errors). `let (stream, _) = listener.accept().await?;` propagates a *single* `EMFILE`/`ENFILE`/`ECONNABORTED` and **kills the whole accept loop forever** — the server stops accepting on the first hiccup. The naive "fix" `Err(e) => { warn!(%e); continue; }` **busy-spins at 100% CPU** on `EMFILE`: the listener stays ready (the FD limit is not cleared by ignoring it) and the kernel keeps completing handshakes into the backlog, so the loop re-arms instantly. This is *not* §B3a's case: an accept loop must **not** "release leadership and return" on a transient error (that would stop serving), and must **not** hot-retry either. REQUIRED: `match` on the error and classify — *fatal* (the listener itself is gone / `ErrorKind` indicates a broken listening socket → stop and propagate) vs *transient-with-backoff* (`EMFILE`/`ENFILE`/`ECONNABORTED`-class → log, `tokio::time::sleep` a brief backoff so you don't hot-loop while resources recover, then continue). tokio's `TcpListener`/`UnixListener` docs note that "not all [accept] errors are necessarily fatal" — but don't spell out this match-don't-`?`/backoff pattern; the classification and backoff design here is this section's own guidance, not a documented tokio recipe.
- **Insert-only keyed collection with no eviction is an unbounded cache/registry** (🔴 when the key space is attacker-extendable — per-IP/per-header/per-path keys — 🟡 otherwise). `CACHE.insert(key, v)` with no eviction, TTL, or cap, where the key derives from request path/header/IP, grows forever: each entry is small and honestly sized (so §B7 does not apply) and the map *has* a consumer (constant reads hit it — so the "`Vec` with no consumer" bullet above does not match). The defect is **no eviction** — entries are immortal, not unread. Same shape wearing other names: per-IP rate-limiter maps, session registries, dedup "have we seen X" sets, high-cardinality metrics-label maps, and the §B13 per-key `OnceCell` map. BANNED: an insert-only keyed collection (`HashMap`/`DashMap`/`BTreeMap`) with unbounded or attacker-influenced key cardinality and no stated bound. REQUIRED: a *stated bound* — an LRU/TTL/capacity policy via `lru` (pin ≥ 0.18.2: RUSTSEC-2026-0002 unsound `IterMut`; RUSTSEC-2026-0253 panic-in-`Drop` use-after-free — see §C12's cache-eviction row) or `moka` (mainstream Rust cache crates), or a written argument (in a comment) that the key cardinality is bounded by an internal invariant (e.g. keyed by a closed enum, or by a fixed set of worker IDs). CWE-770/400. Eviction-lifetime calibration: for the §B13 OnceCell registry, preserve identity while outstanding clients can still initialize the old entry, not only while an initializer is visibly running. Protect the lookup-to-initialization interval with leases or another proved protocol; count pinned entries in the total bound and define full-capacity admission. A completed entry is ordinarily evictable only if it cannot restart under the supported API. Cross: §B10 (this leaks with zero `Rc`/`Arc` cycles), §B13 (the race in filling it).
- **A `reqwest::Client` (or an `sqlx` pool, a cloud-SDK client) constructed per request inside a handler** — each construction carries its own connection pool + TLS config, so N concurrent requests means N independent pools: file descriptors and ephemeral ports climb until exhaustion (`EADDRNOTAVAIL`, sockets stuck in `TIME_WAIT`). Correctness at scale, not just cost. REQUIRED: build once (`LazyLock<reqwest::Client>` or application state) and share by clone — `Client` is an `Arc` internally, so clones share one pool. (`rustls::ClientConfig` is a distinct, narrower case: it is reusable TLS *configuration* — cipher suites, root certs — not a connection pool that owns sockets or accumulates `TIME_WAIT` states. Rebuilding it per request wastes CPU re-parsing certs/config, but it is an §E5 recompute-cost finding, not this FD/port-exhaustion correctness bug; still build it once and share it, just not for the same reason.)

**REQUIRED**:
- Default to **bounded** channels: `tokio::sync::mpsc::channel(N)`. Size `N` from the actual constraints, not from a folk number: large enough to absorb the *expected producer burst over one consumer cycle*, small enough that `N ×` the **worst-case retained bytes per message** fits the per-task memory budget — where retained bytes include everything a queued message transitively owns (a `Vec<u8>`/`String` payload, an open file/socket, a pooled DB connection), not just `size_of::<Message>()` of the stack-resident struct, which massively undercounts when messages carry heap buffers or external resources. Add the queue's own reservation/overhead on top. Require the configured capacity to be **positive** everywhere — `N >= 1`: `tokio::sync::mpsc::channel(0)` **panics at construction** (tokio documents the bound as "must be at least 1" and "panics if the buffer capacity is 0"), `tokio::sync::broadcast::channel(0)` panics the same way, and a drain-at-limit/concurrency-gate loop configured with a zero limit never progresses at all (see the JoinSet/FuturesUnordered bullet above). For `broadcast`, don't assume requested == effective when budgeting memory: the provided capacity is rounded **up** to the next power of two internally — `broadcast::channel(3)` retains 4 messages — so budget memory (and reason about lag distance) against the **effective** ring capacity, not the number passed in. If the right `N` cannot be reasoned about, that is a signal that the backpressure policy itself needs design before the channel is written. Use unbounded only under the explicit finite-envelope exceptions above.
- Decide the **backpressure policy** explicitly: block the producer (default `send().await`), drop newest (`try_send` returning `Err(Full(msg))` — the message that failed to send is returned in the error; log and discard it), or apply rate limiting upstream. **Drop oldest cannot be built on `try_send`**: on a full channel, `try_send(new)` leaves the already-queued value untouched in the channel and fails with the *newest* message in the `Err` — discarding that payload is drop-newest, never drop-oldest. True drop-oldest requires a receiver-owned eviction/coalescing design (e.g. popping the front of a bounded `VecDeque`/ring buffer) or a channel type that natively supports evicting its own head — `try_send` alone cannot implement it. State the choice in a comment.
- For broadcast scenarios where slow consumers shouldn't slow producers: `tokio::sync::broadcast::channel(N)` (`N >= 1`; zero panics, and `N` is rounded up to a power of two internally, so the effective ring capacity can exceed the requested value — budget against the effective capacity, see the sizing bullet above) with explicit handling of `RecvError::Lagged` (which indicates dropped messages).
- For any unbounded queue that *must* exist (e.g., legacy interop): expose its size as a metric and alert when it grows abnormally.

**Detection**: unbounded channel growth doesn't appear in tests. Defense is at write time (default to bounded) and via monitoring. `Sender::capacity()` — remaining permits, decrementing per send and restoring per receive — exists only on a *bounded* `Sender`; `UnboundedSender` has no `capacity()` at all. For the unbounded queue that must exist, track the receiver's queued-message count (`Receiver::len()`) as the metric; on a bounded channel, `Sender::capacity()` plus queue length is the right pair.

## §C8. Channel-and-runtime mismatch

**The trap**: the LLM picks a channel by name recognition — `std::sync::mpsc` because it's standard, `crossbeam::channel` because it's "the fast one", `tokio::sync::mpsc` because it's the tokio one. The code compiles in all four runtime/channel combinations. Behaviour diverges: a sync channel in async code blocks the executor (§B11 surface); multi-consumer built on a tokio MPSC through a hand-rolled wrapper — the LLM-typical shape is the single `Receiver` parked behind an `Arc<Mutex<…>>` that several tasks contend for, or a genuinely MPMC channel (`flume`, crossbeam) misremembered as tokio's — fans messages to whichever task wins the lock race (bare `tokio::sync::mpsc::channel` cannot literally do this: `Receiver` is not `Clone` and only one can exist per channel — see the BANNED bullet below); a `crossbeam::channel::Receiver::recv()` inside an `async fn` blocks the worker thread for as long as the queue is empty. **Whether the mutex-wrapped-receiver shape is actually wrong depends on the delivery requirement** — see the BANNED and "not banned" notes below: it is a correctness bug for broadcast-to-all or routed/affinity delivery, but not for a plain competing-workers queue.

**BANNED**:
- `std::sync::mpsc::Receiver::recv()` inside an `async fn` or any function called from `tokio::spawn` — blocks the worker thread; same defect as `std::thread::sleep` per §B11.
- One mutex-wrapped MPSC receiver used when the contract needs fan-out or per-consumer routing. There is one receiver value with exclusive receive access; sharing that receiver distributes jobs among competing workers, not to every/specific subscriber. For **loss-tolerant fan-out**, Tokio broadcast can fit with a Lagged policy. The type alone does not guarantee that every subscriber receives every event; a no-loss use needs a proved bound preventing lag or an external replay mechanism. For lossless fan-out, design per-subscriber delivery with backpressure and failure handling, or an acknowledged/replayable log when the durability contract requires it. Use explicit routing for affinity delivery.
- `crossbeam::channel::Receiver::recv()` inside async code — sync API, blocks the worker. `crossbeam` is fine in pure-sync contexts (rayon, OS threads); not under tokio.
- `tokio::sync::mpsc::Sender::send(...)` (await form) inside a fast sync producer that cannot afford the await point — use `try_send` and handle the `TrySendError::Full` explicitly (§B14 backpressure). Calibration — this bans the await form in sync code, not blocking bridges in general: `Sender::blocking_send` is a **valid, correct** send from a genuinely synchronous thread (a dedicated `std::thread`, or a `spawn_blocking` closure — not an async task, not a runtime worker thread) **when blocking is the bridge's explicitly stated backpressure policy** — write the policy in a comment at the call site, exactly as §B14 requires of every backpressure choice; tokio documents it as "blocking send to call outside of asynchronous contexts" with its own `std::thread` example. What stays banned is `blocking_send` on **async worker threads/tasks** — there it panics (tokio: "panics if called within an asynchronous execution context"), and any blocking send on a worker is §B11's blocked-executor defect regardless. The reflexive inverse — "a sync producer must therefore always `try_send`" — is also wrong when the producer must not lose messages and blocking is the intended policy: pick the send form by the stated backpressure policy, not by reflex.

**Not banned — the delivery model the mutex-wrapped shape actually gets right:** a **competing-workers** queue (a worker pool where any free worker may take the next job — "delivery to whichever one is free" *is* the intended semantic). There, the mutex-wrapped `Receiver` above is functionally correct — the same distribution semantic as `flume`'s bounded MPMC below — merely an unnecessary/awkward inefficiency (an extra unrelated lock serializing consumers) rather than a correctness bug; prefer a purpose-built MPMC (`flume`) for it anyway, but the mutex-wrapped shape is not itself the finding for this delivery model.

**REQUIRED**:
- **Async multi-producer / single-consumer**: `tokio::sync::mpsc::channel(N)` (bounded; default).
- **Async competing consumers**: a bounded MPMC such as `flume::bounded(N)`, using its async API, distributes each job to one receiver. **Async fan-out** is a different contract: Tokio broadcast is bounded, non-backpressuring and can lose events for lagging subscribers; require a loss/recovery policy, a proof that admitted backlog cannot cause lag, or a lossless fan-out design. Producer count does not determine delivery reliability.
- **Sync MPMC**: `crossbeam::channel::bounded(N)` or `flume::bounded(N)` in sync mode.
- **Async single-producer / single-consumer**: `tokio::sync::oneshot::channel()` for one-shot; `tokio::sync::mpsc::channel(1)` for streamed.
- **Async with priorities**: build on `tokio::sync::Mutex<BinaryHeap<_>>` + a `Notify` for wake-ups, or use the `priority-queue` crate inside a `Mutex`. There is no standard async priority channel; document the choice — and the hand-rolled shape needs two more stated decisions. (a) **Capacity and full policy**: the heap is unbounded by construction — pick a cap and state what a producer does when full (await/backpressure until the consumer drains, or drop the lowest-priority item — evicting a `BinaryHeap`'s minimum is an O(n) scan). (b) **Consumer count**: as shown, `Mutex<BinaryHeap<_>>` + a single `Notify` is **single-consumer** — with two concurrent consumers, `notify_one` stores only one permit, so a consumer that checks the empty heap before arming its `Notified` future loses the wakeup for the item pushed in between and sleeps forever; the multi-consumer form requires the `enable()`-before-check lost-wakeup protocol (tokio's own docs demonstrate exactly this failure for a `Mutex<VecDeque<_>>` + `Notify` mpmc; see §B15e's `Notify` bullet in `async.md`, and this file's §B9 `Condvar` bullet — the sync twin of the same check-then-wait race).

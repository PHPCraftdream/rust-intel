## §C2. Error handling discipline

**The trap**: `anyhow::Error` in library crates poisons downstream error handling. `unwrap()` and `expect()` in non-test code is a runtime panic waiting to happen. The `?` operator silently loses context if `From` impls are too eager.

**REQUIRED**:
- In **published library crates** (anything shipped to crates.io with a `pub` API that other authors consume): use `thiserror` for typed errors, never `anyhow::Error` in public APIs. Each `pub fn` returning `Result` has a typed error. The cost of `anyhow` here is paid by every downstream caller who loses the ability to match on specific error variants.
- For **internal/workspace libraries** (not published, only used within the same workspace by the same team): `anyhow::Error` in `pub fn` is acceptable if the team agrees, but make it a deliberate choice — once a library moves toward publication, the migration to typed errors becomes painful.
- In **binary** crates (`main.rs` and friends): `anyhow::Error` is acceptable for top-level handlers and CLI surfaces — pin ≥ 1.0.103 (RUSTSEC-2026-0190: `Error::downcast_mut` after `.context()` is unsound below it).
- `unwrap()` is allowed only when (a) it is statically impossible to fail and I have a comment explaining why, (b) in tests, or (c) it is a poison-propagating `.unwrap()` on a std lock or condvar result (`Mutex::lock`, `RwLock::read`/`write`, `Condvar::wait`/`wait_while`) used as the codebase's deliberate poison-propagation default (§B2's poison policy: a poisoned lock means another thread already panicked — not flagged per call). Same for `expect()`.
- `?` is fine when the conversion is meaningful; if it loses context, use `.map_err(|e| MyError::Context { source: e, info: ... })` instead.
- `panic!`, `todo!`, `unimplemented!`, `unreachable!` are noted inline (at write time) with justification, per the canonical inline-flag policy (SKILL.md → Enforcement tiers, 🟡 paragraph; Operating mode item 7 names these constructs) — not enumerated in the summary; none of these four is a 🔴-tier item in its own right.
- **Command and argument injection — remedy.** Prefer an allowlisted native executable with separate `.arg()`/`.args()` data arguments; never let untrusted input choose the program. On Unix this supplies an argv array without shell evaluation. **Windows supplies one command-line string, parsed by the child:** Rust's ordinary argument encoding assumes the conventional parser, not every possible target. Batch files (`.bat`/`.cmd`) involve `cmd.exe` even when passed directly to `Command::new`; Rust has special escaping and may reject unrepresentable inputs at spawn. Treat batch wrappers and custom parsers as separate contracts, not as a shell-free guarantee, and do not bypass a safe spawn rejection with `raw_arg` or interpolated shell text. Use a validated input subset or a documented target-specific data channel when necessary. For option injection, use `--` only when the target supports it; otherwise validate or encode positional values according to that target. Argument separation does not neutralize the program's own option or operand syntax.
- **Command injection — remedy when a shell is unavoidable.** If shell syntax is genuinely unavoidable, name the interpreter and use a mechanism documented for *that* context — pass data out-of-band where supported (separate argv elements, environment variables or stdin), without subsequently re-evaluating it as code, or use a vetted escaping rule specific to that shell. Never interpolate raw untrusted data, and never treat one crate as a universal escape hatch: `shell-escape` is **not** a platform-independent remedy (its Windows branch leaves input containing no quote or whitespace unchanged, so `&`, `|`, `^` alone never trigger quoting; its dispatch follows the host OS, not the selected interpreter). Test harmless metacharacters, quotes, whitespace and option-like values against every claimed target/parser, asserting exact data arrival **or explicit rejection** for unsupported inputs. A benign `a&b` success alone does not prove arbitrary input safe.
- **SQL injection — remedy.** Pass every untrusted value as a **bound parameter**, never as formatted SQL: `sqlx::query("SELECT … WHERE id = $1").bind(id)`, the compile-checked `sqlx::query!("… WHERE id = $1", id)`, or Diesel's typed DSL / `diesel::sql_query(...).bind(...)`. For genuinely dynamic SQL (a variable `IN`-list, an optional filter) build it with `sqlx::QueryBuilder` — but `QueryBuilder::push()` does **not** bind: it appends its argument verbatim as a raw, unsanitized SQL fragment, so reserve `push()` for static or explicitly allowlisted SQL syntax and pass **every** untrusted value through `push_bind()`, never `push()` (the BANNED bullets name the banned shapes). A column or table name that must be dynamic cannot be a bound parameter — **allowlist** it against a fixed set, never interpolate it raw. On `sqlx` ≥ 0.9 the `SqlSafeStr` bound enforces this bullet: only `&'static str` passes without an explicit `AssertSqlSafe` assertion.
- **SSRF — remedy.** For a user-supplied outbound destination: a fixed **allowlist** of host/scheme/port validated at save time *and* re-checked at use time. The destination policy is **unconditional** — enforced on the **original** URL / resolved destination **first**, before any connection is made; it is never optional. `ClientBuilder::redirect(reqwest::redirect::Policy::none())` is **not** an alternative to it: disabling redirects only prevents a *follow-up* request, and the **first** request to `http://127.0.0.1:2375/`, `http://169.254.169.254/…` or any other forbidden destination still goes out and still succeeds — a `no_proxy()` + `Policy::none()` client requests its own loopback server and gets 200 with no redirect involved (verified against reqwest 0.13.4). The redirect choice is a separate **second** decision, made on top of a destination policy that already holds: either `Policy::none()` when redirects are not part of the contract, or `redirect::Policy::custom` that re-runs the **same** destination check on **every** hop (inspect `attempt.url()` for each hop — the pre-flight check on the original URL does not cover later hops). **And** resolve the hostname yourself, validate the resolved IP, and pin it via `ClientBuilder::resolve`/`resolve_to_addrs` so the connection cannot be rebound after validation. That pin is a complete control only for **direct** connections: reqwest honors ambient system-proxy settings by default, and with a proxy configured the destination hostname is resolved *at the proxy* — the local resolver override never sees the connection, so the validated IP is silently bypassed. Require direct, proxy-free operation for the validating client (`ClientBuilder::no_proxy()`), or route through a **trusted** egress proxy that itself enforces the same destination policy — a deliberate, policy-enforcing proxy is the architectural form of this control, not whatever proxy the ambient environment happens to supply. And when installing the custom redirect policy, carry an explicit hop bound into it — the custom policy **replaces** reqwest's default 10-hop limit, it does not refine it, so a custom policy without its own bound follows redirects without limit — and keep the overall request budget finite. Tests need **three separate negative cases**: a directly forbidden destination rejected before any connection (no redirect involved — `Policy::none()` does not rescue it), an allowed destination whose 302 lands on a forbidden one rejected (a polite local stub that never redirects proves nothing, §D1a), and the resolver/proxy routing case attempted and blocked.

**BANNED**:
- `anyhow::Result<T>` in a `pub` API of a published library crate.
- Silent `let _ = result;` to discard errors. If discarding is intentional, comment why. The same ban covers the spellings that review and `unused_must_use` both miss: `.ok();` as a statement, `.unwrap_or_default()` on a side-effecting call, and `if let Ok(v) = op() { … }` with no `else` — each compiles warning-free and drops the failure. **Batch form:** a loop over many items whose reported status is the last item's result (`let mut res = Ok(()); for f in files { res = process(f); } res`) reports success after earlier failures — CVE-2026-35339 (uutils `chmod -R`, fixed in 0.6.0: "The final return value is determined solely by the success or failure of the last file processed"), so a script checking the exit code continues over files that were never changed. Accumulate the worst outcome (`failed |= process(f).is_err()`, or collect the errors) and test with a failing item that is **not** the last one.
- `.unwrap()` / `.expect()` (or an unchecked index / `assert!`) on a limit, size or shape check of **data the program loads at runtime — including files its own pipeline generates** (feature files, rule sets, routing tables, model artifacts, hot-reloaded config). "Our generator never emits more than N entries" is a property of today's upstream data and queries, not a static impossibility, so clause (a) of the `unwrap()` allowance above does not apply. Cloudflare, 2025-11-18: a database permissions change made a generation query return duplicate rows, the Bot Management feature file roughly doubled past the preallocated limit of 200 features, and the proxy's `unwrap()` on that limit check panicked on every worker (`thread fl2_worker_thread panicked: called Result::unwrap() on an Err value`) — HTTP 5xx across the network for hours. The stated remediation: "Hardening ingestion of Cloudflare-generated configuration files in the same way we would for user-generated input". REQUIRED: validate a loaded artifact into a `Result` *before* it replaces the active one; on failure log, alert and **keep serving the last-known-good version**; when there is no previous version (cold start) choose fail-open or fail-closed explicitly and document it — a silent default that changes decisions is neither. Tests: `limit + 1` entries, duplicated rows, a truncated file and an empty file — each must leave the previous configuration active and the process alive.
- `Result<T, Box<dyn Error>>` (or `Result<T, Box<dyn Error + Send + Sync>>`) as the return type of any `pub fn` in a published library crate. Callers cannot match on the error variant — every error becomes an opaque blob. For libraries, define a concrete error enum (typically via `thiserror`). Binary `main` and CLI handlers are excepted (same as `anyhow` above) — there is no downstream caller to match. Internal/workspace code may use `Box<dyn Error>` or `anyhow::Error` as a deliberate trade-off.
- Reflexive `#[from]` on every error variant. `#[from] io::Error` makes every `?` on an I/O operation collapse into one variant — the resulting error can no longer say *which* operation failed (the config read? the socket write? the temp-file flush?). It compiles, tests pass, and production logs become "I/O error" with no call-site context. Use `#[from]` only where the source type already uniquely identifies the failure; otherwise carry context with `#[source]` plus an explicit `.map_err(|e| MyError::ConfigRead(e))` at each call site, or use `anyhow::Context::context` in binary code. **Crypto-boundary carve-out:** internal context must not become an outward padding/MAC/parse oracle over unauthenticated ciphertext. Preserve opaque authentication failures; validation after successful authentication follows the protocol and disclosure policy, not an unconditional collapse rule (§B24).
- `std::env::var("X").unwrap()` / `.expect(...)` — panics at startup both when the variable is *missing* and when its value is *not valid UTF-8* (common for paths on Windows / non-UTF8 locales). For values that may be non-UTF8 use `std::env::var_os`; for missing-but-optional config, handle the `Err(VarError::NotPresent)` with a default instead of panicking.
- `base.join(user_segment)` where `user_segment` may be absolute. `Path::join` with an absolute argument (`/etc/passwd`, `C:\…`, or a leading `/`) **discards `base` entirely** and returns the joined path — a path-traversal / write-to-wrong-place hazard when any segment is attacker-controlled. It compiles, tests on relative names pass, and production reads/writes outside the intended directory. The set of segments that drop (or partially drop) `base` is **broader than `is_absolute()`** and is not fully captured by `has_root()` either: on a Windows target a bare separator like `\windows` has `is_absolute() == false` yet still discards a drive-relative `base` (its first component is `Component::RootDir`), while a UNC path `\\server\share` parses as `[Component::Prefix, Component::RootDir]` (so `is_absolute()` and `has_root()` are both `true` there). The robust, OS-independent guard is to inspect the **first component** and reject a leading `Component::Prefix` **or** `Component::RootDir` (this catches `/etc/passwd`, `C:\…`, `\windows`, and `\\server\share` alike) — *not* `is_absolute()` alone. Path parsing is target-OS-specific: prefixes exist only on Windows targets. The robust recipe is a sequence, not an either/or: (1) reject a leading `Component::Prefix`/`Component::RootDir` (above) **and** any `Component::ParentDir` (`..`) in the untrusted segment, and reject or strip a trailing separator (the trailing-separator rule below); (2) join; (3) for a **static** tree (not concurrently attacker-mutable — the mutable case is the caveat below), additionally `canonicalize` and re-verify containment against the canonicalized trusted `base` — **for both the read and the write case**, because a lexical `..`/root check alone is not a containment boundary once an existing symlink can sit in a middle path component: given `base/link -> /outside`, the token-free segment `link/new_file` passes step (1), yet `base.join("link/new_file")` resolves *through* the link to `/outside/new_file` when opened. On the read case canonicalize the joined path itself; on the write case it may not fully exist (`canonicalize` errors on the not-yet-created final component), so canonicalize the **nearest existing ancestor** of the joined path instead — plus the trusted `base` itself — and verify `canonical_ancestor.starts_with(canonical_base)`. On the write case "existing ancestor" must be determined with **non-following** metadata — `fs::symlink_metadata`, which stats the directory entry itself — **not** `Path::exists()`, and not `try_exists()` either: both *follow* symlinks for this purpose and answer `false` for a dangling link. That following lookup is the demonstrated escape: given `base/link -> outside/created.txt` whose target does not exist yet, `link.exists()` is `false`, so the nearest *following-lookup* ancestor walks up to `base`, containment passes, and the subsequent write through `base/link` creates `outside/created.txt` — outside `base` with no `..`, no absolute segment, and a green check. Swapping `exists()` for `try_exists()` does not repair it — both follow the link; only `symlink_metadata`/`read_link` observe the link itself. Under the static write policy: at every component of the joined path strictly below the trusted `base`, `symlink_metadata` must report an existing, non-symlink entry — a dangling or intermediate symlink is an existing directory entry, and the chosen policy must reject it (or resolve it and re-run the full containment check on the resolved path — never treat it as nonexistent); only then is the not-yet-created tail created inside the verified directory. Distinguish create-new from overwrite: on POSIX, `OpenOptions::create_new(true)` (`O_CREAT|O_EXCL`) fails with `EEXIST` when the final component is a symlink even if the link is dangling, while plain overwrite (`File::create`, `create(true)`) follows the link on **every** platform — on Windows, `OpenOptions::create_new(true)` also rejects a dangling final symlink with `AlreadyExists` (verified by probe), so it too does not follow that final link; nevertheless, neither platform's result is a general symlink-containment control for the path — the non-following policy above is the control. Capability/handle-relative creation (`cap-std`/`openat`, the mutable-case answer below) remains the stronger alternative for the write case. **Trailing-separator rule — a trailing `/` defeats every non-following check above.** POSIX pathname resolution treats a trailing `/` as requiring the final component to be a directory, so a final symlink *is* followed. Observed on Linux 6.18 (WSL2), with `base/link -> <dir outside base>`: `lstat("base/link")` reports a symlink, `lstat("base/link/")` reports a directory (not a symlink), and `open("base/link", O_RDONLY|O_NOFOLLOW|O_DIRECTORY)` fails `ENOTDIR` while `open("base/link/", <same flags>)` succeeds — it followed the link. `fs::symlink_metadata` is `lstat` on the bytes it is handed (observed the same way from Rust 1.98.0 on that kernel: `is_symlink() == false` for the `link/` spelling), so the "`symlink_metadata` at every component" check answers "not a symlink" for a path *string* ending in a separator, and `O_NOFOLLOW` fails open the same way. `Path::components()` drops trailing separators (and `.`), so a components-based lexical check and a raw-string stat/open disagree about the final component. REQUIRED: reject or strip trailing separators in the untrusted segment, and build every checked prefix **and** the final opened path from `components()` (e.g. `.components().collect::<PathBuf>()`) — never stat or open the raw joined string; the final component is opened without a trailing separator. `cap-std` itself shipped this bug: GHSA-hp8f-xmx4-4qrg (published 2026-08-20, critical, CVSS 9.0, no CVE) — the fallback resolver (`manually::open` in `cap-primitives`) re-appended a trailing slash before `openat(..., O_NOFOLLOW)`, so the kernel followed the symlink: a full confinement bypass (read/create/delete/rename outside the root) from safe Rust. Affected: `cap-std` and `cap-primitives` ≤ 4.0.2; patched 4.0.3 and 3.4.6. That resolver is the only one on Windows and macOS, and is also used on FreeBSD without `O_RESOLVE_BENEATH` and on Linux without `openat2` (kernel < 5.6, or `openat2` returning `ENOSYS`/`EPERM`, e.g. under a deny-by-default seccomp profile) — a green test on a modern Linux dev box never exercises it. Wasmtime shipped the same escape (RUSTSEC-2026-0269; patched `>=24.0.13, <25.0.0`, `>=36.0.14, <37.0.0`, `>=46.0.3, <47.0.0`, `>=47.0.4`), as did Go's `os.Root` (CVE-2026-39822, fixed in Go 1.25.12 / 1.26.5). Wherever this spec names `cap-std` as the race-free answer, require `cap-std` ≥ 4.0.3 (≥ 3.4.6 on 3.x) **and** verify the *resolved* `cap-primitives` in `Cargo.lock` (`cargo tree -i cap-primitives`) — the resolver lives in that separate crate. For its first 83 days GHSA-hp8f-xmx4-4qrg existed only as a repository security advisory of `bytecodealliance/cap-std` (observed 2026-09-29: `rustsec.org/packages/cap-primitives.html` listed only RUSTSEC-2024-0445; the global GitHub Advisory Database and `api.osv.dev` both returned 404 for the id), so RustSec, OSV and the GitHub Advisory Database (Dependabot) all missed it and `cargo audit` / `cargo deny check advisories` / `osv-scanner` stayed silent on a critical confinement bypass; RustSec issued it as RUSTSEC-2026-0482 only on 2026-11-11. The lag, not this one id, is the lesson: for security-boundary crates (path confinement, TLS, crypto, parsers of untrusted input) also read the crate repository's own Security → Advisories page against the `Cargo.lock`-resolved version — database-backed scanners are necessary but not sufficient. (See `references/sources.md`.) **Threat-model caveat (CWE-367):** step (3) closes the *static* symlink case (a pre-existing link inside `base` pointing out), but it is **not race-free** against an attacker who can swap a component between the `canonicalize` and the subsequent `open` (a privileged process operating over an attacker-writable directory). State the threat model: when the directory tree is not mutable by an untrusted party during the operation, the static check is sufficient; when it is, the check + `open` is a TOCTOU, and the race-free answer is component-wise `openat` + `O_NOFOLLOW` (or Linux `openat2(RESOLVE_BENEATH)`) — in Rust, the `cap-std` crate, at a patched version only (trailing-separator rule above; the component-wise walk must itself never re-append a trailing separator). Severity: 🔴 when untrusted input reaches it, 🟡 otherwise.
- **Joining an archive entry's name onto a destination directory** — `dest.join(entry.path()?)` in a hand-rolled `tar`/`zip` extraction loop, or treating `zip`'s `mangled_name()` as already-safe — without applying the `Path::join` guard above to **every** entry. An archive is a container of *attacker-authored paths*: `../../etc/cron.d/x`, an absolute `/etc/passwd`, a Windows drive prefix or `\`-rooted name, and — the case a `..` check alone misses — a **symlink or hardlink entry extracted first**, so that a later regular-file entry writes *through* it and lands outside the destination tree (the zip-slip / tar-slip family, CWE-22). It compiles, and every test against an archive you built yourself passes. The recipe is the same sequence as the bullet above, applied per entry — reject a leading `Component::Prefix`/`Component::RootDir` and any `Component::ParentDir`, then join — plus two archive-specific rules: **refuse link entries and special files** (device nodes, FIFOs) unless you resolve them against the destination root yourself, and treat the destination as attacker-mutable whenever anything else can write there, which puts you in the `cap-std`/`openat` case (patched version, per the trailing-separator rule above) rather than the `canonicalize` case. Directory entries legitimately carry a trailing `/` (`dir/`): take the entry type from the header, then rebuild the path from `components()` — do not stat or open the raw entry name. `tar::Archive::unpack` applies its own path guard — but only on a current pin: `tar` ≥ 0.4.45 fixes RUSTSEC-2026-0067 (a symlink entry followed by a same-named directory entry lets `unpack` `chmod` an arbitrary directory outside the extraction root — the same bug behind Cargo CVE-2026-33056) and RUSTSEC-2026-0068 (PAX size-header differential against other tar parsers); `zip` ≥ 9.0.5 (which carries the RUSTSEC-2025-0168 fix from 2.3.0: a symlink entry earlier in the archive reused for later entries → arbitrary write). Verify the pinned version against these advisories; a per-entry loop you wrote has none of it. Aggregate output/entry-count quotas are the separate §B7 concern — a traversal-safe extractor can still fill the disk. **Async tar, and validating with one reader while extracting with another.** `tokio-tar` (≤ 0.3.1) is discontinued with **no patched version** (RUSTSEC-2025-0111 / CVE-2025-62518): when a ustar header declares size 0 and the PAX extended header declares a non-zero size, the reader parses the file's bytes as further headers, so the archive shows it different entries than other readers see — files smuggled past whatever inspected the archive. The advisory recommends `astral-tokio-tar`; the sync `tar` crate at the pin above inside `spawn_blocking` (§B11) is the other option. The same parser-differential shape exists inside one crate: `zip` ≤ 9.0.4 (GHSA-m665-v7pm-7grj / CVE-2026-115905, critical; patched 9.0.5) — `ZipArchive` treats the central directory as authoritative while `ZipStreamReader` extracts by the local file header, so a security check made through one approves an entry the other writes to disk under a different name. REQUIRED: scan and extract from **one** parsed entry list produced by **one** reader, and treat any disagreement between duplicated metadata (PAX vs ustar size, central vs local header name) as a hard error, never as "take the first". Severity: 🔴 when untrusted input reaches it, 🟡 otherwise.
- `Command::new("sh").arg("-c").arg(format!("… {user} …"))` — or any subprocess spawned *through a shell* with untrusted data interpolated into the command string: classic **OS command injection** (RCE). The shell re-parses `;`, `|`, `$()`, backticks, `&&` in the injected value. Adjacent: **argument injection** — an untrusted value beginning with `-` is consumed as a *flag* by the target program (`--output=…`, `-o /etc/…`), changing its behavior even without a shell. It compiles, the happy path passes, and production is a remote-code-execution / arg-smuggling hole. Severity: 🔴 when untrusted input reaches it, 🟡 otherwise.
- Untrusted values interpolated into **line-oriented protocol commands** — FTP, SMTP, IMAP, POP3, Redis inline commands, hand-built HTTP/1 request or header text: **CRLF injection**, the twin of the OS-command-injection bullet above. A value containing CR or LF terminates the intended command line and lets a second attacker-chosen command run in the same, already-authenticated session. RUSTSEC-2026-0271 (`suppaftp` < 10.0.2): an argument to `login`, `cwd`, `mkdir`, `rmdir`, `rm`, `rename`, `retr`, `put_file`, `site` or `custom_command` did exactly that; the fix rejects — it does not encode — CR/LF in a command line before it is sent. It compiles, and the happy-path tests use benign filenames. REQUIRED: reject any value containing CR, LF (or NUL), per argument, before writing to the socket; prefer a typed builder that validates — `http::HeaderValue::from_str`/`from_bytes` reject CR, LF, NUL and DEL (observed with `http` 1.5.0: tab and bytes ≥ 128 are accepted, so it is a control-byte check, not an ASCII-only one). Test with a harmless argument such as `"x\r\nNOOP"` that must be refused, asserting that nothing reached the wire. Severity: 🔴 when untrusted input reaches it, 🟡 otherwise.
- `sqlx::query(&format!("SELECT … WHERE id = {id}"))` — or any SQL assembled by string-formatting untrusted input (`sqlx::query_as(&format!(…))`, `diesel::sql_query(format!(…))`, a hand-built `WHERE`/`ORDER BY` fragment): **SQL injection**. `QueryBuilder` is not an exemption — `QueryBuilder::push(format!(…))` and any `.push(untrusted)` of an untrusted value are BANNED on the same terms: `push()` appends a raw, unsanitized SQL fragment and never binds; only `push_bind()` binds. The interpolated value is parsed as SQL, not bound as data. It compiles, passes tests against a local DB on benign inputs, and is a data-exfiltration / data-loss hole in production. On `sqlx` ≥ 0.9 the literal `&format!` form no longer compiles — every `query*()` takes `impl SqlSafeStr`, natively implemented only for `&'static str` — and the new cheapest fix that compiles is the same injection: `sqlx::AssertSqlSafe(format!(…))` or `AssertSqlSafe(s)` (the public path is `sqlx::AssertSqlSafe`, re-exported at the crate root — not `sqlx::query::AssertSqlSafe`) where `s` is the input-derived string. `AssertSqlSafe` is the crate's explicit opt-out ("you have made sure … use at your own risk", modeled on `std::panic::AssertUnwindSafe`) and is BANNED on the same terms. `sqlx::query!` requires its SQL argument to be a compile-time string literal, so — unlike `query`/`query_as`/`sql_query` above — it cannot accept a runtime `format!`'d string at all; this hazard does not apply to it. Severity: 🔴 when untrusted input reaches it, 🟡 otherwise.
- `reqwest::get(&user_url).await?` — or `client.get(user_url)` / any outbound request whose destination is attacker-influenced (webhook, callback URL, link preview, image proxy, "fetch this URL", "validate this URL") — without a destination policy: **SSRF** (CWE-918). The attacker supplies `http://169.254.169.254/latest/meta-data/…` (cloud metadata), `http://127.0.0.1:2375/` (local daemon API), or an internal-only host, and your service makes the request for them. The reflex fix — parse the URL and reject private/loopback hosts — validates only the *original* URL: reqwest's default redirect policy **follows up to 10 hops**, so a public host can answer `302 Location: http://169.254.169.254/…` and the request lands on the forbidden destination anyway. DNS rebinding is the same bypass one layer down: the hostname you validated resolves to the public IP for your check and to `127.0.0.1` for the actual connection. It compiles, and tests against a local stub are green. Severity: 🔴 when untrusted input reaches it, 🟡 otherwise.
- Binding a server to `127.0.0.1`/`::1` is **not authentication** — the inbound twin of the SSRF bullet above. A local HTTP/WebSocket server (dev server, tray-app API, debug endpoint) that exposes state-changing or code-executing operations is reachable from any web page the user visits via **DNS rebinding**, which bypasses the browser's same-origin barrier. RUSTSEC-2026-0279 (`rojo` < 7.7.0): the unauthenticated localhost dev-server API (read project source, write files, an `/api/open` endpoint that reaches the OS opener) was exploitable from a malicious page; the fix validates `Host`/`Origin` to reject cross-origin requests, gates the dangerous endpoint to loopback clients regardless of origin, and warns on a non-loopback bind. It works from `curl` and the intended client, so tests pass. REQUIRED: allowlist `Host` (`localhost`, `127.0.0.1`, `[::1]`, with the server's port), check `Origin` on state-changing requests and on WebSocket upgrades, and require a per-session secret for privileged endpoints. Tests: a request carrying `Host: attacker.example`, and one carrying a foreign `Origin`, are refused. Severity: 🔴 when untrusted input reaches it, 🟡 otherwise.
- Issuing a session cookie without a deliberate attribute policy: `Cookie::new("session", id)` leaves `http_only`, `secure`, and `same_site` unset. For session credentials require `HttpOnly` and `Secure`, and select `SameSite` for the supported flow: prefer `Lax` or `Strict` where compatible; intentional cross-site authentication/embedding may require `SameSite::None` with `Secure` and appropriate server-side CSRF/state validation. `None` is an explicit value, not an omitted attribute. A blanket Lax/Strict rule breaks flows that need a cookie on a cross-site POST; neither those modes nor `None; Secure` replaces the application's CSRF controls. Browser third-party-cookie policy may further restrict delivery. Test emitted attributes and the required browser flow, not just the cookie value.
- Authorization keyed by a **recyclable PID**: an identity decision (polkit, a privileged helper, any local service) made from a bare PID that the authority resolves later — e.g. via `/proc` — is a TOCTOU: terminate the authorized process and win the race to reuse its PID. RUSTSEC-2026-0278 (`zbus_polkit` < 5.1.0): `Subject::new_for_owner()` encoded the UID as D-Bus type `u` while polkit's Authority interface expects `i`, so polkit silently discarded the caller-supplied UID and derived the subject's owner by looking up the PID in `/proc` — an application that passed a UID from `SO_PEERCRED` specifically to defend against PID reuse got no protection. Two lessons. (1) The identity behind an authorization decision comes from credentials bound to the connection — the peer UID from kernel peer credentials, a D-Bus unique bus name, a pidfd — never from a bare PID looked up later (§B13 for the check-then-act shape). (2) A wire-signature mismatch against a peer interface can silently move the peer onto a different code path, with no error on either side — test against the real peer (Tier F), not a stand-in that accepts whatever is sent. Severity: 🔴 when untrusted input reaches it, 🟡 otherwise.
- Check-then-create where **exclusive creation** is the contract: `if !p.exists() { File::create(p)?; }` races and can truncate a file created between check and use. `exists()` also hides metadata errors; `try_exists()` distinguishes absence from an error but does not make a later mutation atomic. Use `OpenOptions::create_new(true)` for exclusive file creation or `fs::create_dir` for a single exclusive directory, and handle `AlreadyExists` according to the caller's contract. **Ensuring a directory tree exists is different:** call `fs::create_dir_all(path)?` directly, without a redundant existence check. It preserves recursive/idempotent behavior and is documented not to fail due to concurrent creation by another `create_dir_all`; it is not an atomic transaction, and partial parents can remain on error. None of these calls establishes path containment in an attacker-mutable tree — retain the path/symlink policy above.
- **Restricting permissions after creation** — `fs::write(p, secret)?` / `File::create(p)?` / `fs::create_dir(p)?` followed by `fs::set_permissions(p, Permissions::from_mode(0o600))`, or a secret file that simply inherits the process umask. Between the two calls the object exists with the default mode (`0o666`/`0o777` masked by umask), and a descriptor another local user opens in that window stays valid after the chmod; `fs::set_permissions` is path-based and follows symlinks, so an entry swapped for a link redirects the chmod onto an arbitrary file; and going on to the chmod after creation failed with `AlreadyExists` re-modes an object this code did not create. It compiles, and a single-user test never observes the window. uutils coreutils shipped the shape: CVE-2026-35353 (`mkdir -m` created the directory with umask-based permissions and applied the requested mode with a separate chmod; published 2026-04-22, fixed in 0.6.0), with sibling findings in the same audit batch. REQUIRED: set the final mode in the creating call — `OpenOptions::new().write(true).create_new(true).mode(0o600)` (`std::os::unix::fs::OpenOptionsExt`), `DirBuilder::new().mode(0o700)` (`DirBuilderExt`), or a `tempfile` handle persisted into place — and make any later mode change through the open handle (`File::set_permissions`, i.e. `fchmod`), never by path. These are Unix-only APIs: gate them with `#[cfg(unix)]` and state the Windows policy (ACLs inherited from the parent directory) rather than silently skipping the restriction. Test from a child process with `umask(0)` (the umask is process-wide, so not inside the parallel test harness — §D1) and assert the mode via metadata of the returned handle.
- **Deciding filesystem identity by comparing path strings** — guarding a destructive or privileged operation with `path == Path::new("/")`, `arg == "."` or `src == dst`. Many spellings name the same object (`/../`, `/./`, `//`, a trailing separator, a symlink whose target is the protected object), so the guard passes and the operation runs on exactly the object it was meant to refuse. CVE-2026-35349 (uutils `rm --preserve-root`, fixed in 0.7.0): the safeguard recognized the root directory by its path text instead of its device and inode numbers, so a symlink pointing at `/` bypassed it and the recursive delete proceeded on the root filesystem. Tests that pass the literal `/` are green. REQUIRED: compare the identity of the opened objects — `(dev, ino)` from `std::os::unix::fs::MetadataExt`, or the `same-file` crate (`is_same_file`, `Handle`) portably — taken from metadata of the handle the operation will use, not from a second path lookup (the check-then-act race above). `canonicalize` + compare is acceptable only for a static tree (threat-model caveat above). Test with a symlink to the protected object and with `dir/../` spellings.
- **Name lookups after `chroot` while still privileged** — resolving a user, group or host name (`getpwnam`/`getgrnam` through `libc`, `nix::unistd::User::from_name`, `uzers`, `ToSocketAddrs`) after entering the new root and before dropping privileges. On glibc these calls go through the Name Service Switch, which loads `libnss_*.so.2` from the *current* root — now attacker-influenced — so a planted module executes as root. CVE-2026-35368 (uutils `chroot --userspec`): the user specification was resolved via `getpwnam()` after entering the chroot but before dropping root privileges; with an attacker-writable NEWROOT that is arbitrary code execution as root — container escape or privilege escalation. REQUIRED order: resolve every name to numeric ids in the original root → `chroot`/`pivot_root` + `chdir("/")` → `setgroups` → `setgid` → `setuid` → `exec`; after the root change use numeric ids only.
- `print!` / `println!` for a program's primary output where stdout can be a pipe. Both **panic** when the write fails (std: "Panics if writing to `io::stdout` fails"), and a Rust process ignores `SIGPIPE`, so `tool | head -1` ends with `failed printing to stdout: Broken pipe (os error 32)` and exit status 101 — a failure under `set -o pipefail`, and a dead daemon once its log consumer goes away (rust-lang/rust#46016, open since 2017-11-15). It never shows in a test, where stdout is captured. REQUIRED for CLIs and filters: write through a handle and propagate — `let mut out = io::stdout().lock(); writeln!(out, "…")?;` (inside a `BufWriter` for volume, with an explicit `flush()?` — §C4) — and map `io::ErrorKind::BrokenPipe` to a quiet exit at the top level. `eprint!`/`eprintln!` carry the same contract for stderr. Test by piping the built binary into a reader that closes early and asserting the exit status.

## §A1. Stale APIs, deprecated-not-removed APIs, and slopsquatting

The class here is **APIs that compile but are wrong**, not APIs that don't exist. The pure-hallucination cases (`E0599` "method does not exist") are noise — rustc catches them and the LLM moves on. The cases that survive the compile are: the API existed in an older version of the crate and still exists in the new one with materially different semantics; the API is `#[deprecated]` but not removed; the LLM picked up a method name from a different crate and the name happens to also exist in the named crate; or — worst — the LLM hallucinated a *crate name* that an attacker has since registered on crates.io with a malicious payload.

**The trap, by sub-class:**

- **Stale-but-still-valid APIs.** `tokio` 0.2's `mpsc::Receiver` implemented `Stream`; in 1.x it does not — the same code needs `tokio_stream::wrappers::ReceiverStream` (while the `(Sender<T>, Receiver<T>)` tuple shape never changed); `rand` 0.8 `thread_rng()` was renamed to `rng()` in 0.9 but the old function lingers in code patterns. The LLM emits the form from the older major; against the pinned version it either fails to compile with a misleading error (`Receiver: Stream is not satisfied`) or — when the old symbol still exists — compiles and behavior diverges from the user's mental model.
- **Deprecated-not-removed APIs.** `#[deprecated]` emits a warning, not an error. LLMs routinely ignore the warning channel and ship deprecated calls. Each deprecated call is a future break.
- **Wrong-version-of-crate APIs.** `serde_json::from_str` exists in every version, but `serde_json::Value::take` did not exist before a specific point. The compile succeeds against the pinned version *because the version pinned is recent enough*, but the LLM has no proof of that — it guessed and was lucky.
- **Slopsquatting (supply-chain).** Hallucinated crate names that an adversary has registered on crates.io. Compiles, runs, exfiltrates secrets, and `cargo build --offline` would not have helped (the malicious payload lives inside a dependency the build script reaches for). Published "package-import hallucination" studies (Lanyado / Spracklen) report elevated hallucination rates for Rust crate names relative to other ecosystems; precise figures require checking against the primary source.
- **Default-of-an-earlier-era crates.** A crate the training corpus is saturated with, that still compiles and usually still works, but stopped being the recognized default before the corpus's cutoff caught up — admitted here on author archival or an explicit advisory (recording the advisory is not the same as recommending a successor): `structopt` (folded into `clap`'s derive API — RUSTSEC-2022-0104, "structopt is in maintenance mode"), `serde_yaml` (archived by its author — and the fork an LLM is most likely to reach for instead, `serde_yml`, is RUSTSEC-2025-0068: unsound (a real segfault via `serde_yml::ser::Serializer.emitter`) and archived; the advisory names `serde_norway` (maintained fork, last publish 2024-12) or `serde_yaml_ng` (last publish 2024-05, itself sitting on unmaintained `unsafe-libyaml`) — verify the current recommendation at write time), `lazy_static`/`once_cell::sync::Lazy` (superseded by std `LazyLock`/`OnceLock`, stable since Rust 1.80 — see Version pins), `dotenv` (RUSTSEC-2021-0141, unmaintained → `dotenvy`), `async-std` (RUSTSEC-2025-0052, "has been discontinued" → `smol`; see §C3 in the async module), `bincode` (RUSTSEC-2025-0141, unmaintained — the reflexive answer for "serialize this fast"; the advisory names alternatives). Verify against the same "current default" question §C12 asks, not against whether the crate still compiles.

**REQUIRED**:
- Before calling any method on a third-party type, check that it exists *with the documented semantics* in the version actually in use. `Cargo.toml` declares a version **range**, not the exact version in use — the resolved version lives in `Cargo.lock` (or `cargo metadata`), per doc.rust-lang.org/cargo/guide/cargo-toml-vs-cargo-lock.html. For an **application**, inspect `Cargo.lock`/`cargo metadata` for the actual resolved version. Exact **locked** resolution and an exact `=`**version manifest requirement** are different mechanisms and must not be conflated: the lockfile pins the **entire resolved graph** that actually builds — direct **and transitive** dependencies alike, including versions `Cargo.toml` never names, each at one exact version — without narrowing the declared range for anyone else, while `=` narrows the requirement itself for every resolver that reads the manifest, but only for the dependency it is written on: it does not pin that dependency's own **transitive** resolutions, which is exactly the lockfile's job. A lockfile also binds only where it is used — a downstream consumer of a published library resolves and locks its **own** graph, so the library's committed `Cargo.lock` forces no version on consumers; it governs the library's own builds and CI. Cargo's guidance on committing changed in 2023 ([blog.rust-lang.org/2023/08/29/committing-lockfiles](https://blog.rust-lang.org/2023/08/29/committing-lockfiles/)): the old "commit for binaries, not libraries" convention is retired — the choice is the project's, with committing `Cargo.lock` the suggested starting point for **all** projects, libraries included (`cargo new` no longer ignores it for libraries) for reproducible CI, bisectable history, and a pinnable MSRV lane — paired with regular latest-dependencies testing (the locked/latest and direct-minimum jobs below) so the pin does not fossilize. For a published **library**, "test the full declared range" is operational, not exhaustive: test the **locked/latest** resolution CI builds (the upper end) **and** a **direct-minimum** job at the lowest versions the direct requirements admit (the lower end) — not a promise to test every released version inside the range, which is impossible. "It compiled" is not proof — semantics drift across minor versions in pre-1.0 crates.
- For high-churn crates (`tokio`, `axum`, `hyper`, `reqwest`, `sqlx`, `serde`, `tonic`, `tower`, `clap`, `rand`), if uncertain about an API or its semantics, **say so explicitly** and ask the user to confirm or run `cargo doc --open`.
- Treat `#[deprecated]` warnings as errors. If the symbol I want to emit is deprecated in the pinned version, switch to the replacement before writing.
- Pre-1.0 crates (any version with leading `0.`) have **breaking changes between minor versions**. Treat 0.6 → 0.7 with the same suspicion as 1.x → 2.x.
- Inspect every `[patch]` override by its **replacement source**, not just the table name. For a **git-sourced** dependency or patch, require a full-commit `rev` (not just a branch), a user-approved repository and a stated removal condition for the temporary override — e.g. `# remove once upstream 1.2.4 ships the fix`. A **path-sourced** patch is a valid local override, not a git dependency missing `rev`: review the resolved local tree and how the build obtains the intended bytes; `Cargo.lock` does not freeze mutable path contents. Apply source/version/provenance review to other supported replacement sources as well. The override is a review trigger, not automatically an unverified-source finding; retain the git pin and fork-approval requirements where they actually apply.

**BANNED**:
- Method calls on types where I have not internally verified the method exists *and means what I think it means* in the pinned version.
- Mixing API styles from different major versions (e.g., axum 0.6 routers with axum 0.7 handlers).
- Adding a crate to `Cargo.toml` that the user did not name and that I have not independently verified exists.
- A **git-sourced dependency or `[patch]` replacement without the required full-commit `rev`**, even under a known-good crate name. A branch-only or bare git source does not advance on each locked build — Cargo keeps the recorded commit — but an applicable update, lock regeneration or fresh resolution can select a new branch tip without a manifest change. The `rev` removes that drift, not the need to approve and review the source. Registry advisories do not attest fork bytes; configured `cargo vet` can audit exact-SHA git deltas against a registry base. A path replacement is reviewed under the separate source-kind rule above, not rejected for lacking a git revision. Workspace-root patches can affect transitive users too, so verify which replacement actually entered the resolved graph.

**Security note: slopsquatting**. Hallucinated *crate names* (not just methods) are a supply-chain attack vector that **survives compilation and runs malicious code**. Adversaries monitor common LLM crate-name hallucinations and **register those names on crates.io with malicious payloads**. This is the canonical Tier A category: the LLM's "fix" for "I need a crate that does X" compiles cleanly and silently runs untrusted code.

**Real attack cases (2022–2026)** — these are not hypothetical:
- `rustdecimal` — typosquat of `rust_decimal`. The malicious crate, documented in the CrateDepression incident (2022), targeted CI pipelines.
- `faster_log`, `async_println` — malicious crates designed to scan for and exfiltrate Solana/Ethereum private keys; reached thousands of downloads before takedown.
- `evm-units` / `uniswap-utils` (2025-12) and `finch-rust` / `sha-rust` (2025-12) — further crates.io malicious-crate takedowns in the same crypto-credential-theft family; by 2026-02 crates.io published a notification-policy update acknowledging such takedowns are now routine, and the cross-ecosystem "TrapDoor" campaign (2026-05) reached crates.io alongside npm/PyPI. The takedown cadence, not any single incident, is the signal. (See `references/sources.md`.)
- `arrayref` 0.3.10 / `append-only-vec` 0.1.9 / `internment` 0.8.7 (2026-08-20; RUSTSEC-2026-0259–0266) — the maintainer-compromise class, a different shape from everything above: a legitimate, widely-used crate whose maintainer's credentials were compromised, so the malicious versions (online 86/107/90 minutes) were published *from the real project*, each pulling a freshly-registered dependency (`proc-macro1` and lookalikes) whose **build script** downloaded a payload. `arrayref` 0.3.10 was downloaded 2,285× — "less than 10% of download traffic … most users had older versions in their lockfiles" — i.e. the committed `Cargo.lock`, not user vigilance, limited the blast radius. The git/`[patch]` BANNED bullet below covers the unverified-source trust decision; this is its registry-published twin: the name was right and the source was still hostile. (See `references/sources.md`.)
- Supply-chain attacks across software ecosystems rose materially in 2025 (published year-over-year estimates cluster around +70–75% ecosystem-wide; no crates.io-specific figure is published).

Concrete defenses:
- I do not add a crate to `Cargo.toml` unless the user explicitly named it OR I verified its existence by reading the project's existing dependencies.
- For any new dependency I suggest, I flag it as a *suggestion to verify*, not a fait accompli: "I'd add `deadpool-postgres` for connection pooling — please verify on crates.io before adding."
- I verify every crate name against the registry before adding it, checking both the `-` and `_` variants, because crates.io normalizes them to the same name (`serde_json` and `serde-json` cannot be distinct crates) — and I never conclude "this variation does not exist" from memory: `tokio-utils` was long cited as a hallucination next to the real `tokio-util`, but it has existed as a real crate (registered 2023-03; content unaudited) since March 2023. Separator *deletion* is a different name and the classic typosquat shape: `rustdecimal` (no separator) was the weaponized typosquat of `rust_decimal` in the CrateDepression incident (2022).
- Surface every newly-added `Cargo.toml` dependency in the post-flight summary so the user can audit it.

**Build-time code execution (a distinct supply-chain vector).** Slopsquatting is about *hallucinated names*; this is about *what a dependency does at build time*. A crate's `build.rs` and any proc-macro it exports run arbitrary code on the developer's machine and in CI **during `cargo build`**, before any runtime guard exists — this is the mechanism behind the malicious crates above, and such payloads read `~/.cargo/credentials`, `~/.ssh`, `.env`, and CI secrets. Build time is not even the earliest execution surface: per RustSec advisories filed 2026-09-07 ([RUSTSEC-2026-0280](https://rustsec.org/advisories/RUSTSEC-2026-0280.html), [RUSTSEC-2026-0281](https://rustsec.org/advisories/RUSTSEC-2026-0281.html)), malicious `greentic` package versions executed malware when a depending project was merely **opened in VS Code** — no build required — so treat **acquisition, workspace-open, and build** as three distinct execution surfaces, and treat **granting workspace trust** as part of the same trust decision (per [VS Code Workspace Trust](https://code.visualstudio.com/docs/editing/workspaces/workspace-trust), an untrusted workspace restricts task/extension execution). Keep an unfamiliar tree untrusted or isolated (container/VM) until its build scripts and proc-macros have actually been reviewed; "inspect before the first build" alone leaves the open-in-IDE surface uncovered. (Those advisories do not pin a single carrier filename; do not assume one.) (The proc-macro-trust surface is not hypothetical even for a *trusted* crate: `serde_derive` briefly shipped a **precompiled binary** it ran during your build instead of building the macro from source (2023) — reverted in v1.0.184 after community pushback, but it is the canonical demonstration that "it's just serde" is not a proof the code running at build time is the code you can read. See `references/sources.md`.) A typosquat that swaps `-` for `_` (or appends a language suffix), plus dependency confusion (a private crate name shadowed by a public one on a default registry), are the same class. Defenses, split by what the crate *is* (per doc.rust-lang.org/cargo/faq.html#why-do-binaries-have-cargolock-in-version-control-but-not-libraries): for a **binary/application**, commit `Cargo.lock` and build `--locked` for reproducibility — the *lockfile* is the exact-pin mechanism (exact **locked** resolution of the whole graph); an exact `=`**version manifest requirement** is a different, coarser mechanism that narrows the declared range itself and is not what makes a binary's build reproducible — the arrayref/append-only-vec/internment compromise (above) is the demonstration of *why*: most would-be victims were protected by their lockfile pinning the last good version, not by noticing the malicious release. For a published **library**, `Cargo.toml`'s declared range *is* the SemVer contract with consumers — do not force exact pins or a committed lockfile of one resolved graph onto every downstream consumer; instead rely on supply-chain audit/provenance (`cargo-vet` attestation, `cargo-audit`/RustSec) and test across the declared compatibility range. In both cases: for a newly-added *direct* dependency that is not a well-known crate, read its source — the repo you are about to pin — **before any execution surface is crossed**: before `cargo add`/`cargo fetch` pulls it, before the tree is opened in an IDE or granted workspace trust (the RUSTSEC-2026-0280/0281 open-in-VS-Code executions above are why "before the first build" is not early enough), and before the first build; and for the transitive graph (which you cannot read by hand) lean on `cargo-deny` / `cargo-audit` (RustSec advisory DB) and `cargo-vet` — plus, for binaries, the committed `Cargo.lock` and `--locked`/vendored builds.

**Lockfile hygiene and yanked versions.** Committing `Cargo.lock` and building `--locked` (above) pins *reproducibility* — but a pinned version is not the same as a *safe* version, and `--locked` actively hides one gap. A version that is **yanked** upstream (for a soundness bug, or because a RUSTSEC advisory was filed against it) stays downloadable, and an existing `Cargo.lock` keeps resolving it: `cargo build --locked` against a yanked pin has been observed to emit only a **warning** ("package `x` in Cargo.lock is yanked"), exit 0 — green in CI; Cargo does not document this as a portable, version-stable guarantee, so don't rely on the warning itself as the detection mechanism. Only a *fresh* resolution refuses a yanked version ("candidate versions … were yanked"), so the day a new contributor runs `cargo update` or a clean `cargo install`, the build breaks — and until then the project may have been building against a version yanked for a security reason for months, unnoticed. REQUIRED regardless of what a bare `--locked` build happens to print: `cargo deny check advisories` **with `yanked = "deny"` explicitly set in `deny.toml`** — cargo-deny's own default for this check is `yanked = "warn"`, which prints but does not fail the build, so a bare unconfigured `cargo deny check advisories` is exactly as silent as the `--locked` warning it was meant to replace — or `cargo audit -D warnings` in CI (whose failing behavior on a yanked pin does not depend on a config default), as the actual, configured mechanism that turns a yanked pin into a red build **with a stated reason** — don't depend on eyeballing `--locked` output, and don't assume `cargo deny check advisories` fails on a yanked crate out of the box. BANNED as the fix: a blanket `cargo update` (the LLM's reflexive "make the CI error go away" move) — it silently swaps many *other* pinned versions too, exactly the Tier-A-shaped residue this spec warns about; the fix for one yanked crate is a **targeted `cargo update -p <crate>`** for that crate alone.

**Network access in your *own* `build.rs` (unpinned bytes outside the lockfile).** The build-time-execution bullet above is the *read* direction — a malicious *dependency's* `build.rs` reading your secrets. This is its **write-direction twin** (mirroring how §B5's padding-leak bullet is the write-direction dual of the validate-before-mint read rule): *your own* `build.rs` reaching the network at build time — shelling out to `curl`/`git clone`, or `reqwest::blocking` — to fetch a schema, model file, `protoc`, or C library. It compiles and passes tests on the author's box, and it is a distinct hazard from everything above: it is not *whose code runs at build time* but *unpinned bytes entering the build outside the lockfile*. `--locked`/`--offline`/`cargo vendor` give **zero** integrity protection here — the download is not in Cargo's hash-verified dependency graph at all — so the fetched artifact can silently change (or be MITM'd) between builds, reproducibility is gone, and offline/vendored builds simply fail. REQUIRED: no network access in your own `build.rs` — vendor the artifact into the repo, or fetch it in a separate, explicit CI step with a **hardcoded SHA-256** you verify; and keep `cargo build --offline`/`cargo vendor` working by providing an offline fallback path. Calibration: build-time *codegen* is fine — generating code from a **local** schema file, or invoking a **local** toolchain binary, touches no network and is not this finding; only reaching the network at build time is.

## §C5. Reflexive `.clone()` as a borrow-checker silencer

**The trap**: when borrow checker complains, the LLM's path of least resistance is to insert `.clone()` or `.to_string()` until errors disappear. The code compiles. The performance cost is invisible until profiling. This is a *different* failure mode from §C4 — it's not an idiom drift, it's a reflexive *fix-it strategy* that resolves a real borrow problem with a hidden allocation.

**Why this happens**: gradient descent rewards "compiles" heavily; the model learned that adding `.clone()` is a reliable way to make red squiggles go away. The cost (allocation, deep copy of `Vec<T>`, etc.) isn't penalized anywhere in training.

**Prompt triggers**: any prompt involving a borrow checker error in the conversation history; "fix the lifetime issue"; "make this compile"; refactoring sessions where the user is iterating on a function signature.

**REQUIRED**:
- Before inserting `.clone()`, ask: can this be solved by restructuring ownership (split borrows, borrow earlier-release later, take `&self` instead of `self`)?
- If the next stage needs ownership of a field behind `&mut self`, consider `mem::take` / `Option::take` / `mem::replace` (§E2) when emptying/replacing the source is allowed. Keep a clone when an independent copy or unchanged-on-failure state is required (§B19).
- For `Copy` types (i32, bool, small struct of `Copy` fields), `.clone()` is a code smell — `clippy::clone_on_copy` exists for a reason. Never insert it.
- For `&str` → `String` conversions purely to escape a lifetime: re-examine the lifetime first. The String allocation is often masking the real problem from §B1.
- For `Vec<T>` clones in hot paths: consider `&[T]`, `Cow<'_, [T]>`, or `Arc<[T]>`.
- A `.clone()` introduced *to silence a borrow error* (the §C5 reflex) gets a one-line inline justification; routine clones, `Arc::clone`/`Rc::clone`, and `Copy`-type clones are 🟢 (clippy) / 🟡 (write-time) — not surfaced.

**BANNED**:
- `.clone()` on a `Copy` type.
- `String::from(s)` or `s.to_string()` immediately followed by use as `&str` (the original would have worked).
- Cloning inside a loop where the cloned value is only read.
- Replacing `&T` with `T` in a function signature just to make a call site compile.

## §C6. Procedural macro hygiene

**The trap**: proc-macros generate code that's pasted into the user's crate. If the macro writes `Option<T>`, it resolves at the call site — and if the user has `type Option = MyOption;`, the macro silently breaks. Hygiene violations in proc-macros are invisible at macro authoring time and only surface at user sites.

**REQUIRED in any proc-macro output**:
- Use absolute paths for every standard library item: `::core::option::Option<T>`, `::core::result::Result<T, E>`, `::std::vec::Vec<T>`, `::std::string::String`. Never bare `Option`, `Result`, `Vec`, `String`.
- For external traits, use a path that resolves in the **consumer's** crate, not a bare `Serialize` or an assumed dependency name. A hard-coded `::serde::Serialize` breaks when Cargo renames that dependency. Support a crate-path override, discover the actual dependency name (for example with `proc-macro-crate`), or route through an ordinary **runtime/facade crate** re-export such as `pub use serde as __serde;`. The facade moves the root path; it does **not** solve its own renaming: `::your_runtime_crate::__serde` still needs the facade's actual consumer-visible name or an override. Keep the implementation proc-macro crate separate from the ordinary facade — a proc-macro crate cannot export arbitrary runtime items. The facade may also `pub use` the derive macro, so consumers can depend **directly only on the facade** and invoke its re-export; the implementation crate is then transitive. A separate direct proc-macro dependency is needed only when consumers import the macro that way. Likewise, direct `serde` is needed only when the generated path refers to it directly; a facade re-export can supply it. Test ordinary and renamed consumer dependencies, including the facade-only import path when offered.
- For error reporting in macro expansion, use `syn::Error::to_compile_error()` returning `TokenStream`, which surfaces correctly at the user's call site. **Never `panic!`** in proc-macros — the user sees an opaque panic message without source location.
- For `#[derive]` macros that add bounds (e.g., `#[derive(Clone)]` adding implicit `T: Clone`), consider whether this matches user intent. For finer control, use `derive_more`, `derive-where`, or `educe` and document the choice (`derivative` is unmaintained — RUSTSEC-2024-0388, no release since 2021).

## §C7. Cargo feature flag hygiene

**The trap**: a typo in a source `#[cfg(feature = "...")]` can leave code disabled while the build succeeds with only a warning. Cargo supplies expected feature names to rustc's automatic `unexpected_cfgs` checking on Rust 1.80+; CI must enforce that lint. This is distinct from requesting an unknown feature with Cargo's `--features`, which Cargo rejects. The known feature set includes implicit optional-dependency features, not just literal `[features]` entries.

**REQUIRED**:
- Every `cfg(feature = "...")` must name a feature Cargo actually defines for that package: an explicit `[features]` entry or the implicit feature from an optional dependency. Using `dep:name` in `[features]` suppresses that dependency's implicit feature, so verify the effective feature map rather than inferring it from `optional = true` alone. Treat `unexpected_cfgs` as `deny` in CI. (From Rust 1.97 Cargo also supports `build.warnings = "deny"` in `.cargo/config.toml` for local-package warnings.)
- Feature names are case-sensitive. A forwarding/grouping feature need not have any local `cfg` occurrence; do not invent gates just to mirror the manifest.
- Rust 1.95 stabilized `cfg_select!`; the same checking applies there. Cargo supplies feature values, rustc knows built-in cfgs such as `windows`/`target_os`, and custom names/values need an appropriate `rustc-check-cfg`/`--check-cfg` declaration. Do not require users to re-declare built-ins manually.
- Avoid feature-gated `pub` fields in structs — they break the public API between feature combinations. If a field is conditional, the whole struct or the whole module should be conditional.
- Features are **additive by convention**: a feature adds capabilities, it does not remove behavior or silently choose between exclusive backends. Nothing in the name/combination checks above forbids a "feature" that *disables* something, and feature unification (§C10) can enable two individually-correct consumers' features in the same final dependency graph — flipping policy through `cfg` precedence in a build neither consumer ever tested. Two corollaries: `default-features = false` on one dependency is **not** a global disable across the graph (any other consumer can re-enable defaults), and a feature named like a disable switch is really an additive "enable the other mode" — name features for what they turn on. For genuinely exclusive policy choices, prefer explicit runtime/configuration selection over feature pairs; if a feature combination is truly invalid, have the crate reject it explicitly (`compile_error!` behind `cfg(all(feature = "a", feature = "b"))`) — and then make the feature-matrix job agree with that rejection, because a bare `cargo hack --feature-powerset check` runs **every** generated combination by design: the deliberately-rejected pair shows up as one more red run, indistinguishable from a genuine unexpected failure. Configure the sweep with cargo-hack's own exclusion mechanisms ([github.com/taiki-e/cargo-hack#usage](https://github.com/taiki-e/cargo-hack#usage)): `--mutually-exclusive-features a,b` (repeatable, one group per flag: `--mutually-exclusive-features a,b --mutually-exclusive-features c,d`) removes exactly the together-runs from the powerset while still testing each feature alone; `--exclude-features`/`--skip` is coarser — it drops **every** combination containing the named feature, so reserve it for a feature unusable in *any* combination, not for a pair whose halves are individually fine. Assert the rejection itself as its own expected-failure case: run `cargo check --features a,b` in a dedicated CI step that passes only when that command fails (checking that the failure is the `compile_error!` message) — never folded into the powerset job's pass/fail.
- **Explicit build-script change detection must cover the inputs that affect its output.** `rerun-if-changed` narrows Cargo's default package-file scanning; list each input file or directory (directories are scanned recursively), not just `build.rs` when schemas/headers also matter. Track externally supplied environment variables read dynamically with `cargo::rerun-if-env-changed=NAME`; a runtime `std::env::var` read alone is not tracked. Variables referenced through `env!`/`option_env!` are tracked automatically since Rust 1.46, and Cargo-provided build variables such as `TARGET` are not inputs for `rerun-if-env-changed`. The rule is not literally "only these paths": tracked environment changes and recompilation of the build script can also re-run it. Verify relevant input changes without a clean build so stale generated output cannot hide behind a successful incremental build.
- Test the full feature matrix in CI: `cargo hack --feature-powerset check` or equivalent, at least for libraries — configured to match any deliberately-rejected combinations per the exclusive-feature rule above, so the sweep's failures are all genuine surprises.
- For platform-conditional dependencies with features (`[target.'cfg(...)'.dependencies]`), the resolver version matters (mirror of §C10). Under **resolver v1** — the default for a pre-2021 edition, an explicit `resolver = "1"`, and notably a **virtual workspace whose root manifest has no `[package]` section**: member editions do not set the resolver, so the root `[workspace]` must declare `resolver` explicitly or the workspace runs v1 (Cargo warns about that default) — `features = [...]` on a target-specific dependency activated *globally*, even for targets not being built — the cargo#2524 gotcha. **Resolver v2+** (v2 = default since edition 2021; v3 = the edition-2024 default this spec targets) fixes it: per the Cargo book, "features for target-specific dependencies are not enabled if the target is not currently being built." v3 is v2's behavior plus **Rust-version-aware resolution** — it avoids selecting dependency versions whose MSRV is newer than the package's `rust-version` when an older compatible version exists — so the same requirements can resolve to a different graph under 2024/v3 than under 2021/v2. Scope the historical resolver-v1 complaints accordingly: the global-activation surprise applies only when actually running v1 (pre-2021 edition, explicit pin, or the virtual-workspace default above). Verify your `resolver` — in the root package, or in the root `[workspace]` for a virtual workspace — before relying on either behavior.

## §C10. Workspace feature unification surprises

**The trap**: workspace-wide and isolated builds can activate different features of the same dependency. Cargo's broad resolution for `Cargo.lock` is not the final compilation feature set: the latter depends on the packages selected for the invocation and their dependency graph. Building members together (`--workspace` or multiple `-p` selections) can unify features that separate invocations do not; mere membership in the workspace does not activate an unselected, unrelated member's features. Within that build graph, **resolver v1** can include selected members' dev-only activations in ordinary release builds; **v2+** separates them unless the relevant dev targets are being built (`cargo test`, `--tests`/`--examples`/`--benches`/`--all-targets`). `--workspace` alone selects packages, not dev targets. Check the root resolver — virtual workspaces need an explicit setting — and test a member's consumer-facing configuration independently, not only the unified workspace build. Non-additive features can also flip shared-package policy when two selected consumers activate conflicting modes (§C7).

**BANNED**:
- `default = ["heavy-dep"]` in `[features]` of a workspace member where `heavy-dep` is only needed by *some* consumers — every consumer who doesn't disable defaults pays the cost.
- Relying on a feature supplied only by a co-built member or a dev dependency to satisfy a library's normal requirements. Declare the needed activation on the dependency used by that library; otherwise isolated consumers can fail while workspace tests pass. Dev-only feature additions for tests are legitimate — their presence alone is not the defect. Interpret observed unification using both selected packages and resolver/dev-target scope.
- Treating workspace-internal features as private. Unification is scoped to a resolved **package identity in the selected build graph**, not a workspace-global namespace. Consumers of that same package can combine activations in a joint build; an isolated downstream build has its own selected graph and feature set. A dependency's feature does not create an identically named local feature in each consumer — provide explicit `[features]` forwarding when that local switch is intended. Resolver v2/v3 further separate host build/proc-macro dependencies from normal dependencies, ignore inactive target-specific activations, and merge dev activations only when those dev targets participate. Verify these axes before assuming "same package → same feature set everywhere".
- Members of one workspace pinning the **same dependency at semver-INCOMPATIBLE versions** (`rand = "0.8"` in one member, `rand = "0.9"` in another — requirement ranges with no overlap, `>=0.8.0, <0.9.0` vs `>=0.9.0, <0.10.0`, which the resolver cannot unify; two compatible requirements like `serde = "1.0.200"` and `serde = "1"` *overlap* and resolve to one version, so they are not this hazard). Cargo can link *multiple copies* into one binary — larger artifact, slower build, and two distinct `rand` types that don't interoperate (a `rand` 0.8 `rngs::StdRng` is not a `rand` 0.9 `rngs::StdRng`; `expected StdRng, found StdRng`). That hazard requires a **value or global state to cross the boundary** between the two copies — a type handed from one side to the other, or shared global/registry state keyed by either copy — which is the only shape this bullet bans: duplicate majors confined to disjoint subtrees (including separate workspace **binaries** that never exchange types or global state across the duplicate boundary) cost artifact size and build time, not correctness, so a `cargo tree -d` hit is a review signal rather than automatically a defect. Centralizing direct requirements in one place (the `[workspace.dependencies]` REQUIRED below) shrinks the surface but cannot by itself *guarantee* a single copy reaches the final binary — a deep transitive dependency elsewhere in the graph can still pull an incompatible major. The lockfile hides it until a value crosses a member boundary.

**REQUIRED**:
- Default features in a workspace member = the **minimum truly required** for the crate to function at all. Every additional default is a tax on every downstream consumer.
- Run `cargo hack --feature-powerset --no-dev-deps check` in CI to detect feature combinations that don't compile (the `--no-dev-deps` flag prevents dev-only features from leaking into the matrix).
- For crate-LOCAL compilation control that must not participate in feature unification, a `build.rs` emitting a custom cfg — `println!("cargo::rustc-cfg=internal");` **paired with** `println!("cargo::rustc-check-cfg=cfg(internal)");` declaring the name so the `unexpected_cfgs` lint (§C7) recognizes it; an emitted cfg that is never declared trips the lint — is a valid alternative to `[features]`: the flags pass `--cfg` to rustc for this package's compilation only, so they cannot unify or leak the way features do. Two limits: a cfg gate is compile-time code selection — it does **not** affect dependency resolution and cannot toggle a *dependency* (optional-dependency activation and feature selection stay Cargo's job, decided from `Cargo.toml`, not from emitted cfgs), and the cfgs are local to the package whose `build.rs` emitted them — not a workspace-wide toggle (`[workspace.metadata]` can carry the shared configuration each member's `build.rs` reads, but the cfg itself never leaves its crate).
- Document on every workspace member's `Cargo.toml`: which features are public (intended for external consumers) vs internal (used only by other workspace members).
- Declare shared dependencies and their versions once in `[workspace.dependencies]` and inherit them with `dep.workspace = true` in each member. This reduces direct-member version drift and gives one place to audit — it does **not** by itself *guarantee* one linked copy: a deep transitive dependency elsewhere in the graph can still pull an incompatible major independent of what members declare (the semver-incompatible-versions BANNED bullet above still applies). Verify the actual resolved graph with `cargo tree -d` (lists duplicated dependencies) rather than assuming centralization alone closes it.
- **Extract a crate late, not early.** A workspace tempts speculative splitting ("one crate per module"). A premature boundary freezes an API you do not yet understand — every cross-crate call becomes a `pub` semver surface (§C1) — and forces exactly the feature/version coordination above. Split a crate out when there is *real* reuse, a *stable* boundary, or a concrete reason (compile-time parallelism, a separate publish cadence, a `proc-macro`/`build.rs` that must be its own crate). The opposite rot — logic copy-pasted across members and fixed in only one place — is the signal that extraction is now overdue, not premature.
- **CI at a non-virtual workspace root runs less than you think.** A bare `cargo test` in a workspace whose root `Cargo.toml` also has a `[package]` includes "only the root crate itself" (Cargo's documented default, absent `default-members`) — the `crates/*` members' tests never execute, and CI reads green while member regressions accumulate; bare `cargo clippy` has the same hole for lint coverage (test/bench code is not linted without `--all-targets`). REQUIRED for CI: `cargo test --workspace` and `cargo clippy --workspace --all-targets` (+ the §C7 feature matrix); the testing-side statement of this is §D4.

**Worked example — rustls 0.23's dual-provider panic (a §A1 stale-API unlocked by this section's unification; version-scoped, not a standing rule).** A `rustls::ClientConfig::builder()` written against rustls 0.21 still compiles on 0.23 — but 0.23 made the crypto provider (`ring` vs `aws-lc-rs`) a *runtime* choice: if feature unification (exactly this section's mechanism — two workspace members depending on different provider features of the same `rustls`) puts **both** provider features in the graph, the process-level provider is ambiguous and `ClientConfig::builder()` **panics at runtime** ("no process-level CryptoProvider available — call `CryptoProvider::install_default()` before this point") — only in the binary whose unified feature set enables both, hence invisible in the member's own tests. Within the 0.23 window the fixes are `rustls::crypto::CryptoProvider::install_default()` in `main` before any config is built, or pinning exactly one provider feature across the workspace. The `0.24` development line (still pre-release at the 2026-09-08 round-52 review — only `0.24.0-dev.*` builds existed then and crates.io's latest stable was `0.23.44`; these are dated snapshots, not standing "latest" claims, so verify the current versions live before relying on either number) passes the provider to `builder(...)` explicitly on `main` — verify against the actual released 0.24 API once it ships, since a pre-release signature can still change.

## §C11. `Deref` polymorphism antipattern

**The trap**: `impl Deref<Target = Inner> for Wrapper` makes `wrapper.field_of_inner` and `wrapper.method_of_inner()` work transparently. The LLM uses this to fake inheritance — `struct UserAdmin(User); impl Deref<Target = User> for UserAdmin` — and the code compiles, runs, and looks elegant for a while. The breakdown comes when `UserAdmin` needs to participate in a trait `User` does not impl, or vice versa: the Rust API Guidelines explicitly call this out as **C-DEREF** ("Only smart pointers implement `Deref` and `DerefMut` (C-DEREF). ... The traits should be used only for that purpose."). Trait resolution does not look through `Deref` for trait bounds, only for method calls, so generic functions taking `User` will not accept `UserAdmin`, generic functions taking `UserAdmin` will not see `User`'s trait impls, and downstream code grows ad-hoc casts and `as_ref()` calls.

**BANNED**:
- `impl Deref<Target = Inner> for Wrapper` where `Wrapper` is not conceptually a *smart pointer to* `Inner`. Wrappers, newtypes for additional invariants, and "extension types" are not smart pointers.
- Using `Deref` to expose all of `Inner`'s methods through `Wrapper` for ergonomic shorthand — this leaks the inner's API surface into the wrapper's, and any future addition to `Inner` becomes part of `Wrapper`'s public API too (semver hazard, mirrors §C1).
- `impl DerefMut<Target = Inner> for Wrapper` on a wrapper that adds invariants — the `DerefMut` lets callers bypass every method `Wrapper` defined to maintain those invariants.

**REQUIRED**:
- `Deref` is reserved for smart pointers: `Box`, `Rc`, `Arc`, `Cow`, `MutexGuard`, `RwLockReadGuard`, `String → str`, `Vec<T> → [T]`, custom guards (`MyHandle<'a, T>` where `T` is the pointee). The relationship must be *pointer-like* (the wrapper owns/references the pointee; the wrapper is morally transparent to the pointee).
- For composition without inheritance, write explicit accessors: `impl UserAdmin { fn user(&self) -> &User { &self.0 } }`. This keeps the API surface of `UserAdmin` separate from `User` and makes the composition explicit at every call site.
- Cite the Rust API Guidelines **C-DEREF** rule in code review when this pattern appears: *"Only smart pointers implement `Deref` and `DerefMut` (C-DEREF). ... The traits should be used only for that purpose."*

## §C12. Reinventing a solved problem instead of reaching for the world-recognized crate

**The trap**: asked for a task with a well-known, high-adoption crate solution, the LLM writes a few lines of hand-rolled logic instead — `split(',')` for CSV, `format!` for JSON/URLs, a hardcoded character-replace table for HTML escaping. The hand-rolled version compiles and passes a plausible unit test built from the same mental model that wrote it. It is silently wrong on an input that model never considered — a quoted field, a non-ASCII path, a leap-second, a crossed antimeridian — and that input shows up in production, not in the test the LLM wrote for itself.

**Membership gate — every row below earned its place the same way, and any addition must clear the same bar**: a row exists only when a **concrete input or scenario** can be named where the hand-rolled version compiles, passes a plausible test, and is silently wrong — not merely "less idiomatic" (style, out of scope), not merely "slower" (performance, → the Substitution catalog in `data-and-types.md`, Tier E). "Silently wrong" means wrong output, data corruption, a security hole, or a crash on a real input a naive test would not cover — a loud panic on the same input is a different (and lesser) defect than a silent wrong answer. A task without a nameable silent-failure input is not a finding here even when a popular crate exists for it (`clap` for argument parsing, `anyhow`/`thiserror` for error types) — that is engineering taste, and per this spec's own acceptance standard, a category exists only where LLMs demonstrably err more than a careful human would, not wherever a preference exists.

**Why this is not a supply-chain shortcut around §A1**: every crate named below is independently verified to exist and carries real, checkable adoption (a download count, cited per row) — but that verification is *this document's*, done once, at write time of this category, not a license to skip §A1's own verification when the rule is applied. §A1 still governs how a suggested crate reaches `Cargo.toml`.

**REQUIRED**:
- On recognizing one of the tasks below, **propose** the named crate — subject to §A1's own verification and the user's approval — rather than silently hand-rolling the naive version. This is the same "suggestion to verify, not a fait accompli" posture §A1 already requires for any new dependency; §C12 does not create an exception to it.
- If the user forbids new dependencies or declines the suggestion, preserve the requested behavior using suitable std/existing APIs or a verified custom implementation. Exercise the catalog's named edge cases; do not assume custom code necessarily misses them. Document **actual** unsupported inputs only. A dependency constraint is not permission to drop required behavior or weaken security: if satisfying both constraints is not feasible, ask for the needed trade-off instead of silently shipping a gap.
- Escalate a row to 🔴 (surface every occurrence) when its silent-failure shape is a security hole, not merely a correctness bug — currently: HTML sanitization (XSS bypass), Markdown-to-HTML rendering (unescaped-HTML XSS), and HTML escaping (attribute/script/style/URL-scheme context escaping gap / extension-keyed autoescape miss — unescaped output, XSS). Every other row is 🟡: get it right, or document the gap, while writing; do not enumerate routine hits in the audit summary.

**BANNED**:
- Hand-rolling one of the tasks below **without** proposing the named alternative first, when there is no stated zero-dependency constraint.
- Shipping a known unsupported required case merely because the user declined a dependency, or inventing an unsupported-case warning for code that handles it correctly. Any real scope reduction needs an explicit compatibility/requirements decision, not just a comment.

## §C12a. Reinventing infrastructure instead of an established subsystem

**The trap**: one altitude above §C12 — not a missed function call but a missed *subsystem*. The LLM is asked for something that sounds like "just write a file" or "just keep this in memory" and reaches for the naive primitive, when the actual requirement (survives a crash, survives more than one instance of the process) needed engineering the naive primitive does not have.

**Utility-level catalog membership gate applies identically** — a concrete input/scenario, not "the established option is more robust in general."

| Task | Hand-rolled shape | Input where it is silently wrong | Option (downloads) |
|---|---|---|---|
| Persistent key-value/document storage | `fs::write(path, json)` on every update, or an in-memory map flushed periodically | process killed mid-write (crash, OOM-kill, power loss) leaves a truncated/corrupt file — but that corruption is *detected*, not silent: the next read rejects the truncated file with a parse error (a loud service outage, not silently-wrong data); the genuinely silent failure mode is the lost update: concurrent writers race on read-modify-write with no error anywhere (→ §C2 TOCTOU family); if a single-file `fs::write` shape survives as the user's informed choice, serialize cross-process writers with `File::lock` / `try_lock` / `lock_shared` (std advisory file locks, stable since Rust 1.89) around the read-modify-write | `rusqlite` (94M, SQL) / `redb` (9.4M), `fjall` (1.4M) (pure KV). `sled` (14M) is deliberately not offered for a durability-critical row: its own README says "if reliability is your primary constraint, use SQLite. sled is beta", warns the on-disk format will require manual migration before 1.0, and its stable line is 0.34.7 (2021) with only 1.0.0-alphas since |
| Any in-process coordination state (cache, dedup set, rate limiter, pub/sub) with no external store | a `static`/`OnceLock`-held in-memory structure as the sole source of truth | the process is horizontally scaled to more than one instance — state silently diverges between replicas: duplicate work, missed events, inconsistent rate-limit counts, no compiler or test signal anywhere | externalize the state (`redis` (94M) is one verified, widely-used option) when multi-instance is a stated requirement — not a blanket mandate to add it otherwise |

**REQUIRED**: same posture as §C12 — propose the named option (subject to §A1 verification and user approval) when one of these shapes is recognized; a user's informed zero-dependency or single-instance decision is not a defect, an undocumented one is.

🟡, escalate to 🔴 only where the specific instance is a stated durability or security guarantee (cross-reference §F1/§F2 documented-guarantee divergence when the project's own docs promise durability or consistency the hand-rolled version does not deliver).

## §E5. Work already done — *The cheapest computation is the one you did once and kept.*

- **Where it shows up**: `Regex::new(...)` (or a parser, schema, template) compiled inside the function that uses it, recompiled every call; a pure derived value recomputed instead of cached; unbuffered I/O — one syscall per small `read`/`write`; a serializer allocating a fresh buffer per item; a log line whose fields are formatted eagerly even when the level is filtered out; dynamic dispatch (`Box<dyn Trait>`) on a hot path where the type set is closed; a `reqwest::Client` (or an `sqlx` pool, a cloud-SDK client) built inside the handler that uses it — a per-request pool + TLS config, and under load the FD/ephemeral-port exhaustion named in §B14's per-request-client bullet. (`rustls::ClientConfig` rebuilt per request belongs in *this* section, not that one: it's reusable TLS configuration, not a connection pool — rebuilding it wastes CPU re-parsing certs/config, but performs no network I/O and holds no socket, so it doesn't cause FD/`TIME_WAIT` exhaustion the way an actual pooled client does. Still build it once and share it — just because it's a recompute cost, not a correctness bug.)
- **The cheaper move**: hoist compile-once values into `LazyLock`/`OnceLock` (§A2) — not a panicking initializer (§A2: a panic poisons `LazyLock` unrecoverably, while `OnceLock` stays empty and the next access retries); wrap I/O in `BufReader`/`BufWriter`; reuse serialization buffers; let `tracing` defer field formatting (record fields, don't `format!` the message) or guard with `if enabled!`; on a closed type set prefer generics or `enum` dispatch over `dyn` when monomorphization cost is acceptable.
- **Reusable record buffers**: `BufRead::lines()` yields a fresh owned `String` for each line; when a hot parser consumes each record before reading the next, consider one `String` with `read_line`, or one `Vec<u8>` with `read_until` for bytes, clearing either buffer before the next record. This targets the allocating `BufRead` iterator, not `str::lines()`, which already yields borrowed slices. The replacement must preserve parsing semantics: both read methods append and include the delimiter, whereas `lines()` removes LF or CRLF; strip only the intended line ending, not arbitrary whitespace with `trim()`. Process the final nonempty record at real EOF even without a newline, preserve I/O/UTF-8 error handling, and bound record growth during reading on untrusted input (§B7), with a deadline/progress policy for streams. Distinguish underlying EOF from an exhausted `Read::take` limit: accepting the capped prefix as an unterminated final record silently truncates input. Detect and report an over-limit record while preserving valid records exactly at the allowed size. Reuse does not make the read bounded; these are synchronous APIs (§B11).
- **Reuse beyond one buffer**: §E2 covers `clone_from`/`clone_into`, repeated growth/shrink and backing-storage retention; §E3 covers `sort_by_cached_key` when repeated key computation dominates. Their ownership, failure and memory trade-offs apply before treating a shorter hot loop as a win.
- **Leave it when**: the work is genuinely once-per-process already, the value changes every call, or the indirection keeps the design open and the path is cold.

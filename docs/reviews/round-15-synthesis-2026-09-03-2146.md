#### Task 2 — Correct the `unnameable_types` claim in the public-alias paragraph; fix `crate::PublicS`

- **Location (verified):** `skill/lifetimes-and-api.md:124` (the §A3 "Nameable" definition and, in
  the same bullet, "`unnameable_types` (also allow-by-default; catches the reachable-but-not-nameable
  case above)"); `skill/SKILL.md:309` (code-pattern row: "`pub type PublicS = hidden::S;` already
  names the type for downstream code as `crate::PublicS`"); mirrors.
- **Defect and fix:** The language-level addition made in `adee2e9` is right and must stay: a public
  type alias is a real naming path and therefore a real API/semver commitment. But the unchanged
  next sentence now misdescribes the lint the paragraph recommends. Verified against current
  `rustc_privacy/src/lib.rs`: `EmbargoVisitor::check_def_id` handles `DefKind::TyAlias` with
  `self.reach(def_id, item_ev).generics().clauses().ty()`, and `reach()` constructs its visitor with
  `level: Level::Reachable` — so an aliased type is marked *Reachable*, never *Reexported*;
  `check_unnameable` then fires `UNNAMEABLE_TYPES` whenever
  `reachable_at_vis.is_public() && reexported_at_vis != reachable_at_vis`. rust-lang/rust#120146
  ("effective visibilities: Count types leaked through trivial type aliases as reexported",
  petrochenkov) is **still OPEN** and describes exactly this false positive. So for
  `mod hidden { pub struct S; } pub type PublicS = hidden::S;` the lint reports `S` as "reachable but
  cannot be named" although the module now (correctly) calls it nameable — a normative rule
  contradicting the tool it tells the reader to enable. Fix: say both things — the alias is a naming
  path and a commitment, **and** `unnameable_types` does not yet model it (#120146), so its firing on
  an alias-exposed type is a known lint false positive, not evidence the type is outside the public
  surface; silence it with a documented `#[allow]` or replace the trivial alias with `pub use`. Also
  fix the path in both files: downstream names it `the_crate::PublicS` (or `dependency::PublicS`);
  `crate::` is the *current* crate, so `crate::PublicS` is wrong from the downstream perspective
  the sentence describes.
- **Severity:** P2 — a verified false factual claim about a recommended tool's behavior inside the
  rule that decides what is a semver commitment; introduced (as an overcorrection) by the fix commit.
  Blast radius is bounded because the same paragraph already treats reachable-but-not-nameable as
  part of the API surface, so the semver conclusion is not inverted — the harm is an unexplained
  lint hit and a wrong remedy. `1653` rated this P3 on that bounded-blast-radius argument; I side
  with `1653-rush`/`1653-final` because the project's calibration puts a clear-scope factual error
  in normative text at P2, but this is the one severity call worth a human look (see Unresolved).
- **Raised by:** `1653` (P3, incl. the `crate::` path), `1653-rush` (P2), `1653-final` (P2, incl. the
  path). `1649` recorded it as "Closed".

#### Task 5 — §F1 oracle: state the pairwise reduction; soften "needs values outside `0`/`1`"

- **Location (verified):** `skill/SKILL.md:408` and `skill/semantics-and-conformance.md:19`
  ("for every non-identity permutation of a group of mutually-reorderable sibling positions …" and
  "a `u8` sibling needs values outside `0`/`1`"); mirrors.
- **Defect and fix:** As a *property* the quantifier is fine; as the *mechanical control* the same
  sentence recommends ("actually construct the reordered/mutated schema, decode each fixture …") it
  reads as `n! − 1` schema constructions per sibling group (479,001,599 for a twelve-field struct) —
  the same shape of infeasible obligation the commit just removed for depth. It reduces: under a
  canonical positional encoding (one byte sequence per value — true for fixtures produced by the
  real bincode 2 / borsh / postcard encoder), a permutation is undetected only if every moved
  position's corpus byte-vector equals that of the position it moves onto; pick any moved position
  and the transposition of that pair is then also undetected. So checking the `C(n, 2)`
  transpositions of each wire-compatible sibling group is equivalent, and "distinct per-position
  encoded-byte signatures across the corpus" is the closed form. Separately, "a `u8` sibling *needs*
  values outside `0`/`1`" is only a sufficient construction, not a necessity: fixtures
  `{ n: 0, flag: false }` and `{ n: 0, flag: true }` give `n` the corpus byte-vector `[0, 0]` and
  `flag` `[0, 1]`, which already differ, so the swap is detected (second fixture decodes as `n: 1`).
  Fix: state the pairwise reduction with the canonical-encoding caveat and downgrade "needs" to "one
  sufficient construction is". Everything else in the rewritten bullet (bincode `bool` = one byte
  `0`/`1`, any other byte → `DecodeError::InvalidBooleanValue`; `u8` a single byte unaffected by
  endianness; struct fields in declaration order with no names) was re-verified against the bincode 2
  spec and is correct.
- **Severity:** P3 — precision of an obligation's arithmetic; the oracle itself is sound.
- **Raised by:** `1653`, `1653-final`.

#### Task 6 — GFM block-start allowlist in the leading-pipe validator is wrong in three places; control 11 pins the wrong semantics

- **Location (verified):** `dev/validate.mjs:296-302` (`blockStartRe`, with the comment claiming a
  link reference definition "breaks the table"), `:357`; `dev/validate-fixtures.mjs:308-311`
  (comment) and `:333-346` (controls 10 "HTML-block-start" and 11 "link-reference-definition").
- **Defect and fix:** Verified against the GFM spec and cmark-gfm (the reference implementation the
  validator's own comment cites): (i) **Link reference definitions are not block starts.**
  cmark-gfm's `open_new_blocks` has no branch for `[label]:` at all — reference definitions are
  extracted from *paragraph* content at finalize time — and the table extension's `matches()` keeps
  the table open for any line that parses as a row with `n_columns ≥ 1`, which a pipe-less line
  always does (`n_columns == 1`). So `[probe]: https://…` directly under a table row is a one-cell
  table row — precisely the pipe-less row this check exists to catch. The `\[[^\]]*\]:` alternative
  therefore creates a false negative for any pipe-less row whose first cell starts with a bracketed
  token and a colon, and control 11 asserts that wrong behavior. (The spec agrees: "A link reference
  definition cannot interrupt a paragraph"; a table is broken only by "an empty line, or beginning of
  another block-level structure".) (ii) **Indented code blocks are missing.** In `open_new_blocks`,
  `indented && !maybe_lazy && !parser->blank` opens a code block whenever the current container is
  not a paragraph (`maybe_lazy = S_type(parser->current) == CMARK_NODE_PARAGRAPH`), and `add_child`
  finalizes the table because it cannot contain a code block — so a ≥4-space content line directly
  after a table breaks it, and the validator would falsely flag it as a pipe-less row (same false-
  positive family round 14 raised for HTML blocks). (iii) **Bare `<` over-approximates.** GFM has
  seven HTML start conditions; type 7 (a complete open/close tag alone on the line) does interrupt a
  table (`cont_type != CMARK_NODE_PARAGRAPH && scan_html_block_start_7`), but a line such as
  `<T as Trait>::f | …` meets none of them and is a table row, so a pipe-less row starting with `<`
  currently escapes. Fix: remove the link-reference alternative and drop or invert control 11 (if
  GitHub-style footnotes matter, `[^label]:` *is* a real block start under cmark-gfm's
  `CMARK_OPT_FOOTNOTES` and may be kept in that narrower form); add an indented-code start
  (`^ {4,}\S` or a leading tab); either tighten `<` to the seven start conditions or document the
  over-approximation deliberately; add negative controls (a pipe-less row starting with `[x]:` and one
  starting with `<T as Trait>` must both be flagged; a ≥4-space line after a table must stay quiet).
  Current `SKILL.md` has no line of any of these shapes outside fenced code, so there is no live
  exposure — this is robustness of the check.
- **Severity:** P3.
- **Raised by:** `1653` (all three, with the removal remedy — correct), `1653-final` (all three, but
  framed the bracket-colon branch as merely under-specified rather than wrong). Round 14's claim that
  link reference definitions are valid block starts that break a table is unsupported by the spec and
  contradicted by cmark-gfm (ledger row, Task 12).
